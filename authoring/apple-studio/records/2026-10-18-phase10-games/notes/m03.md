# Notes m03

## command-model.md
- Sync scope ladder, smallest to largest: intrapass barrier (within one pass) < fence (between passes on one queue; the producer updates it, the consumer waits) < intraqueue barriers (consumer queue barrier and producer queue barrier; coarser than a fence) < `MTLEvent` (every queue on one device) < `MTLSharedEvent` (the CPU, other queues, other devices, other processes). Apple's rule: use the smallest scope that resolves the conflict, because a wider scope holds back more GPU work. — /documentation/Metal/resource-synchronization [symbols: MTLFence, MTLEvent, MTLSharedEvent, MTLStages, MTLRenderStages, MTLBarrierScope, MTL4VisibilityOptions] [gate: Metal 4]
- A hazard can come through any route to a resource: direct bindings or `MTL4ArgumentTable` entries, argument buffers, and render attachments. An attachment has an implicit load at pass start when `loadAction == .load` and an implicit store at pass end when `storeAction == .store`. Concurrent reads never conflict, even over overlapping ranges. — /documentation/Metal/resource-synchronization [symbols: MTL4ArgumentTable, MTLRenderPassAttachmentDescriptor.loadAction, MTLRenderPassAttachmentDescriptor.storeAction, MTLLoadAction.load, MTLStoreAction.store]
- An `MTL4ComputeCommandEncoder` pass runs its dispatches concurrently. The Metal 3 `MTLComputeCommandEncoder` runs them serially unless `MTLComputePassDescriptor.dispatchType` is `.concurrent`. A compute port to Metal 4 must therefore add intrapass barriers wherever the Metal 3 code relied on serial order. — /documentation/Metal/resource-synchronization [symbols: MTL4ComputeCommandEncoder, MTLComputePassDescriptor.dispatchType, MTLDispatchType.concurrent] [gate: Metal 4 vs Metal 3]
- Orderings the GPU already guarantees, which need no sync: atomics; per-fragment attachment loads and stores in primitive order (draw order, then primitive order within a draw); raster-order-group accesses per fragment in primitive order; tile-shader accesses per tile in tile-dispatch order. — /documentation/Metal/resource-synchronization
- An `MTL4CommandBuffer` can be reused as soon as it has been committed to a queue. — /documentation/Metal/running-a-machine-learning-model-on-the-gpu-timeline [symbols: MTL4CommandBuffer, beginCommandBufferWithAllocator:, endCommandBuffer, MTL4CommandQueue commit:count:] [gate: Metal 4]
- CPU wait on Metal 4 queue work: after committing, call the queue's `signalEvent:value:` with `sharedEvent.signaledValue + 1`, then `waitUntilSignaledValue:timeoutMS:` on the CPU. The sample uses a 100 ms timeout so a stall or error surfaces instead of hanging. — /documentation/Metal/running-a-machine-learning-model-on-the-gpu-timeline [symbols: MTL4CommandQueue signalEvent:value:, MTLSharedEvent.signaledValue, MTLSharedEvent.wait(untilSignaledValue:timeoutMS:)] [gate: Metal 4]
- Multi-GPU Mac (Intel-era eGPU and dGPU machines; the samples are macOS 10.13+): render with the GPU that drives the view's display, found with `CGDirectDisplayCopyCurrentMetalDevice(displayID)` (the display ID comes from `window.screen.deviceDescription["NSScreenNumber"]`). Any other GPU forces a cross-bus drawable copy, which is worst over Thunderbolt. Re-pick the device on `NSApplicationDidChangeScreenParametersNotification` and `NSWindowDidChangeScreenNotification`. — /documentation/Metal/selecting-device-objects-for-graphics-rendering [symbols: CGDirectDisplayCopyCurrentMetalDevice, NSApplicationDidChangeScreenParametersNotification, NSWindowDidChangeScreenNotification] [gate: macOS, multi-GPU systems]
- eGPU hot-plug: get the devices with `MTLCopyAllDevicesWithObserver(&observer, handler)`. The handler receives `MTLDeviceWasAddedNotification`, `MTLDeviceRemovalRequestedNotification`, or `MTLDeviceWasRemovedNotification`, and can run on any thread, so marshal its state to the main thread under a lock. Set `GPUEjectPolicy` = `wait` in Info.plist to handle removal yourself; otherwise macOS quits and relaunches the app (state then goes through `application:willEncodeRestorableState:` and `application:didDecodeRestorableState:`). Remove observers with `MTLRemoveDeviceObserver` in `viewDidDisappear`, not `dealloc`, which never runs while Metal and the notification center still hold references. Preloading a renderer per device makes switching smooth but multiplies memory, so choose what to mirror. Keep non-rendering state outside the per-device renderers. — /documentation/Metal/selecting-device-objects-for-graphics-rendering [symbols: MTLCopyAllDevicesWithObserver, MTLDeviceNotificationHandler, MTLDeviceWasAddedNotification, MTLDeviceRemovalRequestedNotification, MTLDeviceWasRemovedNotification, MTLRemoveDeviceObserver] [gate: macOS 10.13.4+ for eGPU]
- Splitting compute and render across GPUs: an `MTLBuffer` cannot move between devices. Share data through page-aligned system memory from `vm_allocate`, wrapped on each device with `makeBuffer(bytesNoCopy:length:options:deallocator:)` in shared mode, and free it with `vm_deallocate` (the sample registers that through an `NSData` deallocator). The simulation thread and the render thread run at their own rates and never wait for each other. On eGPU removal, move the in-flight sim state to the remaining GPU instead of restarting. — /documentation/Metal/selecting-device-objects-for-compute-processing [symbols: MTLDevice.makeBuffer(bytesNoCopy:length:options:deallocator:), vm_allocate, MTLResourceStorageModeShared] [gate: macOS multi-GPU]
- Metal 3 command buffer lifecycle: make the queue, pipelines, buffers, and textures once at init, never in a hot path. Each frame: `makeCommandBuffer()`, encoders, optional `addScheduledHandler(_:)` / `addCompletedHandler(_:)`, then `commit()`. Commit implies enqueue. Execution follows commit order. An `MTLCommandBuffer` cannot be reused after commit; this differs from Metal 4, where an `MTL4CommandBuffer` can be reused right after commit. Metal may reorder commands only where the result cannot be observed. — /documentation/Metal/setting-up-a-command-structure; contrast /documentation/Metal/running-a-machine-learning-model-on-the-gpu-timeline [symbols: MTLDevice.makeCommandQueue(), MTLCommandQueue.makeCommandBuffer(), MTLCommandBuffer.commit(), MTLCommandBuffer.status, MTLCommandBuffer.addScheduledHandler(_:), MTLCommandBuffer.addCompletedHandler(_:)] [gate: Metal 3 vs Metal 4]
- Residency sets make resources resident; they replace per-encoder `useResource`/`useHeap` calls, which cost CPU time per call and make residency happen at commit, delaying GPU start. Build with `MTLResidencySetDescriptor` (`label`, `initialCapacity`) and `device.makeResidencySet(descriptor:)` (throws); `addAllocation(_:)` or `addAllocations(_:)` (duplicates are ignored), then `commit()` to apply. Adding any resource that came from an `MTLHeap` makes the WHOLE heap resident. — /documentation/Metal/simplifying-gpu-resource-management-with-residency-sets [symbols: MTLResidencySet, MTLResidencySetDescriptor, MTLDevice.makeResidencySet(descriptor:), MTLResidencySet.addAllocation(_:), MTLResidencySet.addAllocations(_:), MTLResidencySet.commit(), MTLAllocation]
- Attach a set per command buffer (`useResidencySet(_:)` / `useResidencySets(_:)`) or per queue (`addResidencySet(_:)` / `addResidencySets(_:)`); the queue form is applied to each buffer at commit and is cheaper than attaching to many buffers. A queue or a buffer holds at most 32 residency sets. Put long-lived or frequently used resources on the queue. `removeResidencySet(_:)` does not detach the set from buffers already committed or scheduled. The page's examples use `MTLCommandBuffer`/`MTLCommandQueue`, but the same method names exist on `MTL4CommandBuffer` and `MTL4CommandQueue` (checked against those pages in the corpus). In Metal 4 a residency set is the only residency mechanism, because the Metal 4 encoders have no `useResource`. — /documentation/Metal/simplifying-gpu-resource-management-with-residency-sets; checked /documentation/Metal/MTL4CommandQueue, /documentation/Metal/MTL4CommandBuffer [symbols: MTLCommandBuffer.useResidencySet(_:), useResidencySets(_:), MTLCommandQueue.addResidencySet(_:), addResidencySets(_:), removeResidencySet(_:), removeResidencySets(_:), MTL4CommandQueue.addResidencySet(_:), MTL4CommandBuffer.useResidencySet(_:)] [gate: limit 32 sets per queue and per buffer]
- Residency timing: by default Metal does the CPU-side residency work at the first commit that uses the set, which delays submission. Call `requestResidency()` earlier, at a non-critical moment (launch, level load, a state change); under memory pressure from other apps Metal may postpone part of it. `endResidency()` releases the backing memory for reuse by your other sets or by other apps. That gives a level-streaming pattern: one residency set per level or zone, `requestResidency()` while the previous zone is still playing, `endResidency()` on the old one. — /documentation/Metal/simplifying-gpu-resource-management-with-residency-sets [symbols: MTLResidencySet.requestResidency(), MTLResidencySet.endResidency()]
- Frames in flight (classic Metal 3 sample): a ring of `MaxFramesInFlight = 3` shared buffers, `dispatch_semaphore_create(MaxFramesInFlight)`, `dispatch_semaphore_wait` at the top of the frame, signal in `addCompletedHandler`. Finish all CPU writes to the frame's buffer before committing, and do not touch it again that frame. Apple's sizing rule: no more copies than the max drawable count. `CAMetalLayer.maximumDrawableCount` accepts only 2 or 3, default 3. — /documentation/Metal/synchronizing-cpu-and-gpu-work [symbols: MTLCommandBuffer.addCompletedHandler(_:), CAMetalLayer.maximumDrawableCount, dispatch_semaphore_create, dispatch_semaphore_wait, dispatch_semaphore_signal] [gate: Metal 3 path; Metal 4 has no completed handler on MTL4CommandBuffer, so use an MTLSharedEvent signal from the queue, as in the ML sample]
- When CPU writes always finish before the encode that references the buffer, mark that pipeline buffer slot `MTLPipelineBufferDescriptor.mutability = .immutable` (for example `vertexBuffers[i].mutability`), which lets Metal optimize. Apple: prefer immutable wherever possible. — /documentation/Metal/synchronizing-cpu-and-gpu-work [symbols: MTLPipelineBufferDescriptor.mutability, MTLMutability.immutable]
- Events, Metal 3 spelling: `device.makeEvent()` (one device, across queues) or `device.makeSharedEvent()` (other devices, other processes, the CPU); encode `commandBuffer.encodeSignalEvent(_:value:)` and `encodeWaitForEvent(_:value:)`. Work on two queues with no dependency between them runs concurrently, and a wait blocks that queue until the value is reached. Encode each queue's buffers on its own thread where possible. Metal 4 moves both calls onto the queue: `MTL4CommandQueue.signalEvent(_:value:)` and `waitForEvent(_:value:)` (confirmed on the MTL4CommandQueue page). — /documentation/Metal/synchronizing-events-within-a-single-device; /documentation/Metal/synchronizing-events-across-multiple-devices-or-processes; checked /documentation/Metal/MTL4CommandQueue [symbols: MTLDevice.makeEvent(), MTLDevice.makeSharedEvent(), MTLCommandBuffer.encodeSignalEvent(_:value:), MTLCommandBuffer.encodeWaitForEvent(_:value:), MTL4CommandQueue.signalEvent(_:value:), MTL4CommandQueue.waitForEvent(_:value:)] [gate: Metal 3 vs Metal 4]
- Cross-device events: create the shared event on one device and signal/wait on both devices' queues with the same calls; the resources must be mirrored on each device over one shared memory allocation (see the vm_allocate + bytesNoCopy pattern) so writes are visible to both. — /documentation/Metal/synchronizing-events-across-multiple-devices-or-processes [symbols: MTLSharedEvent] [gate: macOS multi-GPU]
- CPU <-> GPU with a shared event: `MTLSharedEventListener(dispatchQueue:)` plus `sharedEvent.notify(listener, atValue:block:)` runs a CPU block once the value reaches the target; the CPU signals by setting `signaledValue`, and only a larger value takes effect. A wait on value N is released by any value >= N. Pattern: GPU signals 2, the CPU block does its work and sets 3, the GPU waits on 3 — CPU work spliced into the middle of one command buffer. — /documentation/Metal/synchronizing-events-between-a-gpu-and-the-cpu [symbols: MTLSharedEventListener, MTLSharedEvent.notify(_:atValue:block:), MTLSharedEvent.signaledValue, MTLSharedEventNotificationBlock]
- Metal 4 fences are per queue: in Metal 3, an `MTLFence` works across queues of one device; in Metal 4 it only orders passes on the SAME queue (including passes in other command buffers on it), and cross-queue work needs `MTLEvent` or `MTLSharedEvent`. Make one with `device.makeFence()`. Producer: `updateFence(_:afterEncoderStages:)`; consumer: `waitForFence(_:beforeEncoderStages:)`. Fences cannot order stages within one pass (use an intrapass barrier). Encode the update and the wait as close as possible to the conflicting commands. To reuse a fence inside one pass, encode the wait before the update. — /documentation/Metal/synchronizing-passes-with-a-fence [symbols: MTLFence, MTLDevice.makeFence(), MTL4CommandEncoder.updateFence(_:afterEncoderStages:), MTL4CommandEncoder.waitForFence(_:beforeEncoderStages:), MTLStages.blit, MTLStages.dispatch] [gate: Metal 4 vs Metal 3]
- Metal 4 compute passes contain copy commands too: `MTL4ComputeCommandEncoder.copy(sourceBuffer:sourceOffset:destinationBuffer:destinationOffset:size:)` runs in the `.blit` stage of the compute pass, and dispatches run in `.dispatch`. Those two stages, and two dispatches in the same pass, can overlap. Binding is through an `MTL4ArgumentTable` with `setAddress(buffer.gpuAddress, index:)` and `encoder.setArgumentTable(_:)`. — /documentation/Metal/synchronizing-passes-with-a-fence; /documentation/Metal/synchronizing-stages-within-a-pass [symbols: MTL4ComputeCommandEncoder, MTL4ArgumentTable.setAddress(_:index:), MTL4ComputeCommandEncoder.setArgumentTable(_:), MTLBuffer.gpuAddress, MTLStages] [gate: Metal 4]
- Consumer queue barrier: `barrier(afterQueueStages:beforeStages:visibilityOptions:)` in the consuming pass. It blocks the `beforeStages` of this pass AND every later pass on the queue until the `afterQueueStages` of all EARLIER passes finish (this pass's own stages are not waited on). Use it when one pass reads what several earlier passes wrote. Consumer barriers also exist on Metal 3 encoder types. — /documentation/Metal/synchronizing-passes-with-consumer-barriers [symbols: MTL4CommandEncoder.barrier(afterQueueStages:beforeStages:visibilityOptions:), MTL4VisibilityOptions.device] [gate: Metal 4, also Metal 3 encoders]
- Producer queue barrier: `barrier(afterStages:beforeQueueStages:visibilityOptions:)` in the producing pass. It blocks the `beforeQueueStages` of every LATER pass (not this one) until the `afterStages` of this pass and all earlier passes finish. Use it when one pass writes what many later passes read: one producer barrier can stand in for several consumer barriers. Producer barriers exist only on Metal 4 encoders. — /documentation/Metal/synchronizing-passes-with-producer-barriers [symbols: MTL4CommandEncoder.barrier(afterStages:beforeQueueStages:visibilityOptions:)] [gate: Metal 4 only]
- Intrapass barrier: `barrier(afterEncoderStages:beforeEncoderStages:visibilityOptions:)` orders stages inside one pass only; other passes can still overlap it. Typical use: copy (`.blit`) then dispatch (`.dispatch`) on the same buffer in one Metal 4 compute pass. — /documentation/Metal/synchronizing-stages-within-a-pass [symbols: MTL4CommandEncoder.barrier(afterEncoderStages:beforeEncoderStages:visibilityOptions:)] [gate: Metal 4]
- Metal 3 argument-buffer residency: the driver cannot see resources referenced inside an argument buffer, so call `useResource(_:usage:stages:)` / `useHeap(_:stages:)` (render) or `useResource(_:usage:)` / `useHeap(_:)` (compute) before the draw or dispatch that may touch them. These calls both make the resource resident and convert it to the format its `MTLResourceUsage` needs; the `stages:` variants also add a fence-like dependency for that stage. If a needed resource is not resident, the command buffer FAILS. Metal 4 replaces all of this with residency sets. — /documentation/Metal/tracking-the-resource-residency-of-argument-buffers [symbols: MTLRenderCommandEncoder.useResource(_:usage:stages:), MTLRenderCommandEncoder.useHeap(_:stages:), MTLComputeCommandEncoder.useResource(_:usage:), MTLComputeCommandEncoder.useHeap(_:), MTLResourceUsage] [gate: Metal 3]
- Metal 4 to Metal 3 type map: `MTL4CommandQueue` <- `MTLCommandQueue`; `MTL4CommandBuffer` <- `MTLCommandBuffer`; `MTL4RenderCommandEncoder` <- `MTLRenderCommandEncoder`; `MTL4ComputeCommandEncoder` <- `MTLComputeCommandEncoder` + `MTLBlitCommandEncoder` + `MTLAccelerationStructureCommandEncoder` (one encoder now covers all three). The MTL4 types are fully separate types, not subclasses; other types (resources, pipelines' base types, events) are shared. The kind of queue you create (detected at runtime: an MTL4 queue where Metal 4 is supported, otherwise `MTLCommandQueue`) decides which type family the rest of the code uses. — /documentation/Metal/understanding-the-metal-4-core-api [symbols: MTL4CommandQueue, MTL4CommandBuffer, MTL4RenderCommandEncoder, MTL4ComputeCommandEncoder, MTL4MachineLearningCommandEncoder, MTL4CommandEncoder] [gate: Metal 4 vs Metal 3]
- Incremental adoption is allowed: parts of an app can move to an `MTL4CommandQueue` while the rest stays on `MTLCommandQueue`; `MTLEvent` and `MTLSharedEvent` work across any mix of the two queue kinds. — /documentation/Metal/understanding-the-metal-4-core-api [symbols: MTLEvent, MTLSharedEvent] [gate: Metal 4]
- `MTL4CommandQueue` comes from `device.makeMTL4CommandQueue()`; work goes to the GPU at commit, and you can commit from any thread. `commit:count:` submits several command buffers as one group, so worker threads each encode their own buffer and one commit sends them all — like `MTLParallelRenderCommandEncoder`, but for any kind of work. — /documentation/Metal/understanding-the-metal-4-core-api [symbols: MTLDevice.makeMTL4CommandQueue(), MTL4CommandQueue commit:count:] [gate: Metal 4]
- `MTL4CommandBuffer` is made by the DEVICE (`device.makeCommandBuffer()`), not by a queue, and can be committed to any MTL4 queue of that device; it has no `commit()` of its own. It is reusable indefinitely: `beginCommandBuffer(allocator:)`, encode, `endCommandBuffer()`, commit, then begin again. It does NOT retain the resources it references (like Metal 3's `makeCommandBufferWithUnretainedReferences()`), so the app must keep resources alive until the GPU finishes. — /documentation/Metal/understanding-the-metal-4-core-api [symbols: MTLDevice.makeCommandBuffer(), MTL4CommandBuffer.beginCommandBuffer(allocator:), MTL4CommandBuffer.endCommandBuffer(), MTLCommandQueue.makeCommandBufferWithUnretainedReferences()] [gate: Metal 4]
- `MTL4CommandAllocator` (from `device.makeCommandAllocator()`) owns the encoding memory and is bound to one command buffer at a time; to move it to another buffer, end the current one first. The frame pattern: one allocator per frame in flight (Hello Triangle uses `kMaxFramesInFlight = 3`), `allocator.reset()` only after the GPU has finished that frame, then `commandBuffer.beginCommandBuffer(allocator:)`. A single `MTL4CommandBuffer` is reused every frame. — /documentation/Metal/understanding-the-metal-4-core-api [symbols: MTL4CommandAllocator, MTLDevice.makeCommandAllocator(), MTL4CommandAllocator.reset()] [gate: Metal 4]
- Metal 4 encoders have no per-resource bind calls (no setBuffer/setTexture/useResource). Bindings live in an `MTL4ArgumentTable`: fill an `MTL4ArgumentTableDescriptor` (`maxBufferBindCount`, `maxTextureBindCount`, ...), create it with `device.makeArgumentTable(descriptor:)`, set entries with `setResource(_:bufferIndex:)`, `setAddress(_:index:)`, and `setSamplerState(_:index:)`, then assign the table to one or more stages of one or more encoders. A table uses only the memory its bindings need, and one table can be reused across encoders indefinitely. Apple's tip: keep separate tables per kind of work, each holding that work's common resources. — /documentation/Metal/understanding-the-metal-4-core-api [symbols: MTL4ArgumentTable, MTL4ArgumentTableDescriptor, MTL4ArgumentTableDescriptor.maxBufferBindCount, MTL4ArgumentTableDescriptor.maxTextureBindCount, MTLDevice.makeArgumentTable(descriptor:), MTL4ArgumentTable.setResource(_:bufferIndex:), MTL4ArgumentTable.setSamplerState(_:index:)] [gate: Metal 4]
- `MTL4RenderCommandEncoder` drops binding, residency, store-action-option, and tessellation methods. Residency goes through residency sets on the command buffer or the queue; tessellation is replaced by mesh shaders; `MTLStoreActionOptions` is unavailable because it does not apply to Apple silicon. A render pass can span command buffers by suspending at the end of one render encoder and resuming at the start of the next, which replaces `MTLParallelRenderCommandEncoder`: each thread gets its own encoder. — /documentation/Metal/understanding-the-metal-4-core-api [symbols: MTL4RenderCommandEncoder, MTLParallelRenderCommandEncoder, MTLStoreActionOptions] [gate: Metal 4]
- In Metal 4 every resource is untracked: wherever passes overlap and one writes, the app must add a barrier (or a fence or event). Canonical example: a compute dispatch writes data that a later render pass's fragment shader reads, so put a barrier between the `.dispatch` stage and the `.fragment` stage. — /documentation/Metal/understanding-the-metal-4-core-api [symbols: MTLStages.dispatch, MTLStages.fragment, MTLTextureDescriptor.hazardTrackingMode, MTLHeapDescriptor.hazardTrackingMode] [gate: Metal 4]
- Work-submission factories (Metal 3 side): `makeCommandQueue()` and `makeCommandQueue(maxCommandBufferCount:)`, which caps the uncompleted command buffers on that queue; `makeResidencySet(descriptor:)`; `makeIOCommandQueue(descriptor:)`; `makeIndirectCommandBuffer(descriptor:maxCommandCount:options:)` for reusable ICBs. — /documentation/Metal/work-submission [symbols: MTLDevice.makeCommandQueue(), MTLDevice.makeCommandQueue(maxCommandBufferCount:), MTLDevice.makeResidencySet(descriptor:), MTLDevice.makeIOCommandQueue(descriptor:), MTLDevice.makeIndirectCommandBuffer(descriptor:maxCommandCount:options:)]

## pipelines-and-render-passes.md
- Layer selection (one draw writes different slices of a texture array, cube, or 3D texture): a vertex output tagged `[[render_target_array_index]]`, constant across each primitive. The pipeline must fix `inputPrimitiveTopology`, unlike an ordinary pipeline, which accepts any primitive type per draw. The pass sets `renderTargetArrayLength` to the highest slice count the shader can pick (6 for a cube). Several attachments work for arrays and cubes but NOT when the target is a 3D texture. Load and store actions apply to every slice. Use it for one-pass cube reflections or shadow cubes and for stereo. — /documentation/Metal/rendering-to-multiple-texture-slices-in-a-draw-command [symbols: MTLRenderPipelineDescriptor.inputPrimitiveTopology, MTLRenderPassDescriptor.renderTargetArrayLength] [gate: every Mac-family GPU (`MTLGPUFamily.mac2`); Apple family 5 and later]
- Viewport selection: a vertex output `[[viewport_array_index]]` (constant per primitive), with arrays set by `setViewports(_:)` and `setScissorRects(_:)`. Pass the same count to both, and keep the shader's index inside that range. The fragment stage can read the same field to learn its viewport. The per-family maximum viewport count is in the Feature Set Tables. — /documentation/Metal/rendering-to-multiple-viewports-in-a-draw-command [symbols: MTLRenderCommandEncoder.setViewports(_:), MTLRenderCommandEncoder.setScissorRects(_:)] [gate: `mac2` or `apple5`]
- Variable rasterization rate: never render straight into the final target. Allocate intermediate color and depth at `rateMap.physicalSize(layer:)` (`screenSize` is the final target's size, not the intermediate's), set `MTLRenderPassDescriptor.rasterizationRateMap`, then run a later pass that scales the intermediate up into the destination. In MSL, bind the map's data buffer as `rasterization_rate_map_data` and build a `rasterization_rate_map_decoder` to convert between screen and physical coordinates. A uniform rate of 0.5 gives an intermediate at half width and half height. — /documentation/Metal/rendering-with-a-rasterization-rate-map [symbols: MTLRasterizationRateMap, MTLRasterizationRateMap.screenSize, physicalSize(layer:), MTLRenderPassDescriptor.rasterizationRateMap, rasterization_rate_map_data, rasterization_rate_map_decoder]
- VRR resolve pass: size a buffer from `rateMap.parameterDataSizeAndAlign` (the offset must be a multiple of its alignment; the buffer can hold other data too), fill it with `rateMap.copyParameterData(buffer:offset:)`, and bind it to the fragment shader. In MSL, `rasterization_rate_map_decoder map(data); map.map_screen_to_physical_coordinates(pos.xy)`, then sample the intermediate with a `coord::pixel` sampler. Draw text and UI at full rate after the upscale. On iOS, fold the upscale into the following render pass instead of a separate pass, to save bandwidth. — /documentation/Metal/scaling-variable-rasterization-rate-content [symbols: MTLRasterizationRateMap.parameterDataSizeAndAlign, MTLRasterizationRateMap.copyParameterData(buffer:offset:), rasterization_rate_map_data, rasterization_rate_map_decoder, map_screen_to_physical_coordinates]
- Load action choice: `.dontCare` when every pixel gets overwritten (free; contents undefined); `.clear` when only some pixels are drawn and the old contents are not needed (costs a clear-value write per pixel); `.load` only when the old contents are needed, and Apple calls it significantly slower than the other two. A memoryless target cannot use `.load`. — /documentation/Metal/setting-load-and-store-actions [symbols: MTLLoadAction.dontCare, MTLLoadAction.clear, MTLLoadAction.load]
- Store action choice: `.dontCare` for intermediates used only inside the pass, and normally the right choice for depth and stencil; `.store` always for drawables. MSAA: keep samples and resolve = `.storeAndMultisampleResolve` (needs `resolveTexture`; use it with a single render encoder); samples only = `.store`; resolve only = `.multisampleResolve`; neither = `.dontCare`. `.unknown` defers the choice, but a real action must be set before encoding ends, or Metal errors. A memoryless target cannot use `.store` or `.storeAndMultisampleResolve`. Across passes: store/resolve plus `.load` only if the next pass needs the contents; otherwise `.dontCare` then `.dontCare`/`.clear`. — /documentation/Metal/setting-load-and-store-actions [symbols: MTLStoreAction.dontCare, MTLStoreAction.store, MTLStoreAction.storeAndMultisampleResolve, MTLStoreAction.multisampleResolve, MTLStoreAction.unknown, MTLRenderPassAttachmentDescriptor.resolveTexture]
- Doc bug to avoid copying: the Swift sample on the load-and-store page assigns its depth and stencil textures to `colorAttachments[0]`. The correct targets are `depthAttachment` and `stencilAttachment`. — /documentation/Metal/setting-load-and-store-actions [symbols: MTLRenderPassDescriptor.depthAttachment, MTLRenderPassDescriptor.stencilAttachment]
- Pipeline compilation surface (topic list of the Shader libraries collection). Metal 4 names: `MTL4Compiler` / `MTL4CompilerDescriptor`; async jobs `MTL4CompilerTask` with `MTL4CompilerTaskOptions` and `MTL4CompilerTaskStatus`; `MTL4Archive` (a read-only container of compiled pipeline states); `MTL4BinaryFunction` / `MTL4BinaryFunctionDescriptor` / `MTL4BinaryFunctionOptions`; `MTL4PipelineStageDynamicLinkingDescriptor`; `MTL4StaticLinkingDescriptor`; `MTL4FunctionDescriptor` with subclasses `MTL4LibraryFunctionDescriptor`, `MTL4SpecializedFunctionDescriptor`, `MTL4StitchedFunctionDescriptor`; `MTL4LibraryDescriptor`; `MTL4PipelineDescriptor` and `MTL4PipelineOptions`; `MTL4ShaderReflection`. - Pipeline harvesting, the Metal 4 replacement for the Metal 3 binary-archive harvest: `MTL4PipelineDataSetSerializer` (a fast-append collector of data recorded while pipelines are created), configured by `MTL4PipelineDataSetSerializerDescriptor` and `MTL4PipelineDataSetSerializerConfiguration`. ## apple-gpu-tbdr.md
- On TBDR GPUs (Apple silicon), Metal does NOT support an intrapass barrier that waits on the `.fragment` or `.tile` stages. Inside a pass you can still depend on earlier work at the same pixel (fragment after fragment) or in the same tile (tile dispatch after tile dispatch), because those reads stay local. Reading another pixel's or another tile's result needs a new render pass plus sync: end the pass, then a consumer barrier in the new pass; or a producer barrier before `endEncoding()`; or `updateFence` in the old pass and `waitForFence` in the new one (same command buffer). — /documentation/Metal/synchronizing-stages-within-a-pass [symbols: MTLStages.fragment, MTLStages.tile, MTL4CommandEncoder.endEncoding(), MTL4CommandEncoder.barrier(afterQueueStages:beforeStages:visibilityOptions:), MTL4CommandEncoder.updateFence(_:afterEncoderStages:), MTL4CommandEncoder.waitForFence(_:beforeEncoderStages:)] [gate: Apple-family GPUs]
- TBDR model: the GPU bins all of a pass's geometry per tile, rejects occluded primitives, and only then shades the visible fragments into on-chip tile memory, writing the finished tile to device memory once. Apple describes tile memory as many times higher bandwidth and many times lower latency than device memory, at much lower energy. The fragment tail of one render pass can overlap the vertex stage of the next. Practical consequence: every extra pass boundary costs a store plus a reload, so merge work into one pass where you can. — /documentation/Metal/tailor-your-apps-for-apple-gpus-and-tile-based-deferred-rendering [gate: all Apple-family GPUs]
- A11-era (Apple4 family) additions: explicit imageblocks, tile shading, raster order groups, and imageblock sample-coverage control, plus faster fragment discard. Imageblocks: a per-tile 2D structure (width x height x per-pixel struct, each component addressable as a slice, for example albedo/specular/normal) that lives for the whole tile, across draws and tile dispatches. A fragment sees only its own pixel's entry; a tile/compute thread sees the whole imageblock. Attachments create implicit imageblocks automatically; you can declare richer ones (arrays, nested structs) in the shader and reuse them per phase. With explicit imageblocks, write to device memory explicitly from a compute/tile function; load and store actions only cover attachments. Use threadgroup memory for unstructured data and imageblocks for image-shaped data. — /documentation/Metal/tailor-your-apps-for-apple-gpus-and-tile-based-deferred-rendering [gate: A11 (Apple4) and later for explicit imageblocks]
- Tile shaders are compute (or fragment) functions that run inside a render pass on tile memory, replacing a render -> compute -> render sequence that would round-trip device memory between each step. — /documentation/Metal/tailor-your-apps-for-apple-gpus-and-tile-based-deferred-rendering [gate: Apple4+]
- Raster order groups: tag the memory a fragment shader reads and writes (pointers, imageblock fields, threadgroup memory) with a raster-order-group attribute; the hardware then makes overlapping fragments at the same pixel (and sample, with per-sample shading) wait for older ones, so read-modify-write follows submission order. Uses: OIT, dual-layer G-buffers, voxelization. Newer Apple GPUs allow MULTIPLE groups and per-channel ordering of imageblocks: single-pass deferred puts the G-buffer fields (albedo, normal, depth) in group 0 and the light accumulator in group 1, so light fragments read the G-buffer concurrently and serialize only on the accumulate. The G-buffer then stays in imageblock memory and never touches device memory. — /documentation/Metal/tailor-your-apps-for-apple-gpus-and-tile-based-deferred-rendering [gate: Apple4+; multiple groups on newer Apple GPUs]
- Apple MSAA: the hardware tracks per pixel whether an edge is present and how many unique colors it holds, blends per sample only on edges, and collapses to a single color when an opaque primitive covers the pixel. Since A11 it blends once per unique color, not once per covered sample. A tile shader can edit sample coverage to do a custom resolve, for example resolve the opaque geometry in-tile before drawing transparents, all in the same pass. — /documentation/Metal/tailor-your-apps-for-apple-gpus-and-tile-based-deferred-rendering [gate: Apple4+ for coverage control]
- Tile limits from the Feature Set Tables (PDF p.9, column order verified against the page image; families Apple2 to Apple10): tile size 32x32 without MSAA and with 2x, 32x16 with 4x, 16x16 with 8x. 8x MSAA (max sample count 8) exists only on Apple10; every other family caps at 4. The maximum implicit imageblock size per pixel per sample with multiple color targets is 32 B (Apple2-3), 64 B (Apple4-6), 128 B (Apple7-10). The maximum explicit imageblock size is 64 B (Apple4 and later). Up to 8 color render targets per pass descriptor on every family. Max total threadgroup memory is 32 KB (Apple4 and later). — pdf:fst#all (checked while reading /documentation/Metal/understanding-color-renderable-pixel-format-sizes) [gate: per Apple family]
- Color-render-target budget: on Apple GPUs, the summed per-pixel size of ALL color attachments in one pass must fit the tile-memory limit (the implicit imageblock row above). Tile-memory sizes for a format can differ from its system-memory size. A fat G-buffer can therefore fail on Apple GPUs where a discrete GPU would accept it, since non-Apple GPUs only limit the count (8), not the combined size. — /documentation/Metal/understanding-color-renderable-pixel-format-sizes [symbols: MTLPixelFormat.bgra8Unorm, MTLPixelFormat.bgr5A1Unorm] [gate: Apple-family GPUs]

- Generic pointers (MSL 4.1 and later): a pointer with no address-space qualifier can point into `thread`, `threadgroup`, or `device` memory, so one utility function replaces the per-address-space overloads that MSL 4.0 and earlier required. Entry-point resource parameters still need an explicit `device` / `threadgroup` qualifier. — /documentation/Metal/writing-reusable-gpu-functions-with-generic-pointers [symbols: thread, threadgroup, device, constant, threadgroup_imageblock, ray_data, object_data] [gate: MSL 4.1]
- Generic pointer cost: usually zero, because the compiler resolves the address space statically. Where it cannot (across dynamic libraries, or a pointer loaded from an argument buffer), it branches at runtime on the actual space; that is cheap per call but adds up in hot inner loops, and it can raise register pressure slightly on some GPUs. Fix: provide concrete-qualified versions for the hot call sites (these also compile on MSL 4.0). — /documentation/Metal/writing-reusable-gpu-functions-with-generic-pointers [gate: MSL 4.1]
- Silent semantic change: in MSL 4.0 a member function with no qualifier has an implicit `thread` `this`; in MSL 4.1 that same `this` becomes generic. To keep 4.0 behaviour, run `xcrun metal -std=metal4.0 -Wmetal-addr-spaces -Xclang -fixit -fsyntax-only File.metal`, which rewrites unannotated members (including constructors) to `... thread` in place, so back the file up first. `-fsyntax-only` makes the run exit 0 because it stops before linking. — /documentation/Metal/writing-reusable-gpu-functions-with-generic-pointers [symbols: -Wmetal-addr-spaces, -std=metal4.0] [gate: MSL 4.0 -> 4.1 migration]
- Shared host/device headers: in MSL 4.1 a struct with a pointer member (for example `Light* lights;`) compiles unchanged in both C++ and MSL, so one header can serve both sides; MSL 4.0 needed `device Light*`, which forked the definition. Use `#ifndef __METAL_VERSION__` to pull `simd::float3`, `dot`, and `normalize` into the C++ side. — /documentation/Metal/writing-reusable-gpu-functions-with-generic-pointers [symbols: __METAL_VERSION__, simd::float3] [gate: MSL 4.1]
- Casting: concrete to generic is implicit. Generic to concrete uses `static_cast<thread int*>(p)`, which is unchecked (a wrong space is undefined behaviour; Shader Validation catches it during development), or `addrspace_cast<device int*>(p)`, which is checked at runtime and returns `nullptr` on a mismatch. Query with `is_thread_addrspace()`, `is_device_addrspace()`, `is_threadgroup_addrspace()` (each returns false for null). Example need: a 64-bit atomic that only works on a `device` pointer. Casting null yields null. — /documentation/Metal/writing-reusable-gpu-functions-with-generic-pointers [symbols: static_cast, addrspace_cast, is_thread_addrspace, is_device_addrspace, is_threadgroup_addrspace] [gate: MSL 4.1]
- ABI break: MSL 4.1 changes function-name mangling, so linking MSL 4.0 and MSL 4.1 binaries together (metallibs, dynamic libraries, binary archives, even IR) can misbehave at runtime, and neither the compiler nor the linker detects it. Compile everything that links together at ONE language version; it is the language version that matters, not the compiler version (a newer compiler emitting `-std=metal4.0` links fine with other 4.0 binaries). — /documentation/Metal/writing-reusable-gpu-functions-with-generic-pointers [gate: MSL 4.0 vs 4.1]
