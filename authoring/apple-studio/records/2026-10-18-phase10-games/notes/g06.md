## input.md

- A Mac game drawing its own text field (chat box, name entry) in a Metal view gets the system insertion caret, input-language and Caps Lock accessories, and dictation glow by adopting `NSTextInputClient` and layering an `NSTextInsertionIndicator` subview over the text area; set `displayMode` to `.automatic` on becoming first responder and `.hidden` on resigning, and move the indicator's `frame` as the caret moves. Only standard `NSTextView`/`NSTextField` get this for free. — /documentation/AppKit/adopting-the-system-text-cursor-in-custom-text-views [symbols: NSTextInputClient, NSTextInsertionIndicator, NSTextInsertionIndicator.DisplayMode.automatic, NSTextInsertionIndicator.DisplayMode.hidden, NSTextInsertionIndicator.DisplayMode.visible, automaticModeOptions, showWhileTracking, showEffectsView, effectsViewInserter, preferredTextAccessoryPlacement()] [gate: macOS 14]
- For in-game text entry (IME composition, dead keys, dictation) in a custom Metal view, the protocol is `NSTextInputClient`, driven by the view's `NSTextInputContext`; the older `NSTextInput` protocol is listed as deprecated. Raw `keyDown(with:)` key codes alone do not give composed CJK text. Where a real text field is acceptable (login, server address), an overlaid `NSTextField` or `NSSecureTextField` gets all of this for free. — /documentation/AppKit/text-display; /documentation/AppKit/text-field [symbols: NSTextInputClient, NSTextInputContext, NSTextInput, NSTextField, NSSecureTextField]
- Trackpad pinch and two-finger rotate on Mac arrive through AppKit gesture recognizers attached to the game view, not through raw events: `NSMagnificationGestureRecognizer` (pinch, e.g. camera zoom) and `NSRotationGestureRecognizer` (two touches turning opposite each other), both continuous; `NSPanGestureRecognizer` is continuous, `NSClickGestureRecognizer` (N clicks) and `NSPressGestureRecognizer` (hold for a minimum time) are discrete. Subclass `NSGestureRecognizer` for custom sequences. — /documentation/AppKit/gestures [symbols: NSMagnificationGestureRecognizer, NSRotationGestureRecognizer, NSPanGestureRecognizer, NSClickGestureRecognizer, NSPressGestureRecognizer, NSGestureRecognizer, NSGestureRecognizerDelegate]
- The AppKit event path a Mac game's view sits in: events travel the `NSResponder` chain (`NSApplication`, `NSWindow`, `NSView` all inherit from it), so the Metal view must be a responder (accept first responder) to receive `NSEvent` key and mouse events. Trackpad-specific types: `NSTouch` (per-touch snapshots), `NSPressureConfiguration` (Force Touch pressure behavior, e.g. a pressure-sensitive throttle), `NSEvent.Phase` (gesture phases), `NSEvent.ModifierFlags`, and `NSEvent.EventTypeMask` for filtering. — /documentation/AppKit/mouse-keyboard-and-trackpad [symbols: NSResponder, NSEvent, NSTouch, NSPressureConfiguration, NSEvent.Phase, NSEvent.ModifierFlags, NSEvent.EventTypeMask, NSEvent.SwipeTrackingOptions]

## game-loop-and-threading.md

- AppKit's whole OpenGL hosting surface now sits in its Deprecated Symbols collection: `NSOpenGLView`, `NSOpenGLContext`, `NSOpenGLLayer`, `NSOpenGLPixelBuffer`, `NSOpenGLPixelFormat`, plus `NSOpenGLGetOption`/`NSOpenGLSetOption`/`NSOpenGLGetVersion`. A port that still hosts its renderer in one of these needs a Metal-backed view (MTKView or a CAMetalLayer-backed NSView) as the replacement, not a GL-on-Metal shim; `NSDisableScreenUpdates()`/`NSEnableScreenUpdates()` are deprecated too. — /documentation/AppKit/deprecated-symbols [symbols: NSOpenGLView, NSOpenGLContext, NSOpenGLLayer, NSOpenGLPixelFormat, NSOpenGLPixelBuffer, NSDisableScreenUpdates(), NSEnableScreenUpdates()]
- Mac cursor control lives in AppKit: `NSCursor` for the pointer image and hide/show, and `NSTrackingArea` on the game view for mouse-entered/exited and cursor-update events over a region (e.g. show the system cursor only over a HUD rect, hide it over the play area). — /documentation/AppKit/menus-cursors-and-the-dock [symbols: NSCursor, NSTrackingArea]
- To have a windowed Mac game reopen at its last size and position, give the window an `identifier`, a `setFrameAutosaveName(_:)`, a `restorationClass` conforming to `NSWindowRestoration`, and `isRestorable = true`, and return `true` from `applicationSupportsSecureRestorableState(_:)`. AppKit calls the static `restoreWindow(withIdentifier:state:completionHandler:)` per window at launch, then `restoreState(with:)`; call `invalidateRestorableState()` whenever the saved state goes stale (e.g. resolution or windowed/full-screen change). Saved state is thrown away on force quit, so test with Command-Q. — /documentation/AppKit/restoring-your-app-s-state-with-appkit [symbols: NSWindowRestoration, restoreWindow(withIdentifier:state:completionHandler:), setFrameAutosaveName(_:), restorationClass, isRestorable, applicationSupportsSecureRestorableState(_:), encodeRestorableState(with:), restoreState(with:), invalidateRestorableState()] [gate: macOS 12.5 sample]
- AppKit chrome around the Metal view (settings panes, overlay labels) can follow an `@Observable` model automatically: whatever Observable properties are read inside `NSView.layout()`, `draw(_:)`, `updateConstraints()`, or `NSViewController.viewWillLayout()` / `updateViewConstraints()` are tracked, and a change re-runs that method. On macOS 15 this is opt-in via the `NSObservationTrackingEnabled` Info.plist key set to true. Keep per-frame sim state out of such a model, or every tick re-lays-out the AppKit views; the Metal view itself should stay on the display-link loop. — /documentation/AppKit/updating-views-automatically-with-observation-tracking-in-appkit [symbols: Observable, NSObservationTrackingEnabled, NSView.layout(), NSView.draw(_:), NSView.updateConstraints(), NSViewController.viewWillLayout(), NSViewController.updateViewConstraints()] [gate: macOS 15 needs plist opt-in]
- Porting a job system from x86 Macs: Apple silicon is weakly ordered, so lock-free queues and hand-rolled spin flags that were correct by accident under x86's strong ordering (implicit barriers) can race. Use explicit primitives (Dispatch serial queues, `os_unfair_lock`, pthreads, or C11/C++11 `<stdatomic.h>` atomics with stated memory orders); if you keep custom lockless code, validate it on Apple silicon and run Thread Sanitizer. — /documentation/Apple-Silicon/addressing-architectural-differences-in-your-macos-code [symbols: os_unfair_lock, stdatomic.h, DispatchQueue] [gate: arm64 Mac]
- Do not hard-code hardware constants a job system or allocator depends on: read the page size from the `vm_page_size` global and the cache-line size from `sysctl` `hw.cachelinesize` (use it for false-sharing padding of per-thread counters), and probe CPU features with `sysctlbyname("hw.optional.<feature>")`; `sysctl hw` in Terminal lists them. Both page and cache-line sizes differ from Intel Macs. — /documentation/Apple-Silicon/addressing-architectural-differences-in-your-macos-code [symbols: vm_page_size, sysctlbyname, hw.cachelinesize, hw.optional.*]
- Frame timing: `mach_absolute_time()` ticks are not nanoseconds and differ between native and Rosetta-translated processes; always scale by `mach_timebase_info` (numer/denom), or call `clock_gettime_nsec_np` to get nanoseconds directly. A fixed-step sim accumulator built on raw ticks runs at the wrong rate on Apple silicon. — /documentation/Apple-Silicon/addressing-architectural-differences-in-your-macos-code [symbols: mach_absolute_time, mach_timebase_info, mach_timebase_info_data_t, clock_gettime_nsec_np]
- Determinism hazards in a sim or netcode ported between Intel and Apple silicon builds: C/C++ float-to-int casts of out-of-range values differ (arm64 saturates, e.g. `(uint32_t)INFINITY` = 0xffffffff, `(int32_t)INFINITY` = 0x7fffffff; x86_64 gives 0 and 0x80000000), so lockstep peers on mixed architectures can diverge. Swift defines one behavior on every architecture. Catch it with UBSan `float-cast-overflow` and `-Wconversion`. Also: Objective-C `BOOL` is native `bool` on arm64 but `signed char` on x86_64 (warn with `-Wobjc-signed-char-bool-implicit-int-conversion`). — /documentation/Apple-Silicon/addressing-architectural-differences-in-your-macos-code [symbols: BOOL] [gate: arm64 vs x86_64]
- SSE/AVX intrinsics in math or sim code: replace with clang builtins (`__builtin_clz` etc., guarded with `__has_builtin`) or with Accelerate, which Apple names as the best replacement for x86 vector code (vector/matrix math, image ops, DSP, linear algebra, compression, neural-net ops). For a game, that means vDSP for audio/DSP-style batch math and simd for per-object vector math on the CPU; per-pixel and large data-parallel work belongs in Metal compute instead. Other ABI notes: Apple silicon's C++ ABI follows iOS, not Intel macOS; variadic arguments go on the stack on arm64, so never redeclare a fixed-argument function as variadic, and call `objc_msgSend` only through a cast, type-exact function pointer (turn on the build setting for strict `objc_msgSend` checking). — /documentation/Apple-Silicon/addressing-architectural-differences-in-your-macos-code [symbols: __builtin_clz, __has_builtin, objc_msgSend, Accelerate]
- Thread priority on Apple silicon is expressed as QoS, not raw priority: QoS decides which core type (performance vs efficiency) the scheduler favors, and background QoS tends to land on efficiency cores. Replace `pthread_setschedparam`, `setpriority`, and `thread_set_policy` in an engine's thread setup with QoS APIs such as `pthread_set_qos_class_self_np` (user-interactive for the frame-critical main/render/sim threads, utility or background for streaming and saves). Unassigned work hurts both responsiveness and efficiency. — /documentation/Apple-Silicon/tuning-your-code-s-performance-for-apple-silicon [symbols: pthread_set_qos_class_self_np, pthread_setschedparam, setpriority, thread_set_policy, QOS_CLASS_USER_INTERACTIVE] [gate: arm64 Mac]
- Parallel-for sizing: `DispatchQueue.concurrentPerform(iterations:execute:)` work-steals across mixed P and E cores; give it at least 3x as many iterations as total cores so the work can rebalance. A custom job pool must also work-steal, because a static split leaves the P-core threads idle while E-core threads finish their equal share. — /documentation/Apple-Silicon/tuning-your-code-s-performance-for-apple-silicon [symbols: DispatchQueue.concurrentPerform(iterations:execute:)] [gate: arm64 Mac]
- No spin-waiting in job systems or frame sync: a thread that spins holds a core, and on Apple silicon a fast consumer spinning while a slow producer runs on an E core makes it worse. Block on `os_unfair_lock`, a condition variable, or a mutex instead, and avoid `pthread_yield_np`-style yielding, which keeps the yielding thread running whenever the waiters have lower priority. — /documentation/Apple-Silicon/tuning-your-code-s-performance-for-apple-silicon [symbols: os_unfair_lock, pthread_yield_np]
- Do separate perf passes on Apple silicon and Intel hardware; a change that helps one can regress the other, and Instruments runs natively on both. — /documentation/Apple-Silicon/tuning-your-code-s-performance-for-apple-silicon

## audio-and-haptics.md

- AppKit's API for the Mac's built-in haptic hardware is `NSHapticFeedbackManager`, which applies only on a system with a Force Touch trackpad (pair it with `NSPressureConfiguration` for pressure stages). Core Haptics is also in the macOS SDK (`CHHapticEngine`, macos 10.15 per the header), but the page does not route trackpad haptics through it; gate any Core Haptics use on `CHHapticEngine.capabilitiesForHardware().supportsHaptics` rather than assuming the trackpad answers it. Controller rumble is a separate path (Game Controller haptics). — /documentation/AppKit/mouse-keyboard-and-trackpad [symbols: NSHapticFeedbackManager, NSPressureConfiguration, CHHapticEngine, capabilitiesForHardware, supportsHaptics] [gate: Force Touch trackpad]
- Trackpad haptics are not a waveform API: per the AppKit header, `NSHapticFeedbackManager.defaultPerformer` (an `NSHapticFeedbackPerformer`) plays only three fixed `NSHapticFeedbackPattern`s, `.generic`, `.alignment`, `.levelChange`, via `performFeedbackPattern(_:performanceTime:)`; re-request `defaultPerformer` each time because the device behind it can change. Good for a UI snap or menu tick, not for gameplay rumble. `NSAlignmentFeedbackFilter` adds snap-to-guide haptics to drags (e.g. a level editor). — /documentation/AppKit/sound-speech-and-haptics; SDK AppKit/NSHapticFeedback.h [symbols: NSHapticFeedbackManager, defaultPerformer, NSHapticFeedbackPerformer, NSHapticFeedbackPattern, performFeedbackPattern(_:performanceTime:), NSAlignmentFeedbackFilter, NSAlignmentFeedbackToken]
- Sample-accurate scheduling from the audio thread: `AUScheduleParameterBlock` and `AUScheduleMIDIEventBlock` take an `AUEventSampleTime`; pass `AUEventSampleTimeImmediate` to land in the next render cycle, optionally plus a small frame offset (under 4096 frames). The base `AUAudioUnit` converts the immediate value to a real sample time, so a subclass's render code never sees it. — /documentation/AudioToolbox/1387633-aueventsampletime [symbols: AUEventSampleTime, AUEventSampleTimeImmediate, AUScheduleParameterBlock, AUScheduleMIDIEventBlock, AUAudioUnit]
- Occlusion vs obstruction in Apple's 3D mixers are both a 5 kHz low-pass attenuation in dB (-100 to 0, 0 = no filtering), but placed differently: occlusion filters the sound before the reverb send (wall between listener and source muffles direct and reverb), obstruction filters only the direct path after the send (object in the way, room reverb still bright). The parameter pages list `k3DMixerParam_OcclusionAttenuation` / `k3DMixerParam_ObstructionAttenuation` (plus `...InDecibels` variants, macOS 10.15+) for AUMixer3D; the macOS `kAudioUnitSubType_3DMixer` is deprecated (macos 10.3 to 10.10), and the header points to `kAudioUnitSubType_SpatialMixer`, whose equivalents are `kSpatialMixerParam_OcclusionAttenuation` (10) and `kSpatialMixerParam_ObstructionAttenuation` (11), alongside azimuth (-180..180 deg), elevation (-90..90), distance (0..10000 m), `kSpatialMixerParam_PlaybackRate` (0.5..2.0), and global head yaw/pitch/roll (`kSpatialMixerParam_HeadYaw` 19 etc.). The reverb's filter type and enable switch (`kReverbParam_FilterType`, `kReverbParam_FilterEnable`) exist only on AUSpatialMixer, next to `kReverbParam_FilterFrequency` / `_FilterBandwidth` / `_FilterGain`. — /documentation/AudioToolbox/1389763-3d_mixer_unit_parameters; /documentation/AudioToolbox/1390073-auspatialmixer-parameters; /documentation/AudioToolbox/1390119-reverb_parameters; SDK AudioToolbox/AudioUnitParameters.h, AUComponent.h [symbols: k3DMixerParam_OcclusionAttenuation, k3DMixerParam_ObstructionAttenuation, k3DMixerParam_OcclusionAttenuationInDecibels, k3DMixerParam_ObstructionAttenuationInDecibels, kAudioUnitSubType_3DMixer, kAudioUnitSubType_SpatialMixer, kSpatialMixerParam_OcclusionAttenuation, kSpatialMixerParam_ObstructionAttenuation, kSpatialMixerParam_HeadYaw, kSpatialMixerParam_HeadPitch, kSpatialMixerParam_HeadRoll] [gate: 3DMixer deprecated on macOS; InDecibels variants macOS 10.15/iOS 13]
- Metering and bus mix values a game's mixer HUD or ducking logic can read straight off Apple's stock units: `kMultiChannelMixerParam_PreAveragePower` / `PostAveragePower` / `PrePeakHoldLevel` / `PostPeakHoldLevel` (dB) plus `_Volume` (linear gain), `_Pan`, `_Enable`; a master-bus limiter is `kAudioUnitSubType_PeakLimiter` (`kLimiterParam_AttackTime`, `_DecayTime`, `_PreGain`), and single-band compression/expansion is the Dynamics Processor (`kDynamicsProcessorParam_Threshold`, `_HeadRoom`, `_AttackTime`, `_ReleaseTime`, `_OverallGain`). These raw IDs matter when you host the AU directly through AudioToolbox (`AudioUnitSetParameter`); check the AVAudioEngine node's own properties before assuming a wrapper exposes the same knob. — /documentation/AudioToolbox/1389739-aumultichannelmixer_parameters; /documentation/AudioToolbox/1389597-peak_limiter_unit_parameters; /documentation/AudioToolbox/1389787-dynamics_processor_unit_paramete [symbols: kMultiChannelMixerParam_PreAveragePower, kMultiChannelMixerParam_PostAveragePower, kMultiChannelMixerParam_PrePeakHoldLevel, kMultiChannelMixerParam_PostPeakHoldLevel, kMultiChannelMixerParam_Volume, kLimiterParam_AttackTime, kLimiterParam_DecayTime, kLimiterParam_PreGain, kAudioUnitSubType_PeakLimiter, kDynamicsProcessorParam_Threshold, kDynamicsProcessorParam_HeadRoom, kDynamicsProcessorParam_OverallGain, AudioUnitSetParameter]
- Slow-motion or pitch-shifted gameplay audio: the time-pitch unit (`kAudioUnitSubType_NewTimePitch`) takes `kNewTimePitchParam_Rate` and `kNewTimePitchParam_Pitch` independently, with quality knobs `_Overlap`, `_EnablePeakLocking`, `_EnableSpectralCoherence`, `_EnableTransientPreservation`, `_Smoothness`; under AVAudioEngine use the `AVAudioUnitTimePitch` node (AVFAudio header). The older AUTimePitch / offline AUTimePitch / AUPitch family has its own, smaller ID set (`kTimePitchParam_Rate`, `kTimePitchParam_Pitch`, `kTimePitchParam_EffectBlend`); do not mix the two ID sets across units. When pitch should follow speed (engine RPM, tape-stop, whole-mix slow-mo), the cheaper Varispeed unit resamples instead: `kVarispeedParam_PlaybackRate` or `kVarispeedParam_PlaybackCents`, wrapped by `AVAudioUnitVarispeed.rate`; per its header, rate 2.0 is one octave up, and rate = 2^(cents/1200). — /documentation/AudioToolbox/1389643-aunewtimepitch-parameters; /documentation/AudioToolbox/1389946-autimepitch_autimepitch_offline; /documentation/AudioToolbox/1390014-varispeed_unit_parameters; SDK AVFAudio/AVAudioUnitVarispeed.h [symbols: kVarispeedParam_PlaybackRate, kVarispeedParam_PlaybackCents, AVAudioUnitVarispeed, kTimePitchParam_Rate, kTimePitchParam_Pitch, kTimePitchParam_EffectBlend, kAudioUnitSubType_NewTimePitch, kNewTimePitchParam_Rate, kNewTimePitchParam_Pitch, kNewTimePitchParam_Overlap, kNewTimePitchParam_EnablePeakLocking, kNewTimePitchParam_EnableSpectralCoherence, kNewTimePitchParam_EnableTransientPreservation, kNewTimePitchParam_Smoothness, AVAudioUnitTimePitch]
- One place AudioToolbox is still the right layer: decoding compressed music or VO that lives inside the game's own pack file or arrives over the network rather than as a standalone file. `AudioFileStreamOpen` + `AudioFileStreamParseBytes` take bytes you push in and call back with properties and packets; wait for `kAudioFileStreamProperty_ReadyToProducePackets`, then read `_DataFormat` (an `AudioStreamBasicDescription`), `_MagicCookieData` (required by some codecs before decoding), `_PacketSizeUpperBound` / `_MaximumPacketSize` for buffer sizing, `_FormatList` (AAC with SBR can decode to several formats), and `_PacketTableInfo` (`AudioFilePacketTableInfo` with `mPrimingFrames` / `mRemainderFrames`, the encoder padding to trim for gapless loops). Byte/packet translations may be estimates: check `kBytePacketTranslationFlag_IsEstimate`. `_AudioDataByteCount` can be absent for some streams. Packaging gotcha: if a file's packet table or other defining info sits after the audio data, the parser returns `kAudioFileStreamError_NotOptimized` and cannot produce packets, so write stream-friendly (header-first) files into the pack; `kAudioFileStreamError_DataUnavailable` just means feed more bytes, `kAudioFileStreamError_DiscontinuityCantRecover` means the stream must be restarted. — /documentation/AudioToolbox/1391506-audio-file-stream-properties; /documentation/AudioToolbox/1391572-audio-file-stream-errors; SDK AudioToolbox/AudioFileStream.h, AudioFile.h [symbols: AudioFileStreamOpen, AudioFileStreamParseBytes, AudioFileStreamGetProperty, kAudioFileStreamProperty_ReadyToProducePackets, kAudioFileStreamProperty_DataFormat, kAudioFileStreamProperty_MagicCookieData, kAudioFileStreamProperty_PacketSizeUpperBound, kAudioFileStreamProperty_MaximumPacketSize, kAudioFileStreamProperty_FormatList, kAudioFileStreamProperty_PacketTableInfo, AudioFilePacketTableInfo, kBytePacketTranslationFlag_IsEstimate, AudioStreamBasicDescription]
- Load-time decode of compressed SFX to the mixer's PCM format (in a C/C++ engine or an asset tool) is ExtAudioFile's job: set `kExtAudioFileProperty_ClientDataFormat` (and `_ClientChannelLayout`) to the engine's format and reads come back converted; `kExtAudioFileProperty_FileDataFormat` / `_FileLengthFrames` (an `SInt64`, read-only for non-PCM files) size the destination buffer, and `kExtAudioFileProperty_PacketTable` reads or overrides priming/remainder frames (it errors if the file type has no packet table). Under AVAudioEngine, `AVAudioFile` with a processing format plays the same role. — /documentation/AudioToolbox/1486859-property-identifiers-for-extende [symbols: ExtAudioFileRef, kExtAudioFileProperty_ClientDataFormat, kExtAudioFileProperty_ClientChannelLayout, kExtAudioFileProperty_FileDataFormat, kExtAudioFileProperty_FileLengthFrames, kExtAudioFileProperty_PacketTable, kExtAudioFileProperty_ClientMaxPacketSize, kExtAudioFileProperty_AudioConverter, AVAudioFile]
- A Mac game that talks to Core Audio devices directly (device picker, output volume) must listen for `kAudioHardwareServiceProperty_ServiceRestarted` on HAL objects: when the audio service restarts, every cached device ID and property listener is gone and must be rebuilt. The system output volume/balance selectors now carry Main names (`kAudioHardwareServiceDeviceProperty_VirtualMainVolume`, `_VirtualMainBalance`); the `VirtualMaster*` spellings are the old ones. — /documentation/AudioToolbox/1405208-audio-hardware-services-properti [symbols: kAudioHardwareServiceProperty_ServiceRestarted, kAudioHardwareServiceDeviceProperty_VirtualMainVolume, kAudioHardwareServiceDeviceProperty_VirtualMainBalance, kAudioHardwareServiceDeviceProperty_VirtualMasterVolume] [gate: macOS]
- System Sound Services suits only short UI blips outside the game mix: set `kAudioServicesPropertyIsUISound` = 1 so the sound obeys the user's Sound Effects setting, and `kAudioServicesPropertyCompletePlaybackIfAppDies` (default 0) if it must finish after quit. - `NSSound` is AppKit's simple load-and-play interface for an audio file (and `NSBeep()` the system beep); it has no mixing graph, so a game's SFX and music belong on AVAudioEngine (or PHASE), with `NSSound` at most for a menu click in a non-game tool. — /documentation/AppKit/sound-speech-and-haptics [symbols: NSSound, NSBeep]

## assets.md

- A Mac game or level editor that opens its own save or level files declares each as a document type in Xcode's Document Types editor, which writes the entry into `Info.plist`; the system uses it to route opened files to the app. Use a system UTI (e.g. `public.plain-text`) only for standard formats; a proprietary save format needs a user-defined (exported) UTI, which also fixes the file extension. Set the Role (Editor vs viewer), name the `NSDocument` subclass as `$(PRODUCT_MODULE_NAME).ClassName`, and tick Bundle only when the format is a package directory. Note the document architecture leans on the Objective-C runtime (KVC/KVO, `@objc dynamic` model properties), which a Swift/C++ engine's data model may not want. — /documentation/AppKit/developing-a-document-based-app [symbols: NSDocument, NSDocumentController, NSWindowController, read(from:ofType:), data(ofType:), makeWindowControllers()]
- Map a file extension to its type identifier with `UTType(filenameExtension:)` from UniformTypeIdentifiers (macOS 11+); the older CoreServices `UTTypeCreatePreferredIdentifierForTag(kUTTagClassFilenameExtension, ...)` is the pre-11 fallback the sample keeps behind `#available`. A tool that accepts dragged-in source art (textures, meshes) should register for `NSFilePromiseReceiver.readableDraggedTypes` as well as `.fileURL`, try promises first (Photos and Safari hand over promises, often the higher-quality file), and fulfil them on a background `OperationQueue` so a large import does not block the main thread. A promise exists because the dragged item may not be a file on disk yet when the drag starts; the drag pasteboard is separate from the copy/paste clipboard. — /documentation/AppKit/supporting-collection-view-drag-and-drop-through-file-promises; /documentation/AppKit/supporting-drag-and-drop-through-file-promises [symbols: UTType(filenameExtension:), UTTypeCreatePreferredIdentifierForTag, NSFilePromiseReceiver, readableDraggedTypes, receivePromisedFiles(atDestination:options:operationQueue:reader:), NSFilePromiseProvider, NSFilePromiseProviderDelegate, operationQueue(for:)] [gate: macOS 11 for UTType]
- Arbitrary binary game data (level blobs, baked tables) can ship as a data set inside an asset catalog and load at runtime with `NSDataAsset` (AppKit; UIKit has its own), rather than as a loose bundle file; the AppKit page lists it only at index level. — /documentation/AppKit/resource-management [symbols: NSDataAsset]

## game-design.md

- A Mac game that draws its menus and HUD in Metal has no `NSView` per button, so VoiceOver sees nothing. Expose each drawn control as an `NSAccessibilityElement` and adopt the role-specific protocol that matches what it does (`NSAccessibilityButton`, `NSAccessibilitySlider`, `NSAccessibilityCheckBox`, `NSAccessibilitySwitch`, `NSAccessibilityStaticText`, `NSAccessibilityGroup` for a container, `NSAccessibilityProgressIndicator` for loading bars); the compiler then demands the accessor and action methods that role needs. Use the method-based `NSAccessibilityProtocol`, not the legacy key-based informal `NSAccessibility` API (its attribute-name/value methods are deprecated); only `accessibilityHitTest(_:)`, `accessibilityFocusedUIElement`, and `accessibilityNotifiesWhenDestroyed` from the old API are still worth combining with it. — /documentation/AppKit/custom-controls; /documentation/AppKit/nsaccessibility [symbols: NSAccessibilityElement, NSAccessibilityProtocol, NSAccessibilityButton, NSAccessibilitySlider, NSAccessibilityCheckBox, NSAccessibilitySwitch, NSAccessibilityStaticText, NSAccessibilityGroup, NSAccessibilityProgressIndicator, NSAccessibilityContainsTransientUI, accessibilityHitTest(_:), accessibilityFocusedUIElement, accessibilityNotifiesWhenDestroyed]
- If a Mac game uses native AppKit chrome over or beside its Metal view (pause overlay, settings window), the Liquid Glass material is available as `NSGlassEffectView` (with a `Style`), and `NSGlassEffectContainerView` merges child glass views that sit close together; `NSVisualEffectView` remains the older translucency/vibrancy view. AppKit's own guidance is to prefer stock views and controls because they track system changes. — /documentation/AppKit/views-and-controls [symbols: NSGlassEffectView, NSGlassEffectView.Style, NSGlassEffectContainerView, NSVisualEffectView, NSBackgroundExtensionView]

## app-release/direct-distribution.md

- A Mac game that ships a launcher, updater, anti-cheat helper, or local server process must end those processes when the visible app quits. If something keeps running, macOS puts a Dock indicator on the app with a "stop running in background" menu item, posts a first-run notification that leads to Settings > Login Items & Extensions, and after repeated stops offers to block the app's background activity for good. An app that drops out of the Dock via `setActivationPolicy(_:)` or `TransformProcessType` loses the Dock indicator but still triggers the notification. — /documentation/AppKit/managing-ongoing-background-processes-in-your-mac [symbols: NSApplication.setActivationPolicy(_:), TransformProcessType]
- Which mechanism to use for helper processes: put helpers spawned with `system()`/`fork()`/`posix_spawn()` into an XPC service or an in-app extension so the system tracks and kills them with the app; register anything meant to outlive the app as a launch agent or daemon through `SMAppService` (ServiceManagement), which surfaces it in System Settings and lets the user disable it, then test with it disabled and read `SMAppService.status`. To stop a separate background app you launched, send it a quit Apple event (`kAEQuitApplication` via `NSAppleEventDescriptor`) before your own exit, or have it declare `NSSupportsAutomaticTermination` (needs graceful shutdown) or `NSSupportsSuddenTermination` (tolerates kill) in its Info.plist. Runtime changes to `automaticTerminationOptOutCounter` are not honored for this; use the plist keys.
