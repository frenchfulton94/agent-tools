## game-loop-and-threading.md

- simd math has three variants of most functions: default (`simd_rsqrt`), precise (`simd_precise_rsqrt`), and fast (`simd_fast_rsqrt`). Precise is within a few ULPs. Fast may keep only 22 bits for double and 8 bits for half. Defaults normally resolve to precise, but `-ffast-math` silently switches every default call to the fast variant. A fixed-step simulation that must be deterministic should call `simd_precise_*` explicitly, or keep `-ffast-math` out of sim targets. Otherwise one build flag changes simulation results between builds. — /documentation/Accelerate/double-precision-floating-point-vectors [symbols: simd_rsqrt(_:), simd_precise_rsqrt(_:), simd_fast_rsqrt(_:)]
- The same three-variant rule applies to half vectors; fast half functions may drop to 8 bits of accuracy. — /documentation/Accelerate/half-precision-floating-point-vectors [symbols: simd_half4, simd_fast_rsqrt(_:)]

## audio-and-haptics.md

### Real-time rules, shown by the vDSP audio-unit sample

- The DSP kernel of the vDSP Audio Unit extension sample is C++, chosen for real-time safety. Filter state is allocated once, in `initialize(...)`, with `vDSP_biquad_CreateSetup`. Each render block then updates coefficients in place with `vDSP_biquad_SetCoefficientsDouble` and runs `vDSP_biquad` per channel at unit stride. Nothing allocates on the render thread. SDK check (`vDSP.h`): `vDSP_biquad_CreateSetup` allocates memory (macOS 10.9 / iOS 6). `vDSP_biquad_SetCoefficientsDouble` / `vDSP_biquad_SetCoefficientsSingle` update a live setup without reallocating (macOS 12 / iOS 15). That makes them the parameter-change path on the audio thread. — /documentation/Accelerate/creating-an-audio-unit-extension-using-the-vdsp-library [symbols: vDSP_biquad_CreateSetup, vDSP_biquad_SetCoefficientsDouble, vDSP_biquad_SetCoefficientsSingle, vDSP_biquad, vDSP_biquad_Setup] [gate: SetCoefficients macOS 12 / iOS 15]
- Parameter handoff: the host-facing `getParameter` returns the target value, never the ramping value the render thread is using. The sample's comment says reading the ramping value is not thread safe. Parameters are declared with `AUParameterAddress` cases plus a spec (range, default, units). The Audio Unit Extension App template supplies the pass-through effect skeleton. AU extensions run on both iOS and macOS (sample metadata: macOS 14, Xcode 15.1). — /documentation/Accelerate/creating-an-audio-unit-extension-using-the-vdsp-library [symbols: AUParameterAddress, AUValue, AUEventSampleTime, AUAudioFrameCount]
- Bypass in the sample is a plain per-channel copy of input to output. Buffers arrive as one deinterleaved `float*` per channel (`std::span<float const*>`). This matches the non-interleaved float layout that AVAudioEngine uses by default. — /documentation/Accelerate/creating-an-audio-unit-extension-using-the-vdsp-library

### vDSP on audio buffers

- Stride costs speed: any stride other than 1 generally stops vDSP from vectorizing, which costs both speed and energy. The one stated exception is interleaved-complex conversion (`vDSP_ctoz` / `vDSP_ztoc`, stride 2). Processing one channel of interleaved stereo with stride 2 works but is slow. Deinterleave first, or keep audio non-interleaved end to end. A strided call reads `(n - 1) * stride + 1` elements, so size buffers to that. A negative stride walks backward from a pointer to the last element. — /documentation/Accelerate/controlling-vdsp-operations-with-stride [symbols: vDSP_Stride, vDSP_vadd, vDSP_ctoz, vDSP_ztoc, vDSP_conv]
- For meters and VU displays, `vDSP.amplitudeToDecibels(_:zeroReference:)` and `vDSP.powerToDecibels(_:zeroReference:)` convert values (C: `vDSP_vdbcon`, where a flag picks power or amplitude). Use the `convert(amplitude:toDecibels:zeroReference:)` form with an `inout` result to avoid allocating per block. — /documentation/Accelerate/conversion-to-decibel-equivalents [symbols: vDSP.amplitudeToDecibels(_:zeroReference:), vDSP.powerToDecibels(_:zeroReference:), vDSP.convert(amplitude:toDecibels:zeroReference:), vDSP_vdbcon]

### Spectrum and EQ (audio-reactive visuals, filters)

- Prefer DFT to FFT. Apple's tip: the vDSP DFT routines accept more lengths than power-of-two FFTs and switch to an FFT internally where possible. Swift wrappers: `vDSP.DFT` / `vDSP.DiscreteFourierTransform`, `vDSP.FFT`, `vDSP.FFT2D`. — /documentation/Accelerate/fast-fourier-transforms [symbols: vDSP.DFT, vDSP.DiscreteFourierTransform, vDSP.FFT, vDSP.FFT2D, vDSP_DFT_zrop_CreateSetup]
- FFT setup objects (`vDSP.FFT(log2n:radix:ofType:)`) precompute twiddle weights and are expensive to build. Create one once, at startup, and reuse it, never per audio block. A setup built for a large size works for smaller FFTs but runs them slower, so keep one per size you use. For a real signal of n samples, pack it as n/2 split-complex values with `vDSP.convert(interleavedComplexVector:toSplitComplexVector:)`. — /documentation/Accelerate/finding-the-component-frequencies-in-a-composite-sine-wave [symbols: vDSP.FFT, DSPSplitComplex, vDSP.convert(interleavedComplexVector:toSplitComplexVector:)]
- Gotchas in the same article. `vDSP_zaspec` accumulates into its output, so clear the buffer first (`vDSP.clear`). The forward transform scales by 2 and the inverse by n, so divide a round trip by 2n. The Nyquist bin is index n/2. — /documentation/Accelerate/finding-the-component-frequencies-in-a-composite-sine-wave [symbols: vDSP_zaspec, vDSP.clear, vDSP.FFT.forward(input:output:), vDSP.FFT.inverse(input:output:)]
- DCT equalization: forward `vDSP.DCT(count:transformType: .II)`, multiply by an envelope built with `vDSP.linearInterpolate(values:atIndices:result:)`, inverse `.III`, then divide by `count / 2` to restore level. Build both setups once. Apple names biquads as the alternative EQ route. My judgment: the sample transforms independent 1024-sample pages without windowing or overlap, so it suits offline or visualization use. For a live game-audio EQ, use the biquad route above. — /documentation/Accelerate/equalizing-audio-with-discrete-cosine-transforms-dcts [symbols: vDSP.DCT, vDSP.DCTTransformType, vDSP.linearInterpolate(values:atIndices:result:), vDSP.multiply, vDSP.divide]
- To decode a whole audio file into a `[Float]` sample array (for analysis or a procedural-audio table), the sample uses `AVAssetReader` with `AVAssetReaderTrackOutput`. Playback goes through an AVAudioEngine signal generator (see AVFAudio "Building a Signal Generator"). — /documentation/Accelerate/equalizing-audio-with-discrete-cosine-transforms-dcts [symbols: AVAssetReader, AVAssetReaderTrackOutput, AVAudioEngine]

## assets.md

### Compression framework: picking an algorithm

- The Compression docs now recommend `COMPRESSION_LZMESH` for data only Apple platforms read. The buffer-compression article says it matches the ratio of zlib level 5 and encodes and decodes 2–3x faster with better energy use. Use `COMPRESSION_ZLIB` only when a non-Apple reader must decode the bytes. — /documentation/Accelerate/compressing-and-decompressing-data-with-buffer-compression [symbols: COMPRESSION_LZMESH, COMPRESSION_ZLIB, compression_encode_buffer, compression_decode_buffer] [gate: macOS 27 / iOS 27]
- SDK check (`usr/include/compression.h`, MacOSX SDK in this Xcode): `COMPRESSION_LZMESH = 0xE05` and `COMPRESSION_LZRAVEN = 0xD05` are both commented as buffer API only, macOS 27.0 / iOS 27.0. The header's order of choice is LZ4 when speed comes first, LZMA when ratio comes first (an order of magnitude slower), and zlib otherwise. Without interop needs, use LZMESH in place of zlib and LZRAVEN in place of LZMA. `COMPRESSION_BROTLI` (macOS 12 / iOS 15) is there mainly to decode web content. `COMPRESSION_LZBITMAP` is also buffer-only. A writer must not tell readers to stream LZMESH. — /documentation/Accelerate/compressing-and-decompressing-data-with-buffer-compression [symbols: COMPRESSION_LZRAVEN, COMPRESSION_LZMESH, COMPRESSION_LZ4, COMPRESSION_LZ4_RAW, COMPRESSION_LZMA, COMPRESSION_LZFSE, COMPRESSION_BROTLI, COMPRESSION_LZBITMAP] [gate: LZMESH / LZRAVEN macOS 27 / iOS 27, buffer API only]
- Contradiction to note: the stream-compression sample and the filters article still recommend `Algorithm.lzfse`. They make the same zlib-5 and 2–3x claim that the buffer article now makes for LZMESH. The pages agree once you know LZMESH is buffer-only. For streamed data (`compression_stream`, `InputFilter` / `OutputFilter`, AppleArchive streams), LZFSE remains the Apple-only choice. For a whole in-memory buffer on OS 27 and later, use LZMESH. — /documentation/Accelerate/compressing-and-decompressing-files-with-stream-compression [symbols: Algorithm.lzfse, Algorithm.zlib, compression_stream_init, compression_stream_process, compression_stream_destroy, COMPRESSION_STREAM_FINALIZE, COMPRESSION_STATUS_OK, COMPRESSION_STATUS_END, COMPRESSION_STATUS_ERROR]
- Buffer API gotchas. `compression_encode_buffer` returns 0 on failure, and small inputs can fail. Be ready to store those uncompressed. `compression_decode_buffer` returns 0 when the destination is too small, and the format does not record the decoded size. Write the uncompressed byte count into your own asset or save header and size from it, or fall back to the stream API, which can grow its output and resume without repeating work. — /documentation/Accelerate/compressing-and-decompressing-data-with-buffer-compression [symbols: compression_encode_buffer, compression_decode_buffer]
- Pick the API by the data's shape. A whole blob in memory: `NSData.compressed(using:)` / `decompressed(using:)`, one call. Data streamed to or from a file or socket: `InputFilter` / `OutputFilter` in Swift, or `compression_stream` in C (also usable from Objective-C and older OSes). Either filter class can compress or decompress. The page size per step trades progress-report frequency against step count. — /documentation/Accelerate/compressing-and-decompressing-data-with-input-and-output-filters [symbols: InputFilter, OutputFilter, FilterOperation.compress, FilterOperation.decompress, InputFilter.readData(ofLength:), OutputFilter.write(_:), NSData.compressed(using:), NSData.decompressed(using:)]
- The streaming sample runs off the main thread and posts progress to the main queue. It sets `COMPRESSION_STREAM_FINALIZE` on the short final read and loops while status is `COMPRESSION_STATUS_OK`. Bytes produced per step = `bufferSize - stream.dst_size`; reset `dst_ptr` / `dst_size` after each write. Use this pattern to unpack a large level pack at load time without holding both copies in RAM. — /documentation/Accelerate/compressing-and-decompressing-files-with-stream-compression [symbols: compression_stream, compression_stream_process]

### AppleArchive for packed assets and saves

- Writing: chain `ArchiveByteStream.fileStream(path:mode:options:permissions:)` → `ArchiveByteStream.compressionStream(using:writingTo:)` → `ArchiveStream.encodeStream(writingTo:)`. Each entry header carries three-letter fields: `PAT` (path), `TYP` (`ArchiveHeader.EntryType.regularFile` etc.), and `DAT` (a blob whose size is the uncompressed byte count). Write the header, then the payload with `writeBlob(key:from:)`. The `defer` blocks close the streams innermost first. Output is a `.aar`. The algorithm enum here is AppleArchive's `ArchiveCompression` (`.lzfse`), not `Compression.Algorithm`. — /documentation/Accelerate/compressing-and-saving-a-string-to-the-file-system [symbols: ArchiveByteStream, ArchiveStream, ArchiveHeader, ArchiveHeader.FieldKey, ArchiveCompression.lzfse, ArchiveStreamProtocol.writeBlob(key:from:)]
- Reading one entry: `ArchiveByteStream.decompressionStream(readingFrom:)` takes no algorithm argument, then comes `ArchiveStream.decodeStream(readingFrom:)`. Then `readHeader()`, `header.field(forKey: ArchiveHeader.FieldKey("DAT"))`, and a match on `.blob(_, size, _)` give the exact size to preallocate before `readBlob(key:into:)`. Do not copy the sample's final step: it builds the result with `String(cString:)` over a buffer of exactly `byteCount` bytes with no NUL terminator, which reads past the end. Decode with a length instead. — /documentation/Accelerate/decompressing-and-parsing-an-archived-string [symbols: ArchiveByteStream.decompressionStream(readingFrom:), ArchiveStream.decodeStream(readingFrom:), ArchiveStreamProtocol.readBlob(key:into:), ArchiveHeader.field(forKey:)]
- Packing a whole asset directory: `ArchiveStream.writeDirectoryContents(archiveFrom:path:keySet:selectUsing:flags:threadCount:)` with `ArchiveHeader.FieldKeySet("TYP,PAT,LNK,DEV,DAT,UID,GID,MOD,FLG,MTM,BTM,CTM")`. The signature has a `threadCount` parameter and an entry-selection parameter. Unpacking: decode stream → `ArchiveStream.extractStream(extractingTo:flags:)` (the sample passes `.ignoreOperationNotPermitted`) → `ArchiveStream.process(readingFrom:writingTo:)`. This fits packing level or DLC folders at build time and unpacking them into the container at runtime. — /documentation/Accelerate/compressing-file-system-directories [symbols: ArchiveStream.writeDirectoryContents(archiveFrom:path:keySet:selectUsing:flags:threadCount:), ArchiveHeader.FieldKeySet, ArchiveStream.extractStream(extractingTo:flags:), ArchiveStream.process(readingFrom:writingTo:)]
- To compress a single file without an archive container, pipe a read `fileStream` into a `compressionStream` with `ArchiveByteStream.process(readingFrom:writingTo:)`. The output is a raw `.lzfse` file, not `.aar`. Reverse it with `decompressionStream` → write `fileStream`. — /documentation/Accelerate/compressing-single-files [symbols: ArchiveByteStream.process(readingFrom:writingTo:), ArchiveByteStream.fileStream(path:mode:options:permissions:), ArchiveByteStream.decompressionStream(readingFrom:)]
- macOS sandbox: the samples write to Downloads, which needs the matching file-access entitlement in Signing & Capabilities. Saves and unpacked assets belong in the app container, which needs none. — /documentation/Accelerate/compressing-and-saving-a-string-to-the-file-system [gate: App Sandbox, macOS]

### CPU-side image preparation (vImage) before texture upload

- Normalizing arbitrary source images: `vImage.PixelBuffer(cgImage:cgImageFormat:pixelFormat:)` converts to whatever `vImage_CGImageFormat` you pass, including color model and bit depth. An empty `vImage_CGImageFormat()` adopts the image's own format, and the initializer returns nil if the image and pixel-buffer bit depths differ. `vImage_CGImageFormat(cgImage:)` reports an image's actual layout; the sample image reads back as Display P3 with `noneSkipLast`. Inspect before assuming a channel order for an `MTLPixelFormat`. — /documentation/Accelerate/converting-bitmap-data-between-core-graphics-images-and-vimage-buffers [symbols: vImage.PixelBuffer, vImage_CGImageFormat, vImage_CGImageFormat.init(cgImage:), vImage.Interleaved8x4, vImage.PixelBuffer.makeCGImage(cgImageFormat:)]
- Gotcha: converting RGB to a gray `vImage_CGImageFormat` uses Rec. 601 luma weights implicitly (0.299 / 0.587 / 0.114). For Rec. 709 weights (0.2126 / 0.7152 / 0.0722), use the matrix-multiply path instead. This matters when baking masks or heightmaps from color art. — /documentation/Accelerate/converting-bitmap-data-between-core-graphics-images-and-vimage-buffers [symbols: vImageMatrixMultiply_ARGB8888ToPlanar8, vImage.PixelBuffer.multiply(by:divisor:preBias:postBias:destination:)]
- The C-level equivalent is `vImageBuffer_InitWithCGImage`. With an empty format it adopts the image's layout; with a filled-in format it converts. `vImageCreateCGImageFromBuffer` goes the other way. — /documentation/Accelerate/core-graphics-interoperability [symbols: vImageBuffer_InitWithCGImage, vImageCreateCGImageFromBuffer, vImageCGImageFormat_IsEqual]
- Arbitrary conversions: `vImageConverter.make(sourceFormat:destinationFormat:)` handles any bit depth, channel count, or color space, for example 16-bit CMYK to 8-bit RGB. Run it with `convert(from:to:)` on `vImage.PixelBuffer`, or `convert(source:destination:)` on `vImage_Buffer` on older OSes; both wrap `vImageConvert_AnyToAny`. Call `vImageConverter_MustOperateOutOfPlace` before converting in place. — /documentation/Accelerate/building-a-basic-image-conversion-workflow [symbols: vImageConverter, vImageConvert_AnyToAny, vImageConverter_MustOperateOutOfPlace, vImage.Interleaved16Ux4, vImage.Interleaved8x3]
- Metal has no 24-bit RGB8 pixel format (my knowledge, not on the page), so 3-channel source art must gain a fourth channel before upload. `vImageConvert_RGB888toRGBA8888` / `vImageConvert_RGB888toBGRA8888` take either a planar alpha buffer or a constant alpha, plus a premultiply flag. — /documentation/Accelerate/functions-that-add-an-alpha-channel-to-three-channel-buffers [symbols: vImageConvert_RGB888toRGBA8888, vImageConvert_RGB888toBGRA8888, vImageConvert_RGBFFFtoRGBAFFFF]
- Float heightmaps or masks bound for an `r16Float` texture can be narrowed on the CPU with `vImageConvert_PlanarFtoPlanar16F`. — /documentation/Accelerate/functions-that-convert-between-noninteger-planar-buffers [symbols: vImageConvert_PlanarFtoPlanar16F, vImageConvert_Planar16FtoPlanarF]
- Row padding: `vImage_Buffer(width:height:bitsPerPixel:)` and `vImage.PixelBuffer(width:height:pixelFormat:)` pad rows for speed; a 10-pixel 8-bit row gets 16 bytes. Pass `rowBytes` as the `bytesPerRow` of any GPU upload or vDSP call. If you need tight rows, allocate your own storage and wrap it with an explicit `byteCountPerRow`. Padding bytes are uninitialized and corrupt whole-buffer statistics. — /documentation/Accelerate/finding-the-sharpest-image-in-a-sequence-of-captured-images [symbols: vImage_Buffer.rowBytes, vImage.PixelBuffer.init(data:width:height:byteCountPerRow:pixelFormat:), vImageBuffer_Init]
- CPU resize: `vImageScale_ARGB8888` works on any 4×8-bit channel order (RGBA and BGRA too). `kvImageHighQualityResampling` selects Lanczos 5×5; `kvImageNoFlags` is faster. Premultiplied sources produce artifacts in high-frequency regions. Unpremultiply (`vImageUnpremultiplyData_ARGB8888`), scale, then re-premultiply (`vImagePremultiplyData_ARGB8888`). The same rule applies to offline mip generation. — /documentation/Accelerate/building-a-basic-image-processing-workflow [symbols: vImageScale_ARGB8888, kvImageHighQualityResampling, kvImageNoFlags, vImageUnpremultiplyData_ARGB8888, vImagePremultiplyData_ARGB8888]
- Sprite trimming: find the tight opaque bounds of a sprite with `vDSP.sum` per row for top and bottom. For left and right, run `vDSP_sve` down each column with stride = `rowStride`. Then call `vImage.PixelBuffer.cropped(to:)`. The sample also turns a chroma-key color into alpha with a `vImage.MultidimensionalLookupTable` (32 entries per channel, distance in L\*a\*b\*). A sprite or atlas build step can use the same approach. — /documentation/Accelerate/cropping-to-the-subject-in-a-chroma-keyed-image [symbols: vDSP.sum(_:), vDSP_sve, vImage.PixelBuffer.rowStride, vImage.PixelBuffer.cropped(to:), vImage.MultidimensionalLookupTable, vImage.PixelBuffer.overwriteChannels(_:withPlanarBuffer:destination:)]

## apple-metal/compute-and-gpu-driven.md

- The CPU ML option that exists: BNNSGraph runs a whole network from the `.mlmodelc` that Xcode compiles from an ML package. Build it from the file with `BNNSGraphCompileFromFile`, or in Swift with `BNNSGraph.makeContext(options:_:)` and `BNNSGraph.Builder`. Whole-graph optimization fuses kernels, drops copies, and repacks constant weights for the target hardware. `BNNSGraphCompileOptionsSetTargetSingleThread` pins execution to one thread. Caller-supplied workspace and output allocators (`BNNSGraphContextSetWorkspaceAllocationCallback`, sized by `BNNSGraphContextGetWorkspaceSize`) keep execution free of allocation. The topic list links an article on real-time ML inference on the CPU. The old layer-by-layer API sits under the Deprecated heading "Classic BNNS API". Use this when a small model must run on the audio thread or beside game logic instead of as a Metal / MPSGraph pass. — /documentation/Accelerate/bnns-library [symbols: BNNSGraphCompileFromFile, BNNSGraph.makeContext(options:_:), BNNSGraph.Builder, BNNSGraph.Context, BNNSGraphCompileOptionsSetTargetSingleThread, BNNSGraphContextSetWorkspaceAllocationCallback, BNNSGraphContextGetWorkspaceSize, BNNSGraphContextExecute]
