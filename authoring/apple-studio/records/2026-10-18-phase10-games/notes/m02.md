## command-model.md

- A fence only orders against work that was already submitted ahead of it on the same queue; an event can also gate work that arrives later, is placed at command-buffer boundaries (not between encoded commands inside an encoder), and is enforced by the command-buffer scheduler, so a buffer blocked on an event on one queue does not stall a second queue — /documentation/Metal/implementing-a-multistage-image-filter-using-heaps-and-events [symbols: MTLFence, MTLEvent, MTLSharedEvent] [gate: Metal 3 spelling; sample iOS 17 / macOS 14]
- Pattern: keep the event and its monotonically increasing counter in one wrapper object so a signal value is never paired with the wrong event; wait at graph start on the previous frame's value, signal after each producer, wait before each consumer, signal once more after the present — /documentation/Metal/implementing-a-multistage-image-filter-using-heaps-and-events [symbols: encodeWaitForEvent:value:, encodeSignalEvent:value:]
- A plain MTLEvent must belong to the same device as the command buffer that waits or signals on it; only MTLSharedEvent crosses devices (the sample asserts this) — /documentation/Metal/implementing-a-multistage-image-filter-using-heaps-and-events [symbols: MTLEvent, MTLSharedEvent, MTLCommandBuffer.device]
- Fence spelling for producer/consumer encoders on one queue: producer calls updateFence: before endEncoding, consumer calls waitForFence: right after its encoder is created; without it the GPU may overlap the two passes and read uninitialized heap memory — /documentation/Metal/implementing-a-multistage-image-filter-using-heaps-and-fences [symbols: updateFence:, waitForFence:] [gate: Metal 3 encoder API]
- Argument buffers can hold MTLBuffer, MTLTexture, MTLSamplerState, MTLAccelerationStructure, MTLIndirectCommandBuffer, MTLComputePipelineState, MTLRenderPipelineState and inline constants, but no unions; they are mandatory for pipelines built from Metal shader converter output — /documentation/Metal/improving-cpu-performance-by-using-argument-buffers [symbols: MTLArgumentEncoder]
- Tier 2 on iOS/tvOS 16+ and macOS 13+: an argument buffer has plain C-struct layout, so write MTLBuffer.gpuAddress (plus a uint64 offset) and gpuResourceID for textures, samplers, acceleration structures and pipelines directly into the struct. Tier 1, or Tier 2 on older OSes, has an opaque per-GPU layout and needs MTLArgumentEncoder — /documentation/Metal/improving-cpu-performance-by-using-argument-buffers [symbols: MTLBuffer.gpuAddress, gpuResourceID, MTLArgumentEncoder, MTLDevice.argumentBuffersSupport] [gate: Tier 2 + iOS 16 / macOS 13]
- Residency with argument buffers is explicit: one useHeap covers all read-only resources from a heap, but every writable resource still needs its own useResource even if the pass only reads it — /documentation/Metal/improving-cpu-performance-by-using-argument-buffers [symbols: useHeap:, useResource:usage:] [gate: Metal 3 encoder residency; Metal 4 uses residency sets]
- Limits: unique samplers with supportArgumentBuffers = true are capped at 96 per app on iOS/tvOS and 1024+ on macOS (query maxArgumentBufferSamplerCount); uniqueness is by descriptor configuration. Tier 1 counts argument-buffer entries against the per-function argument-table limit, forbids writable textures, requires immutable CPU-visible (shared/managed) buffers, and allows no pointer indexing or nested argument buffers — /documentation/Metal/improving-cpu-performance-by-using-argument-buffers [symbols: MTLDevice.maxArgumentBufferSamplerCount, MTLSamplerDescriptor.supportArgumentBuffers] [gate: Tier 1 vs Tier 2; per-table limits in Feature Set Tables]
- Tier 2 argument buffers may be mutated by CPU or GPU; declare MTLPipelineBufferDescriptor.mutability = .immutable when neither side changes it between bind and completion so Metal can optimize — /documentation/Metal/improving-cpu-performance-by-using-argument-buffers [symbols: MTLPipelineBufferDescriptor.mutability, MTLMutability.immutable]
- Argument buffers move per-draw binding cost from the render loop to setup: bind one buffer instead of many setFragmentTexture/setVertexBuffer calls — /documentation/Metal/managing-groups-of-resources-with-argument-buffers [symbols: setFragmentBuffer:offset:atIndex:]
- Metal 2 path: argument encoder from the function (newArgumentEncoderWithBufferIndex:), size from encodedLength, setArgumentBuffer:offset:, then setTexture:atIndex:/setSamplerState:atIndex:/setBuffer:offset:atIndex: matched to [[id(n)]], and constantDataAtIndex: to write inline constants. Metal 3 path: share the struct in a header, size with sizeof, write texture/sampler gpuResourceID and buffer gpuAddress straight into contents — /documentation/Metal/managing-groups-of-resources-with-argument-buffers [symbols: MTLArgumentEncoder, newArgumentEncoderWithBufferIndex:, encodedLength, setArgumentBuffer:offset:, constantDataAtIndex:, gpuResourceID, gpuAddress] [gate: Metal 2 vs Metal 3]
- Doc errors to avoid copying: this sample's prose names `MTLArgumentBufferEncoder` (the type is MTLArgumentEncoder) and a buffer `gpuHandle` property (the code uses gpuAddress) — /documentation/Metal/managing-groups-of-resources-with-argument-buffers [symbols: MTLArgumentEncoder, MTLBuffer.gpuAddress]
- Metal never inspects an argument buffer to discover residency: call useResource:usage:stages: once per encoder per resource (cheap compared to individual binds), even across many draws; samplers and inline constants are not MTLResources and need no call — /documentation/Metal/managing-groups-of-resources-with-argument-buffers [symbols: useResource:usage:stages:, MTLResourceUsageRead, MTLRenderStageFragment] [gate: Metal 3 encoders; Metal 4 replaces with residency sets]
- Error structs worth handling: MTLCommandBufferError (why the GPU did not finish a command buffer), MTLBinaryArchiveError, MTLDynamicLibraryError, MTLCounterSampleBufferError, MTLIOError (IO file-handle creation), MTLTensorError; also MTLStitchedLibraryOptions, MTLComponentTransform, MTLPackedFloatQuaternion — /documentation/Metal/metal-structures [symbols: MTLCommandBufferError, MTLBinaryArchiveError, MTLDynamicLibraryError, MTLCounterSampleBufferError, MTLIOError, MTLTensorError]
- Multi-GPU Macs (Intel-era, eGPU): enumerate with MTLCopyAllDevices, or MTLCopyAllDevicesWithObserver to get MTLDeviceNotificationName add/remove callbacks (remove with MTLRemoveDeviceObserver); find a display's GPU with CGDirectDisplayCopyCurrentMetalDevice; an eGPU can vanish at any time. Choose by memory bandwidth and storage modes. Mostly irrelevant on Apple silicon (one GPU) — /documentation/Metal/multi-gpu-systems [symbols: MTLCopyAllDevices, MTLCopyAllDevicesWithObserver, MTLRemoveDeviceObserver, MTLDeviceNotificationHandler, MTLDeviceNotificationName, CGDirectDisplayCopyCurrentMetalDevice] [gate: macOS]
- Basics that still matter: every object made from an MTLDevice works only with that device; pipeline-state creation finishes the GPU-specific compile and is slow, so never create PSOs synchronously in hot code; size 1D dispatches with maxTotalThreadsPerThreadgroup (it varies with kernel complexity) clamped to the data size and dispatchThreads:threadsPerThreadgroup:; prefer addCompletedHandler: or status over waitUntilCompleted in a game. This sample is Metal 3 (MTLCommandBuffer from a queue) — /documentation/Metal/performing-calculations-on-a-gpu [symbols: MTLCreateSystemDefaultDevice, newComputePipelineStateWithFunction:error:, MTLComputePipelineState.maxTotalThreadsPerThreadgroup, dispatchThreads:threadsPerThreadgroup:, addCompletedHandler:, MTLCommandBuffer.status] [gate: Metal 3 spelling]

## pipelines-and-render-passes.md

- MSAA sample counts: every Apple GPU supports at least 4; 2 and 8 vary, so probe each with supportsTextureSampleCount: and default to 4. The pipeline's sampleCount (rasterSampleCount) must match the attachment's — /documentation/Metal/improving-edge-rendering-quality-with-multisample-antialiasing-msaa [symbols: MTLDevice.supportsTextureSampleCount:, MTLTextureType2DMultisample, MTLTextureDescriptor.sampleCount, MTLRenderPipelineDescriptor.sampleCount]
- Three resolve paths: built-in (store action MTLStoreActionMultisampleResolve plus resolveTexture; a plain average), custom compute resolve for IMR/Intel/AMD/Simulator (MSAA texture must be private + ShaderRead and stays in memory, extra pass reading texture2d_ms via get_num_samples/read(gid, i)), and a tile-shader resolve on Apple4+ that runs before the tile is stored — /documentation/Metal/improving-edge-rendering-quality-with-multisample-antialiasing-msaa [symbols: MTLStoreActionMultisampleResolve, MTLRenderPassColorAttachmentDescriptor.resolveTexture, texture2d_ms, get_num_samples] [gate: tile resolve needs MTLGPUFamilyApple4: Apple-silicon Mac macOS 11+, A11 iOS 13+, A12 tvOS 14.5+]
- Custom resolve is needed when the operation does not commute with averaging, e.g. tone-map each HDR sample then average (avoids bright-edge aliasing that average-then-tonemap leaves) — /documentation/Metal/improving-edge-rendering-quality-with-multisample-antialiasing-msaa
- Vertex amplification fetches each vertex once and runs the vertex function N times (one per target), cheaper than N draws; typical uses are cascaded shadow maps (N = cascade count), layered render targets, and multi-viewport. Probe supportsVertexAmplificationCount: with values >= 2 (passing 1 or less is an API-validation error), set MTLRenderPipelineDescriptor.maxVertexAmplificationCount to the largest supported, then per encoder setVertexAmplificationCount:viewMappings: with any value in [1, max] — /documentation/Metal/improving-rendering-performance-with-vertex-amplification [symbols: MTLDevice.supportsVertexAmplificationCount:, MTLRenderPipelineDescriptor.maxVertexAmplificationCount, setVertexAmplificationCount:viewMappings:, MTLVertexAmplificationViewMapping]
- MTLVertexAmplificationViewMapping.renderTargetArrayIndexOffset and viewportArrayIndexOffset are added by the GPU to the vertex output tagged [[render_target_array_index]] / [[viewport_array_index]] for each amplification ID, so one shader routes to slices or viewports without branching — /documentation/Metal/improving-rendering-performance-with-vertex-amplification [symbols: renderTargetArrayIndexOffset, viewportArrayIndexOffset]
- Amplification composes with instancing multiplicatively (10 instances x 2 = 20 vertex invocations per vertex), but shared outputs are still computed once per vertex across amplification IDs; instancing alone recomputes every output — /documentation/Metal/improving-rendering-performance-with-vertex-amplification
- Binary archives trade bundle size for zero runtime compile: Metal IR is small and portable but still compiled per GPU at runtime; a binary archive is per-GPU machine code. The Metal translator (`xcrun metal-tt <lib>.metallib <pipelines>.mtlp-json -o <out>.binary.metallib`) builds them from IR plus a JSON pipeline-state description; read the binary-archive articles in order, beginning with the one on device-built PSOs (/documentation/Metal/creating-binary-archives-from-device-built-pipeline-state-objects) — /documentation/Metal/metal-binary-archives [symbols: metal-tt, .mtlp-json]
- By default metal-tt targets every GPU architecture: the sample's 8 KB metallib grew to 696 KB with Apple (applegpu_g13*/g14*/g15*), AMD (amdgpu_gfx8xx-10xx) and Intel (intelgpu_kbl/icl) slices. `metal-lipo -archs` lists slices, `-thin <arch> -output` extracts one (the source is left intact), `-create` rejoins slices; splitting per vendor gave Apple 124K, AMD 180K, Intel 396K. metal-lipo only merges slices of the same pipelines; use `metal-pack` (man metal-pack) to merge different pipelines. Ship slim per-device archives over the air or bundle several for multi-GPU Macs — /documentation/Metal/manipulating-metal-binary-archives [symbols: metal-lipo -archs, metal-lipo -thin, metal-lipo -create, metal-pack]
- Doc inconsistency: the archive page builds shaders.binary.metallib but then inspects render.binary.metallib; writers should use one name — /documentation/Metal/manipulating-metal-binary-archives
- Dynamic libraries avoid each pipeline recompiling and duplicating shared utility code (the default model embeds, like static linking): create with makeDynamicLibrary(library:) from a bundled library, then list it in the pipeline descriptor's preloadedLibraries; it compiles once for the device on first use — /documentation/Metal/metal-dynamic-libraries [symbols: MTLDevice.makeDynamicLibrary(library:), MTLComputePipelineDescriptor.preloadedLibraries, MTLDynamicLibrary]
- Compile model: build-phase .metal files become Metal IR in default.metallib (load with makeDefaultLibrary()); IR is compiled to GPU code at runtime before first use; source strings go source -> IR -> GPU on device (two compiles). Use dynamic libraries for shared utilities and binary archives to skip runtime compilation — /documentation/Metal/metal-libraries [symbols: MTLDevice.makeDefaultLibrary(), default.metallib]
- Size-optimized shader compiles: the default optimizes for speed (inlining, unrolling), which can bloat binaries and compile time; -Os avoids code duplication and usually compiles faster. Set it as Xcode "Metal Compiler - Build Options > Optimization Level = Size [-Os]" (Xcode 14+), `xcrun -sdk macosx metal -Os file.metal`, or MTLCompileOptions.optimizationLevel = MTLLibraryOptimizationLevel.size before makeLibrary(source:options:). Measure: which wins depends on the shader. Runtime compile shrinks the bundle but lengthens first launches — /documentation/Metal/minimizing-the-binary-size-of-a-shader-library [symbols: MTLCompileOptions.optimizationLevel, MTLLibraryOptimizationLevel.size, makeLibrary(source:options:), makeLibrary(source:options:completionHandler:)]
- Programmable sample positions: check MTLDevice.areProgrammableSamplePositionsSupported (else positions are fixed and unqueryable); positions lie on a 16x16 subpixel grid, values k/16 for k = 0..15 in [0,1) with origin top-left; defaults are identical on all supporting GPUs (getDefaultSamplePositions:count:, 1-sample default 0.5,0.5); set per pass with MTLRenderPassDescriptor setSamplePositions:count: — useful for temporal jitter patterns — /documentation/Metal/positioning-samples-programmatically [symbols: areProgrammableSamplePositionsSupported, getDefaultSamplePositions:count:, setSamplePositions:count:, MTLSamplePosition]

- Deferred vs forward: deferred makes many lights cheap without light binning; the sample's frame order is shadow map, G-buffer, directional light, light-volume stencil mask, point lights, skybox, fairy (billboard) lights. ## apple-gpu-tbdr.md

- OIT via imageblocks: a per-pixel fixed-depth array (kNumLayers = 4 in the sample) of packed color + half depth lives in tile memory; an init tile kernel fills sentinels (0 color, INFINITY depth) with dispatchThreadsPerTile:, transparent draws insertion-sort into the array with color writes masked off, and a full-screen pass resolves back-to-front over the opaque color read from the attachment. Overflowing layers drop the farthest fragment, which still looks acceptable — /documentation/Metal/implementing-order-independent-transparency-with-image-blocks [symbols: [[imageblock_data]], imageblock<T, imageblock_layout_explicit>, threadgroup_imageblock, rgba8unorm<half4>, dispatchThreadsPerTile:, MTLColorWriteMaskNone] [gate: MTLGPUFamilyApple4 (A11+); physical device only, Simulator lacks tile shaders/imageblocks]
- Every imageblock member a fragment shader writes must carry [[raster_order_group(N)]], and the resolve shader reads the color attachment with the same group, so overlapping fragments at one pixel are serialized — /documentation/Metal/implementing-order-independent-transparency-with-image-blocks [symbols: raster_order_group, [[color(n)]]] [gate: Apple4]
- Tile-memory budgeting: copy the pipeline's imageblockSampleLength into the render pass descriptor's imageblockSampleLength, and pick tileWidth/tileHeight; larger tiles cost less overhead, but tile size times (attachments + imageblock bytes) must fit tile memory or render-pass creation fails. Use packed types (rgba8unorm<half4>, half) to shrink the imageblock — /documentation/Metal/implementing-order-independent-transparency-with-image-blocks [symbols: MTLRenderPassDescriptor.imageblockSampleLength, MTLRenderPassDescriptor.tileWidth, MTLRenderPassDescriptor.tileHeight, MTLRenderPipelineState.imageblockSampleLength]
- Without Apple4 the sample still runs but blends wrong; a shipping game needs a sorted or weighted-blended fallback path, not a silent wrong image — /documentation/Metal/implementing-order-independent-transparency-with-image-blocks [symbols: supportsFamily:, MTLGPUFamilyApple4]
- Tile-based MSAA resolve: the MSAA color target is MTLStorageModeMemoryless with usage RenderTarget only, so the multisample data never touches DRAM; set tileWidth/tileHeight and imageblockSampleLength (32 in the sample) on the pass, build a tile pipeline (MTLTileRenderPipelineDescriptor with tileFunction, rasterSampleCount, threadgroupSizeMatchesTileSize = YES, colorAttachments pixel format) via newRenderPipelineStateWithTileDescriptor:options:reflection:error:, and dispatchThreadsPerTile: before endEncoding — /documentation/Metal/improving-edge-rendering-quality-with-multisample-antialiasing-msaa [symbols: MTLStorageModeMemoryless, MTLTileRenderPipelineDescriptor, newRenderPipelineStateWithTileDescriptor:options:reflection:error:, dispatchThreadsPerTile:] [gate: MTLGPUFamilyApple4]
- Single-pass deferred on TBDR: G-buffer attachments are MTLStorageModeMemoryless (no system memory at all) and the lighting fragment functions read them as attached render targets inside the same encoder ("programmable blending"); the encoder is never ended between G-buffer fill and lighting. A two-pass path (G-buffer stored with MTLStoreActionStore to private textures, then sampled) is required on IMR Macs (Intel/AMD) and in the iOS/tvOS Simulator, which runs on the Mac's Metal implementation — /documentation/Metal/rendering-a-scene-with-deferred-lighting-in-c++ [symbols: MTL::StorageModeMemoryless, MTL::StorageModePrivate, MTLStoreActionStore, [[color(n)]]] [gate: Apple GPUs; two-pass fallback for IMR]
- Raster order groups for lighting: put the lighting accumulation target in group 0 and the G-buffer reads in group 1 ([[color(i), raster_order_group(g)]] members in one struct passed as the fragment input), so a fragment can start reading the G-buffer before an earlier overlapping light finished writing lighting. Needs MTLDevice.rasterOrderGroupsSupported (check at runtime) — /documentation/Metal/rendering-a-scene-with-deferred-lighting-in-c++ [symbols: raster_order_group, MTLDevice.rasterOrderGroupsSupported] [gate: ROG support]
- Drawable timing differs by path: single-pass must acquire the drawable before the G-buffer stage because lighting writes into it within the same pass; the two-pass path defers nextDrawable until after the G-buffer pass to hold the drawable for less time — /documentation/Metal/rendering-a-scene-with-deferred-lighting-in-c++
- The Objective-C deferred-lighting page is the same technique and text as the C++ one (single-pass memoryless G-buffer with ROGs on TBDR, two-pass on IMR and Simulator); its ObjC spellings: renderCommandEncoderWithDescriptor:, setDepthBias:slopeScale:clamp:, MTLCullModeFront/Back, drawIndexedPrimitives:indexCount:indexType:indexBuffer:indexBufferOffset:instanceCount: fed from MTKMesh/MTKSubmesh buffers — /documentation/Metal/rendering-a-scene-with-deferred-lighting-in-objective-c [symbols: renderCommandEncoderWithDescriptor:, setDepthBias:slopeScale:clamp:, MTKMeshBuffer, MTKSubmesh, MTLStorageModeMemoryless] [gate: Metal 3 encoder path]
- The Swift deferred sample chooses the path with supportsFamily(.apple1): any Apple GPU family means TBDR and programmable blending, so G-buffer textures are bound as fragment textures only when that check fails (IMR) — a simple, version-proof switch between single-pass and two-pass — /documentation/Metal/rendering-a-scene-with-deferred-lighting-in-swift [symbols: MTLDevice.supportsFamily(_:), MTLGPUFamily.apple1, MTLStorageMode.memoryless] [gate: Apple1+ = TBDR]
- Doc error: in the Swift page the snippet labelled SinglePassDeferredRenderer.swift shows `var storageMode = MTLStorageMode.private`, contradicting its own prose (single-pass uses .memoryless; .private is the traditional path) — /documentation/Metal/rendering-a-scene-with-deferred-lighting-in-swift

## resources-and-memory.md

- Allocating from an MTLHeap is much cheaper than from the device, notably mid-frame, because Metal does not track hazards or lifetime for resources inside a heap (only the heap itself); the app owns that synchronization — /documentation/Metal/implementing-a-multistage-image-filter-using-heaps-and-fences [symbols: MTLHeap, MTLHeapDescriptor, newHeapWithDescriptor:]
- Sizing a heap: sum heapTextureSizeAndAlignWithDescriptor: per texture, round each size up to its alignment; for a scratch heap take the max alignment across consumers and rebuild only when maxAvailableSizeWithAlignment: is too small — /documentation/Metal/implementing-a-multistage-image-filter-using-heaps-and-fences [symbols: heapTextureSizeAndAlignWithDescriptor:, MTLSizeAndAlign, maxAvailableSizeWithAlignment:]
- Split heaps by lifetime: one heap for static (loaded) textures, copied in by blit, and a scratch heap for per-frame transients; call makeAliasable on a transient once it is dead so the next allocation from the same heap reuses its memory — which creates a dependency you must then fence or event — /documentation/Metal/implementing-a-multistage-image-filter-using-heaps-and-fences [symbols: makeAliasable, newTextureWithDescriptor:]
- Stale claim: the heaps-and-fences sample page still says Metal is unsupported in the iOS/tvOS Simulator; do not repeat it — /documentation/Metal/implementing-a-multistage-image-filter-using-heaps-and-fences
- Mipmaps: each level is a quarter the area of the one above, down to 1 px per dimension; without them, minified sampling drags in large texture regions (a 256x256 into 8x8 blends ~25% of the texture per output pixel), costing bandwidth and cache and shimmering in motion — /documentation/Metal/improving-texture-sampling-quality-and-performance-with-mipmaps
- The Metal fast resource loading sample (MTLIO, disk straight into textures/buffers; WWDC22 10104) requires macOS 13 and an Apple-silicon Mac; the page carries no prose beyond requirements — /documentation/Metal/loading-textures-and-models-using-metal-fast-resource-loading [gate: macOS 13, Apple silicon, Metal 3]
- Sparse textures: allocate a sparse heap, create textures from it with no backing, then ask the GPU to map/unmap sparse tiles (allocation units like VM pages, unrelated to TBDR tiles) per region — the basis for texture streaming. Requires MTLGPUFamilyApple6 — /documentation/Metal/managing-sparse-texture-memory [symbols: supportsFamily:, MTLGPUFamilyApple6] [gate: Apple6 (A13+)]
- Metal synchronizes heap-allocated resources only when the heap's hazardTrackingMode is MTLHazardTrackingModeTracked; otherwise (the default for heaps) the app synchronizes. ## apple-performance/profiling-workflow.md

- Frame budgets: 30 fps ~33 ms, 40 fps 25 ms, 60 fps ~16 ms; CPU and GPU timelines overlap, so each gets the full budget independently. ProMotion lets a game pick 30/40/60. A long, occasional CPU task (asset or shader load, data dependency) delays encoding and doubles the prior frame's display time; split it across frames or move it off the render thread. Same for GPU: cache transients like shadow maps, cull on GPU, and suspect any task that does not run every frame — /documentation/Metal/improving-your-games-graphics-performance-and-settings
- Apple's investigation method: measure, analyze, improve, re-measure; use "five whys" (frame > 33 ms -> G-buffer 22 ms -> vertex 16 ms -> 5M verts ALU-bound -> no half precision). Keep a data-collection plan with timestamped, location-tagged captures named like YYYYMMDD-HHMM-Tool-Description; separate specific captures (Instruments, GPU debugger) from general ones (Metal HUD over a whole level, onscreen telemetry). For frame-rate work record a Metal System Trace of about 5-10 s; Metal HUD logging to console can be turned into CSV — /documentation/Metal/improving-your-games-graphics-performance-and-settings
