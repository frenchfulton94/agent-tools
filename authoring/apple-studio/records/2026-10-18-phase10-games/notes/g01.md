# Notes g01

## game-design.md

- Launch-to-play target: ship enough playable content in the initial install that first play needs no further wait, and keep the initial download to 30 minutes or less; fetch the rest in the background — /design/human-interface-guidelines/designing-for-games
- Pick defaults from the device rather than asking: native resolution, auto-detected paired controllers and accessories, and the player's system accessibility settings — /design/human-interface-guidelines/designing-for-games
- Ask for sensor or personal-data permission (e.g., hand tracking on visionOS) at the moment gameplay first needs it, framed by that scene, not in a pre-play permission wall; hold rating requests until the player has real play time — /design/human-interface-guidelines/designing-for-games
- Text-size table (default / minimum, pt): iOS+iPadOS 17/11, macOS 13/10, tvOS 29/23, visionOS 17/12, watchOS 16/12 — /design/human-interface-guidelines/designing-for-games
- Button-size table (default / minimum, pt): iOS+iPadOS 44x44/28x28, macOS 28x28/20x20, tvOS 66x66/56x56, visionOS 60x60/28x28, watchOS 44x44/28x28 — /design/human-interface-guidelines/designing-for-games
- In-game menus must survive 16:10, 19.5:9 and 4:3 and (if supported) both orientations on iPhone/iPad; use relative-constraint layouts and build a device-specific layout only as a last resort — /design/human-interface-guidelines/designing-for-games
- Default input per platform: iOS touch (+controller); iPadOS touch (+controller, keyboard, mouse, trackpad, Pencil); macOS keyboard+mouse/trackpad (+controller); tvOS remote (+controller, keyboard, mouse, trackpad); visionOS eyes+hands (+controller, keyboard, mouse, trackpad, spatial game controller); watchOS touch only. Mac-first means keyboard+mouse is the default path, controller is additive — /design/human-interface-guidelines/designing-for-games
- Every platform except watchOS supports physical controllers, but a controller must never be the only way to play — /design/human-interface-guidelines/designing-for-games
- Personalisation the HIG expects a game to expose: type size, control remapping, motion intensity, sound balance; Apple ships Unity plug-ins (github.com/Apple/UnityPlugins) for the accessibility APIs — /design/human-interface-guidelines/designing-for-games
- Accessibility targets a custom-rendered game UI must hit on its own (no system controls to inherit from): text enlargeable to at least 200% (140% on watchOS), either via Dynamic Type or an in-game size setting; thin custom fonts need sizes above the minimums — /design/human-interface-guidelines/accessibility
- Contrast floor Accessibility Inspector applies (WCAG AA): text up to 17 pt needs 4.5:1; 18 pt and up, or any bold text, needs 3:1. If the default art misses it, at least honour Increase Contrast with a higher-contrast scheme; check light and dark — /design/human-interface-guidelines/accessibility [symbols: Accessibility Inspector]
- Never signal state by colour alone (red-green and blue-orange pairs are the common failures); add shape or icon, and consider letting players recolour characters or markers — /design/human-interface-guidelines/accessibility
- Control spacing: about 12 pt padding around bezelled elements, about 24 pt around unbezelled ones' visible edges — /design/human-interface-guidelines/accessibility
- Hearing: caption cutscenes (captions, not just subtitles, for synced media); pair audio cues with haptics, and pair off-screen audio cues with a visual pointer to where the action is — /design/human-interface-guidelines/accessibility
- Cognitive/motor: offer difficulty accommodations (looser completion criteria, longer reaction windows, control assistance); avoid timed auto-dismissing UI; no autoplay without stop controls — /design/human-interface-guidelines/accessibility
- Reduce Motion response list: tighter springs, gesture-tracked animation, no animated z-depth changes, fades instead of x/y/z transitions, no blur-in/out; also honour Dim Flashing Lights for video (`/documentation/MediaAccessibility/flashing-lights`) — /design/human-interface-guidelines/accessibility
- Switch Control can be driven by a game controller, and Full Keyboard Access must work; do not override system keyboard shortcuts — /design/human-interface-guidelines/accessibility
- App Store Connect now carries Accessibility Nutrition Labels declaring which accessibility features the app supports; plan the declared set — /design/human-interface-guidelines/accessibility
- visionOS comfort: keep UI in the field of view, horizontal over vertical layouts, slow peripheral motion, no camera motion the player did not cause, no head-anchored content (also breaks Pointer Control), avoid big repetitive gestures — /design/human-interface-guidelines/accessibility [gate: visionOS]
- Naming: the HIG renamed "In-App Purchase" to "Apple In-App Purchase" on September 17, 2026; StoreKit remains the developer API (`/documentation/StoreKit/in-app-purchase`) — /design/human-interface-guidelines/apple-in-app-purchase [symbols: StoreKit]
- Game mapping of the four IAP types: consumable = lives/gems (depletes, rebuyable); non-consumable = permanent unlock; auto-renewable subscription; non-renewing subscription = time-boxed access such as a battle pass (rebought to extend). Physical goods and services go through Apple Pay, not IAP — /design/human-interface-guidelines/apple-in-app-purchase
- Store rules: let players play before selling; style the store as part of the game; show the full billing price on every item; hide or explain the store when `AppStore.canMakePayments` is false (parental restrictions); never imitate or alter the system purchase confirmation sheet — /design/human-interface-guidelines/apple-in-app-purchase [symbols: AppStore.canMakePayments]
- Family Sharing covers non-consumables and auto-renewables for up to five additional family members; word shared-content messaging for both purchaser and recipient — /design/human-interface-guidelines/apple-in-app-purchase
- Refund help: a custom help screen may precede the system refund flow (`Transaction.beginRefundRequest(for:in:)`) but the refund button must be immediately visible (no scroll, no extra screen); identify recent purchases with image, name, date; never speculate about Apple's refund policy — /design/human-interface-guidelines/apple-in-app-purchase [symbols: Transaction.beginRefundRequest(for:in:)]
- Subscriptions: sign-up screen must show name, period, per-period content, localized billing amount, and a sign-in/restore path; free trials must state the auto-charge at trial end; offer codes (iOS/iPadOS) are one-time (App Store Connect generated) or custom (alphanumeric ASCII only, redeemable only by URL or in-app, not in App Store account settings); in-app redemption via `AppStore.presentOfferCodeRedeemSheet(from:options:)` or SwiftUI `offerCodeRedemption(options:isPresented:onCompletion:)`; management via `AppStore.showManageSubscriptions(in:)`; cancel must be easy to find; retention via RetentionMessaging and win-back offers — /design/human-interface-guidelines/apple-in-app-purchase [symbols: AppStore.presentOfferCodeRedeemSheet(from:options:), offerCodeRedemption(options:isPresented:onCompletion:), AppStore.showManageSubscriptions(in:), Product.SubscriptionInfo, RetentionMessaging]
- tvOS sign-up/auth should hand off to another device via a code rather than text entry on the TV — /design/human-interface-guidelines/apple-in-app-purchase [gate: tvOS]
- Custom (Metal-drawn) buttons: hit region at least 44x44 pt (60x60 pt on visionOS) whatever the input device, and always a press state; one or two prominent buttons per menu screen at most; distinguish the preferred option by style, not by size — /design/human-interface-guidelines/buttons
- Menu dialogs: the primary (default) button answers Return and can close a sheet/alert; never give a destructive action (e.g., delete save, quit without saving) the primary role even when it is the likely choice — /design/human-interface-guidelines/buttons
- macOS: hovering a button shows a tooltip (also on visionOS after a gaze dwell); title a button that opens another window with a trailing ellipsis; image buttons want about 10 px padding inside their clickable edge — /design/human-interface-guidelines/buttons [symbols: NSButton.BezelStyle.flexiblePush, NSButton.isBordered] [gate: macOS]
- visionOS UI: button centres at least 60 pt apart (+4 pt padding for 60 pt+ buttons so hover effects do not overlap); prefer circle/capsule (eyes drift to corners); custom hover effects are not supported; white fill with black content is reserved for the toggled state; standard controls supply audible feedback because the system plays no haptics on visionOS — /design/human-interface-guidelines/buttons [symbols: ButtonBorderShape.circle, ButtonBorderShape.capsule, ButtonBorderShape.roundedRectangle] [gate: visionOS]
- Viewing distance by device, for HUD and text scale: iPhone up to 1-2 ft, iPad within about 3 ft, Mac about 1-3 ft, Apple TV often 8 ft or more, Apple Watch under 1 ft — /design/human-interface-guidelines/designing-for-ios; /design/human-interface-guidelines/designing-for-ipados; /design/human-interface-guidelines/designing-for-macos; /design/human-interface-guidelines/designing-for-tvos; /design/human-interface-guidelines/designing-for-watchos
- Mac expectations a game port must meet: resizable, movable, hideable windows plus full-screen mode; every command reachable from the menu bar; keyboard shortcuts; smooth transitions as the app goes active/inactive while players switch apps; multiple displays (including an iPad as a display) — /design/human-interface-guidelines/designing-for-macos [gate: macOS]
- iPhone: orientation changes are routine and players run several apps, switching often; iPad adds Stage Manager-style multitasking, keyboard/trackpad/Pencil combos, and the HIG expects iPad apps to carry over to running on macOS — /design/human-interface-guidelines/designing-for-ios; /design/human-interface-guidelines/designing-for-ipados
- tvOS: build menus on the focus system (highlight-and-expand), edge-to-edge art legible from across the room, and multiuser: infrequent sign-in, shared sign-in, automatic profile switch when the viewer changes — /design/human-interface-guidelines/designing-for-tvos [gate: tvOS]
- visionOS: apps launch into the Shared Space beside other apps; a Full Space makes the game the only app running (blended, portal, or full world). Choose the minimum immersion each moment needs; support indirect (hands-at-rest) gestures; keep direct-touch targets close and brief; discourage moving around during full immersion; device is for ages 13+ — /design/human-interface-guidelines/designing-for-visionos [gate: visionOS]
- watchOS: sessions under a minute, Digital Crown for vertical navigation, complications and notifications used more than the app; no physical game controller support — /design/human-interface-guidelines/designing-for-watchos [gate: watchOS]
- Inclusion items that change game content, not just copy: give avatar/character creators the tools to self-represent rather than fixed gendered defaults; if the game must ask gender, offer nonbinary, self-identify and decline-to-state plus pronouns; avoid hero/villain casting that maps to real-world race or gender; security questions must not assume college, cars, or similar experiences — /design/human-interface-guidelines/inclusion
- Copy and localisation: address the player as "you", not "the player"/"the user"; reserve "we" for the studio; define jargon; skip idioms and humour that will not translate; check colour meanings per locale (e.g., white = mourning in some regions); SF Symbols supply RTL and language-specific glyphs — /design/human-interface-guidelines/inclusion
- Launch sequence vocabulary: launching (open, initial download, until first screen ready) then optional onboarding; a splash screen belongs at the start of onboarding, not in launch. Target: interactive within a couple of seconds — /design/human-interface-guidelines/launching
- Launch screens are required only on iOS, iPadOS and tvOS (static on tvOS), not on macOS, visionOS, watchOS. Make it near-identical to the first frame (a solid colour if the game first shows a solid colour), match orientation and light/dark, no text (it cannot be localised), no logo or ad unless the first screen has it — /design/human-interface-guidelines/launching [gate: iOS, iPadOS, tvOS]
- Restore state on relaunch with as much detail as possible (position, window placement); landscape-only games must handle both landscape-left and landscape-right — /design/human-interface-guidelines/launching [gate: iOS, iPadOS]
- visionOS: even a fully immersive game should usually open a Shared Space window first (context, load time, an explicit "enter" control) and let the player choose when to go to a Full Space — /design/human-interface-guidelines/launching [gate: visionOS]
- Onboarding: interactive and short; prefer context-specific tips near the relevant UI (TipKit) over one up-front flow; an optional tutorial skipped once must not reappear but must stay findable in settings/help; teach the game, not the device; leave licences to the App Store; put a permission request in onboarding only if the game cannot function without it, otherwise at first use; ratings and purchases only after engagement — /design/human-interface-guidelines/onboarding [symbols: TipKit]
- Loading: draw something immediately (placeholders) — an empty screen reads as a hang; let players browse menus or level briefings while content streams; for long loads show hints sized to the measured remaining time; games may replace system progress indicators with a styled custom loader; on watchOS avoid loaders, but prefer one over a blank screen — /design/human-interface-guidelines/loading
- Layout must adapt even for a landscape-locked game: resizable windows on iPad and Mac, iPhone Mirroring on Mac (freely resizable), external displays, Display Zoom, Dynamic Island, text size. Choose layout from size classes (`UserInterfaceSizeClass`, `UITraitChangeObservable`), never from idiom or orientation; keep functionality constant across size classes — /design/human-interface-guidelines/layout [symbols: UserInterfaceSizeClass, UITraitChangeObservable] [gate: iOS, iPadOS]
- Background art on aspect-ratio change: scale to fill (never stretch, letterbox or pillarbox), and author it wider/taller than the standard visible area because windows can be very wide-short or tall-narrow — /design/human-interface-guidelines/layout
- Safe areas: position HUD with `SafeAreaRegions` (SwiftUI) or the UIKit safe-area article; layout guides `UILayoutGuide` / `NSLayoutGuide` — /design/human-interface-guidelines/layout [symbols: SafeAreaRegions, UILayoutGuide, NSLayoutGuide]
- macOS window layout: keep controls and critical info off the window bottom (players drag windows partly off-screen); keep content out from behind the camera housing — the Info.plist key `NSPrefersDisplaySafeAreaCompatibilityMode` is the linked control — /design/human-interface-guidelines/layout [symbols: NSPrefersDisplaySafeAreaCompatibilityMode] [gate: macOS]
- tvOS safe zone: inset primary content 60 pt top and bottom and 80 pt left and right (overscan); leave padding for focus growth. Grid widths for 2-9 columns: 860/560/410/320/260/217/184/160 pt unfocused width, 40 pt horizontal spacing, 100 pt minimum vertical spacing — /design/human-interface-guidelines/layout [gate: tvOS]
- Testing: Xcode's Device Hub (`/documentation/Xcode/device-hub`) simulates resized iPad windows and iPhone Mirroring for clipping checks; test the largest and smallest layouts first — /design/human-interface-guidelines/layout [symbols: Device Hub]
- The Layout page was revised September 9, 2026 and no longer carries the per-device point-size specification tables earlier versions had; the cached page has none — /design/human-interface-guidelines/layout
- visionOS windows/volumes: support resizing (min/max only to prevent overlap, not to forbid resizing); 3D in windows sparingly and inset; big 3D goes in a volume or immersive space; supplemental content in an adjacent window via `defaultWindowPlacement(_:)`, not an ornament; control centres 60 pt apart — /design/human-interface-guidelines/layout [symbols: defaultWindowPlacement(_:)] [gate: visionOS]
- Liquid Glass era (2025+): controls float on Liquid Glass with a scroll edge effect instead of a solid backing; full-bleed backgrounds extend under sidebars/toolbars, with `backgroundExtensionEffect()` / `UIBackgroundExtensionView` mirroring art under them — relevant only to SwiftUI/UIKit menu chrome around a game, not Metal-drawn HUD — /design/human-interface-guidelines/layout [symbols: backgroundExtensionEffect(), UIBackgroundExtensionView]
- In-game menus: navigable with the platform's default input (touch on iOS/iPadOS, direct+indirect gestures on visionOS, keyboard/mouse on Mac, plus controller per the A/B/shoulder mapping), and re-sized for each screen rather than scaled down from the desktop art — /design/human-interface-guidelines/menus
- Menu-item labels in games normally omit keyboard-shortcut hints because the game accepts many devices and remappable keys; otherwise: verb labels, title case, drop articles, dim unavailable items but keep the menu openable, ellipsis when more input follows. Icons on all items of a group or none. Submenus one level deep, about five items max (e.g., difficulty under New Game; "Sort by" Date/Score/Time) — /design/human-interface-guidelines/menus
- Toggled items: one changeable label (Show Map / Hide Map); add a verb where state vs action is ambiguous (Turn HDR On); or list both with the inapplicable one dimmed — /design/human-interface-guidelines/menus
- macOS and iPadOS menu bar menus must hold every command the game supports (pairs with the designing-for-macos expectation) — /design/human-interface-guidelines/menus [gate: macOS, iPadOS]
- visionOS: menus can be presented from 3D content through a SwiftUI view and may extend outside the window; to stay visible over occluding 3D content use `presentationBreakthroughEffect(_:)` — `.automatic` resolves to `.subtle` (preferred), `.prominent` overlays the whole scene (can cause discomfort), `.none` lets 3D occlude it (puzzle use). Place menus near what they control — /design/human-interface-guidelines/menus [symbols: presentationBreakthroughEffect(_:), BreakthroughEffect.automatic, BreakthroughEffect.subtle, BreakthroughEffect.prominent, BreakthroughEffect.none] [gate: visionOS]
- iOS/iPadOS UIKit menus have small (4 icon-only top row), medium (3 icon+label), large (default list) layouts via `UIMenu.preferredElementSize` — /design/human-interface-guidelines/menus [symbols: UIMenu.preferredElementSize]
- Permission-gated items relevant to games: location, health, contacts, gameplay information (listed as user content), Bluetooth peripherals, local networks, camera, microphone, visionOS ARKit data in a Full Space (hand tracking, plane estimation, image anchoring, world tracking), and the advertising identifier. Ask at first use; ask at launch only if the game cannot run without it (e.g., a visionOS game that bounces objects off your walls) — /design/human-interface-guidelines/privacy
- Purpose strings: one active, specific, sentence-case sentence ending in a period (good: says what is recorded and why; bad: "needed for a better experience" or "Turn on microphone access"). A pre-alert screen may have exactly one button titled like "Continue"/"Next" that opens the system alert, no Cancel/Close, never "Allow" — /design/human-interface-guidelines/privacy [symbols: AppTrackingTransparency]
- App Tracking Transparency: if tracking from launch, show the system alert before collecting anything; pre-alert screens offering incentives, imitating the alert, picturing it, or annotating behind it are App Review rejections (guideline 5.1.1(iv)); a legally required consent screen before/after is allowed — /design/human-interface-guidelines/privacy [symbols: AppTrackingTransparency]
- App Store privacy details (nutrition label) must be declared in App Store Connect for every new or updated app — /design/human-interface-guidelines/privacy
- Accounts and secrets: passkeys or Sign in with Apple over passwords (2FA if passwords remain), Face ID / Optic ID / Touch ID via LocalAuthentication, tokens in the keychain, never plain-text files — /design/human-interface-guidelines/privacy [symbols: LocalAuthentication, Keychain Services]
- macOS: fast user switching means several people may be logged in, so do not assume which user owns saves/settings — /design/human-interface-guidelines/privacy [gate: macOS]
- visionOS privacy: ARKit runs always but sends apps nothing in the Shared Space; ARKit APIs need a Full Space plus permission. Gaze is private: the system draws hover on SwiftUI/RealityKit elements without telling the app where the player looks. Back camera returns blank frames (compatibility only); front camera feeds spatial Personas with permission; iOS games ported to visionOS must drop or replace camera features — /design/human-interface-guidelines/privacy [gate: visionOS]
- Ratings: request via StoreKit `RequestReviewAction` (iOS, iPadOS, macOS system prompt) at a natural stop such as level completion, never on first launch, in onboarding, or mid-play; the system shows it at most three times per app per 365 days and skips players who already rated or opted out globally, so a call may show nothing; space requests a week or two apart. Resetting the summary rating on a new version trades freshness for fewer visible ratings — /design/human-interface-guidelines/ratings-and-reviews [symbols: RequestReviewAction] [gate: system prompt on iOS, iPadOS, macOS]
- Settings defaults: auto-select the best graphics settings for the device instead of asking (developer companion `/documentation/Metal/improving-your-games-graphics-performance-and-settings`, cached); detect controllers and accessories rather than asking; never duplicate system-wide settings (accessibility, scrolling, authentication) in game settings; keep the list short — /design/human-interface-guidelines/settings
- Settings entry points: Esc opens settings in a game (Command-Comma in apps); on macOS also add a Settings item in the App menu, not a toolbar button. In-game settings pane holds rarely changed items (save behaviour, key mappings, account); per-task options live where the task is; rarely changed items only may go in the system Settings app, with a button that opens it; watchOS apps add nothing to system Settings — /design/human-interface-guidelines/settings [symbols: SwiftUI Settings, UserDefaults] [gate: macOS App menu]
- macOS settings window conventions (applies to any AppKit/SwiftUI settings window a game shows outside the Metal view): non-customisable always-visible toolbar of panes with the active one indicated, title updates to the pane (or "<Game> Settings" with one pane), minimise and zoom dimmed, reopens on last pane — /design/human-interface-guidelines/settings [gate: macOS]
- The Technologies index (a link list, no guidance of its own) names the integrations a game might adopt beyond Game Center/iCloud/IAP: App Clips (instant lightweight demo of a game), SharePlay (play together remotely; spatial Personas on visionOS), iMessage apps (games inside a conversation), Mac Catalyst (iPad game to Mac), Generative AI, Machine learning, Augmented reality, AirPlay, Sign in with Apple, VoiceOver — each has its own HIG page outside this slice — /design/human-interface-guidelines/technologies

## input.md

- Virtual on-screen controls for iOS/iPadOS have a dedicated framework, TouchController (`/documentation/TouchController`); the GameController-side article for retrofitting is `/documentation/GameController/adding-virtual-controls-to-games-that-support-game-controllers-in-ios` — /design/human-interface-guidelines/game-controls [symbols: TouchController] [gate: iOS, iPadOS]
- Touch-control layout rules: movement on the left half, camera on the right; spawn the virtual stick where the thumb lands (floating, not fixed); pan the camera by direct drag, not a second stick; menus and secondary controls along the top; keep clear of Home indicator and Dynamic Island; primary controls 44x44 pt minimum, secondary 28x28 pt — /design/human-interface-guidelines/game-controls [gate: iOS, iPadOS]
- Every virtual button needs a press state visible around the thumb (glow/opacity), paired with sound and haptics; label buttons with action art, never "A"/"X"/"R1"; hide controls whose action is unavailable (e.g., stick fades at rest) — /design/human-interface-guidelines/game-controls
- Collapse chords and sequences into one control with tap / double-tap / touch-and-hold variants (e.g., walk vs sprint on one control) — /design/human-interface-guidelines/game-controls
- A controller is optional hardware everywhere except where you declare it required. Only tvOS and visionOS may require one; declaring it (Info.plist `GCRequiresControllerUserInteraction`) earns the App Store "Game Controller Required" badge, and the game must still detect absence at launch and prompt to connect — /design/human-interface-guidelines/game-controls [symbols: GCRequiresControllerUserInteraction] [gate: tvOS, visionOS only]
- Detect paired controllers automatically and read their profile; GameController names elements by position, so prompts must use the connected controller's own labels/glyphs (GCControllerElement provides SF Symbols for most brands' buttons). With several controllers, show the glyphs of the one currently in use, and per-player glyphs in multiplayer — /design/human-interface-guidelines/game-controls [symbols: GCControllerElement]
- Out-of-gameplay UI mapping on all Apple platforms: A activates, B cancels/back, shoulders switch screen or section left/right, sticks and D-pad move selection, Menu opens settings or pauses, Home/logo reserved for the system; X, Y and triggers have no UI convention — /design/human-interface-guidelines/game-controls
- Mac keyboard bindings: favour single keys (I inventory, M map, Space for main action); keep related commands near WASD or grouped (number row for inventory categories); where a PC binding uses Control, consider Command on Apple keyboards since it sits beside Space; always allow rebinding — /design/human-interface-guidelines/game-controls [gate: macOS default input]
- Gesture rules for games: custom gestures are legitimate in games but must be discoverable, easy, distinct, and never the only path to an important action; give feedback during the gesture; show clearly when a gesture is unavailable (locked object, disabled button) or players assume a freeze — /design/human-interface-guidelines/gestures
- iOS/iPadOS reserved gestures to avoid colliding with: three-finger swipe (undo/redo), three-finger pinch (copy/paste), four-finger swipe (iPad app switch), shake (undo). Games may and often should enable simultaneous recognition (stick + fire buttons at once). The HIG says games can defer system edge gestures; on UIKit that is `UIViewController.preferredScreenEdgesDeferringSystemGestures` (iOS 11+, unavailable on tvOS) — the HIG page itself names no iOS symbol; the property was checked in the iPhoneOS SDK header — /design/human-interface-guidelines/gestures [symbols: preferredScreenEdgesDeferringSystemGestures] [gate: iOS, iPadOS]
- macOS: keyboard and mouse primary; standard gestures also arrive from Magic Trackpad, Magic Mouse, and controllers with a touch surface (e.g., DualSense touchpad) — /design/human-interface-guidelines/gestures [gate: macOS]
- Standard gesture support matrix: tap, swipe, drag, double tap on all six platforms; touch-and-hold on all but macOS; zoom and rotate on all but watchOS — /design/human-interface-guidelines/gestures
- visionOS: indirect (look + pinch, works at any distance, hands at rest) for UI; direct touch for close objects and infrequent use (arm fatigue). Custom hand gestures need a Full Space plus hand-tracking permission via ARKit (`/documentation/visionOS/setting-up-access-to-arkit-data`); never require a specific hand, avoid two-hand-only gestures without a fallback, avoid hand/wrist/forearm roll (reserved) — /design/human-interface-guidelines/gestures [gate: visionOS, Full Space]
- visionOS 2+: looking at the palm summons Home / Control Center overlays; keep hand-anchored content off that area. In a Full Space a game (e.g., virtual gloves) can require a tap before the Home indicator shows, via SwiftUI `persistentSystemOverlays(_:)`; apps built for visionOS 1 get that deferral by default — /design/human-interface-guidelines/gestures [symbols: persistentSystemOverlays(_:)] [gate: visionOS 2+]
- watchOS 11+ double tap: scrolls lists and advances vertical tabs, or fires a designated primary action (`handGestureShortcut(_:isEnabled:)` with `HandGestureShortcut.primaryAction`); do not set a primary action in a scrolling view — /design/human-interface-guidelines/gestures [symbols: handGestureShortcut(_:isEnabled:), HandGestureShortcut.primaryAction] [gate: watchOS 11+]
- Pointer support by platform: macOS primary (with keyboard); iPadOS and visionOS additive (never replaces touch or eyes/hands); iOS no extra considerations; tvOS and watchOS not supported — /design/human-interface-guidelines/pointing-devices
- Mac trackpad/mouse: never redefine systemwide gestures even in a game (Dock reveal, Mission Control, swipe between full-screen apps, App Exposé, Notification Center edge swipe, Launchpad, Show Desktop), and remember players customise them; the HIG table lists which clicks and gestures exist on mouse vs trackpad (force click, tap-to-click, pinch, rotate are trackpad only) — /design/human-interface-guidelines/pointing-devices [gate: macOS]
- Keep input-mode parity: a modifier-key behaviour (e.g., Option-drag duplicates) must give the same result by touch or pointer; let the pointer reveal auto-hidden controls — /design/human-interface-guidelines/pointing-devices
- macOS cursor vocabulary for menus/editors is `NSCursor` (`arrow`, `crosshair`, `openHand`, `closedHand`, `pointingHand`, `operationNotAllowed`, `iBeam`, resize variants such as `resizeLeftRight`, `contextualMenu`, `dragCopy`, `dragLink`, `disappearingItem`, `iBeamCursorForVerticalLayout`) — /design/human-interface-guidelines/pointing-devices [symbols: NSCursor] [gate: macOS]
- Gap a writer must fill from elsewhere: this HIG page says nothing about capturing, hiding or relatively-moving the cursor for mouse-look. The SDKs have `UIViewController.prefersPointerLocked` (iOS 14+, unavailable on tvOS/watchOS; iPad pointer lock) and on macOS `CGAssociateMouseAndMouseCursorPosition` (CoreGraphics CGRemoteOperation.h), both confirmed in headers; GCMouse is the GameController route — /design/human-interface-guidelines/pointing-devices [symbols: prefersPointerLocked, CGAssociateMouseAndMouseCursorPosition, GCMouse]
- iPadOS pointer: circle by default, morphs per element; content effects highlight (small, transparent background), lift (small, opaque), hover (large, custom scale/tint/shadow, no magnetism); hit-region padding about 12 pt bezelled / 24 pt unbezelled; contiguous hit regions across bar buttons; provide the corner radius for non-standard lift shapes (`UIPointerShape.roundedRect(_:radius:)`); accessories via `UIPointerAccessory`; band selection via `UIBandSelectionInteraction` (iPadOS 15+) — /design/human-interface-guidelines/pointing-devices [symbols: UIPointerShape.roundedRect(_:radius:), UIPointerAccessory, UIBandSelectionInteraction] [gate: iPadOS]
- visionOS: an attached mouse/trackpad targets whatever window the eyes are on; the pointer hides during trackpad gestures and reappears at the gaze location; no app work needed — /design/human-interface-guidelines/pointing-devices [gate: visionOS]
- visionOS spatial controllers (e.g., PlayStation VR2 Sense) should mirror hand input: look + trigger for indirect, reach + trigger for direct interaction — /design/human-interface-guidelines/game-controls [gate: visionOS]

## audio-and-haptics.md

- HIG says Core Haptics is available in iOS, iPadOS, tvOS and visionOS and on many controllers. The macOS SDK header nonetheless marks `CHHapticEngine` `API_AVAILABLE(ios(13.0), macos(10.15), tvos(14.0))`: on a Mac the engine exists to drive controller haptics (no built-in haptic actuator target for it); Mac trackpad feedback is a separate AppKit API — /design/human-interface-guidelines/designing-for-games [symbols: CHHapticEngine]
- Ship multichannel audio so the system can render Spatial Audio where the device supports it — /design/human-interface-guidelines/designing-for-games
- Platform split, Mac-first: the HIG's audio-session category guidance is iOS/iPadOS/tvOS/visionOS/watchOS. `AVAudioSession` (and `sharedInstance`, `setCategory:error:`, `AVAudioSessionCategorySoloAmbient`, etc.) is `API_UNAVAILABLE(macos)` in the macOS SDK header; a native Mac game has no session or category to configure, no Ring/Silent switch, and no interruption notifications from that API. The HIG's only macOS audio note is that notification sounds mix with other audio by default — /design/human-interface-guidelines/playing-audio [symbols: AVAudioSession, AVAudioSession.Category] [gate: AVAudioSession iOS 3+/tvOS 9+/watchOS 2+, unavailable on macOS]
- Category choice for games (iOS family): `soloAmbient` = game with its own soundtrack (silences other audio, obeys the silent switch, no background play — the default); `ambient` = game that lets the player keep their own music instead of the soundtrack (mixes, obeys silent switch, no background). `playback`, `record`, `playAndRecord` ignore the silent switch; `playAndRecord` is the one for in-game voice chat. In silent mode only player-initiated audio should play, so SFX and soundtrack go quiet — /design/human-interface-guidelines/playing-audio [symbols: AVAudioSession.Category.soloAmbient, AVAudioSession.Category.ambient, AVAudioSession.Category.playAndRecord] [gate: iOS, iPadOS, tvOS, visionOS, watchOS]
- Never set system volume; mix relative levels internally. Allow output rerouting (AirPlay, Bluetooth) and use `MPVolumeView` if you expose a volume/route control. Headphone unplug should pause (media apps); route changes should not interrupt — /design/human-interface-guidelines/playing-audio [symbols: MPVolumeView]
- Interruptions: a game may auto-resume audio when an interruption ends without checking `AVAudioSession.InterruptionOptions.shouldResume`, because game audio was not an explicit user choice (media apps must check it). When temporarily ducking/interrupting others, deactivate with `.notifyOthersOnDeactivation`. Do not react to remote/headphone media controls unless the game is actually playing audio in an audio context; never repurpose them — /design/human-interface-guidelines/playing-audio [symbols: AVAudioSession.InterruptionOptions.shouldResume, AVAudioSession.SetActiveOptions.notifyOthersOnDeactivation] [gate: iOS family]
- iOS/iPadOS short UI sounds and vibrations: AudioToolbox System Sound Services (`/documentation/AudioToolbox/audio-services`) — the HIG's one remaining endorsement of AudioToolbox — /design/human-interface-guidelines/playing-audio [symbols: AudioToolbox audio services] [gate: iOS, iPadOS]
- tvOS plays no system sounds for alerts/notifications; all audio is app-initiated — /design/human-interface-guidelines/playing-audio [gate: tvOS]
- visionOS: silence reads as broken, so give custom UI custom sounds; combine ambient beds with positioned audio sources; decide per sound between head-fixed and object-tracked; vary repeated sounds by randomising pitch and volume at playback rather than authoring many files; non-Now-Playing app audio ducks when the player looks at another app; Now Playing audio pauses on window close — /design/human-interface-guidelines/playing-audio [gate: visionOS]
- watchOS: short clips only while foreground unless background audio is set up; encode media as 64 kbps HE-AAC — /design/human-interface-guidelines/playing-audio [gate: watchOS]
- Where haptics can play, per the HIG: iPhone built-in Taptic (system controls plus `UIFeedbackGenerator`); Apple Watch Taptic Engine; Mac Force Touch / Magic Trackpad only via `NSHapticFeedbackPerformer` with three patterns; game controllers on iPadOS, macOS, tvOS, visionOS; Apple Pencil Pro and some trackpads on certain iPads. The HIG's controller list omits iOS (iPhone), but the SDK header has `GCController.haptics` / `GCDeviceHaptics` as `API_AVAILABLE(macos(11.0), ios(14.0), tvos(14.0))`, so controller haptics do compile and run on iPhone; treat the omission as a HIG wording gap — /design/human-interface-guidelines/playing-haptics [symbols: UIFeedbackGenerator, NSHapticFeedbackPerformer, GCController.haptics, GCDeviceHaptics] [gate: controller haptics macOS 11+/iOS 14+/tvOS 14+]
- Mac-first path: the only haptics a Mac game can drive are (a) a connected controller's actuators — `GCController.haptics` then `GCDeviceHaptics` `createEngineWithLocality:` returns a `CHHapticEngine` per locality (`GCHapticsLocalityDefault`, `GCHapticsLocalityAll`, left/right handle etc., queried via `supportedLocalities`) — and (b) Force Touch trackpad feedback through `NSHapticFeedbackManager` / `NSHapticFeedbackPerformer.performFeedbackPattern:performanceTime:` with `NSHapticFeedbackPatternGeneric`, `NSHapticFeedbackPatternAlignment`, `NSHapticFeedbackPatternLevelChange`, which the HIG ties to drags and force clicks, not gameplay rumble. Developer article: `/documentation/CoreHaptics/playing-haptics-on-game-controllers` — /design/human-interface-guidelines/playing-haptics [symbols: GCDeviceHaptics.createEngineWithLocality:, GCHapticsLocality, CHHapticEngine, NSHapticFeedbackManager, NSHapticFeedbackPattern] [gate: macOS]
- Core Haptics vocabulary: transient events (taps/impulses) and continuous events (sustained), each with intensity (strength) and sharpness (soft/organic to crisp/mechanical), optionally with synchronised audio; patterns may vary dynamically with gameplay (a jump from a tree hits harder than a jump in place) — /design/human-interface-guidelines/playing-haptics [symbols: CHHapticEvent, CHHapticPattern] 
- Design rules: one haptic meaning per pattern for the whole game (never reuse the failure pattern for success); match haptic intensity/sharpness to the accompanying animation and sound; avoid overuse; long continuous haptics are fine in gameplay flow but not in UI; always offer a haptics off switch and keep the game fully playable without them; check vibration does not disturb camera, gyroscope or microphone input — /design/human-interface-guidelines/playing-haptics
- iOS predefined feedback (via `UIFeedbackGenerator` subclasses): notification (success, warning, error), impact (light, medium, heavy, rigid, soft), selection; use each only for its documented meaning, else build a custom Core Haptics pattern — /design/human-interface-guidelines/playing-haptics [symbols: UIFeedbackGenerator] [gate: iOS]
- watchOS haptics via `WKHapticType`: notification, up, down, success, failure, retry, start, stop, click; Digital Crown detents on Series 4+ — /design/human-interface-guidelines/playing-haptics [symbols: WKHapticType] [gate: watchOS]
- Apparent conflict a writer must resolve: the games page lists visionOS among Core Haptics platforms, but the Buttons page says the visionOS system plays no haptics, so UI feedback there must be audible. Reading: on visionOS, haptics reach only a connected controller; UI confirmation must be sound — /design/human-interface-guidelines/buttons; /design/human-interface-guidelines/designing-for-games [gate: visionOS]

## game-center-and-online.md

- Cross-device save is a named framework now: GameSave (`/documentation/GameSave`, present in the macOS SDK as GameSave.framework), recommended by the games HIG for resuming on another device; not just iCloud/CloudKit by hand — /design/human-interface-guidelines/designing-for-games [symbols: GameSave]
- GameSave facts from the framework page (checked to back the HIG claim): syncs a save directory over iCloud Drive, handles conflicts and offline play, ships ready-made alerts for both, and falls back to local saving when the device is not signed into iCloud Drive. Requires the iCloud capability with iCloud Documents checked and a container identifier. Swift class `GameSaveSyncedDirectory`, ObjC `GSSyncedDirectory`, error domain `GameSaveErrorDomain` — /design/human-interface-guidelines/icloud; /documentation/gamesave [symbols: GameSaveSyncedDirectory, GSSyncedDirectory, GameSaveErrorDomain] [gate: iOS/iPadOS/macOS/Mac Catalyst/visionOS 26.0+; no tvOS or watchOS listed]
- The iCloud HIG lets you build custom conflict UI over GameSave data instead of the built-in alerts; resolve conflicts automatically where possible, and early, so no one plays on the wrong save — /design/human-interface-guidelines/icloud
- iCloud etiquette for saves: no per-file "keep in iCloud?" prompts (at most one all-or-nothing choice at first launch); store only what players create (saves, settings meant for all devices), never regenerable game data; everything in Documents goes into iCloud backups, so keep caches and downloaded assets out of it; no alert when iCloud is off or in Airplane Mode, just a quiet note that changes stay on this device; confirm before deleting a synced save, because deletion propagates to every device — /design/human-interface-guidelines/icloud
- Game Center is on every Apple platform and the HIG frames it as a discovery channel across a player's devices, not only social features — /design/human-interface-guidelines/designing-for-games
- Authenticate at launch: check sign-in when the game starts and initialise the local player then; the HIG ties this to discovery (Top Played chart, friend recommendations, activity in the Apple Games app, App Store and notifications) — /design/human-interface-guidelines/game-center [symbols: GKLocalPlayer]
- Access point: Apple-drawn button that opens the Game Overlay on iOS/iPadOS/macOS, or the full-screen in-game dashboard on tvOS/visionOS. Show it on the main menu or settings only, never in gameplay, splash, cinematics or a pre-menu tutorial; it pins to one of four corners and has collapsed and expanded sizes, so keep controls clear of both; on visionOS its location depends on game type (immersive vs volume). Pause the game while overlay/dashboard is up — /design/human-interface-guidelines/game-center [symbols: GKAccessPoint, GKAccessPointLocation (TopLeading, TopTrailing, BottomLeading, BottomTrailing), GKAccessPoint.triggerAccessPointWithGameActivity:]
- Custom UI may deep-link into overlay/dashboard sections (leaderboards, profile); use Apple's artwork unaltered and the exact terms: "Game Center" (not GameKit/GameCenter), "Game Center Profile", "Achievements" (not trophies), "Leaderboards", "Challenges", "Add Friends" — /design/human-interface-guidelines/game-center
- Achievements: four states (locked, in-progress, hidden, completed), shown grouped as Completed vs Locked; display order equals upload order; title and description each truncate past two lines (title case title, sentence case description); progressive achievements get system encouragement messages. Image: PNG/TIF/JPG, sRGB or P3, 512x512 pt (1024 px @2x) under a circular 512 pt mask on iOS/iPadOS/macOS/visionOS; tvOS 320x320 pt with 200 pt mask; unique art per achievement or a placeholder shows — /design/human-interface-guidelines/game-center [symbols: GKAchievement, GKAchievementDescription]
- Leaderboards: classic (all-time best, never ends) vs recurring (resets on your interval: daily puzzle, weekly mode, seasonal); group many boards with leaderboard sets; art 512x512 pt with a 512x312 pt crop (iOS/iPadOS/macOS; cropped further inside sets); tvOS needs a layered focus image 659x371 pt — /design/human-interface-guidelines/game-center [symbols: GKLeaderboard, GKLeaderboardSet]
- Challenges (2025 redesign) sit on top of leaderboards: 1-5 minute single-player skill runs, scored on the most recent attempt (not personal best, which favours veterans); entered via invite links, Game Overlay, or the Games app; deep-link to the exact level, routing first-timers through the tutorial first; artwork 1920x1080 pt with a 1465x767 pt safe crop — /design/human-interface-guidelines/game-center [symbols: GKChallengeDefinition] [gate: iOS/iPadOS/macOS 26 era; check availability]
- Multiplayer activities: real-time and turn-based, joinable by party code (about eight alphanumeric characters, e.g. "2MP4-9CMF"), Game Overlay, dashboard, or Games app. Party codes work even if you use your own networking, not GameKit's. Allow late join, early leave and rejoin; show the current code in-game; allow manual code entry. Artwork 1920x1080 pt, 1465x767 pt crop — /design/human-interface-guidelines/game-center [symbols: GKGameActivity, GKGameActivityDefinition, GKGameActivity.partyCode, GKGameActivity.start(definition:partyCode:)]
- tvOS dashboard can take a 600x180 pt logo/wordmark (not the app icon). watchOS has GameKit API but no system Game Center UI; its content appears on the paired iPhone — /design/human-interface-guidelines/game-center [gate: tvOS; watchOS]
- Local network access is a permission-gated protected resource; LAN or peer-to-peer multiplayer must expect the system prompt and degrade if denied — /design/human-interface-guidelines/privacy

## game-loop-and-threading.md

- Full screen exists only on iPhone, iPad and Mac. tvOS and watchOS are always full screen; visionOS has none (expand the window or move to an immersive space instead) — /design/human-interface-guidelines/going-full-screen
- macOS full screen: use the system mechanism (`NSWindow.toggleFullScreen(_:)`), which automatically avoids the camera housing on notched Macs; never switch the display mode on entering full screen (Apple: it does not improve performance; players own the display mode); let players enter via the window's green button, View menu, or Control-Command-F, and optionally an in-game toggle, but no custom menu of window modes. Companion article: `/documentation/Metal/managing-your-game-window-for-metal-in-macos` — /design/human-interface-guidelines/going-full-screen [symbols: NSWindow.toggleFullScreen(_:), NSWindow.CollectionBehavior, NSScreen] [gate: macOS]
- Games are the stated exception to keeping the Dock reachable: hide it on macOS with `NSApplication.PresentationOptions.hideDock`; on iPadOS defer the bottom-edge swipe — /design/human-interface-guidelines/going-full-screen [symbols: NSApplication.PresentationOptions.hideDock] [gate: macOS, iPadOS]
- iOS/iPadOS: the Home indicator auto-hides shortly after launch and one swipe exits; keep that default and, only if players exit by accident, require two swipes by deferring the bottom edge (`UIViewController.preferredScreenEdgesDeferringSystemGestures`, or `UIHostingController.preferredScreenEdgesDeferringSystemGestures` when hosting SwiftUI) — /design/human-interface-guidelines/going-full-screen [symbols: preferredScreenEdgesDeferringSystemGestures, UIHostingController] [gate: iOS, iPadOS]
- Pause automatically when the player switches away and resume where they left off; never exit full screen automatically; resize layout proportions (not the window) when entering full screen, and keep essential controls reachable without leaving it — /design/human-interface-guidelines/going-full-screen

## assets.md

- Bitmap scale factors to ship per platform: iPadOS and watchOS @2x; iOS @2x and @3x; macOS and tvOS @1x and @2x; visionOS @2x or higher — /design/human-interface-guidelines/images
- Formats: de-interlaced PNG for raster UI art, 8-bit palette PNG where 24-bit colour is not needed, JPEG or HEIC for photos, stereo HEIC for stereo/spatial photos, PDF or SVG for flat icons that must scale; embed a colour profile in every image — /design/human-interface-guidelines/images
- tvOS layered images (2-5 layers, opaque background layer required or the build errors) drive the focus parallax; the app icon must be layered. Layered images fetched from a server at runtime must be `.lcr` runtime files made with Xcode's `layerutil` tool from LSR or Photoshop files, and must not be embedded in the bundle. Preview with Parallax Previewer — /design/human-interface-guidelines/images [symbols: layerutil, .lcr, FocusState] [gate: tvOS]
- visionOS raster art: points are angular, so pixels never map 1:1; @2x looks fine at normal distance but soft up close. Higher resolution sharpens close views but costs file size and runtime, notably above @6x; above @2x also set high-quality filtering (`CALayer.filters`). Prefer vector 2D art — /design/human-interface-guidelines/images [symbols: CALayer.filters] [gate: visionOS]
- visionOS spatial photos (stereo HEIC plus spatial metadata) and spatial scenes (3D generated from 2D, several seconds each to generate) display through RealityKit `ImagePresentationComponent`; show them in standalone views, use `GlassBackgroundEffect` (feathered) for text over them — /design/human-interface-guidelines/images [symbols: ImagePresentationComponent, GlassBackgroundEffect] [gate: visionOS]
- Background Assets (`/documentation/BackgroundAssets`) is the HIG's named route for large post-install content (level packs, character models, textures), scheduled right after install, during updates, or at other idle times, so launch and install stay fast; GameKit's companion article is `/documentation/GameKit/improving-the-player-experience-for-games-with-large-downloads` (both cached in the corpus). Pair with the 30-minute initial-download target in designing-for-games — /design/human-interface-guidelines/loading [symbols: BackgroundAssets]
- Ship enough media in the base package that onboarding never waits on a download — /design/human-interface-guidelines/onboarding
- Game Center artwork specs (see game-center-and-online.md) are asset deliverables too: achievement 1024x1024 px PNG/TIF/JPG sRGB or P3; leaderboard 1024x1024 px with a 1024x624 crop; challenge and activity art 3840x2160 px — /design/human-interface-guidelines/game-center
