## game-loop-and-threading.md

- Do not copy the frame loop in Apple's Accelerate cube sample. It drives updates with `CVDisplayLinkCreateWithCGDisplay(CGMainDisplayID(), …)` + `CVDisplayLinkSetOutputCallback` + `CVDisplayLinkStart`, then hops every tick to `DispatchQueue.main.async`. The current SDK's `CVDisplayLink.h` wraps the whole API in `API_DEPRECATED_BEGIN("use NSView.displayLink(target:selector:), NSWindow.displayLink(target:selector:), or NSScreen.displayLink(target:selector:)", macos(10.4, 15.0))`. On macOS the replacement returns a `CADisplayLink` tied to the view's or window's current screen, so it follows the window across displays, which a link created for `CGMainDisplayID()` does not. The Mac-first default is `NSView.displayLink(target:selector:)`; iOS and iPadOS use `CADisplayLink(target:selector:)` directly. The sample also advances animation by a fixed `0.02` per tick rather than by elapsed time, so speed changes with refresh rate (60 vs 120 Hz ProMotion). Drive the sim from the link's timestamps instead. — /documentation/Accelerate/rotating-a-cube-by-transforming-its-vertices [symbols: CVDisplayLinkCreateWithCGDisplay, CVDisplayLinkSetOutputCallback, CVDisplayLinkStart, NSView.displayLink(target:selector:), NSWindow.displayLink(target:selector:), NSScreen.displayLink(target:selector:), CADisplayLink] [gate: CVDisplayLink deprecated macOS 15.0 per SDK header; NSView/NSScreen displayLink returns CADisplayLink on macOS 14+ (verify the 14 floor on the symbol page)]
- Rotation keyframes in simd: `simd_slerp(q0, q1, t)` gives separate arcs with a visible kink at each keyframe, while `simd_spline(q_prev, q0, q1, q_next, t)` gives one smooth path but needs a neighbour on each side. Duplicate the first and last keyframes so the end segments have neighbours, and start the index at 1. Apply a quaternion to a point with `act(_:)`. Double-precision types are `simd_quatd` / `simd_double3`; use the float `simd_quatf` for per-frame game code. — /documentation/Accelerate/rotating-a-cube-by-transforming-its-vertices [symbols: simd_slerp(_:_:_:), simd_spline(_:_:_:_:_:), simd_quatd, simd_quatd/act(_:), simd_double3, simd_quatf] [gate: sample targets macOS 13.3]
- simd sizes and naming, for CPU-side game math shared with shaders: vectors go up to 16 `Float` or 8 `Double` lanes, and matrices go up to 4×4. Matrix names are columns × rows, so `simd_float4x2` has four columns and two rows. Use vForce or vDSP for longer arrays. ## assets.md

- When an offline asset tool drops bit depth (for example float or 16-bit to 8-bit, or 8-bit to 1-bit masks), the vImage conversion functions take a dither selector: none (round to nearest), ordered blue noise (`kvImageConvert_DitherOrdered` OR'd with `kvImageConvert_OrderedGaussianBlue` or `kvImageConvert_OrderedUniformBlue`), Floyd-Steinberg, or Atkinson. For a reproducible asset build use `kvImageConvert_DitherOrderedReproducible`: it uses the same blue-noise offset on every call, so reruns give identical bytes. — /documentation/Accelerate/improving-the-quality-of-quantized-images-with-dithering [symbols: vImageConvert_Planar8toPlanar1(_:_:_:_:_:), vImageConvert_ARGBFFFFtoARGB8888_dithered(_:_:_:_:_:_:_:), kvImageConvert_DitherNone, kvImageConvert_DitherOrdered, kvImageConvert_OrderedGaussianBlue, kvImageConvert_OrderedUniformBlue, kvImageConvert_DitherFloydSteinberg, kvImageConvert_DitherAtkinson, kvImageConvert_DitherOrderedReproducible] [gate: sample targets macOS 13.3]
- `vImage_Buffer(cgImage:format:)` converts a CGImage to the layout a `vImage_CGImageFormat` describes while it loads, and `vImage_Buffer(size:bitsPerPixel:)` allocates a destination at another bit depth. Together they give an import tool a short CPU path from a PNG to a planar or interleaved buffer. — /documentation/Accelerate/improving-the-quality-of-quantized-images-with-dithering [symbols: vImage_CGImageFormat, vImage_Buffer/init(cgImage:format:flags:), vImage_Buffer/init(size:bitsPerPixel:)]
- In a CPU asset tool, splitting interleaved pixels into planar buffers (`deinterleave(planarDestinationBuffers:)`) lets you skip channels you do not need (for example alpha, or a single-channel roughness map) and run each plane concurrently, here with a task group of three `scale(destination:)` calls, then `interleave(planarSourceBuffers:)`. Apple's advice is to time both layouts, because most vImage functions exist in interleaved and planar forms and planar does not always win. — /documentation/Accelerate/optimizing-image-processing-performance [symbols: vImage.PixelBuffer, vImage.PixelBuffer/init(cgImage:cgImageFormat:pixelFormat:), vImage.PixelBuffer/deinterleave(planarDestinationBuffers:), vImage.PixelBuffer/interleave(planarSourceBuffers:), vImage.PixelBuffer/scale(destination:), vImage.PixelBuffer/makeCGImage(cgImageFormat:), vImage.Interleaved8x3, vImage.Planar8, vImageBuffer_InitWithCGImage(_:_:_:_:_:)]
- Channel reorder on CPU (for example BGRA from Core Graphics to RGBA for a tool's output) is `vImagePermuteChannels_ARGB8888` with a 4-entry permute map; `...WithMaskedInsert` also replaces selected channels with constants in the same pass (for example forcing alpha to opaque). `vImageOverwriteChannelsWithScalar_ARGB8888` / `vImageOverwriteChannels_ARGB8888` write one channel from a scalar or from a planar buffer, which is how a tool packs separate grayscale maps (occlusion, roughness, metalness) into one RGBA texture. At runtime, prefer a Metal texture swizzle over a CPU permute; that is general Metal knowledge, not from this page (hand off to apple-metal/resources-and-memory.md). — /documentation/Accelerate/permuting-channels; /documentation/Accelerate/overwriting-channels [symbols: vImagePermuteChannels_ARGB8888, vImagePermuteChannels_RGB888, vImagePermuteChannelsWithMaskedInsert_ARGB8888, vImageOverwriteChannels_ARGB8888, vImageOverwriteChannelsWithScalar_ARGB8888, vImageSelectChannels_ARGB8888]
- When an asset tool resizes images on CPU with vImage, the default resampling kernel for scale, shear, and arbitrary-angle rotate is Lanczos, which rings (faint halos) near hard edges such as line art, UI glyphs, or pixel art. `kvImageHighQualityResampling` selects a higher-quality, slower built-in filter, but the ringing sample builds its Lanczos filter with that same flag, so the flag does not remove ringing. The fix the sample shows is a custom 1D kernel (linear, normalized to sum 1). To build one, size its storage with `vImageGetResamplingFilterSize(scale, kernelFunc, kernelWidth, flags)`, allocate, then fill it with `vImageNewResamplingFilterForFunctionUsingBuffer`. Apply it through two 1D shears, vertical then horizontal, via an intermediate buffer, because the shear functions do not work in place. A custom filter is freed with `deallocate()`; a default one from `vImageNewResamplingFilter` is freed with `vImageDestroyResamplingFilter`. Reflection functions do not resample. — /documentation/Accelerate/reducing-artifacts-with-custom-resampling-filters; /documentation/Accelerate/resampling-in-vimage [symbols: vImageNewResamplingFilter(_:_:), vImageNewResamplingFilterForFunctionUsingBuffer(_:_:_:_:_:_:), vImageGetResamplingFilterSize(_:_:_:_:), vImageDestroyResamplingFilter(_:), ResamplingFilter, kvImageHighQualityResampling, vImage.PixelBuffer/shear(direction:translate:slope:resamplingFilter:backgroundColor:destination:), vImage.ShearDirection] [gate: sample targets macOS 13]
- Model I/O can generate textures procedurally on CPU. `MDLSkyCubeTexture(name:channelEncoding:textureDimensions:turbidity:sunElevation:upperAtmosphereScattering:groundAlbedo:)` simulates a physically based sunlit sky, and changing its properties and calling `update()` regenerates the texels. The output is a cube map stored as six faces stacked vertically in the order +X, -X, +Y, -Y, +Z, -Z, so the bytes of face i start at `i * width * height * componentCount`. `texelDataWithTopLeftOrigin()` returns rows with the top-left pixel first, which matches the vImage layout. The texels come out RGBA, so vImage's ARGB-expecting `alphaComposite` needs `permuteChannels(to: (3, 0, 1, 2), …)` first. For a game, bake the sky offline or at load and upload it as a cube texture (handoff to apple-metal/resources-and-memory.md); do not regenerate it per frame. — /documentation/Accelerate/sharing-texture-data-between-the-model-io-framework-and-the-vimage-library [symbols: MDLSkyCubeTexture, MDLSkyCubeTexture/update(), MDLTexture/texelDataWithTopLeftOrigin(), MDLTexture, vImage.PixelBuffer/init(pixelValues:size:pixelFormat:), vImage.PixelBuffer/permuteChannels(to:destination:), vImage.PixelBuffer/alphaComposite(_:topLayer:destination:), Pixel_8] [gate: sample targets macOS 14]

## audio-and-haptics.md

- For a spectrum display or beat detector on CPU, the classic vDSP real FFT (`vDSP_fft_zrip`) works in place on a `DSPSplitComplex`. The N real samples are packed even/odd into `realp`/`imagp` (N/2 each). The forward result packs the purely real DC term into `realp[0]` and the purely real Nyquist term into `imagp[0]`, so bin 0 must be special-cased before magnitudes are computed. Scaling is a trap. The FFT reference pages and the SDK `vDSP.h` comments write the inverse as `scale = 1./N`. Apple's own article (/documentation/Accelerate/understanding-data-packing-for-fourier-transforms, "Scale time- and frequency-domain data") says vDSP Fourier routines do not scale, and gives the factors: real forward ×2, real inverse ×N real elements, complex forward ×1, complex inverse ×N complex elements (rows×columns in 2D). Its round-trip sample multiplies by 1/2 after the forward transform and by 1/n after the inverse. The DCT sample (signal-extraction-from-noise row) agrees: it divides the inverse by N/2. Trust the article and the round trip over the reference pseudocode, and have the writer test it. Length must be a power of two (`N = 1 << Log2N`), and the `...t` variants take a caller-supplied temporary buffer for speed. `vDSP_fft_zrop` is the out-of-place form with the same packing and scaling; use it to keep the time-domain buffer intact. — /documentation/Accelerate/in-place-functions-for-1d-real-fft; /documentation/Accelerate/out-of-place-functions-for-1d-real-fft [symbols: vDSP_fft_zrip, vDSP_fft_zript, vDSP_fft_zripD, vDSP_fft_zrop, vDSP_fft_zropt, DSPSplitComplex, FFTSetup, FFTDirection]
- To transform several equal-length channels in one call (for example left and right of a stereo buffer), use the multiple-signal real variants, which add a between-signal stride `IM` and a count `M` and use the same DC/Nyquist packing. The signals sit back to back in one buffer, `vDSP_ctoz` with stride 2 splits real samples even/odd into the split-complex halves, and the between-signal stride is counted in complex elements (N/2 per real signal of N samples). `vDSP.squareMagnitudes(_:result:)` then gives per-bin energy. The samples call `vDSP_create_fftsetup` and `vDSP_destroy_fftsetup` around a single transform. In a game, build the setup once per FFT size at load and reuse it on every audio or analysis callback, because creating a setup allocates. — /documentation/Accelerate/in-place-functions-for-1d-multiple-signal-real-fft; /documentation/Accelerate/performing-fourier-transforms-on-multiple-signals [symbols: vDSP_fftm_zrip, vDSP_fftm_zript, vDSP_fftm_zip, vDSP_ctoz, vDSP_create_fftsetup, vDSP_destroy_fftsetup, FFTRadix, kFFTRadix2, kFFTDirection_Forward, vDSP/squareMagnitudes(_:result:)]
- The DFT setup API is the modern path: `vDSP_DFT_zop_CreateSetup(previous, count, .FORWARD)` + `vDSP_DFT_Execute`, which the page says switches to an FFT internally when the count allows. It takes a plain count rather than `Log2N`, which suggests it accepts lengths the `fft_` functions cannot; check the setup's symbol page for the allowed lengths before saying so. When the data is already interleaved (`DSPComplex`), `vDSP_DFT_Interleaved_CreateSetup(..., .interleaved_ComplextoComplex)` + `vDSP_DFT_Interleaved_Execute` skips the `vDSP_ctoz` / `vDSP_ztoc` round trip. Destroy each setup with its matching `...DestroySetup`. — /documentation/Accelerate/performing-fourier-transforms-on-interleaved-complex-data [symbols: vDSP_DFT_zop_CreateSetup, vDSP_DFT_Execute, vDSP_DFT_DestroySetup, vDSP_DFT_Interleaved_CreateSetup, vDSP_DFT_Interleaved_Execute, vDSP_DFT_Interleaved_DestroySetup, vDSP_ctoz, vDSP_ztoc, DSPComplex, DSPSplitComplex, vDSP/indexOfMaximum(_:)]
- Converting raw PCM integers to float for mixing: the C functions `vDSP_vflt16` / `vDSP_vflt32` (and `...D` for double) convert with no scaling, so a scale step must follow to reach the [-1, 1] range. Packed 24-bit samples have their own types, `vDSP_int24` / `vDSP_uint24`, and `vDSP_vfltsm24` / `vDSP_vfltsmu24` convert and scale in one pass. Real-time rule: the Swift overlay `vDSP.integerToFloatingPoint(_:floatingPointType:)` returns a new `[U]` array, so it allocates. On an audio render thread, use `vDSP.convertElements(of:to:)` into a preallocated buffer, or the C functions. (Page slip: the `vDSP_vfltu32` summary says "unsigned 16-bit"; the signature takes `unsigned int`.) — /documentation/Accelerate/integer-to-single-precision-floating-point-conversion [symbols: vDSP_vflt16, vDSP_vflt32, vDSP_vfltu32, vDSP_vflt24, vDSP_vfltu24, vDSP_vfltsm24, vDSP_vfltsmu24, vDSP_int24, vDSP_uint24, vDSP/integerToFloatingPoint(_:floatingPointType:), vDSP/convertElements(of:to:)]
- For CPU-side EQ or a filter sweep across several channels (for example a low-pass for an "underwater" or occlusion effect), vDSP offers cascaded biquad IIR filters. Each section is direct form 2, and the sections run in sequence. The filters work in place, so source and destination may alias. `vDSP_biquadm` is tuned for many independent channels. For one channel, Apple says `vDSP_biquad` may give better performance and energy use, and calls it best practice for a channel in isolation. To change a filter while it runs without zipper noise, `vDSP_biquadm_SetTargetsSingle` / `...Double` set target coefficients plus an `interp_rate` and `interp_threshold`, and the filter ramps toward them. `vDSP_biquadm_SetActiveFilters` bypasses individual sections. `vDSP_biquadm_ResetState` clears history (for example on voice reuse), and `vDSP_biquadm_CopyState` carries history across setups. The setup is built from double coefficients (`vDSP_biquadm_CreateSetup(coeffs, M sections, N channels)`). Creation and destruction allocate, so do them off the render thread; that is my inference, the page does not say it. In most games an `AVAudioUnitEQ` node in AVAudioEngine is the higher-level choice (my framing, not the page's), and vDSP fits inside a custom render callback or source node. — /documentation/Accelerate/multichannel-biquadratic-filters [symbols: vDSP_biquadm, vDSP_biquad, vDSP_biquadm_CreateSetup, vDSP_biquadm_Setup, vDSP_biquadm_SetTargetsSingle, vDSP_biquadm_SetTargetsDouble, vDSP_biquadm_SetCoefficientsSingle, vDSP_biquadm_SetActiveFilters, vDSP_biquadm_ResetState, vDSP_biquadm_CopyState, vDSP_biquadm_DestroySetup, AVAudioUnitEQ]
- The single-channel `vDSP_biquad` differs from `vDSP_biquadm` in two ways that matter. First, filter history lives in a caller-owned `Delay` array passed on every call, so one setup can serve many voices if each voice keeps its own delay buffer. Second, its page says each section is direct form 1, while the multichannel page says direct form 2. One of the two pages is likely wrong; flag it rather than repeat either. It also has no `SetTargets` ramping, only `vDSP_biquad_SetCoefficientsSingle` / `...Double`. — /documentation/Accelerate/single-channel-biquadratic-filters [symbols: vDSP_biquad, vDSP_biquad_CreateSetup, vDSP_biquad_Setup, vDSP_biquad_SetCoefficientsSingle, vDSP_biquad_SetCoefficientsDouble, vDSP_biquad_DestroySetup]
- Window each analysis block before the FFT, or energy smears across bins (spectral leakage) whenever a frequency does not fit a whole number of periods in the block, which is nearly always the case for live game audio. Build the window once with `vDSP.window(ofType:usingSequence:count:isHalfWindow:)` and multiply each block by it. Choice: Hann (`.hanningDenormalized` in the sample) is the general default and tapers to zero; Hamming (`vDSP.WindowSequence.hamming`) separates close frequencies better but does not reach zero at the edges, so low-level leakage remains everywhere; Blackman (`.blackman`) suppresses far leakage best at the cost of a wider main peak. The Swift wrapper `vDSP.FFT(log2n:radix:ofType:)` with `forward(input:output:)` replaces the C setup calls. — /documentation/Accelerate/reducing-spectral-leakage-with-windowing [symbols: vDSP/window(ofType:usingSequence:count:isHalfWindow:), vDSP.WindowSequence.hanningDenormalized, vDSP.WindowSequence.hamming, vDSP.WindowSequence.blackman, vDSP.FFT, vDSP/convert(interleavedComplexVector:toSplitComplexVector:), vDSP/multiply(_:_:)]
- To draw a waveform of a long clip (an editor, a rhythm-game track preview), decimate first with `vDSP.downsample(_:decimationFactor:filter:)` (it wraps `vDSP_desamp`). Make the filter length equal to the decimation factor (for example `[0.5, 0.5]` for factor 2) so every source sample contributes; a one-tap `[1.0]` filter just keeps every Nth sample and can drop peaks. Output length is `(source.count - filter.count) / decimationFactor + 1`. — /documentation/Accelerate/resampling-a-signal-with-decimation [symbols: vDSP/downsample(_:decimationFactor:filter:), vDSP_desamp, vDSP_desampD]
- For real-valued signals where phase does not matter (denoising, compression-style spectral edits), vDSP's DCT is the real-input counterpart: forward is type II and inverse is type III, through `vDSP.DCT(count:transformType:)` + `transform(_:result:)`. Apple calls setup creation expensive and builds both setups once as statics; do the same in a game (never per audio callback). Zero low-magnitude bins with `vDSP.threshold(_:to:with: .zeroFill, result:)`, then rescale the inverse output by dividing by `count / 2`. — /documentation/Accelerate/signal-extraction-from-noise [symbols: vDSP.DCT, vDSP.DCTTransformType.II, vDSP.DCTTransformType.III, vDSP/DCT/transform(_:), vDSP/threshold(_:to:with:result:), vDSP/divide(_:_:)] [gate: sample lists iOS 13]
- For writing float mix output to integer PCM (a capture or export feature), scale to the integer range first, then convert. The plain `vDSP_vfix16` / `vDSP_vfix32` truncate toward zero; the `vDSP_vfixr16` / `vDSP_vfixr32` variants round to nearest, which is the right choice for audio. 24-bit packed output uses `vDSP_vsmfix24` (scale and convert in one pass into `vDSP_int24`). The Swift `vDSP.convertElements(of:to:rounding:)` takes an explicit `vDSP.RoundingMode`; `vDSP.floatingPointToInteger(_:integerType:rounding:)` allocates its result. The page does not say whether out-of-range values saturate, so clamp first. (Page slip: `vDSP_vsmfixu24` is described as "signed" but writes `vDSP_uint24`.) — /documentation/Accelerate/single-precision-floating-point-to-integer-conversion [symbols: vDSP_vfix16, vDSP_vfixr16, vDSP_vfix32, vDSP_vfixr32, vDSP_vsmfix24, vDSP_vsmfixu24, vDSP/convertElements(of:to:rounding:), vDSP.RoundingMode, vDSP/floatingPointToInteger(_:integerType:rounding:)]
