# Notes m05

## command-model.md

- On a Mac with Apple silicon the GPU belongs to two families at once: the Mac 2 family and an Apple family. Use the Mac family check to choose the baseline feature set, and the Apple family check only to unlock TBDR-only features or tile-based optimizations. Where the device has a dedicated property or method for a feature, query it instead of a family. Never infer capability from the GPU name string, and never hardcode per-GPU values, because both break on new hardware. — /documentation/apple-silicon/porting-your-metal-code-to-apple-silicon [symbols: MTLGPUFamily.mac2, MTLDevice.name] [gate: Mac2 + Apple family on Apple silicon]
- A compute encoder in concurrent dispatch mode does no automatic ordering between its dispatches, and an untracked heap gets no hazard tracking. Apple GPUs exploit both aggressively. Missing synchronization therefore surfaces on Apple silicon as wrong ordering, memory corruption, or a GPU fault, even when the same code appeared to work on Intel or AMD Macs. The page points to `memoryBarrier(_:)` and to the resource-synchronization article. (Writer: Metal 4 encoders are untracked by default, so this porting note describes Metal 4's normal case. Confirm that against the command-model sources.) — /documentation/apple-silicon/porting-your-metal-code-to-apple-silicon [symbols: MTLComputeCommandEncoder, memoryBarrier(_:)] [gate: Metal 3 spelling]
- An out-of-bounds device or threadgroup access can count as a hardware fault on an Apple GPU, and that fault ends the command buffer that caused it. A discrete GPU might silently tolerate the same access. Use Shader Validation to find these accesses. — /documentation/apple-silicon/porting-your-metal-code-to-apple-silicon
- Gating idioms for a renderer that has both a Metal 4 path and a Metal 3 path. In Swift: `#available(...)` at the call site and `@available(...)` on declarations. In Objective-C: `@available` and `API_AVAILABLE(...)`. In C, C++, and ObjC: the `TARGET_OS_*` macros from `TargetConditionals.h`. For the Simulator: `#if targetEnvironment(simulator)` in Swift, or `TARGET_OS_SIMULATOR`. `#if canImport(Module)` gates a whole framework. — /documentation/Xcode/running-code-on-a-specific-version [symbols: TARGET_OS_IOS, TARGET_OS_SIMULATOR, API_AVAILABLE]
- The Metal framework landing page now leads with the Metal 4 material: "Understanding the Metal 4 core API", "Drawing a triangle with Metal 4", and "Using the Metal 4 compilation API". The "GPU devices and work submission" collection covers suspending work and coordinating several GPUs. — /documentation/metal
- New top-level Metal symbols are marked available in OS 27 (iOS/macOS/tvOS/visionOS 27.0), and their pages carry no abstract. `MTLContentionRelief` has the cases `.automatic` and `.none`. `MTLForwardProgressUsage` has the cases `.automatic`, `.simdGroupParallel`, and `.weak`. `MTLDeviceError` (struct) and `MTLDeviceErrorDomain` also appear. They are listed so the writer can find them. Their semantics are undocumented, so make no behavioural claims about them. — /documentation/metal [symbols: MTLContentionRelief, MTLForwardProgressUsage, MTLDeviceError, MTLDeviceErrorDomain] [gate: OS 27]
- API Validation's check for unretained resources applies only to `MTLCommandBuffer`. It does not cover `MTL4CommandBuffer`. A Metal 4 app that frees a resource while the GPU still uses it gets no validation error from this check, so the engine must manage that lifetime itself (for example, with deferred release tied to frame completion). — /documentation/xcode/validating-your-apps-metal-api-usage [symbols: MTLCommandBuffer, MTL4CommandBuffer] [gate: Metal 4]
- Shader Validation defines "resource not resident" for Metal 4: a shader or Metal 4 command touches a resource that is in no residency set attached to the command buffer or the queue, and in no `useResource:usage:[stages:]` call. The "usage flag mismatch" check applies only before Metal 4. — /documentation/xcode/validating-your-apps-metal-shader-usage [symbols: MTLResidencySet, useResource:usage:stages:] [gate: Metal 4 vs Metal 3]

## pipelines-and-render-passes.md

- Wrong load and store actions often have no visible effect on Intel Macs, because those GPUs render straight to memory. On Apple GPUs a `dontCare` action really skips the tile load or store, and that shows up as artifacts. Code ported from macOS-only engines often carries these latent bugs. One exception: an app linked against macOS 10.15 or earlier and running under Rosetta has `dontCare` loads forced into real loads, which hides the bug and costs performance. — /documentation/apple-silicon/porting-your-metal-code-to-apple-silicon [symbols: MTLLoadAction.dontCare]
- Multipass techniques need bit-identical positions across different vertex shaders, for example a depth prepass followed by a pass that tests against that depth. Mark the position output `[[position, invariant]]` in every vertex shader involved, then compile with preserve-invariance. Offline, that is the `preserve-invariance` flag. At runtime it is `MTLCompileOptions.preserveInvariance`. In Metal 4 the same `MTLCompileOptions` object arrives through `MTL4LibraryDescriptor.options`. The Apple GPU compiler fuses and reorders floating-point work aggressively, so without invariance you get z-fighting-like artifacts that other GPUs do not show. Under Rosetta, apps linked against 10.15 or earlier get invariance implicitly. — /documentation/apple-silicon/porting-your-metal-code-to-apple-silicon [symbols: MTLCompileOptions.preserveInvariance, MTL4LibraryDescriptor.options] [gate: Metal 4 path via MTL4LibraryDescriptor]
- A texture may not be bound to more than one shader argument if any of those bindings can write to it. Use a single `access::read_write` binding and synchronize. A depth attachment that a pass writes must not also be sampled as a shader input in that pass, because results differ across GPUs. Split the work into separate passes. API Validation catches both cases. — /documentation/apple-silicon/porting-your-metal-code-to-apple-silicon
- Combined depth24/stencil8 exists only on some Mac GPUs. Check the device property (the page links `MTLDevice.isDepth24Stencil8PixelFormatSupported`; the symbol page is not cached, so verify the spelling in the SDK) before choosing `depth24Unorm_stencil8`, and otherwise use `depth32Float_stencil8`. — /documentation/apple-silicon/porting-your-metal-code-to-apple-silicon [symbols: MTLDevice.isDepth24Stencil8PixelFormatSupported]
- For MSAA: with `storeAndMultisampleResolve`, both the multisample texture and the resolve texture are stored. With `multisampleResolve`, the multisample texture is discarded (shown as don't-care) and only the resolve target is stored. On TBDR, prefer `multisampleResolve` with a memoryless MSAA target. — /documentation/xcode/analyzing-resource-dependencies [symbols: MTLStoreAction.storeAndMultisampleResolve, MTLStoreAction.multisampleResolve]
- To find shader-compile hitches at runtime, set `MTL_HUD_ENABLED=1` and `MTL_HUD_LOG_SHADER_ENABLED=1`. The HUD then emits a log line for every shader compilation, with the function name, the compilation time, and a `cached:` flag (0 or 1). The subsystem is `com.apple.metal.hud` and the category is `Logging`. The page does not state the unit of the compile time (its example values are around 5.5M). — /documentation/xcode/monitoring-your-metal-apps-graphics-performance
- Shader Validation instruments shaders live, so it cannot be used together with Metal binary archives. Indirect command buffers work with it only when pipeline and buffer inheritance are enabled. It does not track the residency of pages that back sparse resources. To instrument individual pipelines, set `shaderValidation` to `.enabled` or `.disabled` on the pipeline descriptor (`MTLRenderPipelineDescriptor.shaderValidation`; in Metal 4, `MTL4PipelineOptions.shaderValidation`), and read it back from the pipeline state. — /documentation/xcode/validating-your-apps-metal-shader-usage [symbols: MTLShaderValidation, MTLRenderPipelineDescriptor.shaderValidation, MTL4PipelineOptions.shaderValidation, MTLRenderPipelineState.shaderValidation] [gate: Metal 4 via MTL4PipelineOptions]

## apple-gpu-tbdr.md

- During a pass, Apple GPUs keep attachment contents in on-chip tile memory. The load action decides whether existing contents are copied in, and the store action decides whether the tile is written back. Many tiny passes waste time on those copies. When consecutive logical passes share render targets, merge them into one Metal render pass. This applies to G-buffer plus lighting in a deferred renderer, and to chains of post effects on one target. Inside the merged pass, use programmable blending (reading the current pixel in the fragment shader) and tile shaders, so data stays in tile memory until the pass ends. The reference samples are "Rendering a scene with deferred lighting" and "Rendering a scene with Forward+ lighting using tile shaders". — /documentation/apple-silicon/porting-your-metal-code-to-apple-silicon [gate: Apple family]
- On Apple GPUs, vertex, fragment, and compute work from independent passes run at the same time. When the Performance timeline shows no overlap, suspect over-serialization: unnecessary barriers or dependencies. Use concurrent compute where dispatches touch disjoint resources. Each pass boundary also has a fixed setup cost, which is another reason to avoid many small passes. — /documentation/xcode/analyzing-apple-gpu-performance-using-a-visual-timeline [gate: Apple GPUs only; non-Apple GPUs use counter statistics instead]

## resources-and-memory.md

- A volatile resource (purgeable state set to volatile) does not count toward the app's memory footprint, which lowers the jetsam risk on iOS. If you might need a resource again but do not need it now, mark it volatile instead of releasing it. You then rebuild its contents only if Metal actually purges them. The Memory viewer's "Time Since Last Bound" and "Use" columns find candidates. — /documentation/xcode/analyzing-memory-usage [symbols: MTLResource.setPurgeableState(_:), MTLPurgeableState]
- Compare a buffer's `length` with its `allocatedSize`: Metal can round small allocations up. Merge many small buffers that are used together into one buffer, or suballocate them from an `MTLHeap`. That saves memory and also cuts dependency-tracking work. Restrict `MTLTexture.usage` to what you actually use, because tighter usage permits more optimization (the viewer also shows whether lossless compression applies). Use the Storage Mode breakdown to spot too much `.shared` or `.managed`. — /documentation/xcode/analyzing-memory-usage [symbols: MTLBuffer.length, MTLResource.allocatedSize, MTLTexture.usage, MTLHeap, MTLStorageMode.shared, MTLStorageMode.managed]
- An ICB's reported `size` excludes commands that have been reset. Size the ICB to the number of commands you expect to encode. — /documentation/xcode/analyzing-memory-usage [symbols: MTLIndirectCommandBuffer.size]
- In Instruments, the Allocations track omits `.private` Metal resources. It shows only shared and managed. Metal allocations appear under the `VM: IOAccelerator` category and drawables under `VM: IOSurface`. The system charges compressed or swapped dirty memory against the app at its uncompressed size, so compression does not save you from footprint limits. Footprint is dirty memory plus compressed or swapped memory, which VM Tracker shows. — /documentation/xcode/analyzing-the-memory-usage-of-your-metal-app
- In an untracked heap, Metal neither tracks resource dependencies nor orders the commands that touch them. Synchronize with fences or barriers, or Apple GPUs will reorder the commands and corrupt memory. — /documentation/apple-silicon/porting-your-metal-code-to-apple-silicon [symbols: MTLHeap, MTLFence] [gate: Metal 3 spelling]

## shading-language.md

- SIMD-group width varies across GPUs, Mac GPUs especially. Never hardcode 32. On the host, read `threadExecutionWidth` from the compute pipeline state after you create it. In the shader, take a `[[threads_per_simdgroup]]` argument. — /documentation/apple-silicon/porting-your-metal-code-to-apple-silicon [symbols: MTLComputePipelineState.threadExecutionWidth, threads_per_simdgroup]
- Barriers are mandatory even when the threadgroup is exactly one SIMD-group wide. Apple GPUs reorder memory operations aggressively, so a missing barrier corrupts data. Use `threadgroup_barrier(...)` across the threadgroup and `simdgroup_barrier(...)` within a SIMD-group. The page has three spelling and cross-reference errors. It shows the shorthand `threadgroup_barrier(mem_device)`, while the MSL 4.1 spec spells the flag `mem_flags::mem_device`. Its code shows `simd_barrier(mem_threadgroup)`, but MSL 4.1 has no `simd_barrier`; the function is `simdgroup_barrier`. It also cites MSL section 6.8.1 for barriers, but in MSL 4.1 the synchronization functions are section 6.10.1, and 6.8.1 is now SIMD-group matrix loads. — /documentation/apple-silicon/porting-your-metal-code-to-apple-silicon [symbols: threadgroup_barrier, simdgroup_barrier, mem_flags::mem_device, mem_flags::mem_threadgroup]
- The MSL 4.1 spec is 383 pages and dated 2026-06-04. A feature being present in MSL does not mean every GPU supports it. Check the Metal Feature Set Tables for each feature. Unless the spec marks a feature otherwise, it has been available on iOS and macOS since Metal 1. In the spec, "X.Y" means Metal version X.Y. — pdf:msl-4.1#front
- A section map of MSL 4.1 from the table of contents, for writers who need to find things. Compiler options: 1.6.x. This includes invariance (1.6.4), maximum total threadgroup size (1.6.6), texture write rounding mode (1.6.7), modules (1.6.8), logging (1.6.9), language version (1.6.10), the warning about missing address spaces (1.6.11), target conditionals (1.6.13), dynamic library linking (1.6.14), compiling to GPU binaries (1.6.15), and library symbol files (1.6.16). Address spaces: chapter 4. This includes SIMD-groups and quad-groups (4.4.1), threadgroup imageblock (4.5), ray data (4.6), object data (4.7), and memory coherency (4.8). Function kinds: 5.1.1 to 5.1.9. Tile functions are 5.1.9 and raster order groups are 5.2.1.2. Imageblocks: 5.6 and 6.14. Function constants: 5.8. Synchronization: 6.10.1. SIMD-group functions: 6.10.2. Quad-group functions: 6.10.3. Atomics and memory order: 6.16. ICB encoding from shaders: 6.17. Variable rasterization rate: 6.18. Ray tracing: 2.17 and 6.19. Mesh types: 2.20. Tensors and cooperative tensors: 2.22. Logging: 6.20. Metal Performance Primitives (MatMul2D, Convolution2d): chapter 7. Numerical accuracy, including fast math and half precision: chapter 8 (Tables 8.1 to 8.5). — pdf:msl-4.1#front
- Placement new is new in Metal 4.1 (sections 1.5.4 and 6.2). Section 1.3, on page 11 just past this row, also lists an option to make float-to-float conversions round toward zero (1.6.3). That option probably pairs with the new host enum `MTLFloatingPointConversionRoundingMode` (`.towardZero`, `.toNearestEven`), but no page states the link, so verify it. — pdf:msl-4.1#front [symbols: MTLFloatingPointConversionRoundingMode] [gate: Metal 4.1]

## compute-and-gpu-driven.md

- If a render pass needs results from a compute pass before its commands can be encoded, do not stall the CPU waiting for them. Build the draws on the GPU into an indirect command buffer, so the CPU and GPU keep overlapping. — /documentation/xcode/analyzing-the-performance-of-your-metal-app [symbols: MTLIndirectCommandBuffer]
- MPS still ships image filters, CNN and RNN kernels, matrix and NDArray kernels (including int4 and LUT dequantize, and quantized matmul), `MPSSVGF`/`MPSSVGFDenoiser` (a ray-tracing denoiser), and `MPSTemporalAA`. The MPS ray-tracing classes are deprecated: `MPSRayIntersector` is marked iOS 12–17 and macOS 10.14–14, so use Metal's own acceleration structures instead. MPS kernels encode into an `MTLCommandBuffer` (the Metal 3 type). `MPSSupportsMTLDevice(_:)` gates support. Device-capability constants include `MPSDeviceSupportsSimdgroupBarrier`, `MPSDeviceSupportsQuadShuffle`, and `MPSDeviceSupportsBFloat16Arithmetic`. — /documentation/metalperformanceshaders [symbols: MPSSVGFDenoiser, MPSTemporalAA, MPSRayIntersector, MPSSupportsMTLDevice(_:), MPSCommandBuffer, MPSNDArrayQuantizedMatrixMultiplication]
- MPSGraph compiles a symbolic tensor graph into an `MPSGraphExecutable`. The executable can target the GPU, the CPU, or the Neural Engine, and it can be serialized to and loaded from a `.mpsgraphpackage`. That lets you skip graph compilation at game launch. `MPSGraphExecutionStage` exposes execution events for use with shared events. `MPSGraphSDPADescriptor` (scaled dot-product attention) and `MPSGraphReducedPrecisionFastMath` exist. Use it for ML inference that is not a per-frame shader. — /documentation/metalperformanceshadersgraph [symbols: MPSGraph, MPSGraphExecutable, MPSGraphExecutableSerializationDescriptor, MPSGraphExecutionStage, MPSGraphSDPADescriptor]
- The Metal landing page lists "Machine learning passes" as an encoder category next to render, compute, blit, ICB, and ray tracing. It also lists tensor plane types: `MTLTensorPlaneType` (`.data`, `.scales`), `MTLTensorAuxiliaryPlaneDescriptor`, and `MTLTensorBufferAttachments`. These are multiplane, block-scaled tensors, available in OS 27. — /documentation/metal [symbols: MTLTensorPlaneType, MTLTensorAuxiliaryPlaneDescriptor, MTLTensorBufferAttachments, MTLTensorAuxiliaryPlaneDescriptorMap] [gate: OS 27]

## display-and-upscaling.md

- MetalFX modes: the temporal scaler (needs color, depth, and motion vectors) and the spatial scaler (color only). Both have Metal 4 variants: `MTL4FXTemporalScaler` and `MTL4FXSpatialScaler`. The frame interpolator is `MTLFXFrameInterpolatorDescriptor` → `MTLFXFrameInterpolator`/`MTL4FXFrameInterpolator`; a scaler that can feed it conforms to `MTLFXFrameInterpolatableScaler`. The temporal denoised scaler is `MTLFXTemporalDenoisedScalerDescriptor` → `MTLFXTemporalDenoisedScaler`/`MTL4FXTemporalDenoisedScaler`. Effects are expensive to create, so build them at launch or on a display-resolution change, then reuse them every frame. — /documentation/metalfx [symbols: MTLFXTemporalScaler, MTLFXSpatialScaler, MTL4FXTemporalScaler, MTL4FXSpatialScaler, MTLFXFrameInterpolatorDescriptor, MTL4FXFrameInterpolator, MTLFXTemporalDenoisedScalerDescriptor, MTL4FXTemporalDenoisedScaler, MTLFXFrameInterpolatableScaler]

They give `MTLFXTemporalDenoisedScalerDescriptor` as iOS 18 (sic), macOS 26, and tvOS 27.1. Gate MetalFX on tvOS at 27.1 and use the per-symbol availability, not the framework page. — /documentation/metalfx [gate: frame interpolator and MTL4FX iOS/macOS 26, tvOS 27.1]
- MetalKit offers `MTKView`/`MTKViewDelegate` for view management, `MTKTextureLoader`, and the Model I/O bridge classes (`MTKMesh`, `MTKSubmesh`, `MTKMeshBuffer`, `MTKMeshBufferAllocator`). — /documentation/metalkit [symbols: MTKView, MTKViewDelegate, MTKTextureLoader, MTKMesh, MTKMeshBufferAllocator]
- Core Animation's frame-pacing types: `CADisplayLink`, `CAMetalDisplayLink` (with `CAMetalDisplayLink.Update` and `CAMetalDisplayLinkDelegate`), `CAMetalLayer`, `CAMetalDrawable`, `CAEDRMetadata` (EDR tone-mapping metadata), and `CACurrentMediaTime()`. ## gpu-debugging-and-profiling.md

- `gpudebug` is a terminal REPL over a `.gputrace`. Start it with `gpudebug -t <trace>` to open a numbered session. The REPL answers immediately while the replayer loads in the background: `list` and `go` work right away, and replay-backed commands such as `info pipeline` and `fetch` block until replay is ready. The tree root has four children: `commands`, `performance`, `api_calls`, and `resources`. Paths look like `commands/cb1/re0/grp0/draw6`, where debug groups appear as `grpN`. The verbs are `go`, `list` (`list N-M`, `list --all`), `info`, `info pipeline` (entry points, attachment formats, vertex layout), `fetch <attachment>` (writes a PNG), and `prev`/`next`. In `api_calls`, `go :d` jumps to the draw and `go :a` jumps back to the API call. The full reference is `man gpudebug`. — /documentation/xcode/debugging-with-interactive-command-line-tools
- `gpudebug` sessions outlive the connection. `exit` detaches, `gpudebug -s <id>` reattaches, and `exit --terminate` (or `gpudebug --terminate <id>`) ends a session. `gpudebug --list-devices` lists replay targets, and `-d <id>` replays on a remote device, which requires Xcode to be running for device discovery. Replay is local by default. — /documentation/xcode/debugging-with-interactive-command-line-tools
- Agent workflow: Apple's own advice is to give an agent `man gpudebug` and a `.gputrace`, because every node lists its children and actions, so an agent can discover the trace without knowing its shape. Create one session and reuse it with `gpudebug -s <id> -c "<cmd>" -c "<cmd>"`, since loading a trace and starting the replayer can take seconds to minutes. `--oneshot -t <trace> -c ...` creates a session, runs the commands, and tears it down, paying the full load cost on every call. — /documentation/xcode/investigating-gpu-issues-with-ai-agents
- Programmatic capture. Enable it with `MetalCaptureEnabled` = YES in Info.plist, or on macOS 14 and later with the env var `MTL_CAPTURE_ENABLED=1`. Enabling capture costs a little CPU time, so drive the key from a build setting and keep it out of release builds. Set `MTLCaptureDescriptor.captureObject` to a device, a queue, or an `MTLCaptureScope`. For a file, use `destination = .gpuTraceDocument` with an `outputURL` ending in `.gputrace`, after checking `supportsDestination(.gpuTraceDocument)`. Only command buffers created after the capture starts and committed before it stops are recorded. A capture may span several frames. The page's examples use `MTLCommandQueue`, but `MTLCaptureManager` also has `makeCaptureScope(commandQueue: any MTL4CommandQueue)` for Metal 4. — /documentation/xcode/capturing-a-metal-workload-programmatically [symbols: MTLCaptureManager, MTLCaptureDescriptor.captureObject, MTLCaptureDestination.gpuTraceDocument, MTLCaptureManager.supportsDestination(_:), MTLCaptureScope.begin(), MTLCaptureScope.end(), MTLCaptureManager.makeCaptureScope(commandQueue:)] [gate: MTL_CAPTURE_ENABLED macOS 14+; MTL4 scope overload]
- API Validation env vars. `MTL_DEBUG_LAYER=1` turns it on. `MTL_DEBUG_LAYER_ERROR_MODE` is `assert` (default), `ignore`, or `nslog`. `MTL_DEBUG_LAYER_WARNING_MODE` is `assert`, `ignore` (default), `nslog`, or `oslog`. `MTL_DEBUG_LAYER_VALIDATE_LOAD_ACTIONS=1` turns `dontCare` loads into fuchsia clears, and `MTL_DEBUG_LAYER_VALIDATE_STORE_ACTIONS=1` writes a red and white checkerboard into `dontCare` stores; together they make wrong load and store assumptions visible. `MTL_DEBUG_LAYER_VALIDATE_UNRETAINED_RESOURCES` is a bitfield: 0x1 (default) tags unretained bound objects, 0x2 tags retained ones, and 0x4 errors at deallocation time instead of at commit. Validation has a small CPU cost. The full list is in `man MetalValidation`. — /documentation/xcode/validating-your-apps-metal-api-usage
- Shader Validation env vars: `MTL_SHADER_VALIDATION=1`, `..._REPORT_TO_STDERR=1`, and `..._ABORT_ON_FAULT=1`. Use abort-on-fault when repeated GPU restarts make the system unresponsive. `..._FAIL_MODE` is `zerofill` (default: invalid reads return 0 and invalid writes are dropped) or `allow` (cheaper, but the command buffer may fail). `..._GLOBAL_MEMORY`, `..._THREADGROUP_MEMORY`, and `..._TEXTURE_USAGE` add checks. `..._STACK_OVERFLOW` checks indirect and recursive calls against `maxCallStackDepth`. `..._TENSOR_VALIDATION`, `..._GENERIC_ADDRESS_SPACE`, and `..._NAN_INF` default to 1. `..._COMPILER_INLINING` is `default` or `full`. Output goes to the OS log by default, which you read with `log stream -process <app>`. These variables work on any app, even without its source. — /documentation/xcode/validating-your-apps-metal-shader-usage
- Selective Shader Validation keeps a large game playable while it runs. Set `MTL_SHADER_VALIDATION_DEFAULT_STATE` to `all` or `none`, then list pipelines in `MTL_SHADER_VALIDATION_ENABLE_PIPELINES` or `..._DISABLE_PIPELINES`, as comma-separated labels or UIDs with no spaces. Print UIDs with `MTL_SHADER_VALIDATION_DUMP_PIPELINES=1`, and turn on Include Debug Messages in Console to see them. Shader Validation slows the GPU and lengthens runtime compiles. Set the deployment target to the OS you run on, even temporarily, to get the newest diagnostics. — /documentation/xcode/validating-your-apps-metal-shader-usage
- Shader Validation also covers newer cases: misuse of Metal Performance Primitives tensors (rank, alignment, stride, plane), INF or NaN written to interpolants other than `[[position]]`, an illegal cast from the generic address space, and a wrong acceleration-structure kind. Starting with `MTLGPUFamilyApple10`, binding a texture array to a slot that expects a plain texture is legal, and so is the reverse. — /documentation/xcode/validating-your-apps-metal-shader-usage [symbols: MTLGPUFamily.apple10] [gate: Apple10]
- The Metal Performance HUD: `MTL_HUD_ENABLED=1`, `MTL_HUD_LOG_ENABLED=1` for per-frame console stats, `MTL_HUD_ENCODER_TIMING_ENABLED=1` for per-encoder GPU time and a timeline of the last three frames plus top labeled command buffers and encoders, and `MTL_HUD_SHOW_VALUE_RANGE=1` for the average over 120 frames and the min/max over 1200 frames. Other ways to turn it on: Info.plist `MetalHudEnabled`, the user default `MetalHUDForceEnabled=1`, the scheme options Show and Log Graphics Overview (logging requires both), or on iOS, iPadOS, and tvOS the Developer settings → Graphics HUD (needs a development profile). The HUD header shows whether the present mode is direct or composited, and whether Game Mode is on. Encoder timing is unavailable if the app itself uses counter sample buffers. The per-second log line format is `metal-HUD: <frame>,<gfx mem>,<proc mem>,<present interval>,<gpu time>,...`. — /documentation/xcode/monitoring-your-metal-apps-graphics-performance
- Performance heat maps and the shader cost graph require A17 Pro or later, or M3 or later. Heat maps work for render encoders, render pipelines, and compute dispatches, but not compute encoders or compute pipeline states. They cover fragment shaders (pixel = fragment) and object, mesh, and compute shaders (pixel = thread; past 8192 threads on x or y, each pixel becomes one SIMD-group). The heat map kinds are Shader Execution Cost, ALU Cost, Non-ALU Cost, Thread Divergence, Control Flow Divergence, Inactive Threads, Overdraw, Instruction Count, Raytracing Latency, and Draw ID. Selecting a pixel shows that SIMD-group's execution history. The shader cost graph works per pipeline state only: it is a flame graph with per-line cost, instruction-type, and data-type (Float16/Float32/Integer/Bits) breakdowns. Divergence = 1 − active / total instructions. — /documentation/xcode/analyzing-apple-gpu-performance-using-performance-heatmaps-a17-m3; /documentation/xcode/analyzing-apple-gpu-performance-using-shader-cost-graph-a17-m3 [gate: A17 Pro / M3+]
- The Performance timeline exists only for Apple GPUs; non-Apple GPUs get counter statistics instead. It has Vertex, Fragment, and Compute tracks with per-shader waterfalls, plus counter tracks for Occupancy, Limiter/Utilization, and Read/Write Bandwidth. A shader's sidebar shows its Max Theoretical Occupancy. To compare passes in isolation, the Metal debugger can profile at a forced GPU performance state and in Serial instead of Concurrent execution mode. Serial gives precise per-pass numbers but does not match runtime behaviour. Export with "Embed performance data" to open the profile on any Mac without replay. Shader edits made through Reload Shaders are not written back to your source. — /documentation/xcode/analyzing-apple-gpu-performance-using-a-visual-timeline; /documentation/xcode/optimizing-gpu-performance
- In the Dependencies viewer, solid edges mean data flow and dashed edges mean synchronization only. For example, a pass that clears on load has no data dependency but must still wait. Viewer modes are All, Synchronization, and Data Flow. Unused resources in the frame show up as wasted work. The Memory viewer exports CSV (Editor > Export Memory Report) and offers Insights. Both are GUI-only. — /documentation/xcode/analyzing-resource-dependencies; /documentation/xcode/analyzing-memory-usage

## cpp-and-rust.md

- An External Build Tool target or an Aggregate target cannot contain a Compile Sources phase or a Link Binary With Libraries phase. A cargo/CMake/make target therefore builds only the artifact. A separate app target must depend on it and link or embed the output. — /documentation/Xcode/customizing-the-build-phases-of-a-target
- Xcode's Find Implicit Dependencies cannot see a target that consumes files a script produced in another target. Add the dependency explicitly under Target Dependencies, or Xcode may build out of order or with stale output. For a separate project (for example, a generated CMake Xcode project), drag that project into the navigator first so that dependencies are tracked. — /documentation/Xcode/configuring-a-new-target-in-your-project; /documentation/Xcode/improving-the-speed-of-incremental-builds
- Run Script phases. A script with no declared inputs or outputs runs on every build, and it runs serially with respect to other tasks. Declare at least one input and one output, or `.xcfilelist` files, so the build system can skip the script and schedule it correctly. The available environment variables are `SCRIPT_INPUT_FILE_n`, `SCRIPT_OUTPUT_FILE_n`, `SCRIPT_INPUT_FILE_LIST_n`, their `_COUNT` forms, `BUILT_PRODUCTS_DIR`, and every build setting. For cargo, which does its own incremental checks, running every time may be acceptable, but it serializes the build. Emit `<abs path>:<line>: error|warning|note: <msg>` lines so that cargo or compiler diagnostics appear in Xcode's Issue navigator. A nonzero exit fails the build. Quote variables, because paths contain spaces. — /documentation/Xcode/running-custom-scripts-during-a-build; /documentation/Xcode/improving-the-speed-of-incremental-builds
- Use a build rule, not a Run Script, when files can be processed one at a time (for example, a shader cross-compiler or an asset cooker). Each file becomes its own parallel task. The rule matches with `fnmatch` patterns against the full path, and the first matching rule wins. It uses `SCRIPT_INPUT_FILE`, `INPUT_FILE_BASE`, `INPUT_FILE_NAME`, `INPUT_FILE_DIR`, `INPUT_FILE_PATH`, and `DERIVED_FILE_DIR`. Put outputs in `DERIVED_FILE_DIR`, or clean builds will miss them. Without declared outputs, the rule reruns on every build. Turn on "Use discovered dependency file" and write makefile-format dependency rules so that include changes trigger rebuilds. — /documentation/Xcode/creating-build-rules-for-custom-file-types
- Swift C++ interop does not support explicitly built modules, which are the Xcode 16 and later default for C, ObjC, and Swift. A Swift target that uses C++ interop to call into a C++ engine or metal-cpp therefore falls back. Turn the behaviour on or off with the "Explicitly Built Modules" build setting. Targets that differ only in Preprocessor Macros cannot share module builds. Product > Perform Action > Build With Timing Summary (or `xcodebuild -showBuildTimingSummary`) reports module variants and their differing options. — /documentation/Xcode/building-your-project-with-explicit-module-dependencies; /documentation/Xcode/improving-the-speed-of-incremental-builds
- Build-setting precedence, highest first: settings passed to `xcodebuild` on the command line, the target level, the xcconfig mapped to the target, the project level, the xcconfig mapped to the project, and finally the system defaults. The Levels view shows the resolved value. — /documentation/Xcode/configuring-the-build-settings-of-a-target [symbols: ONLY_ACTIVE_ARCH]
- For C, C++, and ObjC code, Apple frameworks such as Metal, QuartzCore, and Foundation link automatically only when `CLANG_MODULES_AUTOLINK` is on (the default) and the code imports modules. Add third-party and Rust static libraries to Link Binary With Libraries explicitly. Embed dylibs with a Copy Files phase (destination Frameworks or Executables), which also signs them. Swift links Apple frameworks automatically. — /documentation/Xcode/customizing-the-build-phases-of-a-target [symbols: CLANG_MODULES_AUTOLINK, APPLY_RULES_IN_COPY_FILES]
- Debug Swift app targets now link the app's code into `<App>.debug.dylib` behind a small stub executable, so that Previews works. This happens when `ENABLE_DEBUG_DYLIB` defaults to YES: the target is a bundled executable, `SWIFT_VERSION` is set, and optimization is `-Onone`. Tooling that scans the main binary for symbols or custom Mach-O sections will miss them in debug builds; Rust crates such as `inventory` or `linkme`, which register through linker sections, are an example (this is an inference). Set `ENABLE_DEBUG_DYLIB=NO` on that target only, at the cost of Previews. — /documentation/Xcode/understanding-build-product-layout-changes [symbols: ENABLE_DEBUG_DYLIB]
- Mergeable libraries (Xcode 15 and later): set `MERGED_BINARY_TYPE=automatic` on the app target. Release builds then merge the dylibs of directly dependent framework targets into the app binary, giving launch speed close to static linking, and debug builds keep ordinary dylibs. Indirect or prebuilt dependencies need `MERGEABLE_LIBRARY=YES` or a manual setup. `IS_UNOPTIMIZED_BUILD` marks debug builds. This is an option when an engine is split into several frameworks. — /documentation/Xcode/configuring-your-project-to-use-mergeable-libraries [symbols: MERGED_BINARY_TYPE, MERGEABLE_LIBRARY, MAKE_MERGEABLE, IS_UNOPTIMIZED_BUILD]
- If you ship a C or C++ engine as a framework, the module verifier (Xcode 14.3 and later) flags these problems: imports inside `extern "C"`, quoted includes in framework headers, `@import` in headers, non-modular includes, and a missing `#include <TargetConditionals.h>` before `TARGET_OS_*`. Set `DEFINES_MODULE` and import with `<Framework/Header.h>` so that the module cache is used. Keep the bridging header minimal. — /documentation/Xcode/identifying-and-addressing-framework-module-issues; /documentation/Xcode/improving-build-efficiency-with-good-coding-practices; /documentation/Xcode/improving-the-speed-of-incremental-builds [symbols: DEFINES_MODULE]
- The Enhanced Security capability is risky for a C++ or Rust engine. `ENABLE_CPLUSPLUS_BOUNDS_SAFE_BUFFERS=YES` turns on fast libc++ hardening and also makes unsafe raw-pointer indexing, pointer arithmetic, and two-argument `std::span` construction into errors. That breaks most engine and metal-cpp code that touches buffer `contents()`. Override it per file with `_LIBCPP_HARDENING_MODE` (`_NONE`, `_FAST`, `_EXTENSIVE`, `_DEBUG`), defined before any std include, or set the setting to NO. The capability also brings arm64e pointer authentication (`ENABLE_POINTER_AUTHENTICATION`), typed allocators (`CLANG_ENABLE_CPLUSPLUS_TYPED_ALLOCATOR_SUPPORT`, which affects custom allocator wrappers), stack zero-init (`CLANG_ENABLE_STACK_ZERO_INIT`), `-Wshadow`, and `ENABLE_SECURITY_COMPILER_WARNINGS`. `-fbounds-safety` for C is optional, through `ENABLE_C_BOUNDS_SAFETY`. — /documentation/Xcode/enabling-enhanced-security-for-your-app [symbols: ENABLE_CPLUSPLUS_BOUNDS_SAFE_BUFFERS, _LIBCPP_HARDENING_MODE, ENABLE_POINTER_AUTHENTICATION, CLANG_ENABLE_C_TYPED_ALLOCATOR_SUPPORT, CLANG_ENABLE_CPLUSPLUS_TYPED_ALLOCATOR_SUPPORT, CLANG_ENABLE_STACK_ZERO_INIT, ENABLE_C_BOUNDS_SAFETY]
- With the platform-restrictions entitlement, crash reporters or engine code that use raw Mach APIs crash with `EXC_GUARD` / `GUARD_TYPE_MACH_PORT`. That covers setting exception ports with `EXCEPTION_DEFAULT`, calling `thread_set_state`, or moving task or thread control ports to another process. Allowed exception behaviours are `EXCEPTION_IDENTITY_PROTECTED`, `EXCEPTION_STATE`, and `EXCEPTION_STATE_IDENTITY_PROTECTED`, and the handler converts the token with `task_identity_token_get_task_port`. Check third-party crash SDKs before adopting it. — /documentation/Xcode/conforming-to-mach-ipc-security-restrictions [symbols: thread_set_state, EXCEPTION_IDENTITY_PROTECTED]

You must Accept Change in the Issues navigator, after confirming the change with the vendor. — /documentation/Xcode/verifying-the-origin-of-your-xcframeworks

Filter C++ or Rust sources and libraries per platform in Compile Sources and Link Binary With Libraries. ## apple-games/game-loop-and-threading.md

- Apple recommends priority 45 for rendering threads. Set it with `pthread_attr_setschedparam` on the attribute before `pthread_create`. Starvation shows as orange spikes in System Load (more runnable threads than cores) and as the render thread in the Preempted state. Fewer threads plus a higher priority fixes it. See the tech talk "Tune CPU job scheduling for Apple silicon games". — /documentation/xcode/analyzing-the-performance-of-your-metal-app [symbols: pthread_attr_setschedparam, pthread_create]
- Frame-pacing diagnosis in Game Performance: a stutter is a Display interval that is much longer than its neighbours. Vsync interval can be about 4 ms on high-refresh displays, and a steady 20 ms (50 fps) is healthy, so consistency is the metric. If the GPU is idle in the gap, the CPU is the cause. A healthy render thread spends a large share of each interval blocked (about 75% in Apple's example), and a render thread that is rarely blocked means the CPU is overcommitted. — /documentation/xcode/analyzing-the-performance-of-your-metal-app
- A SwiftUI game shares one `App` across platforms in a multiplatform target. Use separate targets when the Mac uses AppKit and iOS uses UIKit. Gate platform-only frameworks with `#if canImport(...)` and APIs with `#if os(...)`. — /documentation/Xcode/configuring-a-multiplatform-app-target
