## apple-games/game-loop-and-threading.md

- For core-topology guidance (how many P vs E cores, cache sharing, how to place job-system workers on an asymmetric chip), the authoritative source is the gated Apple Silicon CPU Optimization Guide download, not a public page. — /documentation/Apple-Silicon/cpu-optimization-guide
- Saving game state when the app is backgrounded (iOS/iPadOS): wrap the save in `beginBackgroundTask(withName:expirationHandler:)` and always call `endBackgroundTask(_:)`; the system grants a bounded window, and an unended task gets the app terminated. Use the expiration handler to abandon or defer the write. Long transfers go to a background `URLSession`, not a background task. — /documentation/BackgroundTasks/choosing-background-strategies-for-your-app [symbols: UIApplication.beginBackgroundTask(withName:expirationHandler:), UIApplication.endBackgroundTask(_:)]
- Deferred heavy work (e.g. shader-cache warming, asset re-transcode, database compaction) belongs in `BGProcessingTask`, which the system runs at low-activity times such as overnight on charge; short periodic refresh is `BGAppRefreshTask` via `BGAppRefreshTaskRequest`, with up to 30 s of runtime, ended by `setTaskCompleted(success:)` or the app is killed. — /documentation/BackgroundTasks/choosing-background-strategies-for-your-app [symbols: BGProcessingTask, BGAppRefreshTask, BGAppRefreshTaskRequest, BGTask.setTaskCompleted(success:)]
- Launch-time trap for engines that load everything before drawing: iOS's watchdog kills an app that has not put its first frame on screen within a wall-clock allowance (`scene-create`; the page's example shows 19.97 s) or that stops updating the screen because the main thread is busy (`scene-update`), with code `0x8badf00d`, namespace SPRINGBOARD. "scene" there means any drawn content, not `UIScene`. Present a loading frame first and load models, large JSON, or level data off the main thread. — /documentation/Xcode/addressing-watchdog-terminations
- Reading the watchdog report: the crashed main-thread backtrace shows what was running at the kill, not necessarily what consumed the budget (a 4 s step that finished does not appear). "Elapsed application CPU time" high means the app was working across all threads; low means it was blocked waiting (network, I/O). — /documentation/Xcode/addressing-watchdog-terminations
- Frame pacing: a steady lower rate beats a higher rate that sometimes misses, because every missed deadline is a hitch. Start the next frame's work on the vsync callback of a display link so the full interval is available. The page names `CADisplayLink` and `CVDisplayLink`; contradiction: the macOS SDK header marks all of `CVDisplayLink` deprecated in macOS 15.0 with the message "use NSView.displayLink(target:selector:), NSWindow.displayLink(target:selector:), or NSScreen.displayLink(target:selector:)", so on macOS use the `CADisplayLink` vended by those methods. — /documentation/Xcode/improving-app-responsiveness [symbols: CADisplayLink, NSView.displayLink(target:selector:), NSWindow.displayLink(target:selector:), NSScreen.displayLink(target:selector:)] [gate: CVDisplayLink deprecated macOS 15.0]
- Swift-concurrency trap for a game's main-actor code: `Task { syncHeavyWork() }` created in a `@MainActor` context (e.g. SwiftUI `body`, a button action) still runs on the main actor and only postpones the hang. Either make the work a `nonisolated async` function and `await` it, or use `Task.detached`; a detached task inherits no priority and defaults to `.medium`, so pass a priority explicitly. Do not make the main thread join or synchronously wait on a worker. — /documentation/Xcode/improving-app-responsiveness [symbols: Task.detached(name:priority:operation:), MainActor]
- Prefer the system pools (Swift concurrency, Dispatch, `OperationQueue`) to a hand-rolled thread per job; more runnable threads mean every thread, the main thread included, gets less core time. — /documentation/Xcode/improving-app-responsiveness
- On entering the background (or screen lock), release view-side content that can be rebuilt: Apple names images, video, and SceneKit scenes; for a game that means render targets, streamed textures, and scene caches, rebuilt on return to foreground. A small suspended footprint makes the game less likely to be jetsammed while away. Also bound any accumulating cache (it will not show in Leaks). — /documentation/Xcode/making-changes-to-reduce-memory-use
- Level loads that allocate a big block at once can be killed before the low-memory warning ever arrives: warnings are best effort, and when demand rises faster than warnings relieve it the system jetsams directly. Grow large allocations gradually (stream the level in) so the system has time to reclaim memory elsewhere. Warning channels: `applicationDidReceiveMemoryWarning(_:)`, `UIViewController.didReceiveMemoryWarning()`, `UIApplication.didReceiveMemoryWarningNotification`, and a dispatch source of type `DISPATCH_SOURCE_TYPE_MEMORYPRESSURE` (the one an engine core without UIKit can use). On a warning, drop known caches; do not walk the whole object graph looking for things to free, because touching cold pages pulls them out of the memory compressor and raises demand. — /documentation/Xcode/responding-to-low-memory-warnings [symbols: DISPATCH_SOURCE_TYPE_MEMORYPRESSURE, UIApplicationDelegate.applicationDidReceiveMemoryWarning(_:)]
- Hang detection is a main-run-loop measurement: the system and tools time the busy span between two "waiting for events" periods; most Apple tools report once that span passes 250 ms (the Hangs instrument lets you lower it). The main dispatch queue, main `OperationQueue`, and the main actor are all clients of the main `RunLoop`, so one long item on any of them blocks the others and blocks input delivery. Implication for a game (inference, not a page claim): an engine that spins its own `while` loop on the main thread instead of returning to the run loop starves UIKit/AppKit/Game Controller event delivery and reads to the system as one continuous hang; drive frames from a display-link callback or a render thread so the run loop sleeps between frames. — /documentation/Xcode/understanding-hangs-in-your-app [symbols: RunLoop, MainActor]
- Apple's stated perceptual rule for frame pacing: inconsistent latency is far more visible than slightly longer constant latency (a constant 50 ms lag on a drag is hard to see; a stall-then-jump is obvious), and Apple's own devices trade a little latency for smooth motion. So pace to a steady interval before chasing minimum input latency, except for direct-manipulation cases like Pencil drawing where both matter. Hang threshold ~50–100 ms+; hitch threshold one refresh interval (8–16 ms). Hitches are only detected when something triggers a screen update, which a continuously rendering game always does, so a game exposes every late frame to hitch reporting; hangs are "potential" hangs measured on the run loop even with no user input. Fix hangs first: they are easier and often remove hitch sources. — /documentation/Xcode/understanding-user-interface-responsiveness
- Job-system design on asymmetric cores: Apple advises dynamic task allocation over static thread pools, because the scheduler places threads on cores of different types and speeds, so evenly pre-split work finishes unevenly and leaves threads idle while others catch up. For a game, that argues for fine-grained jobs with work stealing (or Dispatch/Swift concurrency) rather than one fixed slice per worker per frame; tag background work with an appropriate `DispatchQoS`. Apple's companion page is "Tuning your code's performance for Apple silicon". — /documentation/xcode/addressing-cpu-bottlenecks [symbols: DispatchQoS]
- Priority-inversion rule that touches every frames-in-flight throttle: `dispatch_semaphore_wait` and `dispatch_group_wait` cannot pass the waiter's priority to the thread that will signal, so the system cannot resolve an inversion through them, and Thread Performance Checker flags QoS mismatches across them. Apple's precautions: do not use them to fake synchronous calls over async APIs; where a wait is unavoidable, the waiting thread's QoS must be the same as or lower than the signaler's, and queues/`OperationQueue`s should get an explicit QoS at creation. A render thread at high QoS that waits on a semaphore signaled from a lower-QoS context is the shape to check (writer: verify how apple-metal's frames-in-flight pattern signals, and which thread runs Metal completion handlers, before asserting either way). — /documentation/Xcode/diagnosing-performance-issues-early [symbols: dispatch_semaphore_wait, dispatch_group_wait, DispatchSemaphore, DispatchQoS.userInteractive]
- Non-UI main-thread work Apple names: synchronous file or device I/O (use a serial queue and post completion to main), synchronous networking, and `AVCaptureSession.startRunning()`. — /documentation/Xcode/diagnosing-performance-issues-early [symbols: AVCaptureSession.startRunning()]
- Latency arithmetic for input-to-photon on the system render loop (render-loop basics are already in responsiveness-hangs-and-hitches.md; this is the game-latency delta): double-buffer mode is three vsyncs from the app starting a frame to the last pixel lit (one app, one render server, one display scan), i.e. 25 ms at 120 Hz, 50 ms at 60 Hz; triple-buffer mode is four (33.3 ms at 120 Hz, 66.7 ms at 60 Hz) with no late frames. The system may switch to triple buffering on its own, to absorb a render hitch or to save energy by running the GPU in low power, which silently adds a vsync of latency; it can also enter a low-latency mode (drawing apps). Even in triple-buffer mode the app still gets one vsync and the render server's CPU prep is not parallel. Begin time, commit deadline, and presentation time do not always sit on vsyncs (variable refresh), so a frame scheduler should read the times the API supplies (e.g. the display link's target timestamp) rather than compute them from the nominal rate. Hitch duration = actual minus expected frame lifetime. — /documentation/xcode/understanding-hitches-in-your-app [symbols: CADisplayLink.targetTimestamp] [gate: Hitches instrument not on visionOS; Organizer hitch metrics not on tvOS or visionOS]
- Silent background push: `content-available: 1` with no alert/sound/badge, `apns-priority` 5, `apns-push-type` `background`; up to 30 s of work in `application(_:didReceiveRemoteNotification:fetchCompletionHandler:)`; more than three per hour gets rate-limited. Not a channel for real-time game state. — /documentation/BackgroundTasks/choosing-background-strategies-for-your-app

## apple-games/input.md

- Apple's end-to-end latency breakdown for one input-to-photon path: hardware input plus event delivery under ~10 ms; rendering 8–33 ms; display update 8–16 ms; whole path goal under 100 ms for a discrete action. Outside the main-thread work, event delivery and rendering add 10–50 ms even when the app is healthy, so the game's own input-handling plus frame work is the only large adjustable term. — /documentation/Xcode/understanding-hangs-in-your-app
- Touch event routing detail that matters for on-screen game controls: the touch-up goes to the view that received the touch-down even if the finger has moved off it; a `Button` fires only if the finger is still inside its bounds at touch-up. Mouse-down on macOS is the analogue. — /documentation/Xcode/understanding-hangs-in-your-app

## apple-games/audio-and-haptics.md

- visionOS spatializes app audio by default, in real time against listener position and surroundings, and too many sources stall audio output. Limit concurrent sources, moving sources, and soundstage size; keep a fixed pool of audio players; attach players to stationary entities where possible; and stagger player creation, because initializing several at once costs enough to disturb rendering. The process track's Audio Playback lane in RealityKit Trace shows the overhead. — /documentation/visionOS/analyzing-the-performance-of-your-visionOS-app [gate: visionOS]

## apple-games/game-center-and-online.md

- Portable (C/C++) netcode hides main-thread blocking that ends in a watchdog kill: BSD `gethostbyname`/`gethostbyaddr` are never main-thread safe; `getaddrinfo`/`getnameinfo` are safe only for numeric hosts (`AI_NUMERICHOST`/`NI_NUMERICHOST`); `SCNetworkReachability` (e.g. `SCNetworkReachabilityGetFlags`) is synchronous by default; URL-taking initializers like `String(contentsOf:)`, `NSData`, `XMLParser` with an https URL fetch synchronously. Fixes in Apple's order: async `URLSession`; `NWPathMonitor` started on your own queue via `start(queue:)` instead of reachability; if a synchronous code base cannot change, run it on a secondary thread; for manual DNS use `CFHost` or `<dns_sd.h>`. Test under Xcode's adverse-network device conditions. — /documentation/Xcode/addressing-watchdog-terminations [symbols: NWPathMonitor, NWPathMonitor.start(queue:), SCNetworkReachabilityGetFlags(_:_:), CFHost]

## apple-games/assets.md

- Use the async loader of any framework that has one: RealityKit `Entity.loadAsync(contentsOf:withName:)` rather than the synchronous `Entity.load(contentsOf:withName:)`; Vision's `VNRequest.preferBackgroundProcessing`. Large 3D model parsing on the main thread is one of Apple's named watchdog causes. — /documentation/Xcode/addressing-watchdog-terminations [symbols: Entity.loadAsync(contentsOf:withName:), Entity.load(contentsOf:withName:)]

- If content packs are fetched with a background `URLSession` rather than Background Assets: build it from `URLSessionConfiguration.background(withIdentifier:)` with a fixed identifier (one session is normal), keep `sessionSendsLaunchEvents` true, set `isDiscretionary` for non-urgent packs (forced true anyway when the transfer starts while backgrounded), and give each task `countOfBytesClientExpectsToSend`/`countOfBytesClientExpectsToReceive` and optionally `earliestBeginDate`. — /documentation/Foundation/downloading-files-in-the-background [symbols: URLSessionConfiguration.background(withIdentifier:), URLSessionConfiguration.sessionSendsLaunchEvents, URLSessionConfiguration.isDiscretionary, URLSessionTask.earliestBeginDate, URLSessionTask.countOfBytesClientExpectsToReceive]
- Gotcha for chained pack downloads: each background resume/relaunch grows a rate-limit delay before a newly started background task begins, so "finish one pack, start the next" from the background stalls badly. Enqueue all packs at once on one session, and prefer fewer, larger transfers over thousands of tasks; the delay resets when the user foregrounds the app. — /documentation/Foundation/downloading-files-in-the-background
- The downloaded file at `urlSession(_:downloadTask:didFinishDownloadingTo:)` is only valid until that delegate returns: move it to a permanent location inside the callback. On a relaunch after termination, recreate the session with the same identifier at launch; store the `application(_:handleEventsForBackgroundURLSession:completionHandler:)` handler and call it on the main queue from `urlSessionDidFinishEvents(forBackgroundURLSession:)`. Limits: delegate required, HTTP(S) only, redirects always followed, uploads only from a file. — /documentation/Foundation/downloading-files-in-the-background [symbols: URLSessionDownloadDelegate.urlSession(_:downloadTask:didFinishDownloadingTo:), URLSessionDelegate.urlSessionDidFinishEvents(forBackgroundURLSession:)]
- Where game files live relative to iCloud Backup: regenerable data (transcoded textures, baked caches, pipeline/shader caches you rebuild) goes in `Library/Caches` or `tmp`, which backup skips and the system may purge; re-downloadable content packs that must persist go elsewhere with `URLResourceValues.isExcludedFromBackup = true`, ideally on one directory named after the bundle ID under `Library`. Re-apply the flag after each save of an excluded file, because some file operations reset resource values; the flag is advisory, not a guarantee. Save games are user-created data: never exclude them. — /documentation/Foundation/optimizing-your-app-s-data-for-icloud-backup [symbols: URLResourceValues.isExcludedFromBackup, URL.setResourceValues(_:), FileManager.temporaryDirectory, FileManager.SearchPathDirectory.cachesDirectory]
- Memory-mapped asset archives carry a jetsam risk of their own: frequent non-sequential reads and writes of mapped files thrash the system file cache, and the system answers with an `fc-thrashing` jetsam (often of a background app, not necessarily the culprit). Many open files at once can exhaust kernel vnodes (`vnode-limit`). Read packed assets in large sequential spans and keep the open-file count bounded. For a game killed in the foreground, `per-process-limit` is the usual reason; bytes at kill = `rpages` × header `pageSize` (16384 on the page's example device), and `lifetimeMax` gives the peak in pages. Match the entry's `uuid` to the shipped build's dSYM. Extensions get a far lower limit than a foreground app, and SpriteKit is named as a high-baseline-memory technology to avoid in one. — /documentation/Xcode/identifying-high-memory-use-with-jetsam-event-reports
- Debug aid: the Background Networking logging profile from developer.apple.com/bug-reporting/profiles-and-logs shows how the system schedules background transfers on a device. — /documentation/Foundation/downloading-files-in-the-background

- Frames-in-flight throttles are commonly a `DispatchSemaphore` waited on by the render thread and signaled from a command-buffer completion handler. ## apple-metal/resources-and-memory.md

- CPU-side analogue of GPU purgeability, for the writer to cross-reference: `NSPurgeableData` contents not held under `beginContentAccess()` are discarded by the kernel under memory pressure, faster than an app reacting to a warning; Apple says not to combine `NSCache` with `NSPurgeableData`. Recreatable CPU-side asset data (decoded but not yet uploaded) fits this; GPU resources use Metal's own purgeable state. — /documentation/Xcode/responding-to-low-memory-warnings [symbols: NSPurgeableData, NSDiscardableContent.beginContentAccess(), NSCache]
- How iOS counts an app's memory, for unified-memory budgeting: pages in use × page size (typically 16 KB); freshly allocated memory is clean and costs no RAM until written, and writing even one byte dirties a whole 16 KB page. So an engine that pre-reserves a large arena is cheap, but one that zero-fills it at startup pays for all of it at once. Executable and library data count too. Organizer and MetricKit report peak memory (periodic samples through the day) and memory at suspension, filterable at the 50th and 90th percentile per device type. An `EXC_RESOURCE` report with subtype `MEMORY` means the app neared its device-specific limit, not that it was killed. Whether GPU resource memory lands in this same count is not stated on the page (writer: verify before claiming). — /documentation/xcode/reducing-your-app-s-memory-use

## apple-metal/gpu-debugging-and-profiling.md

- Comparable GPU traces need a pinned GPU performance state: hold the Record button > Recording Options > Metal Application, set Counter Set to **Performance Limiters** and Performance State to **Minimum** or **Medium** (the dialog also has a Device picker and an "Enable Shader Timeline" checkbox). Without pinning, the GPU's clock state moves between runs. Profile a custom material in isolation with Metal System Trace and watch GPU ALU instructions and texture reads/writes per frame. On visionOS, eye position, viewer distance, and content amount change GPU work, so hold them fixed (empty the immersive scene, or head-anchor the test content). With Compositor Services full immersion the pixel count makes cheap/unlit materials matter even more. — /documentation/visionOS/analyzing-the-performance-of-your-visionOS-app [gate: visionOS for the RealityKit/Compositor parts; the recording-options steps are general Instruments]
