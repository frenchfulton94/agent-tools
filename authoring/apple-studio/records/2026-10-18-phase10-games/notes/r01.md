# Notes r01

## direct-distribution.md

### What app-release already covers, and what a Developer ID release lacks

The skill's five references are `signing-and-provisioning.md` (certificates vs
API keys, automatic vs manual signing, the Development / Ad Hoc / App Store
profile table, entitlements as an allowlist, classic signing failures, free vs
paid team, the App Store distribution path, signature-format currency),
`app-store-submission.md`, `testflight-and-versioning.md` (includes the
release-build test and the Release Testing option), `push-notifications.md`,
and `ci-release-automation.md` (Xcode Cloud, `xcodebuild archive` /
`-exportArchive`, Team API keys). A grep for Developer ID, notarization,
hardened runtime, stapler, Gatekeeper, DMG, `pkgbuild`, `productbuild`, and
`spctl` finds only passing mentions of `notarytool` as an upload tool. The
skill lacks all of these for a direct Mac release:

- the Developer ID Application and Developer ID Installer identities, and the
  Developer ID provisioning profile for restricted entitlements;
- the hardened runtime and its exception entitlements;
- `notarytool` submit / log / history / credentials, and `stapler`;
- container choice (zip, DMG, flat pkg) and their signing and stapling rules;
- manual signing of nested code, inside-out ordering, and secure timestamps;
- Gatekeeper and quarantine checks (`spctl`, `syspolicy_check`);
- which capabilities need a profile outside the Mac App Store;
- Mac-specific symbol and TCC (privacy prompt) handling.

### Notes
- The command-line notarization path covers what Xcode's Organizer cannot do: software that already shipped, plug-ins, Aggregate and External Build System targets, DMG or installer distributions, and scripted builds. Export first with `xcodebuild -exportArchive -archivePath … -exportOptionsPlist … -exportPath …`. The easiest ExportOptions.plist is the one Xcode writes beside an export done once by hand, and `xcodebuild -help` lists its keys. The archive scheme's post-action is a natural place for the export — /documentation/Security/customizing-the-notarization-workflow [symbols: xcodebuild -exportArchive, ExportOptions.plist]
- The notary service rejects a bare `.app`. It accepts three containers: UDIF disk images, signed flat installer packages, and ZIP archives. It also processes nested containers (a pkg inside a DMG). Make the zip with `/usr/bin/ditto -c -k --keepParent "$APP_PATH" "$ZIP_PATH"` — /documentation/Security/customizing-the-notarization-workflow [symbols: ditto]
- The service issues a ticket for the submitted top-level file and for each nested item (the DMG, the pkg inside it, the app inside the pkg) — /documentation/Security/customizing-the-notarization-workflow
- A custom third-party installer needs two notarization rounds: notarize and staple the payload, then build the installer around it and notarize the installer. For a network installer, notarize the installer and each downloaded item separately — /documentation/Security/customizing-the-notarization-workflow
- `altool` stopped working with the notary service on 2023-11-01. `notarytool` (Xcode 13+) is the only CLI. Select the Xcode with `sudo xcode-select -s`. Local check: `xcrun notarytool --version` prints `1.1.3 (42)` under Xcode 27.1 (27A9275) — /documentation/Security/customizing-the-notarization-workflow [symbols: notarytool, altool]
- Exact submit spelling, checked against `xcrun notarytool submit --help` on this machine: `xcrun notarytool submit <file-path> --keychain-profile "<name>" --wait [--timeout 1h] [--webhook <url>] [--no-s3-acceleration] [--output-format json]`. There are three auth forms. API key: `--key <p8 path> --key-id <id> --issuer <uuid>`; `--issuer` is required for Team keys and must be omitted for Individual keys. Apple ID: `--apple-id … --team-id … --password <app-specific password>`; 2FA makes the app-specific password mandatory. Stored: `--keychain-profile` (`-p`). `--wait` defaults to false. `--timeout` ends only the local wait; the service keeps processing. `--force` uploads despite pre-flight validation failures — /documentation/Security/customizing-the-notarization-workflow [symbols: notarytool submit]
- Store credentials once so that scripts hold no cleartext password: `xcrun notarytool store-credentials "<profile>" --apple-id … --team-id … --password …` (or `--key/--key-id/--issuer`). The help on this machine also shows `--validate/--no-validate`, `--sync` (iCloud keychain; not allowed with `--keychain`), and `--keychain <path>` for a CI keychain file — /documentation/Security/customizing-the-notarization-workflow [symbols: notarytool store-credentials]
- Other subcommands on this machine: `info <submission-id>`, `wait <submission-id>`, `history`, and `log <submission-id> [<output-path>]`. The output path is optional and defaults to stdout. The log is always pretty-printed JSON; `-f` does not change it. Keep the `id:` UUID that submit prints — /documentation/Security/customizing-the-notarization-workflow [symbols: notarytool log, notarytool info, notarytool history, notarytool wait]
- Always fetch and read the JSON log, also on `status: Accepted`, because it holds warnings to fix before the next submission. Each issue has `severity`, `path`, and `message`. The top level has `status` (Accepted / Invalid), `statusSummary`, and `ticketContents` — /documentation/Security/customizing-the-notarization-workflow
- For a pipeline that must not depend on Xcode, the Notary API (REST) is the alternative — /documentation/Security/customizing-the-notarization-workflow [symbols: NotaryAPI]
- After acceptance, Gatekeeper on macOS 10.14+ finds the ticket online, also for copies downloaded before notarization. Staple the ticket so the check works offline: `xcrun stapler staple <path>`, then `xcrun stapler validate <path>`. The stapler usage text on this machine lists the formats it accepts: UDIF disk images, code-signed executable bundles, and signed flat installer packages. You cannot staple a ZIP: staple each item, then zip again. A standalone binary gets a ticket, but you cannot staple it — /documentation/Security/customizing-the-notarization-workflow [symbols: stapler staple, stapler validate]
- CI network needs: `notarytool` uploads to `notary-submissions-prod.s3-accelerate.amazonaws.com` by default; `--no-s3-acceleration` uses `notary-submissions-prod.s3.us-west-2.amazonaws.com` instead. `stapler` gets tickets through CloudKit on port 443 from 17.36.196.0/22, 17.57.0.0/22, 17.248.128.0/17, 17.250.48.0/20, 17.250.64.0/18, 17.252.62.0/23, plus ten IPv6 ranges (copy the full list from the page for a firewall rule) — /documentation/Security/customizing-the-notarization-workflow
- Numbers: most submissions complete within 5 minutes, and 98% within 15. Apple asks for at most 75 notarizations per day. To keep it fast: keep the file count low, keep non-executable files out of code locations (`Contents/MacOS/`; use `Contents/Resources/`), do not submit corrupted or heavily compressed DMGs (check with `hdiutil verify <image>`), and avoid huge data files that change often — /documentation/Security/customizing-the-notarization-workflow [symbols: hdiutil verify]
- Pattern for games with large data: notarize only an installer package that holds the executables, put the bulk data in a folder next to it, put both in a DMG that ships without notarization, and staple the pkg — /documentation/Security/customizing-the-notarization-workflow
- The hardened runtime is mandatory for notarization. Turn it on in Signing & Capabilities with + → Hardened Runtime; it is the `ENABLE_HARDENED_RUNTIME` setting, and manual signing passes `codesign --options runtime`. It blocks code injection, dylib hijacking, and process-memory tampering. Each restriction it imposes can be lifted one at a time by a Boolean exception entitlement. Grant only those the app needs — /documentation/Security/hardened-runtime [symbols: com.apple.security.cs.allow-jit, com.apple.security.cs.allow-unsigned-executable-memory, com.apple.security.cs.allow-dyld-environment-variables, com.apple.security.cs.disable-library-validation, com.apple.security.cs.disable-executable-page-protection, com.apple.security.cs.debugger]
- Game-engine mapping of the exceptions. `com.apple.security.cs.allow-jit` permits W+X memory only through `mmap()` with `MAP_JIT`; this is the narrow exception for a JIT scripting VM (Apple's examples: the JavaScriptCore fast path, some Python frameworks, PCRE, a custom macro language). Gotcha: without it, a JIT framework can fall back to its interpreter without any error, which costs frame time, or it can crash. `com.apple.security.cs.allow-unsigned-executable-memory` permits W+X memory without the `MAP_JIT` limits. It is for rare cases (patching C code, `NSCreateObjectFileImageFromMemory`, DVDPlayback), and Apple warns it exposes the app to memory-safety exploits. DRM that uses unsigned executable memory should move to `MAP_JIT` with `allow-jit`. Loading mods or plug-ins signed by another team needs `com.apple.security.cs.disable-library-validation` — /documentation/Security/hardened-runtime; /documentation/BundleResources/Entitlements/com.apple.security.cs.allow-jit; /documentation/BundleResources/Entitlements/com.apple.security.cs.allow-unsigned-executable-memory [symbols: MAP_JIT, mmap]
- Spellings checked: the Xcode build setting is `ENABLE_HARDENED_RUNTIME` (/documentation/Xcode/build-settings-reference). `man codesign` on this machine documents `--options runtime` (honored on macOS 10.14.0+; older systems ignore the flag) and `--timestamp[=URL]`. With no value, `--timestamp` uses Apple's default server and signing fails if that server cannot be reached. `--timestamp=none` turns timestamping off. Without `--timestamp`, the system default applies, and it may timestamp only some signatures, so always pass it explicitly for Developer ID — `man codesign` [symbols: codesign --options runtime, codesign --timestamp]
- Entitlements go only on executables. Frameworks, dylibs, and in-process plug-ins take the host's entitlements and declare none of their own — /documentation/Security/hardened-runtime
- All hardened-runtime entitlements default to false. Xcode writes one only when it is true. Manual signing should follow that rule: leave the key out instead of writing it as false — /documentation/Security/hardened-runtime
- Resource-access entitlements under the hardened runtime: `com.apple.security.device.audio-input` (voice chat needs this), `com.apple.security.device.camera`, `com.apple.security.personal-information.location`, `.addressbook`, `.calendars`, `.photos-library`, and `com.apple.security.automation.apple-events`. Each also needs its Info.plist purpose string — /documentation/Security/hardened-runtime [symbols: com.apple.security.device.audio-input, com.apple.security.device.camera, com.apple.security.automation.apple-events]
- System extensions with hardened-runtime exception entitlements do not load. The one exception: non-DEXT system extensions may use `allow-jit` — /documentation/Security/hardened-runtime
- Notarization is an automated malware and signing scan, not App Review. Gatekeeper shows the "Apple checked it" first-launch dialog when it finds a ticket (stapled or online). Notarize apps, non-app bundles (kexts), UDIF DMGs, and flat pkgs — /documentation/Security/notarizing-macos-software-before-distribution
- Gates: from macOS 10.14.5, code whose Developer ID certificate is new must pass notarization before it runs (new and updated kexts too). Since macOS 10.15, all Developer ID software built after 2019-06-01 must be notarized. Mac App Store builds need no notarization. Since 2023-11-01 the service also refuses Xcode 13 and earlier (Xcode 14+ is required) — /documentation/Security/notarizing-macos-software-before-distribution [gate: macOS 10.14.5 / 10.15]
- Notarization also limits damage from a leaked Developer ID key: Apple keeps an audit trail per signing key and can revoke the tickets of rogue builds — /documentation/Security/notarizing-macos-software-before-distribution
- The notary checklist: every executable signed and valid; a Developer ID certificate (Application, Installer, kext, or system-extension), never Mac App Distribution, Apple Development, ad hoc, or a local cert; hardened runtime on app and command-line targets; a secure timestamp; no `com.apple.security.get-task-allow` set to true; a macOS 10.9+ SDK; XML, ASCII-encoded entitlements — /documentation/Security/notarizing-macos-software-before-distribution [symbols: com.apple.security.get-task-allow]
- Plug-ins and mods: from macOS 10.15, an app can load a quarantined plug-in (downloaded, or received by AirDrop) only when the plug-in is notarized; otherwise the user must approve it in system settings. The host must declare every entitlement and purpose string its plug-ins need, because plug-ins inherit the host's. This applies even when each plug-in is notarized separately; without the host entitlement, some plug-ins fail to load at all — /documentation/Security/notarizing-macos-software-before-distribution [gate: macOS 10.15]
- An app with no plug-in system can still load third-party code, for example camera drivers that are not UVC; that needs `disable-library-validation` — /documentation/Security/notarizing-macos-software-before-distribution
- Organizer path: Archive → Window > Organizer → Distribute App → Developer ID → Upload. Xcode staples the ticket into the archive when the scan finishes; export again after that to get the stapled, distributable app. The page says the Account Holder must sign with Developer ID (in practice the Account Holder creates the Developer ID certificate; see the sharing-certificates page). If Upload is unavailable, the archive is not a macOS app archive; use `notarytool` for other targets — /documentation/Security/notarizing-macos-software-before-distribution
- Notarizing old releases needs no rebuild or re-sign. Submit the DMG, pkg, or zip that already shipped, then staple. The service may relax rules for older software. A relaxed acceptance does not ensure the build passes Gatekeeper, so read the log and test — /documentation/Security/notarizing-macos-software-before-distribution
- Notary error strings and their causes, for an error-to-fix table. "The signature of the binary is invalid." means the code is unsigned, or the bundle changed after signing. "The binary is not signed with a valid Developer ID certificate." means a Mac App Distribution or self-signed identity was used. "The signature does not include a secure timestamp." "The executable requests the com.apple.security.get-task-allow entitlement." "The binary uses an SDK older than the 10.9 SDK." "The executable does not have the hardened runtime enabled." "Embedded entitlements are invalid: syntax error near line 1" means a binary plist was embedded — /documentation/Security/resolving-common-notarization-issues
- Verify a signature before submitting: `codesign -vvv --deep --strict <bundle>`. `--strict` matches what notarization enforces, and `--deep` checks nested code. For a pkg, use `pkgutil --check-signature <file.pkg>` instead (`man pkgutil` here confirms it prints the trust status and the certificate chain). A good pkg shows "Signed with a trusted timestamp" and "1. Developer ID Installer:" — /documentation/Security/resolving-common-notarization-issues [symbols: codesign -vvv --deep --strict, pkgutil --check-signature]
- Identity per artifact: Developer ID Application signs Mach-O files, apps, bundles, command-line tools, and disk images. Developer ID Installer signs installer packages. Kexts need a Developer ID Application certificate with the kext capability, which Apple must grant on request, and Apple discourages kexts. pkgs are signed at build time with `pkgbuild --sign` / `productbuild --sign`, or afterwards with `productsign`; all three add a secure timestamp by default. PackageMaker is dead and cannot sign — /documentation/Security/resolving-common-notarization-issues [symbols: pkgbuild, productbuild, productsign]
- Pre-flight Gatekeeper check: `spctl -vvv --assess --type exec <app>`; add `--raw` for a plist. `man spctl` on this machine spells the type values `execute`, `install` (pkg), and `open` (documents); the page uses `exec`. As of macOS 15.0, spctl no longer supports changing the rule database or global state (`--global-disable` and similar) — /documentation/Security/resolving-common-notarization-issues; `man spctl` [symbols: spctl --assess, spctl --type] [gate: macOS 15 deprecates spctl rule edits]
- Not on any slice page, found on this machine: `/usr/bin/syspolicy_check` has two subcommands. `syspolicy_check notary-submission <bundle>` checks readiness for notarization. `syspolicy_check distribution <bundle-path> [-v] [--json]` runs the launch-time checks that macOS runs (Gatekeeper, XProtect, provisioning profile). It is a better pre-flight than `spctl` alone — `syspolicy_check --help` [symbols: syspolicy_check]
- Secure timestamps: Xcode adds one only on archive (since Xcode 10.2) and export, not on ordinary builds. A custom export must add `--timestamp` to `OTHER_CODE_SIGN_FLAGS` or to the `codesign` call. The only timestamp server macOS accepts is `timestamp.apple.com` (IPv4 17.32.213.0/24, 17.157.80.0/24, 17.179.249.0/24; IPv6 2620:149:980:500::/64, 2620:149:981:603::/64, 2620:149:982:404::/64), so a CI signer needs internet access. To check: `codesign -dvv <path>` shows `Timestamp=<date>` when a secure timestamp is present; `Signed Time` means it is absent — /documentation/Security/resolving-common-notarization-issues [symbols: OTHER_CODE_SIGN_FLAGS, codesign -dvv]
- get-task-allow: new macOS projects set `CODE_SIGN_INJECT_BASE_ENTITLEMENTS = YES`, which injects `com.apple.security.get-task-allow` so the debugger can attach under SIP. Xcode's archive and export strip it. A custom pipeline that signs build products directly must set the setting to `NO` for the distribution build only, because the binary then cannot be debugged. A plug-in host may keep get-task-allow only together with `disable-library-validation` — /documentation/Security/resolving-common-notarization-issues [symbols: CODE_SIGN_INJECT_BASE_ENTITLEMENTS, com.apple.security.get-task-allow]
- Manual hardened runtime: `OTHER_CODE_SIGN_FLAGS = --options=runtime` (works on macOS 10.13.6+ with Xcode before 10). Test on macOS 10.14+ — /documentation/Security/resolving-common-notarization-issues
- Entitlements file hygiene for custom signing: ASCII, no BOM, XML plist. `plutil -convert xml1 <file>.entitlements`, then `plutil -lint <file>.entitlements`. After signing, run `codesign -d --entitlements :- <app>` (the page's form); `bplist00` in the output means the notary service will reject it. Current `man codesign` describes `--entitlements -` with `--xml` or `--der` for display, so `codesign -d --entitlements - --xml <app>` is the modern spelling. Gate: since macOS 10.15.4, a process with malformed embedded entitlements aborts with an AMFI "entitlements cannot be parsed" error — /documentation/Security/resolving-common-notarization-issues [symbols: plutil -lint, codesign -d --entitlements] [gate: macOS 10.15.4]
- Stapler errors: `error -68` on 10.13 is fixed by upgrading to 10.14 or by clearing the trustd Valid cache (`sudo killall -9 trustd; sudo rm /Library/Keychains/crls/valid.sqlite3`). `error -73` needs Xcode 10.1+ and a writable DMG or pkg; staple writes into the file, so a read-only DMG fails. See `man stapler` for the other codes — /documentation/Security/resolving-common-notarization-issues
- Engine-relevant gotcha: Xcode can notarize only a macOS App Archive. Aggregate and External Build System targets (cargo, CMake, or make wrappers) give a "Generic Xcode Archive" with no notarize button, so use `notarytool`. A real app target also becomes Generic when a dependency (framework target) has `SKIP_INSTALL = NO`, because that places the dependency under `Products/Library/` in the xcarchive. Set Skip Install to Yes on every dependency — /documentation/Security/resolving-common-notarization-issues [symbols: SKIP_INSTALL]
- On macOS a provisioning profile is optional. A Mac app needs one only when it claims a restricted entitlement. That holds for the Mac App Store too; the one exception is TestFlight, which always needs a profile. The unrestricted entitlements, which need no profile, are `com.apple.security.get-task-allow`, `com.apple.security.application-groups`, the App Sandbox entitlements, and the hardened-runtime entitlements. Restricted ones (for example `keychain-access-groups`) need a profile, which stops another team from impersonating the app to read its keychain items — /documentation/Technotes/tn3125-inside-code-signing-provisioning-profiles [symbols: com.apple.security.application-groups, keychain-access-groups]
- Developer ID profiles exist. Like In-House profiles, they carry `ProvisionsAllDevices` (no UDID list), and their `ExpirationDate` is far in the future, while other types last about a year at most. A Developer ID profile embeds at `MyApp.app/Contents/embedded.provisionprofile`; note the `.provisionprofile` extension on macOS against `embedded.mobileprovision` elsewhere — /documentation/Technotes/tn3125-inside-code-signing-provisioning-profiles [symbols: ProvisionsAllDevices, ExpirationDate, embedded.provisionprofile]
- The macOS App ID entitlement is `com.apple.application-identifier`; Mac Catalyst apps carry both that and `application-identifier` — /documentation/Technotes/tn3125-inside-code-signing-provisioning-profiles
- A standalone executable (daemon, CLI tool, or a dedicated game server binary) has no place for an embedded profile, so it cannot claim a restricted entitlement. Wrap it in an app-like bundle (see the daemon page below) — /documentation/Technotes/tn3125-inside-code-signing-provisioning-profiles
- Profile inspection commands (also for the existing signing reference): `security cms -D -i <profile> -o payload.plist`, `plutil -extract Entitlements xml1 -o - payload.plist`, `plutil -extract ProvisionedDevices xml1 -o - …`, `plutil -extract ExpirationDate raw -o - …`, `plutil -extract DeveloperCertificates.0 raw -o - … | base64 -D > cert0.cer`, then `certtool d cert0.cer`. Claimed entitlements: `codesign --display --entitlements - --xml <app> | plutil -convert xml1 -o - -`. The DER form (`DER-Encoded-Profile`) is the source of truth on modern systems; its `DeveloperCertificates` holds SHA-256 hashes, not whole certificates. Apple warns the format is not API, so do not parse it in a product — /documentation/Technotes/tn3125-inside-code-signing-provisioning-profiles [symbols: security cms, plutil -extract, DER-Encoded-Profile]
- **Which capabilities need a profile outside the Mac App Store, and which Developer ID cannot have at all.** This is from Apple's "Supported capabilities (macOS)" table, which TN3125 links. I read it with curl (`https://developer.apple.com/help/account/reference/supported-capabilities-macos`, HTTP 200, saved under `$TMP/r01-extra/`); it is not a slice row. Developer ID **supports**: iCloud (CloudKit, iCloud documents, iCloud key-value storage), Push notifications, Associated domains, App groups, Keychain sharing, Apple Pay, Network extensions, Personal VPN, System Extension, Time Sensitive and Communication Notifications, Spatial Audio Profile, Head Pose, Maps, and others. Developer ID does **not support**: **Game Center**, **In-App Purchase**, **Sign in with Apple**, HomeKit, WeatherKit, Shared with You, Messages Collaboration, Sensitive Content Analysis, Managed App Installation UI, Low Latency HLS, HLS Interstitial Previews. iCloud and Push are restricted entitlements (`com.apple.developer.*`), so a Developer ID build that uses them must embed a Developer ID provisioning profile. Consequence for games: a direct-download Mac game gets no Game Center, no StoreKit IAP, and no Sign in with Apple. Cloud saves (CloudKit or iCloud documents/KVS) and push work with a profile — help.apple.com supported-capabilities-macos (via TN3125) [symbols: com.apple.developer.game-center, com.apple.developer.icloud-services, com.apple.developer.aps-environment]
- Privacy prompts in a Developer ID build: some protected resources need both an entitlement and a purpose string. Under the hardened runtime, microphone voice chat needs `com.apple.security.device.audio-input` plus `NSMicrophoneUsageDescription`. Without the purpose string, the access fails and can crash the app; Xcode reports the cause when it catches that crash. Check authorization before every use, because the user can revoke it in Settings at any time. On macOS, reset a prompt for testing with `tccutil reset <service>` (for example `tccutil reset AppleEvents`, `Camera`, `Calendar`); it resets that service for all apps — /documentation/UIKit/requesting-access-to-protected-resources [symbols: NSMicrophoneUsageDescription, tccutil reset]
- Mac crash symbolication: OS framework symbols are tied to the OS build, device model, and CPU architecture. For iOS, tvOS, visionOS, and watchOS, Xcode copies them from each connected device into `~/Library/Developer/Xcode/<platform> DeviceSupport`, or `xcodebuild -prepareDeviceSupport -destination "id=<UDID>"` fetches them (find the UDID with `devicectl list devices --columns 'UDID'`). **macOS and Mac Catalyst have no such download**: symbolicate a player's crash report in Xcode on a Mac running the same macOS version as the report. That is a real cost for a directly distributed Mac game that gathers crash reports itself — /documentation/Xcode/acquiring-operating-system-symbol-information [symbols: xcodebuild -prepareDeviceSupport, devicectl list devices]
- Toolchain pinning for a release script: `xcode-select --print-path` (`-p`) shows the active developer directory. `sudo xcode-select --switch <path>` changes it for every user. `env DEVELOPER_DIR="<path>" <command>` overrides it for one command without sudo, which is the right form for a CI job that must notarize with the release Xcode while a beta is the default. With no active directory, `xcode-select -p` prints "Unable to get active developer directory". Observed here: the standalone Command Line Tools package (`/Library/Developer/CommandLineTools/usr/bin`) also ships `notarytool` and `stapler` (and `codesign_allocate`), so a signing-only CI image can skip full Xcode. Full Xcode 27.1 still ships `altool` — /documentation/Xcode/configuring-command-line-tools-settings [symbols: xcode-select --switch, DEVELOPER_DIR]
- Three routes to distribution-signed Mac code. An Xcode-built app: archive, then export (Organizer, or `xcodebuild archive` then `xcodebuild -exportArchive`). A non-app product built with Xcode: archive, copy the parts out, and sign by hand. An external build system (make, and by extension cargo or CMake): add a manual `codesign` step. Then package (pkg, DMG, or zip) — /documentation/Xcode/creating-distribution-signed-code-for-the-mac
- **Organizer naming**: the Distribute App sheet has preset methods and a Custom path. **"Direct Distribution"** is the preset that notarizes a Developer ID app. **"Developer ID"** is the Custom method, with the Upload (notarize) or Export choice, which is the flow the Security notarization page describes. Both are Mac-only (see the beta-testing page below). "Distribute Content" in place of "Distribute App" means the archive has several items in `Products/`; set `SKIP_INSTALL` on every embedded target (TN3110) — /documentation/Xcode/creating-distribution-signed-code-for-the-mac; /documentation/Security/notarizing-macos-software-before-distribution [symbols: SKIP_INSTALL]
- Copy code with `ditto`, never `cp`, because `ditto` keeps the symlinks that framework bundles depend on — /documentation/Xcode/creating-distribution-signed-code-for-the-mac [symbols: ditto]
- Manual signing method. (1) List every code item and classify it: bundled code or not, main executable or not (`file <binary>` prints `Mach-O … executable` for a main executable and `dynamically linked shared library` for a framework). (2) Sign inside out: dependencies before dependents (framework, then appex, then app); independent items in any order. (3) Entitlements go on main executables only. On library code they do nothing useful and can stop the code from running. `man codesign` here adds that from macOS 15.0 codesign does not embed entitlements in library signatures unless `--force-library-entitlements` is passed — /documentation/Xcode/creating-distribution-signed-code-for-the-mac; `man codesign` [gate: macOS 15 codesign default]
- Entitlements file format for manual signing: standard XML plist, LF line endings, no comments, no BOM. Start from the development build's claims with `codesign -d --entitlements - --xml <app> | plutil -convert xml1 -o - -`, then change `com.apple.developer.aps-environment` from `development` to `production` and remove `com.apple.security.get-task-allow` — /documentation/Xcode/creating-distribution-signed-code-for-the-mac [symbols: com.apple.developer.aps-environment]
- **MAS and Developer ID variants do not share TCC grants by default.** macOS keys privacy permissions (microphone and others) on the designated requirement (DR), and the default DRs of a Mac App Store build and a Developer ID build are incompatible. A game sold both ways makes players grant mic (voice chat) again per variant, unless both are signed with compatible custom DRs (TN3127) passed as `codesign -r <reqfile>`, with the code-signing identifier adjusted per code item — /documentation/Xcode/creating-distribution-signed-code-for-the-mac [symbols: codesign -r]
- Profiles in manual signing: a restricted entitlement needs a distribution profile of the matching type (Mac App Store or Developer ID), copied to `<bundle>/Contents/embedded.provisionprofile`; each appex has its own profile. Xcode-archived bundles carry a **development** profile; replace it.
