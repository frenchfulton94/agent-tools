# Notes g08

## game-loop-and-threading.md

- Never block inside work on a concurrent queue: a blocked worker makes GCD spawn more threads, and enough of them exhausts the app's thread budget. Also avoid a private concurrent queue per subsystem — each costs threads. Apple's pattern is to submit to the global concurrent queues and give each serial subsystem queue (audio-decode, asset-load, save) a global queue as its target, keeping serial order without new thread pools — /documentation/Dispatch/dispatch-queue [symbols: dispatch_get_global_queue, dispatch_queue_create_with_target, DispatchObject.setTarget(queue:)]
- `DispatchQueue.main.sync` from the main thread deadlocks; a render/sim thread that hops to main must use async. Blocks get only minimal autorelease handling by default — for Obj-C-heavy per-frame work (Metal objects created in a loop on a worker queue) create the queue with `dispatch_queue_attr_make_with_autorelease_frequency` (`.workItem`) or wrap in `autoreleasepool` — /documentation/Dispatch/dispatch-queue [symbols: dispatch_queue_attr_make_with_autorelease_frequency, dispatch_autorelease_frequency_t, DispatchQueue.sync(execute:)]
- Parallel-for over job slices (culling, animation, particle update): `dispatch_apply` / `DispatchQueue.concurrentPerform` with `DISPATCH_APPLY_AUTO` as the queue lets the system pick the right pool for the caller's QoS (the SDK header names it the preferred value) — /documentation/Dispatch/dispatch-queue [symbols: dispatch_apply, DISPATCH_APPLY_AUTO]
- QoS is set at queue creation (`dispatch_queue_attr_make_with_qos_class`) or per block (`dispatch_block_create_with_qos_class`); `dispatch_assert_queue` / `dispatch_assert_queue_not` are cheap thread-ownership guards for "sim state touched only on the sim queue" — /documentation/Dispatch/dispatch-queue ; /documentation/Dispatch/dispatch-work-item [symbols: dispatch_queue_attr_make_with_qos_class, dispatch_block_create_with_qos_class, dispatch_assert_queue, dispatch_assert_queue_not]
- `dispatch_get_current_queue` is deprecated; do not use it to decide "am I on the render queue" — use `dispatch_assert_queue` or queue-specific keys (`dispatch_queue_set_specific` / `dispatch_get_specific`) — /documentation/Dispatch/deprecated-symbols ; /documentation/Dispatch/dispatch-queue [symbols: dispatch_get_current_queue, dispatch_queue_set_specific, dispatch_get_specific]
- A workloop (`dispatch_workloop_t`, Swift `DispatchWorkloop`) is a queue that always runs the highest-QoS pending item next (user-interactive first) instead of FIFO — fits one game-thread queue where input/sim work must jump ahead of background jobs; `dispatch_set_qos_class_floor` sets its minimum QoS — /documentation/Dispatch/workloop [symbols: dispatch_workloop_create, dispatch_workloop_create_inactive, dispatch_set_qos_class_floor]
- Workgroup tie-in: `dispatch_workloop_set_os_workgroup` makes the workloop's worker threads join an `os_workgroup_t` while they run its items. SDK header: the workloop must still be **inactive** (create with `dispatch_workloop_create_inactive`, then `activate()`); calling it on an active workloop terminates the process. In Swift the call is refined away — pass `osWorkgroup:` to `DispatchWorkloop(label:attributes:autoreleaseFrequency:osWorkgroup:)`. Workgroup policy beats `dispatch_workloop_set_scheduler_priority` when both are set — /documentation/Dispatch/dispatch-functions ; /documentation/Dispatch/workloop [symbols: dispatch_workloop_set_os_workgroup, dispatch_workloop_create_inactive, DispatchWorkloop.init(label:attributes:autoreleaseFrequency:osWorkgroup:)] [gate: macOS 11, iOS 14]
- Frame pacing with a counting semaphore: `DispatchSemaphore` only enters the kernel when a wait actually has to block, so `wait`/`signal` per frame for frames-in-flight is cheap in the uncontended case — /documentation/Dispatch/dispatch-semaphore [symbols: DispatchSemaphore.init(value:), dispatch_semaphore_wait, dispatch_semaphore_signal]
- Fan-out/fan-in of per-frame jobs: `DispatchGroup` with `notify` (async, no stall) rather than `wait` on the main or render thread; `enter()`/`leave()` cover callback-based jobs. A concurrent-queue barrier (`dispatch_barrier_async`) gives a reader-writer lock for shared caches (many readers, exclusive writer) — barriers serialize only on a concurrent queue you create — on a global queue they act as plain async (dispatch_barrier_async reference, not this page) — /documentation/Dispatch/dispatch-group ; /documentation/Dispatch/dispatch-barrier [symbols: dispatch_group_notify, dispatch_group_wait, DispatchGroup.enter(), DispatchGroup.leave(), dispatch_barrier_async]
- Dispatch sources cover timers (`dispatch_source_set_timer` with explicit leeway) and memory-pressure events (`dispatch_source_memorypressure_flags_t`) — the latter is the hook to drop texture/asset caches on iOS/iPadOS before jetsam; a timer source is not a frame clock (use the display link) — /documentation/Dispatch/dispatch-source [symbols: dispatch_source_create, dispatch_source_set_timer, dispatch_source_memorypressure_flags_t]
- Controller connect/disconnect notifications are delivered on whatever queue you pass to `addObserver(forName:object:queue:)` (Apple's sample uses `.main`); the game thread should consume a thread-safe snapshot of "active controllers" rather than mutating game state from the observer — /documentation/GameController/discovering-game-controllers [symbols: NotificationCenter.addObserver(forName:object:queue:using:)]
- Input integration with a fixed-step sim: give the controller's live input a dedicated `queue`, set `inputStateQueueDepth` to cover the inputs that arrive between sim ticks, and drain `nextInputState()` at the top of each tick; `capture()` when you only need the current absolute state — /documentation/GameController/handling-input-events [symbols: GCDevicePhysicalInput.queue, inputStateQueueDepth, nextInputState(), capture()] [gate: macOS 14, iOS 17]

## input.md

- `GCVirtualController` (on-screen gamepad that shows up as a regular `GCController` in `GCController.controllers()`) is iOS/iPadOS only: the iOS SDK header marks it `API_AVAILABLE(ios(15.0)) API_UNAVAILABLE(macos, tvos) API_UNAVAILABLE(visionos)`, and the macOS SDK has no `GCVirtualController.h` at all. A Mac-first game must wrap it in `#if os(iOS)` — /documentation/GameController/adding-virtual-controls-to-games-that-support-game-controllers-in-ios [symbols: GCVirtualController, GCVirtualController.Configuration, GCVirtualControllerConfiguration] [gate: iOS 15; not macOS/tvOS/visionOS]
- Virtual-controller lifecycle: build it in `viewDidLoad` from a configuration whose `elements` lists only inputs the game already handles (`GCInputButtonA`, `GCInputLeftThumbstick`, …); call `connect(replyHandler:)` at game start and on `GCControllerDidDisconnect` when `controllers()` is empty; call `disconnect()` on `GCControllerDidConnect` when some controller other than `virtualController.controller` exists. Connections are async, so the physical pad's notification can arrive before the virtual one — compare against `.controller`, don't count — /documentation/GameController/adding-virtual-controls-to-games-that-support-game-controllers-in-ios [symbols: connect(replyHandler:), disconnect(), GCVirtualController.controller, GCControllerDidConnectNotification, GCControllerDidDisconnectNotification]
- Hide context-irrelevant virtual buttons (cutscene: only skip) with `updateConfiguration(forElement:configuration:)` setting the element configuration's `hidden` — /documentation/GameController/adding-virtual-controls-to-games-that-support-game-controllers-in-ios [symbols: updateConfiguration(forElement:configuration:), GCVirtualControllerElementConfiguration]
- Custom-drawn touch controls (better immersion and perf than the default overlay): set the configuration's `hidden = true` but still set `elements` (they define the synthesized `GCController`), drive it from your own `UIGestureRecognizer`s via `setValue(_:forButtonElement:)` and `setPosition(_:forDirectionPadElement:)`, and draw the controls in your own UI pass. Pan recognizer for a stick, `UILongPressGestureRecognizer` with `minimumPressDuration = 0` for a button; bound each to safe-area rects in `gestureRecognizer(_:shouldReceive:)`. UIKit touch handling is main-thread only, so hand state to the render thread thread-safely — /documentation/GameController/adding-virtual-controls-to-games-that-support-game-controllers-in-ios [symbols: GCVirtualController.Configuration.hidden, setValue(_:forButtonElement:), setPosition(_:forDirectionPadElement:)] [gate: hidden, setValue, setPosition are iOS 17 per the header]
- Root view controller for a controller game subclasses `GCEventViewController` (required on tvOS; on macOS the header gives it macOS 10.11, as an `NSViewController`) — /documentation/GameController/adding-virtual-controls-to-games-that-support-game-controllers-in-ios [symbols: GCEventViewController]
- Snapshot classes are deprecated: `GCGamepad`, `GCGamepadSnapshot`, `GCExtendedGamepadSnapshot`, `GCMicroGamepadSnapshot`, and the `*SnapshotData` structs/functions. For a frozen copy of input state use `GCDevicePhysicalInput.capture()` on `GCController.input` (macOS 14 / iOS 17), or `GCPhysicalInputProfile.capture()` on older targets — /documentation/GameController/deprecated-symbols [symbols: GCGamepad, GCExtendedGamepadSnapshot, GCMicroGamepadSnapshot, GCExtendedGamepadSnapshotData]
- Siri Remote (2nd gen) names: `GCInputDirectionalDpad` (primary pad), `GCInputDirectionalCardinalDpad` (optional secondary), `GCInputDirectionalTouchSurfaceButton`, `GCInputDirectionalCenterButton` — tvOS input names for the `Directional` profile — /documentation/GameController/directional-gamepad-input-names [symbols: GCInputDirectionalDpad, GCInputDirectionalCardinalDpad, GCInputDirectionalTouchSurfaceButton, GCInputDirectionalCenterButton]
- Pairing differs per platform: a wireless pad is invisible until paired in Settings > Bluetooth (System Settings on macOS; Remotes and Devices on tvOS). USB connects automatically on iOS/iPadOS, but on a **Mac a USB/new controller triggers a system approval prompt** before the game sees it — expect a delay and don't treat "no controller yet" as final — /documentation/GameController/discovering-game-controllers
- Startup pattern: read `GCController.controllers()` (already-connected pads; empty array when none) and observe `.GCControllerDidConnect`/`.GCControllerDidDisconnect` (the notification's `object` is the `GCController`). The spatial-controller page adds that the initial check is not synchronous and can come back empty while an accessory is connected — rely on the notification, not one launch-time poll — /documentation/GameController/discovering-game-controllers ; /documentation/GameController/discovering-and-tracking-spatial-game-controllers-and-styli [symbols: GCController.controllers(), GCControllerDidConnect, GCControllerDidDisconnect]
- Choosing the primary pad: filter out touch controllers (`productCategory != "Touch Controller"`), then prefer one where `isAttachedToDevice` is true (an iPhone clipped into a controller), else connection order. Zero physical pads → Touch Controller framework for Metal games, `GCVirtualController` otherwise — /documentation/GameController/discovering-game-controllers [symbols: GCController.productCategory, GCController.isAttachedToDevice]
- `playerIndex` (`.index1`…`.index4`, `.indexUnset` when released) maps a pad to a player and lights the matching LED where the hardware has one — /documentation/GameController/discovering-game-controllers [symbols: GCController.playerIndex, GCControllerPlayerIndex]
- Declare supported profiles in Info.plist `GCSupportedGameControllers`. Profiles: `Extended` (Xbox-class full pad), `DualShock` (PS4), `DualSense` (PS5), `Xbox`, `Micro` (pad + motion, 1st-gen Siri Remote), `Directional` (2nd-gen Siri Remote, no motion), `Spatial` (e.g. PlayStation VR2 Sense). A profile guarantees its controls exist; one pad can satisfy several — /documentation/GameController/discovering-game-controllers [symbols: GCSupportedGameControllers, GCExtendedGamepad]
- Callback style: per element `valueChangedHandler` (sticks, dpad, analog shoulders) and `pressedChangedHandler` (digital buttons) on `GCExtendedGamepad` — /documentation/GameController/discovering-game-controllers [symbols: GCControllerDirectionPad.valueChangedHandler, GCControllerButtonInput.pressedChangedHandler, GCExtendedGamepad.buttonMenu]
- visionOS: by default the system turns gamepad presses plus gaze into pinch events for the gazed view. To get raw controller events, add `GCEventInteraction` to the UIKit view hosting the `CAMetalLayer`, or apply `.handlesGameControllerEvents(matching: .gamepad)` in SwiftUI — /documentation/GameController/discovering-game-controllers [symbols: GCEventInteraction, View.handlesGameControllerEvents(matching:)] [gate: visionOS]
- Spatial controllers and styli: add the Game Controller capability with the Spatial Gamepad profile (not needed for stylus-only). Detect via `productCategory == GCProductCategorySpatialController`; styli use `GCStylusDidConnectNotification`/`GCStylusDidDisconnectNotification` and `GCStylus.styli`. Inputs: `.a`, `.b`, `.grip`, `.trigger`, `.thumbstickButton`, `.menu`, dpad `.thumbstick`; stylus `.stylusTip` (pressure), `.stylusPrimaryButton`, `.stylusSecondaryButton` — /documentation/GameController/discovering-and-tracking-spatial-game-controllers-and-styli [symbols: GCProductCategorySpatialController, GCStylus, GCStylus.styli, GCStylusDidConnectNotification, GCController.input] [gate: visionOS-focused]
- Tracking a spatial controller: RealityKit `AnchoringComponent.AccessoryAnchoringSource(device:)` + `AnchorEntity(.accessory(from:location:), trackingMode:)`; `.predicted` for low latency, `.continuous` for accuracy at higher latency. Requires `SpatialTrackingSession` with `.accessory` and Info.plist `NSAccessoryTrackingUsageDescription` — /documentation/GameController/discovering-and-tracking-spatial-game-controllers-and-styli [symbols: AnchoringComponent.AccessoryAnchoringSource, SpatialTrackingSession, NSAccessoryTrackingUsageDescription]
- Modern input model (`GCController.input` → `GCControllerLiveInput`, conforming to `GCDevicePhysicalInput`) is gated macOS 14 / iOS 17 / tvOS 17 per `GCController.h`; older OS targets fall back to `extendedGamepad` / `physicalInputProfile`. Racing wheels use `GCRacingWheel.wheelInput` (`GCRacingWheelInput`) — /documentation/GameController/handling-input-events ; /documentation/GameController/input [symbols: GCController.input, GCControllerLiveInput, GCDevicePhysicalInput, GCRacingWheelInput] [gate: macOS 14, iOS 17, tvOS 17]
- Typed element lookup: `input.buttons[.a]`, `input.dpads[.leftThumbstick]`, plus `axes`, `switches`, `elements`. The Swift subscripts return an **optional** (swiftinterface: `subscript(elementName: GCButtonElementName) -> T?`), so the page's unwrapped one-liner `input.buttons[.a].pressedInput.isPressed` does not compile — needs `?` or `if let` — /documentation/GameController/handling-input-events [symbols: GCPhysicalInputElementCollection, GCButtonElementName, GCDirectionPadElementName, GCButtonElement.pressedInput]
- Callbacks run on the device's `handlerQueue`, which is the **main queue by default**; for a game thread set `GCControllerLiveInput.queue` (or `GCRacingWheelInput.queue`) to a dedicated serial queue so input never waits behind main-thread UI work — /documentation/GameController/handling-input-events [symbols: GCDevice.handlerQueue, GCDevicePhysicalInput.queue]
- Fixed-step sim reading many buttons: one element read is atomic, but two reads can straddle an update; call `capture()` once per tick and read every element from the returned `GCControllerInputState`. Snapshots are cheap if not retained long — /documentation/GameController/handling-input-events [symbols: GCDevicePhysicalInput.capture(), GCControllerInputState]
- Don't drop high-rate input: polling once per frame misses events from devices that report hundreds of times per second (racing wheels). Set `inputStateQueueDepth` (default 1 = no buffering; Apple's example 20), then each tick drain `nextInputState()` until `nil`. Optional `inputStateAvailableHandler` fires once when the queue becomes non-empty and not again until drained — use it to wake an event-driven loop — /documentation/GameController/handling-input-events ; /documentation/GameController/racing-wheel-device-support [symbols: inputStateQueueDepth, nextInputState(), inputStateAvailableHandler]
- Per-state diffs: `change(for:)` and `changedElements()` on each queued state (`GCDevicePhysicalInputStateDiff`). Overflow is detectable — `changedElements()` returns `nil` and `change(for:)` returns `.unknownChange`; treat that as "resync from absolute values" — /documentation/GameController/handling-input-events [symbols: GCDevicePhysicalInputStateDiff.change(for:), changedElements(), GCDevicePhysicalInputElementChange.unknownChange]
- Event-driven style: per-input `pressedInput.pressedDidChangeHandler`, or one `elementValueDidChangeHandler` on the live input that fires once per changed element — /documentation/GameController/handling-input-events [symbols: GCPressedStateInput.pressedDidChangeHandler, GCDevicePhysicalInput.elementValueDidChangeHandler]
- Element taxonomy for remapping UIs: element protocols `GCButtonElement`, `GCAxisElement`, `GCSwitchElement`, `GCDirectionPadElement`; `GCPhysicalInputSource` describes an element without system-level remapping (what the user physically pressed) — /documentation/GameController/input [symbols: GCPhysicalInputElement, GCPhysicalInputSource, GCPhysicalInputElementName]
- Legacy string names for `GCPhysicalInputProfile` subscripts and `allElements`: shoulders `GCInputLeftShoulder`/`GCInputRightShoulder` plus extra `GCInputLeftBumper`/`GCInputRightBumper`; triggers `GCInputLeftTrigger`/`GCInputRightTrigger`; face `GCInputButtonA/B/X/Y`, `GCInputButtonMenu`, `GCInputButtonOptions` (secondary menu), `GCInputButtonHome`; `GCInputDirectionPad`; sticks and stick-clicks `GCInputLeftThumbstick(Button)`/`GCInputRightThumbstick(Button)`; arcade grids via `GCInputArcadeButtonName(row, column)`; back paddles via `GCInputBackLeftButton(position)`/`GCInputBackRightButton(position)` — /documentation/GameController/extended-gamepad-input-names [symbols: GCInputArcadeButtonName, GCInputBackLeftButton, GCInputBackRightButton, GCInputLeftBumper]
- Controller-specific names: DualShock 4 touchpad `GCInputDualShockTouchpadButton`, `GCInputDualShockTouchpadOne`/`Two` (first/second finger, as dpads); Xbox `GCInputButtonShare`, `GCInputXboxPaddleOne`…`Four` (Elite P1–P4); micro gamepad `GCInputMicroGamepadDpad`, `GCInputMicroGamepadButtonA`, `GCInputMicroGamepadButtonX`, `GCInputMicroGamepadButtonMenu` — /documentation/GameController/dualshock-controller-input-names ; /documentation/GameController/xbox-controller-input-names ; /documentation/GameController/micro-gamepad-input-names [symbols: GCDualShockGamepad, GCXboxGamepad, GCInputXboxPaddleOne, GCInputMicroGamepadDpad]

## audio-and-haptics.md

- Gate every haptic path on `CHHapticEngine.capabilitiesForHardware().supportsHaptics`; the page names iPad, iPod touch, and Apple Vision Pro as devices with no haptics, so an iPad build (and the Mac, which the page does not list as supported) needs a fallback cue such as audio or a visual effect — controller rumble is the Mac/iPad route (see input.md, `GCDeviceHaptics`) — /documentation/CoreHaptics/preparing-your-app-to-play-haptics [symbols: CHHapticEngine.capabilitiesForHardware(), CHHapticDeviceCapability.supportsHaptics]
- `CHHapticEngine` is not a singleton; several independent engines may exist (per level or per view controller), and Core Haptics is thread-safe, so player calls can come from any thread — keep a strong reference or playback dies when it goes out of scope — /documentation/CoreHaptics/preparing-your-app-to-play-haptics [symbols: CHHapticEngine]
- Install `resetHandler` and `stoppedHandler` before calling `start()`. After a media-server reset you must restart the engine, re-register audio via `registerAudioResource(_:options:)`, and rebuild every player from `makePlayer(with:)`; a restart inside the reset handler can still fail while the external cause persists — /documentation/CoreHaptics/preparing-your-app-to-play-haptics [symbols: CHHapticEngine.resetHandler, CHHapticEngine.stoppedHandler, CHHapticEngine.start(), registerAudioResource(_:options:), makePlayer(with:)]
- `stoppedHandler` receives a `CHHapticEngine.StoppedReason` (`.audioSessionInterrupt`, `.applicationSuspended`, `.idleTimeout`, `.systemError`) and fires only for external stops; an explicit `stop(completionHandler:)` reports through its completion handler instead. Stopping is a normal lifecycle event, so restart before the next haptic; `.systemError` is a candidate for "carry on without haptics" — /documentation/CoreHaptics/preparing-your-app-to-play-haptics [symbols: CHHapticEngine.StoppedReason, stop(completionHandler:)]
- AHAP is a JSON-shaped bundle resource with exactly two top-level keys, `Pattern` (array) and `Version`; one pattern per file. Missing keys take defaults, out-of-range values clamp to the nearest bound, unknown keys are ignored — so a typo in a key fails silently, not loudly — /documentation/CoreHaptics/representing-haptic-patterns-in-ahap-files
- AHAP pattern entries are `Event`, `Parameter` (dynamic, whole-pattern), and `ParameterCurve`. Event keys: `EventType` (`HapticTransient`, `HapticContinuous`, `AudioContinuous`, `AudioCustom`), `Time`, `Duration`, `EventParameters` (array of `ParameterID` + `ParameterValue`), and `EventWaveformPath` (bundle-relative audio file such as a `.caf`, audio events only) — /documentation/CoreHaptics/representing-haptic-patterns-in-ahap-files [symbols: CHHapticEvent.EventType, CHHapticEvent.ParameterID]
- Event parameter IDs and ranges: `HapticIntensity`, `HapticSharpness`, `AttackTime`, `DecayTime` (unsustained envelopes only), `ReleaseTime`, `Sustained` (0/1), `AudioBrightness`, `AudioVolume` are 0…1; `AudioPan` and `AudioPitch` are -1…1. All are normalized to the device's supported min/max — 1 for a time key is the maximum, not one second — /documentation/CoreHaptics/representing-haptic-patterns-in-ahap-files
- Dynamic-parameter math: intensity and audio volume controls (`HapticIntensityControl`, `AudioVolumeControl`, 0…1) multiply, so they can only attenuate; sharpness, brightness, pan, pitch, and every attack/decay/release control (-1…1) add. `HapticSharpnessControl` affects continuous haptics only. Design patterns at full intensity and scale down at runtime — /documentation/CoreHaptics/representing-haptic-patterns-in-ahap-files ; /documentation/CoreHaptics/updating-continuous-and-transient-haptic-parameters-in-real-time [symbols: CHHapticDynamicParameter.ID.hapticIntensityControl, .hapticSharpnessControl, .audioVolumeControl]
- A dynamic parameter jumps immediately; for a gradual change schedule a `CHHapticParameterCurve` (control points `(time, value)`, linear interpolation, same IDs as dynamic parameters) — /documentation/CoreHaptics/updating-continuous-and-transient-haptic-parameters-in-real-time ; /documentation/CoreHaptics/representing-haptic-patterns-in-ahap-files [symbols: CHHapticParameterCurve]
- Continuous rumble that follows gameplay (engine throttle, terrain): build one long `.hapticContinuous` event (sample uses duration 100 s), play it through `makeAdvancedPlayer(with:)`, keep the player, and push `sendParameters(_:atTime:)` each update; stop with `stop(atTime: CHHapticTimeImmediate)` — /documentation/CoreHaptics/updating-continuous-and-transient-haptic-parameters-in-real-time [symbols: CHHapticAdvancedPatternPlayer, makeAdvancedPlayer(with:), sendParameters(_:atTime:), CHHapticTimeImmediate, CHHapticEventParameter, CHHapticPattern(events:parameters:)]
- Cost model: pattern players are cheap — create, play, and discard one per transient hit without lag — but starting and stopping `CHHapticEngine` is expensive; start once at launch and leave it running. Simulator has no haptics; test on device — /documentation/CoreHaptics/updating-continuous-and-transient-haptic-parameters-in-real-time [symbols: CHHapticEngine.makePlayer(with:)]
- Game Center voice chat used the shared `AVAudioSession` that the game activates (`setActive(true)`) and deactivates on stop — on iOS any in-game voice path needs the session category to allow recording. `GKVoiceChat` itself is deprecated (iOS 18 / macOS 15); see game-center-and-online.md — /documentation/GameKit/adding-voice-chat-to-multiplayer-games [symbols: AVAudioSession.sharedInstance(), AVAudioSession.setActive(_:options:)] [gate: AVAudioSession is iOS/iPadOS/tvOS/visionOS, not macOS]

- If the game handles controller/Siri Remote focus itself, it must hit-test the access point frame for focus feedback and call `trigger(state:handler:)` to open the dashboard — the system won't do it for a custom-input game — /documentation/GameKit/adding-an-access-point-to-your-game [symbols: GKAccessPoint.trigger(state:handler:)]
