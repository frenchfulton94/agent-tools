# Notes m04

## compute-and-gpu-driven.md

- MPS image kernels (every `MPSUnaryImageKernel`/`MPSBinaryImageKernel` subclass) encode only onto a Metal 3 `MTLCommandBuffer`; the SDK headers (Xcode 27 MacOSX.sdk) give `encodeWithMTL4CommandEncoder:` / `reshapeWithMTL4CommandEncoder:` only to the MPSNDArray kernels, and MPSGraph adds `run(on: any MTL4CommandQueue, ...)` / `runAsync(on: any MTL4CommandQueue, ...)`. So a Metal 4 renderer that wants an MPS blur/histogram/scale must keep a Metal 3 `MTLCommandQueue` beside its `MTL4CommandQueue` and order the two with events, or write the filter itself — /documentation/MetalPerformanceShaders/image-filters (checked against corpus `mpsunaryimagekernel.md`, `mpsndarrayunarykernel.md`, `mpsndarrayidentity.md`, `mpsgraph.md`, `mpsgraphexecutable.md`, and `MPSNDArrayKernel.h`) [symbols: MPSUnaryImageKernel.encode(commandBuffer:sourceTexture:destinationTexture:), MPSNDArrayUnaryKernel.encode(withMTL4CommandEncoder:sourceArray:destinationArray:), MPSNDArrayMultiaryKernel.encode(withMTL4CommandEncoder:sourceArrays:destinationArray:), MPSNDArrayIdentity.reshape(withMTL4CommandEncoder:sourceArray:shape:destinationArray:), MPSGraph.runAsync(on:feeds:targetTensors:targetOperations:executionDescriptor:), MPSGraphExecutable.runAsync(on:inputs:results:executionDescriptor:)] [gate: Metal 3 command buffer only for image kernels; MTL4 entry points exist for NDArray and Graph]
- Game-relevant MPS image filters that exist and save writing a shader: `MPSImageGaussianBlur` (bloom/DoF chains), `MPSImageHistogram` + `MPSImageHistogramEqualization` (auto-exposure input), `MPSImageStatisticsMean` / `MPSImageStatisticsMeanAndVariance` / `MPSImageStatisticsMinAndMax` (average luminance), `MPSImageGaussianPyramid` / `MPSImageLaplacianPyramid` (mip-chain style downsample), `MPSImageLanczosScale` / `MPSImageBilinearScale` (resample), `MPSImageEuclideanDistanceTransform` (SDF generation for fonts/decals), `MPSImageGuidedFilter` (edge-aware filter), `MPSImageSobel`, `MPSImageConversion` (color space/alpha/format) — /documentation/MetalPerformanceShaders/image-filters [symbols: as listed]
- Shared kernel geometry: `clipRect` bounds the destination region written (intersected with destination bounds), `offset` (`primaryOffset`/`secondaryOffset` on binary kernels) places the source top-left relative to the clip rect, `edgeMode` (`primaryEdgeMode`/`secondaryEdgeMode`) governs reads off the image edge, which happen for negative offsets, oversized clip+offset, or a filter window that reaches past the border. Use `clipRect` to skip obscured regions or to tile — /documentation/MetalPerformanceShaders/image-filters [symbols: MPSUnaryImageKernel.clipRect, MPSUnaryImageKernel.offset, MPSUnaryImageKernel.edgeMode, MPSBinaryImageKernel.primaryOffset, MPSBinaryImageKernel.secondaryEdgeMode, MPSRectNoClip]
- In-place filtering is never guaranteed: whether a kernel can run in place depends on hardware, OS version, and parameters, and can change in future releases. Call `encode(commandBuffer:inPlaceTexture:fallbackCopyAllocator:)` with an `MPSCopyAllocator` block so MPS allocates a fresh destination when in place fails (the input texture pointer is then swapped for the new texture) — /documentation/MetalPerformanceShaders/image-filters [symbols: MPSUnaryImageKernel.encode(commandBuffer:inPlaceTexture:fallbackCopyAllocator:), MPSCopyAllocator]
- The page's Objective-C sample is broken as written (encodes onto an undeclared `commandBuffer`, calls `encodeToCommandBuffer:inPlaceTexture:copyAllocator:` rather than the real `fallbackCopyAllocator:` selector, returns an undeclared `result`, uses MRC `release`, and never commits). A writer must not copy it — /documentation/MetalPerformanceShaders/image-filters
- Pixel-format support: all MPS image kernels read/write 8-bit unorm (incl. sRGB and BGRA), 16/32-bit float, 16-bit unorm, and the packed 16-bit, `rgb10a2Unorm`, `rg11b10Float`, `rgb9e5Float` formats. Compressed PVRTC, EAC/ETC, ASTC work as sources only, never destinations. Integer (`r8Sint`…`rgba32Uint`) formats work only with `MPSImageTranspose`, `MPSImageIntegral`, `MPSImageIntegralOfSquares` — /documentation/MetalPerformanceShaders/image-filters [symbols: MTLPixelFormat.rg11b10Float, MTLPixelFormat.rgb9e5Float, MPSImageTranspose, MPSImageIntegral, MPSImageIntegralOfSquares]
- MPS kernel lifecycle: check `MPSSupportsMTLDevice(_:)` first; a kernel is bound to one device (`init(device:)` may allocate buffers/textures; use `copy(with:device:)` to move to another). The encode call opens and ends its own encoder, so end your current encoder before calling it and open a new one after. MPS encodes inline into a command buffer you are already using — no dedicated buffer needed. Kernels are not thread-safe: never have two kernels write the same command buffer at once, and mutating a shared kernel's properties while another thread encodes with it is undefined; make one copy per thread (`NSCopying`) — /documentation/MetalPerformanceShaders/the-mpskernel-class [symbols: MPSSupportsMTLDevice(_:), MPSKernel.init(device:), MPSKernel.copy(with:device:), MTLCommandEncoder.endEncoding()] [gate: describes Metal 3 MTLCommandBuffer/MTLCommandQueue flow]
- MPS tuning numbers Apple states: an empty command buffer can take up to 2.5 ms to round-trip to `waitUntilCompleted()`, and overlapping CPU encode with GPU execution (encode and enqueue the next buffer before the previous finishes) can raise throughput up to 10x; resource allocation is expensive enough to starve the GPU, so preallocate and reuse; render↔compute encoder switches carry a GPU mode-switch cost, so batch compute together and use fewer command buffers; chained multipass image filters can run up to 2x faster when split into ~512 KB tiles, sized via `sourceRegion(destinationSize:)` — /documentation/MetalPerformanceShaders/tuning-hints [symbols: MTLCommandBuffer.waitUntilCompleted(), MPSUnaryImageKernel.sourceRegion(destinationSize:)]
- MPS heap/temporary-memory knobs: `MPSHintTemporaryMemoryHighWaterMark(_:_:)` prefetches an MPS-internal heap of a given size for a command buffer, `MPSSetHeapCacheDuration(_:_:)` sets how long unused cached heaps survive; `MPSTemporaryMatrix`/`MPSTemporaryVector`/`MPSTemporaryImage` live in GPU-private memory scoped to a command buffer; `MPSGetPreferredDevice(_:)` picks a device by `MPSDeviceOptions` — /documentation/MetalPerformanceShaders/metalperformanceshaders-functions, /documentation/MetalPerformanceShaders/matrices-and-vectors [symbols: MPSHintTemporaryMemoryHighWaterMark(_:_:), MPSSetHeapCacheDuration(_:_:), MPSGetPreferredDevice(_:), MPSTemporaryMatrix, MPSTemporaryVector]
- MPS linear algebra at what-exists level: `MPSMatrixMultiplication`, `MPSMatrixVectorMultiplication`, Cholesky/LU decomposition and solve (`MPSMatrixDecompositionCholesky`, `MPSMatrixSolveLU`, `MPSMatrixSolveTriangular`), `MPSMatrixFindTopK`, softmax and batch-norm on matrices; for a game this is the "don't hand-write a GEMM" option (cloth/physics solves, ML-ish work) — /documentation/MetalPerformanceShaders/matrices-and-vectors [symbols: MPSMatrix, MPSMatrixDescriptor, MPSMatrixMultiplication, MPSMatrixFindTopK]
- MPS's own ray-intersector types (`MPSRayOriginDirection`, `MPSIntersectionDistancePrimitiveIndex…`, `MPSAccelerationStructureUsage`, `MPSTriangleIntersectionTestType`) are still listed in the enumerations/structures indexes; they belong to the older MPS ray-tracing path. Current ray tracing is Metal's own acceleration structures and MSL intersectors — a writer should not route new code to the MPS types — /documentation/MetalPerformanceShaders/metalperformanceshaders-structures, /documentation/MetalPerformanceShaders/metalperformanceshaders-enumerations [symbols: MPSRayOriginDirection, MPSIntersectionDistancePrimitiveIndexInstanceIndex, MPSAccelerationStructureStatus]
- MPS reserves function-constant indices for its own kernels; custom kernels that plug into MPS start at `MPSUserAvailableFunctionConstantStartIndex` — /documentation/MetalPerformanceShaders/metalperformanceshaders-constants [symbols: MPSFunctionConstantIndex, MPSFunctionConstantIndexReserved, MPSUserAvailableFunctionConstantStartIndex]
- Neural networks in MPS: the legacy graph is `MPSNNGraph` built from `MPSNNImageNode`/`MPSNNFilterNode`/`MPSNNStateNode` (filter nodes wrap `MPSCNNKernel` subclasses); RNNs via `MPSRNNImageInferenceLayer`/`MPSRNNMatrixInferenceLayer` with `MPSLSTMDescriptor`/`MPSGRUDescriptor`. MPSGraph (`MPSGraph`, with FFT ops and custom functions) is the newer tensor graph and the one with MTL4 queue entry points. For a game's ML pass, prefer MPSGraph (or Core ML) over MPSNNGraph — /documentation/MetalPerformanceShaders/objects-that-simplify-the-creation-of-neural-networks, /documentation/MetalPerformanceShaders/recurrent-neural-networks, /documentation/MetalPerformanceShadersGraph/filtering-images-with-mpsgraph-fft-operations [symbols: MPSNNGraph, MPSNNImageNode, MPSNNFilterNode, MPSNNStateNode, MPSCNNKernel, MPSRNNMatrixInferenceLayer, MPSLSTMDescriptor, MPSGraph]
- Sample projects only (no body text beyond configuration): training an MNIST classifier with `MPSNNGraph` (WWDC19 614, macOS 10.15+), training one with `MPSGraph` (WWDC20 10677, macOS 11/iOS 14+), custom functions in MPSGraph (WWDC20 10677), FFT image filtering with MPSGraph via the convolution theorem (WWDC23 10050, macOS 14+) — /documentation/MetalPerformanceShaders/training-a-neural-network-with-metal-performance-shaders, /documentation/MetalPerformanceShadersGraph/training-a-neural-network-using-mps-graph, /documentation/MetalPerformanceShadersGraph/adding-custom-functions-to-a-shader-graph, /documentation/MetalPerformanceShadersGraph/filtering-images-with-mpsgraph-fft-operations [symbols: MPSNNGraph, MPSGraph]

## gpu-debugging-and-profiling.md

### Capture
- GPU Frame Capture is a scheme setting (Edit Scheme > Run > Options): Automatically / Metal / Disabled. Xcode enables it whenever the target links Metal or a framework that uses Metal. It costs a small but measurable amount of CPU time, so choose Disabled when measuring peak performance. Disabling it also removes live resource preview at breakpoints — /documentation/Xcode/Capturing-a-Metal-workload-in-Xcode, /documentation/Xcode/Inspecting-live-resources-at-runtime
- Scopes offered by the Metal Capture button: frame, Metal layer, command queue, device, or any labeled custom scope, plus a count (frames or command buffers). To capture an already-built app: Debug > Debug Executable, choose the bundle, set the GPU Frame Capture option, Product > Run — /documentation/Xcode/Capturing-a-Metal-workload-in-Xcode
- Advanced capture options (GUI-only, popover > Advanced): capture keyboard shortcut (macOS only); Profile after Replay; "Include MetalFX temporal scaler history" (better replayed texture quality, slower capture, offered only when the app uses the MetalFX temporal scaler); "Optimize shared memory capture" with Automatic (on when Xcode can confirm system-call interposition), Always (for large/slow captures when the app never writes shared-storage buffers through syscalls), Never (when results look wrong). Save with File > Export as a GPU trace — /documentation/Xcode/Capturing-a-Metal-workload-in-Xcode
- Custom capture scopes: never allocate an `MTLCaptureScope` yourself; get one from `MTLCaptureManager.makeCaptureScope(device:)` or `makeCaptureScope(commandQueue:)`, which has both an `MTLCommandQueue` and an `MTL4CommandQueue` overload. Create it outside the frame loop, bracket work with `begin()`/`end()`, hold a strong reference for the whole captured span and for as long as it should be listed in Xcode, and set `label` so it shows by name. Assign `MTLCaptureManager.shared().defaultCaptureScope` to change what the capture button grabs; when nil, Xcode delimits a frame by drawable presents (`MTLCommandBuffer.present(_:)` / `MTLDrawable.present()`) — /documentation/Xcode/Creating-and-using-custom-capture-scopes (overloads checked in corpus `metal__mtlcapturemanager.md`) [symbols: MTLCaptureManager.makeCaptureScope(device:), MTLCaptureManager.makeCaptureScope(commandQueue:), MTLCaptureScope.begin(), MTLCaptureScope.end(), MTLCaptureScope.label, MTLCaptureManager.defaultCaptureScope] [gate: MTL4CommandQueue overload for Metal 4]
- Trace replay portability: a GPU trace replays reliably only on the same device type, same GPU, and same OS it came from; an AMD-Mac capture may fail or behave differently on an M1. The Replay dialog picks the device and whether to profile (Profile GPU Trace) — /documentation/Xcode/Replaying-a-GPU-trace-file
- The Shader editor, shader debugger, and per-line profiling need Metal "Produce Debugging Information" set to "Yes, include source code" for Debug; set Release back to No before shipping. For release builds, the alternative is a separate Metal library symbol file per library — /documentation/Xcode/Building-your-project-with-embedded-shader-sources [symbols: MTL_ENABLE_DEBUG_INFO]

Filters: related stack frames only (fresh captures keep call stacks), calls with issues only, markers and commands only — /documentation/Xcode/Analyzing-your-Metal-workload
- Apple-GPU "Performance counters" (Encoders vs GPU Commands tabs, editable counter sets) are gathered with passes serialized, one at a time and without overlap, and include deterministic counts such as vertices. Start with the Performance Limiters set and the Vertices count; twice the expected vertices usually means duplicate meshes or draws. Non-Apple GPUs get a separate Counters viewer with an orange per-pass shader-time bar — /documentation/Xcode/Analyzing-Apple-GPU-performance-using-counter-statistics, /documentation/Xcode/Analyzing-non-Apple-GPU-performance-using-counter-statistics

- Pipeline Statistics viewer (assistant editor > Pipeline Statistics) splits each stage's time into ALU, Memory, Control flow, and Synchronization (wait memory, wait pixel, barrier, atomics), with compiler instruction counts, and lists every command using that PSO with its GPU time. Apple's remedies: ALU → `half` and fewer `sqrt`/`sin`/`cos`/`recip`; Memory → smaller textures (or spend spare bandwidth on resolution); Control flow → constant loop trip counts; wait pixel → blending is the usual cause, use raster order groups — /documentation/Xcode/Analyzing-draw-command-and-compute-dispatch-performance-with-pipeline-statistics

### Counters, occupancy, bandwidth
- Limiter vs utilization: utilization is busy time excluding stalls; a limiter is busy time including stalls. Both kinds exist for MMU, last level cache, tile memory read/write, ALU, texture sampling, texture write, buffer read/write, fragment input interpolation. Limiter only: GPU memory read/write (% of peak), texture filtering, texture read cache. Utilization only: F16, F32. Read them in Instruments' Metal System Trace or the debugger's Performance timeline — /documentation/Xcode/Reducing-shader-bottlenecks
- Apple's bottleneck-to-fix table: ALU → approximations, `half`, `-ffast-math` (MSL spec §1.5), lookup tables or a noise texture; texture sampling → mipmaps for minified textures, bilinear over trilinear, smaller formats, gather for single-channel reads; texture write → smaller formats, fewer MSAA samples, fewer tiny triangles, writes clustered in space/time; buffer read/write → tighter packing, `float4` over four scalars, `packed_half3` instead of `float4` for positions, no dynamically indexed thread-local arrays (they spill to device memory), read via textures, fewer device atomics; tile memory → 16-byte-aligned threadgroup allocations, fewer threadgroup atomics, quad-neighbor threads touching neighboring elements, avoid many threads on one address; interpolation → fewer varyings; last level cache → smaller working sets, compressed formats for read-only textures, do atomics in threadgroup memory first — /documentation/Xcode/Reducing-shader-bottlenecks [symbols: MTLLoadAction.load, MTLStoreAction.store, packed_half3]
- Occupancy is the share of the GPU's maximum resident threads in use, split into compute, vertex, and fragment occupancy that sum to the total. Each shader has its own maximum theoretical occupancy, shown in the Performance timeline. Low occupancy means exhausted thread/threadgroup/imageblock resources, shaders so short that threads finish faster than they launch, or tiny render areas or grids. Neither high nor low is a problem alone; cross-check limiters (low limiters plus low occupancy = little work). Very high occupancy can thrash caches — then reduce access count, size, or change access pattern — /documentation/Xcode/Finding-your-Metal-apps-GPU-occupancy
- Bandwidth counters report GB/s; unexpectedly high GPU bandwidth can starve CPU memory access on unified memory. Reduce it by reading only what a pass needs, writing only what later passes consume, loading/storing only needed attachments, and narrowing `MTLTextureDescriptor.usage` so Metal can optimize access; the Dependencies viewer finds removable loads/stores — /documentation/Xcode/Measuring-the-GPUs-use-of-memory-bandwidth [symbols: MTLTextureUsage, MTLTextureDescriptor.usage]

## shading-language.md

- Contradiction: the Reducing-shader-bottlenecks page tells you to opt into `-ffast-math`, but Xcode already compiles shaders fast by default.
