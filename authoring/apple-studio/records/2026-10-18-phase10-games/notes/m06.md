# Notes m06

## shading-language.md

- MSL 4.1 is the language revision for the OS 27 releases (iOS/iPadOS/macOS/tvOS/visionOS 27); MSL 4.0 pairs with the OS 26 releases; 3.2 with iOS 18/macOS 15; 3.1 with iOS 17/macOS 14/visionOS 1; 3.0 with iOS 16/macOS 13 and is where the per-platform `ios-metalX`/`macos-metalX` -std values were unified into `metalX.Y` — pdf:msl-4.1#ch1 [symbols: -std=metal3.0, -std=metal3.1, -std=metal3.2, -std=metal4.0, -std=metal4.1] [gate: Metal 3.0+ unified]
- New features from language standard 3.2 upward are Apple-silicon only; an Intel/AMD Mac cannot use them regardless of OS — pdf:msl-4.1#ch1 [symbols: -std=metal3.2] [gate: Apple silicon, MSL 3.2+]
- Metal 4 (MSL 4.0+) is C++17-based; every earlier MSL revision is C++14-based. So C++17 idioms (structured bindings, if constexpr, fold expressions, etc.) need -std=metal4.0 or later — pdf:msl-4.1#ch1 [gate: MSL 4.0]
- What MSL 4.1 adds over 4.0: placement new; an RTZ default for float-to-float conversion (`-fmetal-rtz-fp-conversion`); `function_id` in ray intersection results; packed numeric types for block-scaling formats (sec 2.21); multiplane tensors and `tensor_blockwise` (sec 2.22); deinterleave/interleave (sec 6.4); memory order including acquire/release on barriers and atomics (6.10, 6.16); clamp-to-edge texture reads, integer-coordinate reads with offsets, multi-pixel reads (6.13); new Metal Performance Primitives matmul data types — pdf:msl-4.1#ch1 [gate: MSL 4.1 / OS 27]
- C++ features still absent: `dynamic_cast`, RTTI/typeid, `new`/`delete` (except placement new from 4.1), `noexcept` operator, `goto`, `register`/`thread_local`, virtual functions, derived classes (inheritance is listed as unavailable), exceptions. Lambdas arrived in 3.2. Do not include the C++ standard library; use `<metal_stdlib>` — pdf:msl-4.1#ch1 [gate: lambdas MSL 3.2; placement new MSL 4.1]
- Pointer arguments to graphics and kernel functions must carry an address space: `device`, `constant`, `threadgroup`, `threadgroup_imageblock`, `object_data`, or `ray_data`. Function pointers need MSL 2.3+; recursion is allowed only in compute (kernel) context and only from MSL 2.4; a function may not be named `main`; graphics/kernel entry points cannot be overloaded, but ordinary functions may overload on address space — pdf:msl-4.1#ch1 [gate: function pointers MSL 2.3; recursion MSL 2.4 kernels only]
- Version-gate shader code with `__METAL_VERSION__`, encoded MajorMinorPatch (Metal 2.1 patch 1 = 211, Metal 1.2 = 120); `__METAL_MACOS__`/`__METAL_IOS__` mark the old per-platform dialects and `__METAL__` marks the unified dialect (-std=metal3.0+). Platform checks use `<TargetConditionals.h>` macros (`TARGET_OS_OSX`, `TARGET_OS_IOS`, `TARGET_OS_VISION`, `TARGET_OS_SIMULATOR`, ...), which is not part of `<metal_stdlib>` and must be included explicitly — pdf:msl-4.1#ch1 [symbols: __METAL_VERSION__, __METAL__, __METAL_MACOS__, __METAL_IOS__, TARGET_OS_VISION]
- Fast math is the default and is a correctness contract, not just a speed knob: under `-fmetal-math-mode=fast` the compiler may assume no NaN/INF ever occurs, so an `x/y` where y can be zero is undefined behaviour. `relaxed` keeps the reassociation/reciprocal/contract freedoms but honours INF and NaN (Apple silicon); `safe` forbids result-changing transforms and sets FP contract to on. `-fmetal-math-fp32-functions=<fast|precise>` separately picks fast or precise fp32 math library calls (default fast); from Apple GPU Family 4 the fast functions still honour INF/NaN. Legacy `-ffast-math` = fast+fast; `-fno-fast-math` = precise+safe. These options need Xcode 16 / an SDK for iOS 18 or macOS 15 — pdf:msl-4.1#ch1 [symbols: -fmetal-math-mode, -fmetal-math-fp32-functions, -ffast-math, -fno-fast-math] [gate: Xcode 16+ / iOS 18 / macOS 15 SDK; fast fp32 functions honour INF/NaN from Apple4]
- Per-region FP control: `#pragma METAL fp math_mode(relaxed|safe|fast)` and `#pragma METAL fp contract(off|on|fast)` (valid at file/namespace scope or at the start of a compound statement, scoped to it); `#pragma STDC FP_CONTRACT OFF` also works; `-ffp-contract=off` disables FMA contraction globally. Use this when one expression must be bit-reproducible (e.g. a deterministic sim kernel) without giving up fast math elsewhere — pdf:msl-4.1#ch1 [symbols: #pragma METAL fp math_mode, #pragma METAL fp contract, -ffp-contract]
- `[[invariant]]` on vertex outputs (e.g. for multi-pass z-equal depth prepass) is silently ignored unless you compile with `-fpreserve-invariance` (SDKs from iOS 14/macOS 11); the newer model is conservative and can cost performance — pdf:msl-4.1#ch1 [symbols: -fpreserve-invariance, [[invariant]]]
- Shader logging (`os_log` in shaders, sec 6.20) requires compiling with `-fmetal-enable-logging`; MSL 3.2+, Apple silicon only — pdf:msl-4.1#ch1 [symbols: -fmetal-enable-logging] [gate: MSL 3.2, Apple silicon]
- `-Wmetal-addr-spaces` warns when a member function has no address space; the fix-it form (flags in symbols) `-Xclang -fixit -Xclang -fix-what-you-can -Wmetal-addr-spaces` auto-inserts missing `thread` qualifiers — pdf:msl-4.1#ch1 [symbols: -Wmetal-addr-spaces]
- `-ftexture-write-rounding-mode=native|rte|rtz` controls float texture-write rounding (rte/rtz need MSL 2.3, SDK macOS 11/iOS 14); which families honour non-native modes is in the Feature Set Tables — pdf:msl-4.1#ch1 [symbols: -ftexture-write-rounding-mode]
- Coordinate conventions to get right when porting: NDC is left-handed, z visible range is 0..1 (not GL's -1..1), +z points into the screen; viewport/window coordinates have origin top-left, +y down; normalized texture coordinate (0,0) is the top-left (first byte) of the image. With variable rasterization rate the viewport space is logical and a rate map maps it to physical pixels — pdf:msl-4.1#ch1
- No `double`, `long long`, `unsigned long long`, or `long double` exist in MSL at all; 64-bit `long`/`ulong` (`int64_t`/`uint64_t`) need MSL 2.2; `bfloat` (8-bit exponent, 7 stored mantissa bits) needs MSL 3.1; `size_t` and `ptrdiff_t` are 64-bit. Literal suffixes: `h` for half (`0.5h`), `bf` for bfloat (`0.5bf`), `f` for float — pdf:msl-4.1#ch2 [symbols: half, bfloat, long, ulong] [gate: long MSL 2.2; bfloat MSL 3.1]
- Three-component vectors are padded to the four-component size and alignment: `float3` is 16 bytes/16-aligned, `half3` is 8, `int3` 16, `long3` 32. `sizeof(float3)==16`. For tight CPU-shared layouts use `packed_float3` (12 bytes, 4-aligned) and friends (`packed_halfN`, `packed_bfloatN` 3.1+, `packed_longN` 2.3+; `packed_vec<T,n>` generic form). Packed types are storage formats — loads/stores convert to aligned vectors; `.xyzw` swizzles on packed types need MSL 2.1 — pdf:msl-4.1#ch2 [symbols: packed_float3, packed_half4, packed_vec, vec] [gate: packed swizzle MSL 2.1]
- Matrices are column-major, `floatCxR`/`halfCxR` (C columns of R-vectors; also `matrix<T,c,r>`). Padding follows the column vector: `float3x3` is 48 bytes (16-aligned), `float4x3` is 64 bytes, `half3x3` 24 bytes. A single subscript selects a column. Scalar constructor fills the diagonal. Constructing from n*m scalars needs MSL 2; mixing vectors and scalars in a matrix constructor is not supported — pdf:msl-4.1#ch2 [symbols: float3x3, float4x3, half3x3, matrix]
- Writing a swizzle (`pos.xw = ...`) is a read-modify-write of the whole vector; two threads writing different components of the same vector concurrently is undefined. Don't pack per-thread outputs into components of a shared vector — pdf:msl-4.1#ch2
- `simdgroup_matrix<T,8,8>` (`simdgroup_half8x8`, `simdgroup_float8x8`, `simdgroup_bfloat8x8` from 3.1) in `<metal_simdgroup_matrix>` are cooperative across the SIMD-group: every operation must be under SIMD-group-uniform control flow, and the element-to-thread mapping is unspecified — pdf:msl-4.1#ch2 [symbols: simdgroup_matrix, simdgroup_half8x8, simdgroup_float8x8, simdgroup_bfloat8x8] [gate: MSL 2.3; bfloat MSL 3.1]
- Atomic types: `atomic_int`/`atomic_uint` (Metal 1), `atomic_bool`/`atomic_ulong` (MSL 2.4), `atomic_float` (MSL 3.0). `atomic<T>` only accepts those types; atomic functions accept only these atomic types — pdf:msl-4.1#ch2 [symbols: atomic, atomic_int, atomic_uint, atomic_bool, atomic_ulong, atomic_float] [gate: float atomics MSL 3.0; ulong/bool MSL 2.4]
- Pixel data types in `<metal_pixel>` (`r8unorm<T>`, `rg8unorm<T>`, `rgba8unorm<T>`, `srgba8unorm<T>`, `rgba16unorm<T>`, `rgb10a2<T>`, `rg11b10f<T>`, `rgb9e5<T>`, snorm variants) store compressed formats in buffers/threadgroup memory while you compute in `half4`/`float4`; only assignment and ==/!= with the ALU type are allowed. Gate: iOS MSL 2, macOS MSL 2.3 — pdf:msl-4.1#ch2 [symbols: rgba8unorm, srgba8unorm, rg11b10f, rgb9e5, rgb10a2] [gate: macOS MSL 2.3, iOS MSL 2]
- Texture template signature in MSL 3.2+: `texture2d<T, access a = access::sample, memory_coherence c = memory_coherence_threadgroup>`; `memory_coherence_device` makes texture writes visible to other threadgroups (with proper synchronization) — Apple silicon only. Element `T` must match the format class (int/short for sint, uint/ushort for uint, half for normalized/half, float for normalized/half/float); depth textures require `float` — pdf:msl-4.1#ch2 [symbols: texture2d, memory_coherence, memory_coherence_device, depth2d, access::read_write] [gate: memory_coherence MSL 3.2, Apple silicon]
- Access restrictions: multisampled textures are `read` only; depth textures `sample`/`read` only; sparse textures cannot be `write` or `read_write`; textures declared as locals must be `read` or `sample`. `read_write` needs MSL 1.2. `texture2d_ms_array`/`depth2d_ms_array` are macOS-only (MSL 2) — pdf:msl-4.1#ch2 [symbols: texture2d_ms, texture2d_ms_array, depth2d_ms_array, access::sample]
- `texture_buffer<T, access>` (MSL 2.1) views a buffer as a large 1D texel array with hardware format conversion — bigger than a 1D texture's 16384-texel maximum width, one PSO can read data stored in different pixel formats without recompiling; cannot be sampled; out-of-bounds reads return (0,0,0,1) for formats without alpha and (0,0,0,0) with alpha (may be slower on some devices); out-of-bounds writes are dropped — pdf:msl-4.1#ch2 [symbols: texture_buffer] [gate: MSL 2.1]
- In-shader `constexpr sampler` can set only address mode, filter, coord normalization, compare func (plus `max_anisotropy(n)`, `lod_clamp(min,max)`, `reduction`, `bias`). Defaults are a trap: `filter::nearest`, `mip_filter::none` (only mip 0 is ever read), `address::clamp_to_edge`, `compare_func::never`. `coord::pixel` forces equal min/mag filters, no mip filter, and clamp address modes. `clamp_to_border`/`border_color`: macOS MSL 1.2, iOS/iPadOS MSL 2.3. `reduction` (`minimum`/`maximum`) MSL 2.3. `bias` (LOD bias) MSL 4.0, family-gated per the Feature Set Tables. `clamp_to_zero` keeps the texture's alpha — pdf:msl-4.1#ch2 [symbols: constexpr sampler, mip_filter, lod_clamp, max_anisotropy, reduction, clamp_to_border, border_color, bias] [gate: sampler bias MSL 4.0 + FST; reduction MSL 2.3]
- Arrays of textures/samplers: `array<texture2d<float>, N>` (read/sample textures; writable texture arrays on macOS MSL 2, on iOS MSL 2.2 with Apple GPU Family 5+), `array<sampler, N>`, `array<texture_buffer<T>, N>` (MSL 2.1). They cannot be struct members except inside an argument buffer. `array_ref<T>` (via `make_array_ref`) lets user functions accept any-size texture array but cannot be a kernel/graphics argument or a local. `is_null_texture()` tests empty slots — pdf:msl-4.1#ch2 [symbols: array, array_ref, make_array_ref, is_null_texture] [gate: writable texture arrays iOS MSL 2.2 + Apple5]
- A struct of only buffers/textures/samplers (nesting allowed) may be passed by value to graphics/kernel/visible functions with per-member `[[texture(n)]]`/`[[sampler(n)]]`; adding a plain `int` member makes it a compile error — pdf:msl-4.1#ch2
- Argument buffers (MSL 2): structs that contain pointers, textures, texture buffers, samplers — no unions. `[[id(n)]]` indices must be unique and monotonically increasing (gaps allowed); unannotated members get max-previous-ID+1, applied recursively into nested structs and arrays (an array of 3 textures consumes 3 IDs) — this ID layout is what the host-side encoder or Metal 4 argument-table/buffer layout must match — pdf:msl-4.1#ch2 [symbols: [[id(n)]]] [gate: MSL 2]
- Tier 2 argument buffers add: indexing an array of independently encoded argument buffers via pointer (`constant Resources *resArray`), copying resource handles between argument-buffer structs inside a shader (the basis of GPU-driven pipelines), and argument buffers pointing to other argument buffers. Samplers can only be copied argument-buffer-to-argument-buffer (device to device), never from a thread-space sampler or `constexpr sampler` — pdf:msl-4.1#ch2 [gate: argument buffers Tier 2]
- `uniform<T>` (`<metal_uniform>`, MSL 2) marks a value as identical across all threads of the draw/dispatch so the hardware can optimize dynamic indexing into texture arrays/buffers. Lying is undefined behaviour; mixing uniform with non-uniform yields non-uniform; `uniform<device int*>` is illegal but `device uniform<int>*` is fine — pdf:msl-4.1#ch2 [symbols: uniform] [gate: MSL 2]
- Visible function tables `visible_function_table<Sig>` (`<metal_visible_function_table>`): kernels from MSL 2.3, vertex/fragment/tile from 2.4; the GPU cannot modify the table; pass via buffer binding or argument buffer; `is_null_visible_function_table()`. `[[function_groups("g1","g2")]]` on a declaration/expression/return narrows candidate callees so the compiler can optimize the indirect call — pdf:msl-4.1#ch2 [symbols: visible_function_table, is_null_visible_function_table, function_groups] [gate: MSL 2.3 kernel; 2.4 render stages]
- `interpolant<T, interpolation::perspective|no_perspective>` (`<metal_interpolate>`, MSL 2.3) enables pull-model interpolation in fragment shaders; only as a `[[stage_in]]` member (no sampling-and-interpolation attribute) or a local copy of one; not implicitly convertible to T — pdf:msl-4.1#ch2 [symbols: interpolant, interpolation::perspective, interpolation::no_perspective] [gate: MSL 2.3]
- `vertex_value<T>` (`<metal_vertex_value>`, Metal 4) gives the fragment shader the three un-interpolated per-vertex values via `.get(vertex_index::first|second|third)`; pair with `[[barycentric_coord]]` for custom interpolation. GPU support is in the Feature Set Tables — pdf:msl-4.1#ch2 [symbols: vertex_value, vertex_index, barycentric_coord] [gate: MSL 4.0 + FST]
- Type conversions: `static_cast` rounds to nearest-even for float targets and toward zero for integer targets, never saturates; `as_type<T>` reinterprets bits and requires equal sizes (`float4`→`float3` is legal since both are 16 bytes; `half4`→`float4` is an error). `bfloat` converts implicitly only to `float` — never implicitly to/from `half`, and `float`→`bfloat` needs an explicit cast. Vector-to-vector implicit conversion (`float4 f = int4`) is a compile error; scalar-to-vector broadcast is allowed — pdf:msl-4.1#ch2 [symbols: as_type, static_cast, bfloat]
- Integer pitfalls that differ from C++ intuition: integer division by zero or `INT_MIN/-1` gives an unspecified value (no trap); `%` with a zero divisor or with any negative operand is undefined (only nonnegative operands are defined); signed overflow is undefined, unsigned wraps mod 2^n; shift counts use only the low log2(N) bits of the shift amount (so `x << 33` on a 32-bit int shifts by 1) — pdf:msl-4.1#ch3
- Floating division by zero yields ±INF/NaN per IEEE-754 — but under the default fast-math mode the compiler may assume it never happens (see ch1 note) — pdf:msl-4.1#ch3
- Any relational comparison with NaN is false, `==` with NaN false, `!=` true; reduce boolean vectors with `any()`/`all()` inside `if` — pdf:msl-4.1#ch3 [symbols: any, all]
- `half` and `bfloat` cannot be mixed in an operator expression (no implicit conversion either way); cast one side explicitly — pdf:msl-4.1#ch3 [symbols: half, bfloat]
- Bitwise operators are not defined on floating types; use `as_type<uint>` first. Ternary `?:` needs a scalar bool condition (use `select()` for per-component choice) and evaluates only one branch — pdf:msl-4.1#ch3 [symbols: as_type, select]
- Matrix multiply: a vector on the right is a column vector (`m * v`), on the left a row vector (`v * m` = dot with each column); `m * n` is standard linear-algebra product; summation order is unspecified so results need not be bit-identical across compilers/GPUs — pdf:msl-4.1#ch3
- Address-space rules for entry-point arguments: graphics (vertex/fragment) pointer/reference arguments must be `device` or `constant`; kernel arguments may be `device`, `threadgroup`, `threadgroup_imageblock`, or `constant`. Threadgroup-pointer arguments to fragment shaders exist only on some GPUs (see Feature Set Tables). Program-scope variables must be `constant` and initialized with a core constant expression. A pointer or reference without an address space is a compile error — pdf:msl-4.1#ch4 [symbols: device, constant, threadgroup, threadgroup_imageblock, thread]
- `ray_data` (MSL 2.3) and `object_data` (MSL 3.0) are the two newer address spaces; `threadgroup_imageblock` needs iOS MSL 2 / macOS MSL 2.3 — pdf:msl-4.1#ch4 [symbols: ray_data, object_data, threadgroup_imageblock] [gate: ray_data MSL 2.3; object_data MSL 3.0]
- Constant-address-space buffers bound to kernel/vertex/fragment functions have a GPU-specific minimum offset alignment — check "Minimum constant buffer offset alignment" in the Feature Set Tables before sub-allocating uniforms from a ring buffer — pdf:msl-4.1#ch4 [gate: FST minimum constant buffer offset alignment]
- Threadgroup memory is allocated in kernel, mesh, and object functions; it lives only for the threadgroup's lifetime — except in a mid-render kernel (tile function), where threadgroup variables persist across the tile's tile and fragment functions — pdf:msl-4.1#ch4 [symbols: threadgroup, [[threadgroup(n)]]]
- SIMD-group mapping is stable for a kernel's run, across dispatches with the same launch parameters, and across threadgroups (except trailing-edge threadgroups with non-uniform sizes); all SIMD-groups are equal size except possibly the highest-indexed one. A quad-group is a SIMD-group of width 4. Gates: macOS SIMD-group MSL 2, quad-group 2.1; iOS quad-group MSL 2, some SIMD-group functions 2.2 — pdf:msl-4.1#ch4 [gate: macOS simd MSL 2; iOS simd MSL 2.2]
- Memory coherence (MSL 3.2+, Apple silicon): `device` memory is by default only threadgroup-coherent — writes from one threadgroup are not guaranteed visible to another even with barriers. To communicate across threadgroups within a dispatch (e.g. single-pass reductions, persistent-thread work queues), qualify buffers `coherent(device)` and textures `memory_coherence_device`, and synchronize properly (atomics / memory order) — pdf:msl-4.1#ch4 [symbols: coherent(device), memory_coherence_device] [gate: MSL 3.2, Apple silicon]
- Function kinds and attributes: `[[vertex]]`, `[[fragment]]`, `[[kernel]]` (keyword forms since Metal 1, attribute forms MSL 2.3), `[[visible]]` (2.3), `[[stitchable]]` (2.4), `[[intersection(...)]]` (2.3), `[[object]]` and `[[mesh]]` (3.0); tile functions are kernels or fragments used mid-render. Entry points cannot call each other but may call `[[visible]]` functions and reach intersection functions only via `intersect()`. Kernels, object and mesh functions must return `void` — pdf:msl-4.1#ch5 [symbols: vertex, fragment, kernel, visible, stitchable, intersection, object, mesh] [gate: MSL 2.3 attribute spelling; object/mesh MSL 3.0]
- Namespaces: from MSL 2.2 a qualified function declared inside a namespace must be looked up from the API by its fully qualified name (`outer::inner::functionB`). `[[host_name("abc")]]` (MSL 2.2) overrides the API name and is how you give each explicit template instantiation of a templated entry point (`template [[host_name("bar_int")]] kernel void bar(device int*);`) a distinct name — templates must be explicitly instantiated to emit code — pdf:msl-4.1#ch5 [symbols: host_name, newFunctionWithName] [gate: MSL 2.2]
- `[[user_annotation("str")]]` (Metal 4) attaches a string to a qualified function readable through reflection; template instantiations inherit it unless overridden — pdf:msl-4.1#ch5 [symbols: user_annotation] [gate: MSL 4.0]
- Device buffer arguments of one entry point are assumed not to alias each other (no overlapping ranges across separate arguments) — binding overlapping views of one MTLBuffer to two arguments is a contract violation. Program-scope (global) resource bindings (MSL 3.2) carry no such no-alias assumption and must be given explicit indices — pdf:msl-4.1#ch5 [gate: globals MSL 3.2]
- Entry-point arguments cannot be `size_t`/`ptrdiff_t` or structs containing them; cannot be derived classes; `[[stage_in]]` struct members must be scalars, vectors, or (fragment) `interpolant` — no packed vectors, matrices, nested structs, arrays, pointers. Only one `[[stage_in]]` argument per function — pdf:msl-4.1#ch5 [symbols: stage_in, attribute]
- Binding attributes: `[[buffer(n)]]` covers device/constant buffers, acceleration structures, intersection function tables, and tensors; `[[texture(n)]]` covers textures and texture buffers; `[[sampler(n)]]`; `[[threadgroup(n)]]`. Unannotated arguments get the first free index per resource class; function-constant-assigned indices are skipped by the auto-assigner; duplicate indices are compile errors unless guarded by function constants — pdf:msl-4.1#ch5 [symbols: buffer, texture, sampler, threadgroup]
- Program-scope built-ins (MSL 3.1): declare e.g. `uint2 gid [[thread_position_in_grid]];` globally and use it in kernel/tile/mesh/object helpers without threading it through parameters — not usable in dynamic libraries or separately compiled binary functions until MSL 3.2 (Apple silicon). MSL 3.2 also allows global `device`/`constant`/`threadgroup` buffers, textures and samplers with explicit binding attributes; multiple globals may share a binding only with identical type; `extern` declarations must match type and binding — pdf:msl-4.1#ch5 [symbols: thread_position_in_grid] [gate: MSL 3.1; dylib use MSL 3.2 Apple silicon]
- Storage classes: `static` only for program-scope `constant` variables; `extern` for program-scope declarations or locals; `thread_local` unsupported — pdf:msl-4.1#ch5
- Interpolation qualifiers on fragment `[[stage_in]]` members: `center_perspective` (default), `center_no_perspective`, `centroid_perspective`, `centroid_no_perspective`, `sample_perspective`, `sample_no_perspective`, `flat`. Integers must be `flat`; `[[position]]` input only `center_no_perspective`. From MSL 2.4 a qualifier on a nested struct member is inherited by its fields — pdf:msl-4.1#ch5 [symbols: center_perspective, centroid_perspective, sample_perspective, flat] [gate: struct inheritance MSL 2.4]
- Vertex–fragment linkage: matching is by `[[user(name)]]` if present, otherwise by member name and exact type (`float3` vs `half3` mismatch fails), or the fragment may declare `interpolant<T,P>`. A vertex function returning `float4` returns position implicitly; a struct return needs a `[[position]]` member. `void` return only with rasterization disabled; a vertex function that writes buffers/textures must return `void`. Vertex/fragment return types cannot contain packed vectors, matrices, structs, references, or pointers — pdf:msl-4.1#ch5 [symbols: user, position, interpolant]
- Mesh→fragment linkage: per-vertex mesh outputs interpolate, per-primitive outputs never do; a `flat` fragment input matched to a per-vertex output gets the provoking vertex's value — pdf:msl-4.1#ch5 [gate: MSL 3.0]
- Fragment `[[stage_in]]` input count is limited per GPU family (vector counts as its component count) — see "Implementation Limits by GPU Family" in the Feature Set Tables; `[[viewport_array_index]]` as fragment input counts against it — pdf:msl-4.1#ch5 [gate: FST implementation limits]
- Writes a vertex function makes to a buffer are not guaranteed visible to that primitive's fragment function — pdf:msl-4.1#ch5
- Built-in type rules for vertex: `[[vertex_id]]`/`[[instance_id]]` include `[[base_vertex]]`/`[[base_instance]]`; if the id is `ushort` the base must be `ushort` too — pdf:msl-4.1#ch5 [symbols: vertex_id, instance_id, base_vertex, base_instance]
- Function constants (MSL 1.2; resource indices, `color()`/`raster_order_group` indices, and optional struct members from MSL 2): `constant T name [[function_constant(i)]]` with i in 0–65535, scalar or vector types only, values supplied at specialization (`MTLFunctionConstantValues` via `MTLFunctionDescriptor`). `is_function_constant_defined(name)` is false if unset. An argument or `[[stage_in]]`/struct member tagged `[[function_constant(flag)]]` exists only when flag is true — this replaces `#ifdef`'d signatures, so one library ships and variants are produced at pipeline creation instead of compiling every macro permutation offline. Do not put function constants on imageblock struct members — pdf:msl-4.1#ch5 [symbols: function_constant, is_function_constant_defined, MTLFunctionDescriptor, MTLFunctionConstantValues] [gate: MSL 1.2; binding indices MSL 2]

## pipelines-and-render-passes.md

- Offline compile to GPU binaries (SDK iOS 16/macOS 13+): `-arch <arch>`, `-gpu-family <MTLGPUFamily name>`, and `-N descriptor.mtlp-json` to feed pipeline descriptors in Metal script format — this is the path to shipping precompiled pipeline binaries and avoiding runtime compile hitches — pdf:msl-4.1#ch1 [symbols: -arch, -gpu-family, -N, .mtlp-json, MTLGPUFamily]

## apple-gpu-tbdr.md

- Imageblocks: a 2D (width, height, samples) structure in threadgroup/tile memory with opaque layout. Fragment functions see only their own pixel's imageblock data, dimensions from the tile size; kernel (tile) functions see the whole imageblock, typically sized from threadgroup size. Elements may be scalars, vectors, pixel types, arrays, or structs. Gate: iOS MSL 2, macOS MSL 2.3 (i.e. Apple silicon Macs) — pdf:msl-4.1#ch2 [symbols: imageblock, imageblock_data] [gate: macOS MSL 2.3, iOS MSL 2]
- Imageblock slice → render-target format compatibility (Table 2.8): `half`/`float` slices store to R32Float/R16Float/R8Unorm/R8Snorm/R16Unorm/R16Snorm; `half4`/`float4` to RGBA32Float/RGBA16Float/RGBA8Unorm/RGBA8Snorm/RGBA16Unorm/RGBA16Snorm/RGB10A2Unorm/RG11B10Float/RGB9E5Float; `rgba8unorm<T>` to RGBA8Unorm or BGRA8Unorm; `srgba8unorm<T>` to the _sRGB variants; integer vectors to matching Sint/Uint formats. Using pixel types in the imageblock shrinks tile-memory footprint — pdf:msl-4.1#ch2 [symbols: rgba8unorm, srgba8unorm, MTLPixelFormatBGRA8Unorm]
- `threadgroup_imageblock` memory is reachable only through `imageblock<T, L>`; a tile function may take a pointer to a user type in that space. Exactly one threadgroup runs per tile, with access to that tile's threadgroup memory and imageblock; do not assume any spatial mapping from thread to imageblock pixel (threadgroup may be smaller than the tile) — pdf:msl-4.1#ch4 [symbols: threadgroup_imageblock, imageblock] [gate: macOS MSL 2.3]
- Threadgroup variables in a tile (mid-render kernel) function persist across the tile and fragment functions for that tile — the mechanism for keeping per-tile data (light lists, etc.) on chip between passes — pdf:msl-4.1#ch4
- Tile functions (iOS MSL 2; macOS MSL 2.3, i.e. Apple silicon): compute dispatched inside a render pass between draws, fully barriered against earlier and later draws in that pass; the GPU finishes each tile's draws and dispatches before moving on. They get 32 KB of threadgroup memory shared between imageblock and threadgroup storage; imageblock size depends on tile width × height × per-sample bit depth (from attachments for implicit layout, or the declared struct for explicit layout) — pdf:msl-4.1#ch5 [symbols: tile function, threadgroup_imageblock] [gate: macOS MSL 2.3]
- Fragment tile inputs: `[[pixel_position_in_tile]]` and `[[pixels_per_tile]]` (same type, ushort2/uint2), `[[tile_index]]` in [0, tiles), `[[render_target_array_index]]` — macOS MSL 2.3 / iOS MSL 2 — pdf:msl-4.1#ch5 [symbols: pixel_position_in_tile, pixels_per_tile, tile_index]
- In tile kernels, `thread_index_in_threadgroup` is not a row-major function of the 2D position (only unique in [0, Sx*Sy)), and threads are packed as 2×2 quads, so `simdgroups_per_threadgroup = ceil(Wx/2)*ceil(Wy/2)*4/threads_per_simdgroup` — pdf:msl-4.1#ch5 [symbols: thread_index_in_threadgroup, simdgroups_per_threadgroup, quadgroups_per_threadgroup]
- Programmable blending / framebuffer fetch: read the current attachment value via a fragment input `[[color(m)]]` (iOS Metal 1; macOS MSL 2.3, Apple silicon). This is the implicit imageblock: types are ALU types and Metal picks the storage format; pixel storage types are not allowed there — pdf:msl-4.1#ch5 [symbols: color] [gate: macOS MSL 2.3]
- Explicit imageblock layout (`[[imageblock_data(MasterType)]]` on fragment input/output; `imageblock<T, imageblock_layout_explicit|imageblock_layout_implicit>` in kernels, `<metal_imageblocks>`): you declare the per-pixel struct (scalars, vectors, pixel types like `rgb9e5<float4>`/`rgba8unorm<half4>`, arrays, structs) — a G-buffer that never leaves tile memory. View structs pick a subset by `[[user(name)]]` or same name+type; each view field maps to exactly one master field; no `[[color(n)]]` members in explicit imageblocks — pdf:msl-4.1#ch5 [symbols: imageblock_data, imageblock, imageblock_layout_explicit, imageblock_layout_implicit, user] [gate: macOS MSL 2.3 Apple silicon]
- Raster order groups with imageblocks: in fragment functions every master explicit-imageblock member must carry `[[raster_order_group(i)]]` (either on a nested struct as a whole or on each of its fields, not both; arrays get one group for all elements); view-struct groups must match the master; in kernels the attribute is ignored — pdf:msl-4.1#ch5 [symbols: raster_order_group]
- Explicit and implicit imageblocks are separate storage unless the explicit one is tagged `[[alias_implicit_imageblock]]` (alias all) or `[[alias_implicit_imageblock_color(n)]]` (alias starting at attachment n; n beyond declared attachments is silently ignored, n naming a gap is a compile error). Writing aliased members through the explicit view then reading the implicit side is undefined — pdf:msl-4.1#ch5 [symbols: alias_implicit_imageblock, alias_implicit_imageblock_color]
- Raster order groups (MSL 2) in general: `[[raster_order_group(i)]]` on a device buffer or texture argument (not threadgroup/constant, not on a struct; allowed on argument-buffer members) serializes overlapping fragments at the same pixel/sample in submission order; different indices synchronize independently. This is how order-independent transparency / custom blending on device memory stays correct — pdf:msl-4.1#ch5 [symbols: raster_order_group] [gate: MSL 2]
