# Notes m01

## command-model.md

- Metal 4 gate at runtime: `[device supportsFamily:MTLGPUFamilyMetal4]` (`MTLGPUFamily.metal4`). Apple's triangle sample ships two renderers, a Metal 4 one and a fallback on the older API, and picks one at launch; the sample's own floor is iOS/tvOS 16, macOS 13 because of that fallback. — /documentation/Metal/drawing-a-triangle-with-metal-4 [symbols: MTLDevice.supportsFamily(_:), MTLGPUFamily.metal4] [gate: Metal 3 vs 4]
- Frames in flight, Metal 4 shape: `kMaxFramesInFlight = 3` (encode N, GPU runs N-1, display shows N-2). Per-frame copies: one `MTL4CommandAllocator` and one data buffer per in-flight frame. Shared across frames: one `MTL4CommandBuffer`, one `MTL4ArgumentTable`, one long-lived `MTLResidencySet`. — /documentation/Metal/drawing-a-triangle-with-metal-4 [symbols: MTL4CommandAllocator, MTL4CommandBuffer, MTL4ArgumentTable, MTLResidencySet]
- Reuse rules, the core Metal 4 gotcha: you may reuse a `MTL4CommandBuffer` right after committing it, because its allocator keeps the recorded commands. You may not reuse the allocator until the GPU finishes that frame. Per frame: `[allocator reset]` then `[commandBuffer beginCommandBufferWithAllocator:allocator]`, and at the end `endCommandBuffer`. — /documentation/Metal/drawing-a-triangle-with-metal-4 [symbols: MTL4CommandAllocator.reset(), MTL4CommandBuffer.beginCommandBuffer(allocator:), MTL4CommandBuffer.endCommandBuffer()]
- CPU throttle with a shared event: create it with `newSharedEvent` and set `signaledValue = 0`. Before reusing frame slot N, call `waitUntilSignaledValue:N-kMax timeoutMS:10` (Swift `wait(untilSignaledValue:timeoutMS:)`). After the commit, queue `[commandQueue signalEvent:sharedEvent value:frameNumber]`. Example: frame 4's signal frees its resources for frame 7. Ideally the wait returns at once. — /documentation/Metal/drawing-a-triangle-with-metal-4 [symbols: MTLSharedEvent, MTLSharedEvent.wait(untilSignaledValue:timeoutMS:), MTLSharedEvent.signaledValue, MTL4CommandQueue.signalEvent(_:value:)]
- Residency in Metal 4: `[residencySet addAllocation:buf]` for each long-lived buffer, then `[residencySet commit]`, then `[commandQueue addResidencySet:residencySet]`. Also add the layer's own set, `((CAMetalLayer *)view.layer).residencySet`, which MetalKit maintains for drawables. — /documentation/Metal/drawing-a-triangle-with-metal-4 [symbols: MTLResidencySet.addAllocation(_:), MTLResidencySet.commit(), MTL4CommandQueue.addResidencySet(_:), CAMetalLayer.residencySet]
- Metal 4 submit order, on the GPU timeline: `[queue waitForDrawable:d]` → `[queue commit:&cb count:1]` → `[queue signalDrawable:d]` → `[d present]` → `[queue signalEvent:…]`. Command buffers can go to any queue only when both come from the same device. — /documentation/Metal/drawing-a-triangle-with-metal-4; /documentation/Metal/combining-blit-and-compute-operations-in-a-single-pass [symbols: MTL4CommandQueue.waitForDrawable(_:), MTL4CommandQueue.commit(_:options:), commit:count:, MTL4CommandQueue.signalDrawable(_:), MTLDrawable.present()]
- Metal 4 object creation: `[device newMTL4CommandQueue]` (Swift `makeMTL4CommandQueue()`), and the command buffer comes from the device (`[device newCommandBuffer]`), not from the queue. The Metal 4 encoder kinds are `MTL4ComputeCommandEncoder`, `MTL4RenderCommandEncoder`, and `MTL4MachineLearningCommandEncoder`; one command buffer can hold several passes of mixed kinds. — /documentation/Metal/drawing-a-triangle-with-metal-4 [symbols: MTLDevice.makeMTL4CommandQueue(), MTL4MachineLearningCommandEncoder]
- Argument tables: one table can bind `MTLBuffer` (by `gpuAddress`), `MTLTexture` (by `gpuResourceID`), `MTLTensor`, `MTLSamplerState`, and `MTLAccelerationStructure`. Size `maxBufferBindCount` / `maxTextureBindCount` to the most you bind at once, because a smaller table uses less memory. You can edit a table after `setArgumentTable`, since Metal reads it at each draw or dispatch, so one table serves many draws and both pass kinds. On a render encoder, bind with `setArgumentTable:atStages:` (e.g. `MTLRenderStageVertex`). — /documentation/Metal/drawing-a-triangle-with-metal-4; /documentation/Metal/combining-blit-and-compute-operations-in-a-single-pass [symbols: MTL4ArgumentTableDescriptor, newArgumentTableWithDescriptor:error:, MTL4ArgumentTable.setAddress(_:index:), setTexture:atIndex:, setArgumentTable:atStages:, MTLTensor]
- Metal 4 has no separate blit encoder. `MTL4ComputeCommandEncoder` holds copies, dispatches, and acceleration-structure builds in a single pass, which cuts encoder overhead. Copies to different textures or non-overlapping regions run concurrently; copies to overlapping regions run in sequence. — /documentation/Metal/combining-blit-and-compute-operations-in-a-single-pass [symbols: MTL4ComputeCommandEncoder, copyFromTexture:sourceSlice:sourceLevel:sourceOrigin:sourceSize:toTexture:destinationSlice:destinationLevel:destinationOrigin:] [gate: Metal 4, iOS/tvOS/macOS 26]
- Intrapass barrier for copy-then-dispatch inside one Metal 4 compute pass: `barrierAfterEncoderStages:MTLStageBlit beforeEncoderStages:MTLStageDispatch visibilityOptions:MTL4VisibilityOptionDevice`. Without it the dispatch can read a half-finished copy. — /documentation/Metal/combining-blit-and-compute-operations-in-a-single-pass [symbols: barrierAfterEncoderStages:beforeEncoderStages:visibilityOptions:, MTLStages.blit, MTLStages.dispatch, MTL4VisibilityOptions.device]
- Cross-pass hazard in Metal 4 is a consumer barrier on the later encoder: `barrierAfterQueueStages:MTLStageDispatch beforeStages:MTLStageFragment visibilityOptions:MTL4VisibilityOptionDevice`. "AfterQueueStages" names stages of earlier passes; "beforeStages" names this pass and later ones. Name only the stage that reads (here fragment, not vertex), so the vertex work can overlap the earlier compute pass. Over-broad stage masks cost GPU time. — /documentation/Metal/combining-blit-and-compute-operations-in-a-single-pass [symbols: barrierAfterQueueStages:beforeStages:visibilityOptions:, MTLStages.fragment, MTLStages.vertex]
- Metal 3 vs 4 hazard model: in Metal 3, a pass that writes a tracked resource and a later pass that reads it run in order automatically, because Metal detects the dependency. The Metal 4 sample for the same write-then-sample pattern encodes an explicit barrier. Code ported from Metal 3 therefore needs barriers wherever Metal 3 inferred an order. — /documentation/Metal/customizing-render-pass-setup vs /documentation/Metal/combining-blit-and-compute-operations-in-a-single-pass [gate: Metal 3 vs 4]
- Two event kinds: `MTLEvent` syncs within one device. `MTLSharedEvent` syncs across devices, the CPU, or processes, and costs more, so don't use it for same-device sync. An event holds a UInt64 that starts at 0 and only rises (a smaller signal is ignored). A wait holds later queue work until the value reaches the target. — /documentation/Metal/about-synchronization-events [symbols: MTLEvent, MTLSharedEvent]
- Event spelling, Metal 3: `MTLCommandBuffer.encodeSignalEvent(_:value:)` / `encodeWaitForEvent(_:value:)`, legal only between encoders. Metal 4 moves both to the queue: `MTL4CommandQueue.signalEvent(_:value:)` / `waitForEvent(_:value:)` (confirmed on the MTL4CommandQueue symbol page). — /documentation/Metal/about-synchronization-events [symbols: MTLCommandBuffer.encodeSignalEvent(_:value:), MTLCommandBuffer.encodeWaitForEvent(_:value:), MTL4CommandQueue.signalEvent(_:value:), MTL4CommandQueue.waitForEvent(_:value:)] [gate: Metal 3 vs 4]
- Metal 3 argument-buffer residency: `useResource(_:usage:stages:)` / `useResources` per resource, and `useHeap(_:stages:)` / `useHeaps` per heap. Heap calls take no usage and mark everything `.read`; to allow writes, add a `useResource` after the `useHeap`, and Metal combines the usages. Metal 4 encoders have no `useResource` or `useHeap` (checked the MTL4RenderCommandEncoder and MTL4CommandEncoder pages); residency sets replace them. — /documentation/Metal/argument-buffer-resource-preparation-commands [symbols: MTLRenderCommandEncoder.useResource(_:usage:stages:), useHeap(_:stages:), MTLResourceUsage.read, MTLComputeCommandEncoder.useResource(_:usage:), useHeap(_:)] [gate: Metal 3 only]
- Compute-pass setup objects are thread-safe; the encoder itself is not. CPU access to a resource during a GPU pass that uses it can corrupt memory and show as visual artifacts; sync with `MTLFence`, `MTLEvent`, or a completion handler. Untracked resources need manual fences and barriers (`MTLHazardTrackingMode`). — /documentation/Metal/compute-passes [symbols: MTLComputeCommandEncoder, MTLFence, MTLHazardTrackingMode]
- Treat with care: compute-passes says a resource must be `.shared` or `.managed` to be resident for argument-buffer use. That conflicts with putting private resources in argument buffers. Check the `useResource` symbol page before repeating the claim. — /documentation/Metal/compute-passes
- Feature detection: there are four family kinds (Common, Apple, Mac, Mac Catalyst). Within one family, a higher member is always a superset. Gate with `supportsFamily(_:)`, check features that vary inside a family with per-feature properties (e.g. `argumentBuffersSupport == .tier2`), and gate APIs with `#available`. Design a few paths (current GPUs and earlier ones) rather than one path per GPU. `supportsFeatureSet(_:)` / `MTLFeatureSet` is the legacy path for old OSes only. The page's Swift writes `.familyMac2`; the symbol is `MTLGPUFamily.mac2`. — /documentation/Metal/detecting-gpu-features-and-metal-software-versions [symbols: MTLDevice.supportsFamily(_:), MTLGPUFamily, MTLDevice.argumentBuffersSupport, MTLArgumentBuffersTier.tier2, MTLDevice.supportsFeatureSet(_:), MTLFeatureSet]
- Device selection: on iOS and tvOS, `MTLCreateSystemDefaultDevice()` is the one GPU. On a dual-GPU Intel MacBook Pro the default is the discrete GPU. Apple silicon Macs have exactly one GPU. The default-GPU page labels an Objective-C snippet as Swift. — /documentation/Metal/getting-the-default-gpu; /documentation/Metal/finding-multiple-gpus-on-an-intel-based-mac [symbols: MTLCreateSystemDefaultDevice()]
- Intel multi-GPU enumeration: `MTLCopyAllDevices()` gives a snapshot. `MTLCopyAllDevicesWithObserver(handler:)` gives the list plus change notifications; remove the observer with `MTLRemoveDeviceObserver(_:)`. GPU type from `isLowPower` / `isRemovable`: integrated is (true, false), discrete (false, false), external (false, true). `isHeadless` means no display, which suits compute. Power and bandwidth: integrated is low power with high bandwidth, discrete medium power with high bandwidth, external high power with low bandwidth. Start on the integrated GPU, move heavy work to discrete, and use an eGPU for ALU-heavy or high-resolution work that moves little data per frame. — /documentation/Metal/finding-multiple-gpus-on-an-intel-based-mac [symbols: MTLCopyAllDevices(), MTLCopyAllDevicesWithObserver(handler:), MTLRemoveDeviceObserver(_:), MTLDevice.isLowPower, MTLDevice.isRemovable, MTLDevice.isHeadless] [gate: Intel Macs]
- eGPU hot-unplug: Metal posts `MTLDeviceNotificationName.wasAdded`, `.removalRequested`, and `.wasRemoved`. After `removalRequested` the app has about one second to move its work off the device and drop every reference, or macOS names the app as blocking the disconnect. An unsafe yank posts `wasRemoved` with no warning; queued command buffers then complete with an error, and any new call on that device fails. — /documentation/Metal/handling-external-gpu-additions-and-removals [symbols: MTLDeviceNotificationName.wasAdded, .removalRequested, .wasRemoved] [gate: Intel Macs]
- Suspension: when the app is suspended, use the command queue to finish command buffers already in flight (see "Preparing your Metal app to run in the background"). The Metal 4 submission types are listed together on this page: `MTL4CommandQueueDescriptor`, `MTL4CommandBufferOptions`, `MTL4RenderEncoderOptions`, `MTL4CommandAllocatorDescriptor`, `MTL4CommitOptions`, `MTL4CommitFeedback` / `MTL4CommitFeedbackHandler`, and `MTL4CommandQueueError`. — /documentation/Metal/gpu-devices-and-work-submission [symbols: MTL4CommitOptions, MTL4CommitFeedback, MTL4CommitFeedbackHandler, MTL4CommandQueueError]
- Visibility-result buffers are read on the CPU while the GPU writes the next frame's buffer, so keep a ring of (frames in flight + 1) `.storageModeShared` buffers. Advance the read index in the command buffer's completion handler, next to the in-flight semaphore signal. — /documentation/Metal/culling-occluded-geometry-using-the-visibility-result-buffer [symbols: MTLCommandBuffer.addCompletedHandler(_:)]

## pipelines-and-render-passes.md

- Metal 4 compile path: `MTL4CompilerDescriptor` → `[device newCompilerWithDescriptor:error:]` → `MTL4Compiler`. Name each function with `MTL4LibraryFunctionDescriptor` (`.library`, `.name`) and set them on `MTL4RenderPipelineDescriptor.vertexFunctionDescriptor` / `.fragmentFunctionDescriptor` or `MTL4ComputePipelineDescriptor.computeFunctionDescriptor`. Build the pipeline on the compiler, not the device: `newRenderPipelineStateWithDescriptor:compilerTaskOptions:error:` / `newComputePipelineStateWithDescriptor:compilerTaskOptions:error:`. `MTL4CompilerTaskOptions` carries references to binary archives. Xcode turns on API validation by default in debug builds. — /documentation/Metal/drawing-a-triangle-with-metal-4; /documentation/Metal/combining-blit-and-compute-operations-in-a-single-pass [symbols: MTL4CompilerDescriptor, MTL4Compiler, MTL4LibraryFunctionDescriptor, MTL4RenderPipelineDescriptor, MTL4ComputePipelineDescriptor, MTL4CompilerTaskOptions] [gate: Metal 4]
- MetalKit with Metal 4: `MTKView.currentMTL4RenderPassDescriptor` supplies the pass descriptor (its color attachment 0 is `currentDrawable`), and `[commandBuffer renderCommandEncoderWithDescriptor:]` returns an `MTL4RenderCommandEncoder`. Label encoders and command buffers so passes are easy to find in the Metal debugger. — /documentation/Metal/drawing-a-triangle-with-metal-4 [symbols: MTKView.currentMTL4RenderPassDescriptor, MTKView.currentDrawable, MTL4CommandBuffer.makeRenderCommandEncoder(descriptor:options:), MTL4RenderPassDescriptor]
- Metal 4 binary-archive flow (the archive articles below are Metal 3): attach an `MTL4PipelineDataSetSerializer` to `MTL4CompilerDescriptor` to record every pipeline the compiler builds. Then call `serializeAsArchiveAndFlush(url:)` to write an archive, or `serializeAsPipelinesScript()` to get a `metal-tt` script. Load pipelines through `MTL4Archive` (`makeRenderPipelineState(descriptor:dynamicLinkingDescriptor:)`, `makeComputePipelineState(descriptor:dynamicLinkingDescriptor:)`, `makeBinaryFunction(descriptor:)`). A serializer can't speed up a compiler it isn't attached to, and its data can't be read back. — cross-check of /documentation/Metal/creating-binary-archives-from-device-built-pipeline-state-objects against the MTL4Archive and MTL4PipelineDataSetSerializer symbol pages [symbols: MTL4PipelineDataSetSerializer, serializeAsArchiveAndFlush(url:), serializeAsPipelinesScript(), MTL4Archive] [gate: Metal 4]
- Metal 3 archive harvest loop: create an `MTLBinaryArchive` from a descriptor whose `url` is nil, which creates a new archive rather than loading one. Call `addRenderPipelineFunctions(descriptor:)` for every pipeline, then `serialize(to:)`. Pull the file off the device: on macOS from `~/Library/Application Support/<bundle id>/`, on iOS via Xcode Devices → Download Container. `metal-source -flatbuffers=json` extracts the `.mtlp-json` script; point its `libraries.paths[].path` at Xcode's IR metallib. Run `metal-tt -target air64-apple-ios16.0 -gpu-family metal3 script.mtlp-json -o precompiled.binary.metallib`, bundle the result, and load it with `makeBinaryArchive(descriptor:)` plus `binaryArchives.append`. — /documentation/Metal/creating-binary-archives-from-device-built-pipeline-state-objects [symbols: MTLBinaryArchive, MTLBinaryArchiveDescriptor.url, addRenderPipelineFunctions(descriptor:), serialize(to:), MTLDevice.makeBinaryArchive(descriptor:), MTLRenderPipelineDescriptor.binaryArchives]
- Archive gotchas: create the archive before the pipelines it records (faster compile, less memory). On macOS, write runtime archives outside the app bundle, because writing inside breaks code signing. Archives keep an IR slice (`air64_v26`), and an OS update can invalidate the GPU binary, which then recompiles from IR. A missing archive silently falls back to a runtime compile unless the pipeline sets `MTLPipelineOption.failOnBinaryArchiveMiss`; use that in QA to catch hitches. On-device serialization of specialized functions needs macOS 15 / iOS 18. An M1 Pro produces `applegpu_g13g`; `metal-lipo -archs` lists an archive's slices. — /documentation/Metal/creating-binary-archives-from-device-built-pipeline-state-objects [symbols: MTLPipelineOption.failOnBinaryArchiveMiss] [gate: macOS 15 / iOS 18 for specialized-function serialization]
- Hand-written `metal-tt` scripts need no device harvest. The file must end in `.mtlp-json`. Keys:
  - `libraries.paths[{label, path}]`
  - `pipelines.render_pipelines[{vertex_function, fragment_function, color_attachments[{pixel_format}]}]`
  - `pipelines.compute_pipelines[{compute_function, linked_functions.binary_functions[]}]`
  - `functions.intersection_functions[{function}]` and `functions.visible_functions`
  - `specialized_functions[{label, function, constant_values[{id_type:"FunctionConstantName", id, value_type:"ConstantBool", value.data}]}]`

  Reference a function as `alias:<library label>#<name>` and a specialization as `alias:<specialization label>#<name>`; `binary_functions` takes bare names, not aliases. Omitted fields take the descriptor defaults. Tile shaders need an `enable` condition. Full format: `man metal-pipelines-script`. — /documentation/Metal/compiling-binary-archives-from-a-custom-configuration-script [symbols: MTLFunctionDescriptor.binaryArchives, MTLFunctionDescriptor.specializedName, MTLFunctionOptions.compileToBinary, MTLFunctionConstantValues, MTLLinkedFunctions.binaryFunctions]
- Hitch trap: a function-constant combination with no specialized entry in the archive falls back to an IR compile at runtime. By default `metal-tt` builds every GPU architecture the target triple supports (the example lists applegpu_g5p through g16p). — /documentation/Metal/compiling-binary-archives-from-a-custom-configuration-script
- Offline shader build: compile each file with `xcrun -sdk macosx metal -c X.metal -o X.ir`. Optionally bundle IR with `metal-ar -q Lights.metalar a.ir b.ir`. Link IR files and archives into a library with `metal -o Out.metallib …`, and load it with `makeLibrary(URL:)`. The Windows Metal tools take the same flags. — /documentation/Metal/building-a-shader-library-by-precompiling-source-files [symbols: MTLDevice.makeLibrary(URL:)]
- Metal dynamic libraries reduce both metallib size and compile time when several libraries share utility code. Build with `metal -dynamiclib utilities.metal -o … -install_name libUtility.metallib`; the install name must have the form `lib<Name>.metallib` or the linker can't find it. Link with `metal shaders.ir -o shaders.metallib -lUtility -L ./`. Ship both files in the bundle with the same relative layout as `-L`. Load with `makeDynamicLibrary(url:)` and add the result to the descriptor's `insertLibraries`. Optionally, `metal-tt` adds GPU binaries to the dylib, using flags from `metal-config --native-arch-flags --gpu-family=metal3`. — /documentation/Metal/compiling-and-linking-metal-dynamic-libraries [symbols: MTLDevice.makeDynamicLibrary(url:), MTLComputePipelineDescriptor.insertLibraries] [gate: FST: render and compute dynamic libraries Apple6+]
- Don't copy Apple's Swift on the dynamic-library page: it uses `fn`, a nonexistent `MTLComputePipeline` type, and a throwing call without `try`, and its file names drift (`libUtility.ir.metallib` vs `libUtility.metalir.metallib`). The serialize snippet on the binary-archive page also uses `fn` and has syntax errors. — /documentation/Metal/compiling-and-linking-metal-dynamic-libraries; /documentation/Metal/creating-binary-archives-from-device-built-pipeline-state-objects
- Depth testing: `MTKView` has no depth target until you set `depthStencilPixelFormat` (e.g. `.depth32Float`). The pipeline's `depthAttachmentPixelFormat` must match. The depth test is a separate `MTLDepthStencilState`, built once from `MTLDepthStencilDescriptor` (`depthCompareFunction`, `isDepthWriteEnabled`) and set per draw with `setDepthStencilState`; you can mix pipelines and depth states freely. `clearDepth` sets the clear value (1.0). Writing depth in the fragment shader can disable the early depth test. — /documentation/Metal/calculating-primitive-visibility-using-depth-testing [symbols: MTKView.depthStencilPixelFormat, MTKView.clearDepth, MTLRenderPipelineDescriptor.depthAttachmentPixelFormat, MTLDepthStencilDescriptor, MTLDepthStencilState, MTLCompareFunction.lessEqual]
- Offscreen pass: set `MTLTextureDescriptor.usage` to exactly the uses you need (`.renderTarget | .shaderRead`) so Metal can lay out the texture for just those. Pipeline color formats must match their target: `colorPixelFormat` for the view pass, the texture's own format for the offscreen pass. Load and store actions are a bandwidth and battery lever: use clear + store when a later pass samples the result. A drawable pass: `loadAction = .clear`, `storeAction = .store`, and skip the frame if `nextDrawable()` returns nil. — /documentation/Metal/customizing-render-pass-setup; /documentation/Metal/creating-a-custom-metal-view [symbols: MTLTextureUsage.renderTarget, MTLTextureUsage.shaderRead, MTLLoadAction.clear, MTLStoreAction.store, MTKView.colorPixelFormat, CAMetalLayer.nextDrawable()]
- Occlusion queries: point `MTLRenderPassDescriptor.visibilityResultBuffer` at a buffer of `uint64_t` slots. Before each draw, call `setVisibilityResultMode(_:offset:)` with `.counting` (number of fragments that pass depth and stencil) or `.boolean` (nonzero if any pass); the offset is in bytes (`index * 8`). Metal 4 spelling: `MTL4RenderPassDescriptor.visibilityResultBuffer`, plus `visibilityResultType` (accumulate across encoders or reset), and `MTL4RenderCommandEncoder.setVisibilityResultMode(_:offset:)`. — /documentation/Metal/culling-occluded-geometry-using-the-visibility-result-buffer (Metal 4 names from the MTL4RenderPassDescriptor and MTL4RenderCommandEncoder pages) [symbols: MTLRenderPassDescriptor.visibilityResultBuffer, setVisibilityResultMode(_:offset:), MTLVisibilityResultMode.counting, MTLVisibilityResultMode.boolean, MTL4RenderPassDescriptor.visibilityResultType, MTLVisibilityResultType] [gate: the counting sample needs MTLGPUFamily.apple3; Simulator lacks counting occlusion queries]
- CPU-side occlusion culling recipe: draw last frame's survivors. Then draw cheap proxies (an icosahedron that fully contains the sphere) with a pipeline that has no fragment function and a depth state with writes off but the test on, in boolean mode per object. Next frame, skip objects whose slot reads 0. Results arrive one frame late, so moving objects pop in; Apple scales the proxy by an animation factor (4 in the sample; 1 suits static scenes, 8 loses most of the benefit). Fragment counts can also choose an LOD. — /documentation/Metal/culling-occluded-geometry-using-the-visibility-result-buffer
- Variable rasterization rate: set `MTLRasterizationRateMapDescriptor.screenSize` to the layer's `drawableSize`. Create one `MTLRasterizationRateLayerDescriptor(sampleCount: zoneCounts)` per layer, with per-column `horizontal[]` and per-row `vertical[]` rates from 0 to 1. Attach with `setLayer(_:at:)` and build with `makeRasterizationRateMap(descriptor:)`. Metal guarantees at least the requested rate and may split cells or raise rates. Zone counts should divide the screen size evenly. — /documentation/Metal/creating-a-rasterization-rate-map [symbols: MTLRasterizationRateMapDescriptor, MTLRasterizationRateLayerDescriptor, MTLDevice.makeRasterizationRateMap(descriptor:)] [gate: FST: variable rasterization rate Apple6+]

## apple-gpu-tbdr.md

- Memoryless means tile memory: more bandwidth, lower latency, and less power than system memory. It works for textures only (no memoryless buffers). Use it for a depth, stencil, or intermediate target that lives within one pass and isn't needed before or after it. — /documentation/Metal/choosing-a-resource-storage-mode-for-apple-gpus [symbols: MTLStorageMode.memoryless, MTLTextureDescriptor.storageMode] [gate: FST: memoryless render targets Apple2+]
- Don't copy Apple's memoryless snippet: it creates a mipmapped `.r16Float` texture and assigns it to `depthAttachment`, but that isn't a depth format. — /documentation/Metal/choosing-a-resource-storage-mode-for-apple-gpus
- Compute passes on Apple GPUs can reserve tile memory as threadgroup or imageblock memory; you reserve it rather than copy data into it. Cited MSL spec sections: 4.4 `threadgroup`, 4.5 `threadgroup_imageblock`, 2.11 imageblocks, 5.6 imageblock attributes. — /documentation/Metal/compute-passes

## resources-and-memory.md

- Apple GPU storage choice: CPU-written data → `.shared` (the default for buffers and textures). GPU-produced data (render targets, intermediates, streamed textures) → `.private`. Pass-local textures → `.memoryless`. — /documentation/Metal/choosing-a-resource-storage-mode-for-apple-gpus [symbols: MTLStorageMode.shared, MTLStorageMode.private, MTLStorageMode.memoryless]
- Intel/AMD Macs: prefer the storage mode Metal picks by default, and use `.private` for GPU-only resources, including render-pass temporaries. To upload, copy from a CPU-filled default-mode resource into a private one. The page says shared resources exist only with integrated graphics (Apple silicon, Intel iGPU). Under memory pressure Metal may evict a private resource to system memory and copy it back before use. `.managed` on a discrete GPU is a pair of allocations and needs an explicit synchronize after CPU or GPU writes. Keep sync points few and batch work. — /documentation/Metal/choosing-a-resource-storage-mode-for-intel-and-amd-gpus [symbols: MTLStorageMode.managed] [gate: Intel Macs]
- On macOS, Metal doesn't rearrange buffer contents, so managed and private buffers perform the same on the GPU; copying a managed buffer to private gains nothing. Upload recipes (Metal 3 blit spellings):
  - shared buffer → private buffer: `copy(from:sourceOffset:to:destinationOffset:size:)`
  - shared buffer → private texture, one copy and no managed-texture sync: `copy(from:sourceOffset:sourceBytesPerRow:sourceBytesPerImage:sourceSize:to:destinationSlice:destinationLevel:destinationOrigin:)`
  - managed texture → private: costs two copies
  - private texture → shared buffer (readback): `copy(from:sourceSlice:sourceLevel:sourceOrigin:sourceSize:to:destinationOffset:destinationBytesPerRow:destinationBytesPerImage:)`

  In Metal 4 these copy commands live on `MTL4ComputeCommandEncoder`. — /documentation/Metal/copying-data-to-a-private-resource [symbols: MTLBlitCommandEncoder.copy variants, MTLDevice.makeBuffer(bytes:length:options:)]
- Mip copies: call `replace(region:mipmapLevel:withBytes:bytesPerRow:)` once per level. Texture to texture, `copy(from:to:)` copies every mip whose size matches (same format and type), and `copy(from:sourceSlice:sourceLevel:to:destinationSlice:destinationLevel:sliceCount:levelCount:)` copies a range whose first levels match in size. Buffer to texture or back takes one blit per mip. — /documentation/Metal/copying-data-into-or-out-of-mipmaps [symbols: MTLTexture.replace(region:mipmapLevel:withBytes:bytesPerRow:), MTLBlitCommandEncoder.copy(from:to:)]
- Mipmaps: `mipmapLevelCount` defaults to 1, and a full chain costs about 33% more memory. Metal neither initializes mips nor tracks which ones you filled. `MTKTextureLoader` options: `.allocateMipmaps` allocates all levels but fills only level 0; `.generateMipmaps` allocates and filters them. Apple's sample computes the count as `ceil(log2(max dim))`, one short of a full chain for power-of-two sizes (256 needs 9 levels, i.e. floor(log2)+1). — /documentation/Metal/creating-a-mipmapped-texture [symbols: MTLTextureDescriptor.mipmapLevelCount, MTKTextureLoader.Option.allocateMipmaps, MTKTextureLoader.Option.generateMipmaps]
- Mip generation choices:
  - Runtime: blit `generateMipmaps(for:)` after filling level 0. It runs asynchronously, and the filter is implementation-defined, so results differ between GPUs.
  - Offline, with good tools: better quality, larger download.
  - Custom filters or MPS: at runtime or offline.

  — /documentation/Metal/generating-mipmap-data [symbols: MTLBlitCommandEncoder.generateMipmaps(for:)]
- Mip streaming: Metal allocates every level at texture creation. Load the small levels first (starting at level 3 is about 2% of the chain's data), and clamp sampling to the loaded levels, either with a sampler that sets the minimum LOD or, on some GPUs, with a min-LOD value passed to the shader. Detect when a closer level is needed (LOD queries or projected size), copy those mips in, and widen the clamp. — /documentation/Metal/dynamically-adjusting-texture-level-of-detail
- Samplers read only mip 0 unless `MTLSamplerDescriptor.mipFilter` is set; linear min, mag, and mip filters give trilinear filtering. MSL equivalent: `constexpr sampler s(filter::linear, mip_filter::linear)`. — /documentation/Metal/adding-mipmap-filtering-to-samplers [symbols: MTLSamplerDescriptor.mipFilter, MTLSamplerMipFilter.linear, MTLSamplerMinMagFilter.linear]
- Metal has no file-to-texture loader; use `MTKTextureLoader`, Image I/O, or your own code. Texture memory is uninitialized at creation, and there is no CPU pointer into texture storage, only `replace` and `getBytes`. A texture's format and layout are fixed for life; only its contents change. The texture-coordinate origin is the top-left corner. — /documentation/Metal/creating-and-sampling-textures [symbols: MTKTextureLoader, MTLTexture.replace(region:mipmapLevel:withBytes:bytesPerRow:)]
- Buffers come from an `MTLDevice` or an `MTLHeap` (`makeBuffer(length:options:)`). — /documentation/Metal/buffers [symbols: MTLBuffer, MTLHeap.makeBuffer(length:options:)]
- Sparse heaps: set `MTLHeapDescriptor.type = .sparse`. Storage must be `.private`, and the size a multiple of `sparseTileSizeInBytes`. Textures made on the heap are sparse and get no memory until mapped. Apple advises one sparse heap for all streamed textures unless you need to partition memory, sized so you rarely have to unmap. — /documentation/Metal/creating-sparse-heaps-and-sparse-textures [symbols: MTLHeapType.sparse, MTLDevice.sparseTileSizeInBytes, MTLHeap.makeTexture(descriptor:)] [gate: FST: sparse textures Apple6+; sparse depth/stencil Apple8 (also some Apple7, including all Apple7 Macs); placement sparse buffers and textures Metal 4, Apple8 (some Apple7; check MTLDevice.supportsPlacementSparse)]
- Sparse tile states, per region: unmapped, mapped but uninitialized, initialized. Metal never fills a newly mapped tile, so write it before sampling. Unmapped tiles read as zero. Mapping runs on the GPU asynchronously, in encode order and row-major within a request. If the heap runs out, the rest of the request is silently skipped. — /documentation/Metal/assigning-memory-to-sparse-textures; /documentation/Metal/estimating-how-often-a-texture-region-is-accessed
- Sparse mapping spellings. Metal 3: `MTLResourceStateCommandEncoder.updateTextureMapping(_:mode:region:mipLevel:slice:)` with `MTLSparseTextureMappingMode.map` / `.unmap`, with the region in tile units. Metal 4 moves mapping to the queue: `MTL4CommandQueue.updateMappings(texture:heap:operations:)` with `MTL4UpdateSparseTextureMappingOperation`, plus buffer variants and `copyMappings(sourceTexture:destinationTexture:operations:)`. — /documentation/Metal/assigning-memory-to-sparse-textures (Metal 4 names from the MTL4CommandQueue symbol page) [symbols: MTLResourceStateCommandEncoder, updateTextureMapping(_:mode:region:mipLevel:slice:), MTLSparseTextureMappingMode, MTL4CommandQueue.updateMappings(texture:heap:operations:), MTL4UpdateSparseTextureMappingOperation] [gate: Metal 3 vs 4]
- Sparse gotchas:
  - Unmap every tile before releasing a sparse texture, or the heap keeps those tiles marked as used. Releasing the heap frees everything.
  - Map the mip tail at creation by mapping any region of `firstMipmapInTail`; that maps the whole packed tail, typically one tile. Keep it mapped for the texture's life so sampling always finds data.
  - Never remap while the texture is being read or written; order the two with a fence or an event.
  - Two resource-state encoders on the same sparse heap must run in sequence, or the app may crash. Across queues, order them with shared events.

  — /documentation/Metal/assigning-memory-to-sparse-textures [symbols: MTLTexture.firstMipmapInTail]
- Tile geometry: a sparse tile has a fixed byte size per device, but its pixel dimensions vary by format; get them from `sparseTileSize(with:pixelFormat:sampleCount:)`. Convert regions with `convertSparsePixelRegions(_:toTileRegions:withTileSize:alignmentMode:numRegions:)`, where `.outward` covers partly touched tiles and `.inward` drops them, and with `convertSparseTileRegions(_:toPixelRegions:withTileSize:numRegions:)`. The page's worked example has a typo: a 2×3-tile region at 64 px is 128×192, not 128×196. — /documentation/Metal/converting-between-pixel-regions-and-sparse-tile-regions [symbols: MTLDevice.sparseTileSize(with:pixelFormat:sampleCount:), MTLDevice.convertSparsePixelRegions(_:toTileRegions:withTileSize:alignmentMode:numRegions:), MTLDevice.convertSparseTileRegions(_:toPixelRegions:withTileSize:numRegions:), MTLSparseTextureRegionAlignmentMode]
- Choosing which sparse tiles to map: the blit command `getTextureAccessCounters(_:region:mipLevel:slice:resetCounters:countersBuffer:countersBufferOffset:)` writes one `uint32` per tile, as a row-major 3D array. Counts come from cache misses, not exact accesses (hot regions stay cached and read low), and are scaled per cache line (a 64 B line of 4 B pixels adds 16). Pick your own threshold for mapping a tile. Use one command per mip or texture, but one large counter buffer with offsets. I found no Metal 4 counterpart on the cached MTL4 encoder pages. — /documentation/Metal/estimating-how-often-a-texture-region-is-accessed [symbols: MTLBlitCommandEncoder.getTextureAccessCounters(_:region:mipLevel:slice:resetCounters:countersBuffer:countersBufferOffset:)]
- Intel multi-GPU bandwidth, relative: Thunderbolt 3 = 1x, PCIe x8 = 2x, PCIe x16 = 4x. GPU-to-GPU copies go through system memory. For discrete GPUs and eGPUs, shared resources are slowest, private fastest, and managed in between. — /documentation/Metal/adjusting-for-gpu-memory-bandwidth-tradeoffs [gate: Intel Macs]
- Simulator resource limits that no Metal API reports, so branch on `#if targetEnvironment(simulator)`:
  - Depth, stencil, and MSAA textures must be private.
  - No MSAA sample count of 2; only combined depth-stencil formats.
  - Banned formats: `r8Unorm_srgb`, `b5g6r5Unorm`, `a1bgr5Unorm`, `abgr4Unorm`, `bgr5A1Unorm`, XR10, YUV. No rendering to `rgb9e5Float`, no writes to sRGB textures.
  - Textures backed by a private buffer use different alignment (`minimumLinearTextureAlignment(for:)`) and can't have `renderTarget` usage.
  - Heaps must be private.
  - Constant buffers: at most 64 KB each, offsets aligned to 256 B (devices need 4 B), at most 14 per pipeline.

  — /documentation/Metal/developing-metal-apps-that-run-in-simulator [symbols: MTLBuffer.makeTexture(descriptor:offset:bytesPerRow:), MTLDevice.minimumLinearTextureAlignment(for:)]

## shading-language.md

- Thread-position attributes for kernels: `[[thread_position_in_grid]]`, `[[thread_position_in_threadgroup]]`, `[[threadgroup_position_in_grid]]`, `[[threads_per_threadgroup]]`; grid position = group position × group size + position in group. Size the buffer as `encodedLength × instance count`. Index per instance with `[[instance_id]]` and pass that index to the fragment stage through `[[stage_in]]`. — /documentation/Metal/encoding-argument-buffers-on-the-gpu [symbols: MTLArgumentEncoder.encodedLength] [gate: argument buffers Tier 2 for GPU writes]

## compute-and-gpu-driven.md

- Threadgroup sizing: `threadExecutionWidth` is the SIMD width. `maxTotalThreadsPerThreadgroup` depends on the GPU and on the kernel's register and threadgroup-memory use; it is fixed once the pipeline exists, and two pipelines on one device can differ. The largest group is `w × (max / w) × 1`. — /documentation/Metal/calculating-threadgroup-and-grid-sizes [symbols: MTLComputePipelineState.threadExecutionWidth, MTLComputePipelineState.maxTotalThreadsPerThreadgroup]
- `dispatchThreads(_:threadsPerThreadgroup:)` takes a total thread count and lets Metal make smaller edge groups: no bounds check, simpler kernels, faster. `dispatchThreadgroups(_:threadsPerThreadgroup:)` takes group counts rounded up, so the kernel must exit early past the data bounds. Worked numbers: max 512 with width 16 gives 16×32; a 1024×768 texture gives 32×48 = 1536 groups. Apple's Metal 4 sample uses a fixed 16×16 group, which it says runs on any Apple silicon GPU. — /documentation/Metal/calculating-threadgroup-and-grid-sizes; /documentation/Metal/combining-blit-and-compute-operations-in-a-single-pass [symbols: dispatchThreads(_:threadsPerThreadgroup:), dispatchThreadgroups(_:threadsPerThreadgroup:)] [gate: FST: nonuniform threadgroup size Apple4+]
- SIMD groups: Metal fixes how threadgroups split into SIMD groups for the whole dispatch, across dispatches with the same launch parameters, and from one threadgroup to the next. The SIMD size equals `threadExecutionWidth` and doesn't depend on threadgroup size. A divergent branch inside a SIMD group costs the time of both paths. — /documentation/Metal/creating-threads-and-threadgroups
- ICB basics: an ICB keeps commands across frames, so you encode once and replay. You can fill it from many CPU threads or from a GPU kernel. Good uses: a HUD, static scene geometry. Create it with `MTLIndirectCommandBufferDescriptor` (`commandTypes`, `inheritBuffers`, `inheritPipelineState`, `maxVertexBufferBindCount`, `maxFragmentBufferBindCount`) and `makeIndirectCommandBuffer(descriptor:maxCommandCount:options:)`. Encode from the CPU through `indirectRenderCommand(at:)` → `MTLIndirectRenderCommand.setVertexBuffer(_:offset:at:)` / `drawPrimitives(…)`. Replay with `executeCommandsInBuffer:withRange:`. State an ICB can't hold (cull mode, depth/stencil) is inherited from the parent encoder. — /documentation/Metal/encoding-indirect-command-buffers-on-the-cpu; /documentation/Metal/creating-an-indirect-command-buffer [symbols: MTLIndirectCommandBufferDescriptor, MTLDevice.makeIndirectCommandBuffer(descriptor:maxCommandCount:options:), MTLIndirectCommandBuffer.indirectRenderCommand(at:), MTLIndirectRenderCommand, MTLRenderCommandEncoder.executeCommandsInBuffer(_:range:)] [gate: FST: ICB render and compute Apple3+; ICB memory barriers Apple3 compute / Apple9 render; raster and depth/stencil state inside ICBs Apple10]
- ICB data updates: you can't rebind an ICB's buffers after encoding, so don't rotate buffers inside it. Fill a per-frame ring buffer on the CPU, then blit it into one fixed buffer that the ICB references. In Metal 3, each buffer the ICB references needs `useResource(_:usage:)` on the executing encoder; in Metal 4 that is residency-set membership. — /documentation/Metal/encoding-indirect-command-buffers-on-the-cpu [gate: Metal 3 spelling]
- GPU-driven culling with an ICB: pack all meshes into one vertex buffer with an offset/size table, because iOS kernels can see only a limited number of buffers. Pass the ICB to the kernel inside an argument buffer (`MTLArgumentEncoder.setIndirectCommandBuffer(_:index:)`, plus `useResource(icb, usage: .write)` in Metal 3). Each frame: blit `resetCommandsInBuffer:withRange:`, dispatch the kernel that culls and encodes, blit `optimizeIndirectCommandBuffer:withRange:` to strip empty commands and redundant state, then `executeCommandsInBuffer:withRange:` on the render encoder. The host chooses where the ICB's commands land in the command stream. — /documentation/Metal/encoding-indirect-command-buffers-on-the-gpu [symbols: MTLArgumentEncoder.setIndirectCommandBuffer(_:index:), MTLBlitCommandEncoder.resetCommandsInBuffer(_:range:), MTLBlitCommandEncoder.optimizeIndirectCommandBuffer(_:range:)]
- Optimize gotcha: after `optimizeIndirectCommandBuffer`, an execute range can't start inside the optimized region; start it at the region's beginning. The page also names an `executeIndirectCommandBuffer` method, which doesn't exist (a typo for `executeCommandsInBuffer`). — /documentation/Metal/encoding-indirect-command-buffers-on-the-gpu
- Metal 4 ICB spellings (checked on the cached encoder pages): `MTL4ComputeCommandEncoder.resetCommands(buffer:range:)`, `optimizeCommands(buffer:range:)`, and `copyCommands(sourceBuffer:sourceRange:destinationBuffer:destinationIndex:)`. Both Metal 4 encoders have `executeCommands(buffer:range:)` and `executeCommands(buffer:indirectBuffer:)`, where the second takes the range from a GPU address. — cross-check from /documentation/Metal/encoding-indirect-command-buffers-on-the-gpu [symbols: MTL4ComputeCommandEncoder.resetCommands(buffer:range:), optimizeCommands(buffer:range:), executeCommands(buffer:range:), executeCommands(buffer:indirectBuffer:)] [gate: Metal 4]
- Argument buffer tiers: Tier 2 lets shaders write argument buffers (Tier 1 can only read them) and allows more textures per instanced draw. Check with `argumentBuffersSupport != .tier2`. — /documentation/Metal/encoding-argument-buffers-on-the-gpu [symbols: MTLDevice.argumentBuffersSupport, MTLArgumentBuffersTier.tier2]
- Mesh shaders: Apple's LOD sample needs `MTLGPUFamily.mac2` or `.apple7` on a physical device, because Simulator has no mesh shaders. The page pairs apple7 with "A15 or later", but the FST puts mesh shading at Apple7 (A14); trust the FST. FST limits: payload up to 16,384 B, minus 16 B if the mesh shader takes `[[threadgroups_per_grid]]` or `[[threads_per_grid]]`. ICBs with mesh draws need Apple9+. In render pipelines, mesh shading doesn't combine with function pointers or ray tracing. — /documentation/Metal/adjusting-the-level-of-detail-using-metal-mesh-shaders [symbols: MTLGPUFamily.mac2, MTLGPUFamily.apple7] [gate: FST: mesh shading Apple7+, Metal 3 & 4]
- Kernels reach visible and intersection functions through function tables (function pointers), which also enable stitching and runtime dynamic-library linking. — /documentation/Metal/compute-passes [gate: FST: function pointers in compute and render Apple6+]
- Several sample pages carry only WWDC links and OS floors, no API content: ray tracing (`accelerating-ray-tracing-using-metal`, `…-and-motion-blur…`, `control-the-ray-tracing-process-using-intersection-queries`; sessions WWDC20 10012, WWDC21 10149, WWDC22 10105), and function pointers and stitching (WWDC21 10229, WWDC22 6596). — those paths [gate: FST: ray tracing compute and render Apple6+; per-component motion interpolation Apple9+]

## gpu-debugging-and-profiling.md

- Counter discovery: check `MTLDevice.counterSets` for the `MTLCommonCounterSet` you want, then that set's `counters` for the specific `MTLCommonCounter`. A supported set can still lack some counters, and skipping the check can crash on a player's machine. — /documentation/Metal/confirming-which-counters-and-counter-sets-a-gpu-supports [symbols: MTLDevice.counterSets, MTLCounterSet.counters, MTLCommonCounterSet, MTLCommonCounter]
- Counter sample buffers (Metal 3): build an `MTLCounterSampleBufferDescriptor` (`counterSet`; `storageMode` `.shared` for a CPU resolve or `.private` for GPU only; `sampleCount`) and call `makeCounterSampleBuffer(descriptor:)`. Per-stage timing of a render pass takes 4 samples: `startOfVertexSampleIndex`, `endOfVertexSampleIndex`, `startOfFragmentSampleIndex`, `endOfFragmentSampleIndex` on `MTLRenderPassSampleBufferAttachmentDescriptor`. Blit and compute passes attach theirs through `MTLBlitPassDescriptor` / `MTLComputePassDescriptor`. Set `MTLCounterDontSample` to skip a slot. FST: counter sample buffers max out at 32 KB. — /documentation/Metal/creating-a-counter-sample-buffer-to-store-a-gpus-counter-data-during-a-pass; /documentation/Metal/blit-passes; /documentation/Metal/gpu-counters-and-counter-sample-buffers [symbols: MTLCounterSampleBufferDescriptor, MTLDevice.makeCounterSampleBuffer(descriptor:), MTLRenderPassSampleBufferAttachmentDescriptor, MTLBlitPassSampleBufferAttachmentDescriptor, MTLComputePassSampleBufferAttachmentDescriptor, MTLCounterDontSample]
- Resolving counters: for a shared buffer, call `resolveCounterRange(_:)` on the CPU after the pass, in `addCompletedHandler`. For a private buffer, use the blit `resolveCounters(_:range:destinationBuffer:destinationOffset:)`, which on some GPUs is the only way; follow with `synchronize(resource:)` if the destination is managed. Cast results by set: timestamp → `MTLCounterResultTimestamp`, stageUtilization → `MTLCounterResultStageUtilization`, statistic → `MTLCounterResultStatistic`. Check every sample against `MTLCounterErrorValue` and against 0. — /documentation/Metal/converting-a-gpus-counter-data-into-a-readable-format [symbols: MTLCounterSampleBuffer.resolveCounterRange(_:), MTLBlitCommandEncoder.resolveCounters(_:range:destinationBuffer:destinationOffset:), MTLCounterResultTimestamp, MTLCounterResultStageUtilization, MTLCounterResultStatistic, MTLCounterErrorValue]
- Metal 4 counters work differently: `MTL4CounterHeap` (from `MTL4CounterHeapDescriptor`) has an `MTL4CounterHeapType` with only `.timestamp` (plus `.invalid`). Its entries are `MTL4TimestampHeapEntry`, `MTL4TimestampGranularity` hints the accuracy you want, and it offers `resolveCounterRange(_:)` and `invalidateCounterRange(_:)`. The stage-utilization and statistic sets exist only on the Metal 3 path. FST: performance counter heaps are Metal 4 on Apple7+, max 32 per process. — /documentation/Metal/gpu-devices-and-work-submission; cross-check against the MTL4CounterHeap symbol pages [symbols: MTL4CounterHeap, MTL4CounterHeapDescriptor, MTL4CounterHeapType.timestamp, MTL4TimestampHeapEntry, MTL4TimestampGranularity] [gate: Metal 4, Apple7+]
- GPU time to CPU time: sample both clocks with `MTLDevice.sampleTimestamps()` (Objective-C `sampleTimestamps:gpuTimestamp:`) when you create the command buffer and again in its completion handler. Convert with `cpu = (gpu − gpuStart) / gpuSpan × cpuSpan + cpuStart`; CPU time is in ns, and `MTLTimestamp` counts ns. Call it sparingly, since it can trap into the kernel; sample every N frames. — /documentation/Metal/converting-gpu-timestamps-into-cpu-time [symbols: MTLDevice.sampleTimestamps(), MTLTimestamp]
- Shader symbols for shipped builds: `metal -frecord-sources=flat a.metal b.metal` writes `default.metallib` plus `default.metallibsym`; this flag replaces the deprecated `-MO`. Multi-step version: `metal -c -frecord-sources` per file, link with `-frecord-sources`, then `metal-dsymutil -flat -remove-source X.metallib` to strip the sources into `X.metallibsym`. The App Store build must not carry shader source, and this avoids building twice. In Xcode, load symbols through the debugger's Import Sources prompt or Debug > Import Metallib Debug Info. Needs Xcode 13+. The page's `-c` step makes `.air` files, despite an earlier page naming them `.ir`. — /documentation/Metal/generating-and-loading-a-metal-library-symbol-file
- Metal 4 commit feedback: `MTL4CommitOptions` can carry an `MTL4CommitFeedbackHandler` that returns an `MTL4CommitFeedback` object with debug information after the work completes. This is the Metal 4 hook for per-commit GPU timing and errors, in place of command-buffer completion handlers. Read the symbol page before relying on exact fields. — /documentation/Metal/gpu-devices-and-work-submission [symbols: MTL4CommitOptions, MTL4CommitFeedback, MTL4CommitFeedbackHandler]
- Simulator: no Xcode memory-footprint analysis or performance measurement, so profile on devices. — /documentation/Metal/developing-metal-apps-that-run-in-simulator
- The programmatic-capture sample page holds only WWDC19 session 606 and an Xcode 11 floor. — /documentation/Metal/capturing-metal-commands-programmatically

## display-and-upscaling.md

- EDR capability: `NSScreen.maximumPotentialExtendedDynamicRangeColorComponentValue` > 1.0 means the display can show EDR. The current headroom, `maximumExtendedDynamicRangeColorComponentValue`, changes with display state. EDR is display-referred: values in 0…1 look exactly like SDR, and headroom usually grows as the user lowers brightness. At maximum brightness, or on a non-HDR panel, the range may equal SDR; a Pro Display XDR always has headroom above SDR. — /documentation/Metal/determining-support-for-edr-values; /documentation/Metal/displaying-hdr-content-in-a-metal-layer [symbols: NSScreen.maximumPotentialExtendedDynamicRangeColorComponentValue, NSScreen.maximumExtendedDynamicRangeColorComponentValue] [gate: macOS]
- HDR strategy on a `CAMetalLayer` (games pick the third):
  1. Content already tone-mapped: let a color space apply the transfer function.
  2. Video that must match AVFoundation playback: linear color space plus system tone mapping (EDR metadata).
  3. Arbitrary rendered content, reference displays, or when speed matters more than matching the system: turn system tone mapping off and tone-map to the current headroom yourself.

  `AVPlayerLayer` / `AVSampleBufferDisplayLayer` handle HDR video by themselves. — /documentation/Metal/displaying-hdr-content-in-a-metal-layer; /documentation/Metal/hdr-content [symbols: CAMetalLayer, AVPlayerLayer, AVSampleBufferDisplayLayer]
- Custom view without MetalKit: a UIKit view returns `CAMetalLayer` from `+layerClass`; an AppKit view sets `wantsLayer = YES` and returns `[CAMetalLayer layer]` from `makeBackingLayer`. Recreate the display link whenever the view moves to another screen (`didMoveToWindow` / `viewDidMoveToWindow`). — /documentation/Metal/creating-a-custom-metal-view [symbols: CAMetalLayer, UIView.layerClass, NSView.wantsLayer, NSView.makeBackingLayer(), CAMetalDrawable]
- Contradiction: the custom-view sample says `CADisplayLink` isn't available on macOS and uses `CVDisplayLink` (`CVDisplayLinkCreateWithActiveCGDisplays`, `CVDisplayLinkSetOutputCallback`, `CVDisplayLinkSetCurrentCGDisplay`). The cached CADisplayLink symbol page lists macOS 14.0+, so treat the CVDisplayLink path as legacy. — /documentation/Metal/creating-a-custom-metal-view [symbols: CADisplayLink, CVDisplayLink] [gate: CADisplayLink macOS 14+]
- The `CAMetalDisplayLink` pacing sample page (WWDC23 10123, "Bring your game to Mac") has no API text; read the symbol pages instead. — /documentation/Metal/achieving-smooth-frame-rates-with-a-metal-display-link
- Multi-GPU Macs: render the drawable on the GPU that drives the target display, or the system copies every frame across the bus (TB3 or PCIe). On an auto-switching MacBook Pro this means the integrated GPU while it drives the panel. Track changes with `NSWindow.didChangeScreenNotification` (the window moved to another display) and `NSApplication.didChangeScreenParametersNotification` (configuration change, including a GPU switch). Then get the display's `CGDirectDisplayID` from `screen.deviceDescription["NSScreenNumber"]` and the GPU driving it from `CGDirectDisplayCopyCurrentMetalDevice(_:)`. — /documentation/Metal/getting-the-gpu-that-drives-a-views-display; /documentation/Metal/adjusting-for-gpu-memory-bandwidth-tradeoffs [symbols: NSWindow.didChangeScreenNotification, NSApplication.didChangeScreenParametersNotification, CGDirectDisplayCopyCurrentMetalDevice(_:), CGDirectDisplayID] [gate: Intel Macs]
- Intel display topology:
  - On a dual-GPU laptop, only the discrete GPU drives external displays, and it also drives the built-in panel whenever an external display is attached.
  - The integrated GPU drives only the built-in panel, and only when no external display is connected.
  - An eGPU can't drive the built-in display, and a display attached to an eGPU is driven only by that eGPU.

  Option: offer the player a GPU and display choice instead of a fixed policy. — /documentation/Metal/assessing-multi-gpu-and-multi-display-setups-on-an-intel-based-mac [gate: Intel Macs]

## apple-games/game-loop-and-threading.md

- Custom-view render-thread choice: rendering on the main thread keeps UI calls simple; rendering on a background thread keeps the UI responsive while the CPU encodes. ## apple-games/game-design.md

- Text legibility across devices: honor the system text-size setting, and avoid fixed-size fonts and fixed-size UI elements. ## app-release/direct-distribution.md

- Rosetta: general-purpose availability runs through macOS 27. After that Apple keeps only a subset aimed at older, unmaintained games built on Intel frameworks. Ship arm64. — /documentation/Apple-Silicon/about-the-rosetta-translation-environment [gate: macOS 27 is the last general-purpose Rosetta release]
- Rosetta works per process: arm64 and x86_64 code can't mix in one process, so one Intel-only plug-in forces the whole app under translation. It handles AVX and AVX2 but not AVX-512 (probe `hw.optional.avx512f` with `sysctlbyname`), and it won't translate kernel extensions or x86 virtual-machine apps. Detect translation with `sysctlbyname("sysctl.proc_translated")`: 1 means translated, 0 native, and ENOENT also means native. — /documentation/Apple-Silicon/about-the-rosetta-translation-environment [symbols: sysctlbyname]
- Info.plist launch control:
  - `LSRequiresNativeExecution = YES` blocks running under Rosetta and removes the "Open using Rosetta" checkbox from Get Info. Add it only after testing both architectures.
  - `LSArchitecturePriority` (an ordered array) prefers an architecture without forbidding the other.
  - An app with no executable binary (script-only) runs under Rosetta as a precaution unless `LSArchitecturePriority` lists arm64 first.

  — /documentation/Apple-Silicon/building-a-universal-macos-binary [symbols: LSRequiresNativeExecution, LSArchitecturePriority]
- eGPU Info.plist keys for Intel Mac builds:
  - `GPUEjectPolicy`: `wait` means the app handles `removalRequested` itself, and Apple recommends it. `relaunch` means macOS quits and relaunches the app on another GPU; save state through `application(_:willEncodeRestorableState:)` / `application(_:didDecodeRestorableState:)`. `kill` means a forced quit.
  - `GPUSelectionPolicy`: `avoidRemovable` (only if the app runs badly on eGPUs) or `preferRemovable`.

  — /documentation/Metal/handling-external-gpu-additions-and-removals [symbols: GPUEjectPolicy, GPUSelectionPolicy, NSApplicationDelegate.application(_:willEncodeRestorableState:)] [gate: Intel Macs]
