# Notes m08

## command-model.md

- Book's lifetime split: one `MTLDevice`, one queue and one library per app (held as statics); all PSOs and depth-stencil states built at init; per frame, only the command buffer and encoders. In `draw(in:)`, return quietly when the command buffer, pass descriptor or drawable is nil, because a skipped frame is normal — book:metal-by-tutorials/chapters/ch03-rendering-pipeline.md [symbols: MTLCreateSystemDefaultDevice(), MTKViewDelegate.draw(in:), MTKView.currentRenderPassDescriptor, MTKView.currentDrawable] [book: ch03 differs: the book calls `commandQueue.makeCommandBuffer()` every frame, then `commandBuffer.present(drawable)` and `commit()`. Metal 4 makes one reusable `MTL4CommandBuffer` from the device, calls `beginCommandBuffer(allocator:)` with a per-frame `MTL4CommandAllocator`, reads `MTKView.currentMTL4RenderPassDescriptor`, and presents with `MTL4CommandQueue.waitForDrawable(_:)`, `commit(_:options:)`, `signalDrawable(_:)`, then `drawable.present()`]
- The book's small-data path is `setVertexBytes(_:length:index:)` / `setFragmentBytes(_:length:index:)` for under 4 KB (uniforms, params, timers), and it uses it on nearly every draw through the whole book — book:metal-by-tutorials/chapters/ch04-vertex-function.md; book:metal-by-tutorials/chapters/ch05-3d-transformations.md; book:metal-by-tutorials/chapters/ch06-coordinate-spaces.md [symbols: MTLRenderCommandEncoder.setVertexBytes(_:length:index:)] [book: ch04 differs: Metal 4 has no bytes-binding call. `MTL4ArgumentTable` offers only `setAddress(_:index:)`, `setAddress(_:attributeStride:index:)`, `setResource(_:bufferIndex:)`, `setTexture(_:index:)` and `setSamplerState(_:index:)`, so per-frame uniforms live in one `MTLBuffer` per frame in flight (or a sub-range of a ring buffer) bound by `gpuAddress`, as the Metal 4 triangle sample does]
- Keep one binding-index convention shared by Swift and MSL. The book uses vertex buffers at 0–10, then uniforms 11, params 12, lights 13, materials 14, declared once in a C header that both languages include (the Objective-C bridging header on the Swift side, `#import "Common.h"` in `.metal`) — book:metal-by-tutorials/chapters/ch04-vertex-function.md; book:metal-by-tutorials/chapters/ch06-coordinate-spaces.md [book: ch06 agrees: the shared header carries over unchanged; the indices become `MTL4ArgumentTable` slots]
- Book binds textures per submesh with `setFragmentTexture(_:index:)` at an index from a shared `TextureIndices` enum — book:metal-by-tutorials/chapters/ch08-textures.md [symbols: MTLRenderCommandEncoder.setFragmentTexture(_:index:)] [book: ch08 differs: Metal 4 binds `MTL4ArgumentTable.setTexture(_:index:)` with the texture's `gpuResourceID` (an `MTLResourceID`) and samplers with `setSamplerState(_:index:)`; the texture must also be in a residency set]
- Once data passes 4 KB (hundreds of lights), the book moves it from `setFragmentBytes` into `MTLBuffer`s (`sunBuffer`, `pointBuffer`) — book:metal-by-tutorials/chapters/ch14-deferred-rendering.md [book: ch14 agrees with the Metal 4 shape, where every constant is a buffer address anyway]
- Indirection has two separate jobs and both are required: telling the shader where a resource is (an argument buffer of `gpuResourceID`s and `gpuAddress`es) and making it resident. Skipping residency compiles and may even render, but produces pink or missing textures, GPU memory errors or a display lockup, and the capture cannot track the resources — book:metal-by-tutorials/chapters/ch25-managing-resources.md; book:metal-by-tutorials/chapters/ch26-indirect-command-encoding.md; book:metal-by-tutorials/chapters/ch27-gpu-command-encoding.md [symbols: MTLTexture.gpuResourceID, MTLBuffer.gpuAddress, MTLResourceID] [book: ch25 differs: the book's residency ladder is `useResource(_:usage:stages:)` per resource, then `useHeap(_:stages:)` per pass, then `MTLResidencySet`; `MTL4RenderCommandEncoder` and `MTL4ComputeCommandEncoder` have no `useResource` or `useHeap`, so in Metal 4 residency sets are the only path — `MTL4CommandBuffer.useResidencySet(_:)` per command buffer or `MTL4CommandQueue.addResidencySet(_:)` per queue, plus the layer's `CAMetalLayer.residencySet` for drawables]
- Residency sets: `MTLResidencySetDescriptor` (`label`, `initialCapacity`; 0 lets Metal pick), `device.makeResidencySet(descriptor:)`, `addAllocation(_:)`, then `commit()` to apply changes. Attach static, level-lifetime sets to the queue and frame-varying sets to the command buffer; load a level's set at level start and drop it at the end. The Feature Set Tables allow 32 residency sets per queue and 32 per command buffer, from Apple6 — book:metal-by-tutorials/chapters/ch25-managing-resources.md; pdf:fst#all [symbols: MTLResidencySetDescriptor, MTLDevice.makeResidencySet(descriptor:), MTLResidencySet.addAllocation(_:), MTLResidencySet.commit(), MTL4CommandQueue.addResidencySet(_:), MTL4CommandBuffer.useResidencySet(_:)] [gate: residency sets Apple6+, 32 per buffer] [book: ch25 agrees on the residency-set API]
- Frames in flight in the book: `maxFramesInFlight = 3` copies of dynamic buffers indexed by a rotating `currentFrameIndex`, guarded by `DispatchSemaphore(value: 3)`: `wait` before writing this frame's buffer, `signal` in `addCompletedHandler`. Two copies risk the CPU overwriting what the GPU still reads; `waitUntilCompleted()` per frame is correct but stalls. Gotcha: if `wait` runs before an early-return path, the semaphore never gets its signal and rendering stops forever — book:metal-by-tutorials/chapters/ch30-profiling.md [symbols: DispatchSemaphore, MTLCommandBuffer.addCompletedHandler(_:), MTLCommandBuffer.waitUntilCompleted()] [book: ch30 differs: the Metal 4 triangle sample replaces the semaphore with an `MTLSharedEvent`: the queue signals `signalEvent(_:value:)` with the frame number after each commit, and before reusing a frame's `MTL4CommandAllocator` and buffers the CPU calls `wait(untilSignaledValue:timeoutMS:)` for frame N − 3 (the sample uses a 10 ms timeout); the allocator may be `reset()` only after the GPU finishes that frame, while the `MTL4CommandBuffer` itself can be reused right after commit]
- Submit early, present late: split the frame into an off-screen command buffer (shadows, G-buffer, compute) committed as soon as it is encoded, and an on-screen one holding only the drawable work; acquire the drawable as late as possible, because holding a drawable ties up a scarce swap-chain image — book:metal-by-tutorials/chapters/ch31-best-practices.md [book: ch31 agrees in principle; in Metal 4 the analogue is committing the off-screen `MTL4CommandBuffer` first and calling `waitForDrawable(_:)` only before the on-screen commit]
- Scope warning for every book-sourced bullet: the book (5th ed., v5.0.0, 2025) targets macOS 14 / iOS 17 and Metal through Metal 3, and states it does not cover Metal 4 (unified encoders, `MTL4` command allocators, tensors, ML). Its techniques port; its API spelling is the Metal 3 path, which remains the right path only behind a `supportsFamily(.metal4)` check failing, or for pre-Apple7 GPUs — book:metal-by-tutorials/SKILL.md [symbols: MTLDevice.supportsFamily(_:), MTLGPUFamily.metal4] [gate: Metal 4 Apple7+ (A14, M1 and later) per the Feature Set Tables]

## pipelines-and-render-passes.md

- Limits the book cites, checked against the Feature Set Tables (May 21, 2026): 31 vertex attributes per descriptor and 31 buffer-argument-table entries per function on every family; texture argument entries 31 (Apple2), 96 (Apple3–4), 128 (Apple5+); 16 sampler entries; inline `setBytes` data up to 4 KB on every family; max point size 511; 8 color render targets per pass — book:metal-by-tutorials/chapters/ch02-3d-models.md; pdf:fst#all [gate: per Apple family as listed] [book: ch02 agrees: 31 slots]
- Take the PSO color format from the view (`metalView.colorPixelFormat`) rather than hardcoding it, and build one PSO per distinct shader, vertex layout and attachment-format combination at init: creation is slow, switching is cheap — book:metal-by-tutorials/chapters/ch03-rendering-pipeline.md [symbols: MTKView.colorPixelFormat] [book: ch03 differs: the book sets `vertexFunction`/`fragmentFunction` (`MTLFunction`) on `MTLRenderPipelineDescriptor` and calls `device.makeRenderPipelineState(descriptor:)`. Metal 4 sets `vertexFunctionDescriptor`/`fragmentFunctionDescriptor` (an `MTL4LibraryFunctionDescriptor`) on `MTL4RenderPipelineDescriptor` and compiles with `MTL4Compiler.makeRenderPipelineState(descriptor:dynamicLinkingDescriptor:compilerTaskOptions:)` (ObjC also has `newRenderPipelineStateWithDescriptor:compilerTaskOptions:error:`). `MTL4RenderPipelineDescriptor` has no buffer-mutability hints and no binary-archive field]
- Set the winding (`setFrontFacing(.counterClockwise)`) and `setCullMode(.back)` before drawing; the book keeps back-face culling on except for one-sided meshes. `setTriangleFillMode(.lines)` is the quick wireframe check — book:metal-by-tutorials/chapters/ch03-rendering-pipeline.md; book:metal-by-tutorials/chapters/ch02-3d-models.md [symbols: MTL4RenderCommandEncoder.setFrontFacing(_:), MTL4RenderCommandEncoder.setCullMode(_:), MTL4RenderCommandEncoder.setTriangleFillMode(_:)] [book: ch03 agrees: all three exist on `MTL4RenderCommandEncoder`]
- Vertex-input ladder: a `[[vertex_id]]` plus a raw pointer for procedural data (the GPU needs only a count), a manual index lookup for learning, and a vertex descriptor with an indexed draw and `[[stage_in]]` for real meshes, because the PSO then knows the format and catches Swift/MSL drift. A quad as 4 vertices plus 6 `UInt16` indices is 60 bytes against 72 for 6 vertices — book:metal-by-tutorials/chapters/ch04-vertex-function.md [symbols: MTLVertexDescriptor, MTL4RenderPipelineDescriptor.vertexDescriptor] [book: ch04 agrees: `vertexDescriptor` remains on `MTL4RenderPipelineDescriptor`; `setAddress(_:attributeStride:index:)` adds a per-binding dynamic stride]
- Depth testing needs three pieces in the book: `MTKView.depthStencilPixelFormat = .depth32Float` (default `.invalid`, meaning no depth texture), a matching `depthAttachmentPixelFormat` on the pipeline descriptor, and an `MTLDepthStencilState` (`depthCompareFunction = .less`, `isDepthWriteEnabled = true`) set on the encoder. Without it, fragments land in submission order and the back of a model shows through the front — book:metal-by-tutorials/chapters/ch07-fragment-function.md [symbols: MTKView.depthStencilPixelFormat, MTLDepthStencilDescriptor.depthCompareFunction, MTLDepthStencilDescriptor.isDepthWriteEnabled, MTL4RenderCommandEncoder.setDepthStencilState(_:)] [book: ch07 differs: `MTL4RenderPipelineDescriptor` has no `depthAttachmentPixelFormat` or `stencilAttachmentPixelFormat` (the MTL4RenderPipeline.h header has no depth property at all); only `MTLRenderPipelineDescriptor` carries them, so the Metal 4 writer must not port the book's pipeline depth-format line. Depth-stencil state and `setDepthStencilState(_:)` are unchanged]
- Different vertex layouts need different PSOs; the model's vertex descriptor must match the pipeline's. Binding mesh vertex buffers by enumerated index will collide with low-numbered uniform slots, which is why the book parks uniforms and materials at 11–14 — book:metal-by-tutorials/chapters/ch11-maps-materials.md
- One encoder is one render pass; its descriptor names every attachment and its load and store actions. Choose `.clear` only when the pass does not cover every pixel, `.dontCare` load for the cheapest undefined start (but never when anything reads unwritten pixels, which come back as garbage), and `.store` only for attachments a later pass or the CPU consumes. A PSO must declare the pass's exact color formats, with `.invalid` for an absent attachment — book:metal-by-tutorials/chapters/ch12-render-passes.md [symbols: MTLLoadAction, MTLStoreAction, MTLRenderPassDescriptor, MTL4RenderPassDescriptor.colorAttachments, MTL4RenderPassDescriptor.depthAttachment] [book: ch12 agrees on load/store: `MTL4RenderPassDescriptor` reuses `MTLRenderPassColorAttachmentDescriptorArray`, `MTLRenderPassDepthAttachmentDescriptor` and `MTLRenderPassStencilAttachmentDescriptor`; differs: Metal 4 drops `MTLStoreActionOptions` as not applicable to Apple silicon, keeps `setColorStoreAction(_:index:)` for deferred store decisions, and has no pipeline depth-format field]
- The book's pass structure: a `RenderPass` protocol with `label`, its own descriptor, `resize(view:size:)` that rebuilds its textures at the drawable size, and `draw(commandBuffer:scene:uniforms:params:)`; the renderer runs passes in order and hands textures forward. Every pass that needs occlusion gets its own depth texture and depth-stencil state — book:metal-by-tutorials/chapters/ch12-render-passes.md
- Shadow pass recipe: a depth-only PSO (vertex function only, no fragment function, color `.invalid`, depth `.depth32Float`) renders models with the light's view and projection into a fixed 2048² depth texture (`.clear`/`.store`, not resized with the window), which a later pass binds as `depth2d<float>`. The two passes must be separate because the map has to be complete before anything samples it — book:metal-by-tutorials/chapters/ch13-shadows.md [symbols: depth2d, MTLPixelFormat.depth32Float] [book: ch13 differs: the book sets `depthAttachmentPixelFormat` on the pipeline and binds with `setFragmentTexture(_:index:)`; in Metal 4 the pipeline descriptor has no depth format and the shadow map goes into the argument table by `gpuResourceID`. Between the shadow pass and the pass that samples it, Metal 4 also needs an explicit barrier or fence, because all resources are untracked]
- Shadow quality is texture resolution spread over the light volume: fit the orthographic light camera to the scene camera's frustum (or its bounding sphere) every frame; a big far plane with one map goes blocky. Cascaded shadow maps put several maps in a depth texture array with different near/far ranges, at the cost of one scene render per cascade. Use orthographic for directional lights, perspective with FOV equal to the cone for spotlights. Debug by rendering the scene through the shadow matrices, which catches the most common bug, mismatched matrices between passes — book:metal-by-tutorials/chapters/ch13-shadows.md
- Forward vs deferred, with the authors' numbers: 200 lights on an iPad mini 6 ran 25 FPS forward and 60 FPS deferred; on an M1 Max in a small window forward degraded near 250 lights while deferred handled 8,000; maximized, forward degraded near 30 lights and deferred managed more than ten times that. Switch to deferred when light count, not geometry, dominates — book:metal-by-tutorials/chapters/ch14-deferred-rendering.md; book:metal-by-tutorials/SKILL.md
- Book's deferred layout: G-buffer MRT with albedo `.bgra8Unorm` (shadow factor packed in alpha), normal and position `.rgba16Float`, depth `.depth32Float` with `storeAction = .dontCare`; attachment 0 is left `.invalid` in the G-buffer PSO so the drawable can join later. The lighting pass shades the sun on a full-screen quad (six `[[vertex_id]]` vertices, no vertex descriptor on that PSO) and point lights as one instanced icosahedron draw (`[[instance_id]]`, passed on `[[flat]]`), with depth writes off and additive blending (`destinationRGBBlendFactor = .one`) enabled only on the light PSO, since blending costs. The G-buffer pass needs its own new descriptor; reusing the view's leaves the drawable unwritten — book:metal-by-tutorials/chapters/ch14-deferred-rendering.md [symbols: [[color(n)]], [[instance_id]], [[flat]], MTLRenderPipelineColorAttachmentDescriptor.isBlendingEnabled, MTLBlendFactor.one, MTLPixelFormat.rgba16Float] [book: ch14 differs: Metal 4 sets blending on `MTL4RenderPipelineColorAttachmentDescriptor`; check its field names against that page before porting]
- Stencil masking: 8-bit stencil shares the depth texture as `.depth32Float_stencil8`, assigned to both `depthAttachment` and `stencilAttachment`. Mark geometry in the G-buffer pass with `frontFaceStencil` compare `.always` and `depthStencilPassOperation = .incrementClamp`; in the lighting pass, test `.notEqual` against reference 0 with all ops `.keep` so the full-screen sun skips the sky (load stencil, `dontCare` depth). Stencil counts above 1 reveal overdraw; flipping to `.equal` is a quick sanity check that inverts the mask — book:metal-by-tutorials/chapters/ch15-tile-based-deferred-rendering.md [symbols: MTLStencilDescriptor, MTLDepthStencilDescriptor.frontFaceStencil, MTLStencilOperation.incrementClamp, MTLCompareFunction.notEqual, MTL4RenderCommandEncoder.setStencilReferenceValue(_:), MTLPixelFormat.depth32Float_stencil8] [book: ch15 agrees: depth-stencil state is shared between Metal 3 and Metal 4]
- Transparency ordering: alpha-test cut-outs with `discard_fragment()` (binary, cheap), alpha-blend translucency with a second PSO (`isBlendingEnabled = true`, `.add`, `.sourceAlpha`, `.oneMinusSourceAlpha`). Draw opaques with the plain PSO, then only transparent submeshes (tagged at load: an opacity map or `opacity < 1`) with the blending PSO, sorted back to front; blending PSOs cost more, so never use one for everything — book:metal-by-tutorials/chapters/ch20-fragment-post-processing.md [symbols: MTLBlendFactor.sourceAlpha, MTLBlendFactor.oneMinusSourceAlpha, MTLBlendOperation.add, discard_fragment]
- MSAA: the PSO's `rasterSampleCount` must equal the target's sample count (`view.sampleCount`); the book keeps opaque/transparent × MSAA PSO variants and picks per frame. The Feature Set Tables cap MSAA at 4 samples through Apple9 and 8 on Apple10, and shrink the max tile to 32×16 at 4× and 16×16 at 8× — book:metal-by-tutorials/chapters/ch20-fragment-post-processing.md; pdf:fst#all [symbols: MTL4RenderPipelineDescriptor.rasterSampleCount, MTKView.sampleCount, MTL4RenderPassDescriptor.defaultRasterSampleCount] [gate: 8× MSAA Apple10 only] [book: ch20 agrees: `rasterSampleCount` exists on `MTL4RenderPipelineDescriptor`]
- `setScissorRect(_:)` discards fragments outside a rectangle for every draw encoded after it, so it can restrict selected models cheaply — book:metal-by-tutorials/chapters/ch20-fragment-post-processing.md [symbols: MTL4RenderCommandEncoder.setScissorRect(_:), MTLScissorRect] [book: ch20 agrees]
- Skybox: an inward-normal unit box (`MDLMesh(boxWithExtent:segments:inwardNormals:geometryType:allocator:)`), a view matrix with translation zeroed, clip position written as `.xyww` so depth lands at exactly 1, a depth compare of `.lessEqual` (`.less` flickers to the clear color), drawn after opaques (early depth rejects hidden sky) and before transparents — book:metal-by-tutorials/chapters/ch21-image-based-lighting.md [symbols: MTLCompareFunction.lessEqual, texturecube]
- Planar water (after Horsch 2005): render the scene twice into half-size offscreen targets before the main pass — reflection from a camera mirrored below the plane (negate pitch, move down by 2 × height above water; sample with v flipped) and refraction from the real camera, plus its depth. The water shader samples both in screen space, offsets them with two crossed scrolling normal-map samples, clamps coords to 0.001…0.999, blends by a Fresnel ratio `dot(view, up)`, and fades the shoreline by linearized depth difference with alpha blending. Half resolution is fine because the result gets distorted anyway — book:metal-by-tutorials/chapters/ch22-reflection-refraction.md
- Function constants specialize one shader source into variants: MSL `constant bool hasSkeleton [[function_constant(0)]];`, and a parameter tagged `[[buffer(n), function_constant(hasSkeleton)]]` disappears when false. Without it, a static mesh run through skinning collapses to the origin, or validation asserts a missing buffer binding. Build every variant PSO at load and keep the PSO per model — book:metal-by-tutorials/chapters/ch24-character-animation.md [symbols: [[function_constant(n)]], MTLFunctionConstantValues.setConstantValue(_:type:index:)] [book: ch24 differs: the book calls `library.makeFunction(name:constantValues:)`; Metal 4 wraps an `MTL4LibraryFunctionDescriptor` in an `MTL4SpecializedFunctionDescriptor` (`functionDescriptor`, `constantValues`, `specializedName`) and hands that to the pipeline descriptor for `MTL4Compiler`]
- Cheap wins the book measured: back-face culling saved at least 0.5 ms (but one-sided meshes vanish from inside); returning `half4` instead of `float4` from the water shader dropped its profiler share from 5.69% to 4.63% on an M1 Max; one instanced `drawIndexedPrimitives(... instanceCount:)` for all rocks, with per-instance data read by `[[instance_id]]`; sort submeshes by pipeline state at load to kill redundant bindings; group draws by shader — book:metal-by-tutorials/chapters/ch30-profiling.md; book:metal-by-tutorials/chapters/ch31-best-practices.md [symbols: half4, [[instance_id]]]
- Replace runtime branches on optional textures with function specialization, build PSOs at launch, and render UI at native resolution (or close), ideally keeping all resources at one resolution — book:metal-by-tutorials/chapters/ch31-best-practices.md

## apple-gpu-tbdr.md

- Book's TBDR model: a tiling phase (vertex fetch, vertex shading, primitive assembly with cull and clip, binning into on-chip tile memory the app cannot address), then a per-tile rendering phase (rasterize, hidden surface removal, fragment shading, depth/stencil/blend). If the binned-geometry storage fills during a draw, the GPU flushes it and runs a partial render, so extremely dense geometry has a cliff — book:metal-by-tutorials/chapters/ch03-rendering-pipeline.md [book: ch03 agrees in concept; confirm the partial-render detail against Apple's TBDR article before stating it as fact]
- With HSR, opaque draw order costs no fragment overdraw on Apple GPUs; transparent geometry is the exception, which is why the book still sorts transparent draws back to front — book:metal-by-tutorials/chapters/ch03-rendering-pipeline.md
- Converting deferred to single-pass tiled deferred, the book's steps: G-buffer textures `.memoryless`; their store action `.dontCare`; stop binding them as textures; lighting fragment functions take the `GBufferOut` struct (members tagged `[[color(n)]]`) as a parameter and read the current pixel straight from tile memory (programmable blending); merge into one encoder on the view's descriptor; and make every PSO in the pass declare the identical full attachment set, with attachment 0 as the drawable format. Memoryless targets cost no app memory; the memory gauge jumps when switching back to non-tiled deferred — book:metal-by-tutorials/chapters/ch15-tile-based-deferred-rendering.md [symbols: MTLStorageMode.memoryless, MTLStoreAction.dontCare, [[color(n)]]]
- Validation messages that diagnose a broken tiled conversion: "Memoryless attachment content cannot be stored in memory" (memoryless with `.store`); "texture is Memoryless, and cannot be assigned" (memoryless bound as a shader texture); "reads from a color attachment whose pixel format is MTLPixelFormatInvalid" (a PSO in the merged pass is missing G-buffer formats) — book:metal-by-tutorials/chapters/ch15-tile-based-deferred-rendering.md
- Gates: the Simulator and Intel Macs cannot read render targets in the fragment shader, so ship a forward or classic-deferred fallback behind `device.supportsFamily(_:)`. The book says Apple3 (A9) and later supports this; the Feature Set Tables list programmable blending and memoryless render targets from Apple2, and Metal 4 itself from Apple7 (A14, M1). The tables map M4 and A18 to Apple9, M5 and A19 to Apple10 — book:metal-by-tutorials/chapters/ch15-tile-based-deferred-rendering.md; pdf:fst#all [symbols: MTLDevice.supportsFamily(_:), MTLGPUFamily.apple9, MTLGPUFamily.metal4] [gate: programmable blending Apple2+; Metal 4 Apple7+] [book: ch15 differs: book's Apple3 floor for TBDR reads is stricter than the tables' Apple2]
- A pass boundary is a trip to system memory on TBDR: merge passes whenever the consumer reads only the same pixel, and keep produce-and-consume-in-pass intermediates memoryless. The book points to WWDC 2019 "Modern Rendering with Metal" for per-tile light culling as the next step — book:metal-by-tutorials/chapters/ch15-tile-based-deferred-rendering.md
- Every transient attachment (G-buffer intermediates, MSAA color) should be `.memoryless` with `.clear` or `.dontCare` load and `.dontCare` store, or `.multisampleResolve` for MSAA (texture type `.type2DMultisample`, sample count 4); that removes the allocation, the bandwidth and false inter-pass dependencies. The dependency viewer exposed a depth texture being stored that nothing read. Tile memory makes MSAA cheap but not free, so check the visual gain — book:metal-by-tutorials/chapters/ch31-best-practices.md [symbols: MTLStorageMode.memoryless, MTLStoreAction.multisampleResolve, MTLTextureType.type2DMultisample]

## resources-and-memory.md

- sRGB rule: render into an sRGB target (`.bgra8Unorm_srgb`) with every color texture sRGB, and keep data textures (normal, roughness) linear. Model I/O loads every USD texture as linear `.rgba8Unorm`, base color included; fix base color with `makeTextureView(pixelFormat: .rgba8Unorm_srgb)`, which needs `.pixelFormatView` in the texture usage (the Simulator's stricter validation rejects it otherwise). A blanket `pow(c, 1/2.2)` in the shader fixes one texture and breaks the rest — book:metal-by-tutorials/chapters/ch08-textures.md [symbols: MTLTexture.makeTextureView(pixelFormat:), MTLTextureUsage.pixelFormatView, MTLPixelFormat.bgra8Unorm_srgb, MTLPixelFormat.rgba8Unorm_srgb] [book: ch08 agrees; Metal 4 also adds `MTLTextureViewPool` for lightweight reinterpreting views with their own `MTLResourceID`]
- Render-target factory: `MTLTextureDescriptor.texture2DDescriptor(pixelFormat:width:height:mipmapped:)` with `.private` storage and `[.shaderRead, .renderTarget]` usage, rebuilt on resize and guarded against zero size. Attachments may hold integer data (`.r32Uint` for object IDs, declared `texture2d<uint32_t>` in MSL and read with `read(coord)`, which needs no sampler) — book:metal-by-tutorials/chapters/ch12-render-passes.md [symbols: MTLTextureDescriptor.texture2DDescriptor(pixelFormat:width:height:mipmapped:), MTLStorageMode.private, MTLTextureUsage.renderTarget, MTLTextureUsage.shaderRead, MTLPixelFormat.r32Uint]
- CPU access to a shared buffer from Swift: `buffer.contents().bindMemory(to: T.self, capacity: n)` gives a typed pointer to walk with `pointee` and `advanced(by:)` — book:metal-by-tutorials/chapters/ch16-gpu-compute.md [symbols: MTLBuffer.contents(), UnsafeMutableRawPointer.bindMemory(to:capacity:)]
- Height maps should be single-channel `R8Unorm`; displace in the vertex function (sampling there is fine where pixel accuracy is not needed) and texture by height or slope in the fragment function. The book derives a slope map once with `MPSImageSobel(device:).encode(commandBuffer:sourceTexture:destinationTexture:)` into a texture with `[.shaderRead, .shaderWrite]` usage; letting the texture loader pick the pixel format crashes Sobel — book:metal-by-tutorials/chapters/ch19-tessellation-terrains.md [symbols: MPSImageSobel, MTLPixelFormat.r8Unorm, MTLTextureUsage.shaderWrite]
- Heaps: size with `device.heapTextureSizeAndAlign(descriptor:)` summed with alignment padding, call `makeHeap(descriptor:)` once at load (slow; adding resources to an existing heap is fast), create each texture with `heap.makeTexture(descriptor:)` using a descriptor whose `storageMode` and `cpuCacheMode` match the heap, and copy every mip level and every slice (cube faces too, halving the region per level). Build argument buffers only after textures reach the heap, or they point at the old copies. Loading then copying creates each texture twice; production loads straight into the heap. Label buffers or they show as `Buffer 0x…` in captures — book:metal-by-tutorials/chapters/ch25-managing-resources.md [symbols: MTLDevice.heapTextureSizeAndAlign(descriptor:), MTLDevice.makeHeap(descriptor:), MTLHeap.makeTexture(descriptor:), MTLHeapDescriptor.size, MTLHeapDescriptor.storageMode, MTLHeapDescriptor.cpuCacheMode] [book: ch25 differs: the book copies with `makeBlitCommandEncoder()` and `copy(from:sourceSlice:sourceLevel:sourceOrigin:sourceSize:to:destinationSlice:destinationLevel:destinationOrigin:)`; Metal 4 has no blit encoder — use `MTL4ComputeCommandEncoder.copy(sourceTexture:sourceSlice:sourceLevel:sourceOrigin:sourceSize:destinationTexture:destinationSlice:destinationLevel:destinationOrigin:)`, and the heap still needs a residency set]
- Texture budget numbers from the book (RGBA8 with mips): 8192² ≈ 341 MB, 2048² ≈ 21.33 MB, 1024² ≈ 5.33 MB, 512² ≈ 1.33 MB. Color matters most, then normal; shrink metallic, roughness and AO first — dropping those from 2048² let the sample run on an iPad mini 6 (about 1.2 GB app memory before, near the limit for older devices). One small mesh with a 21.33 MB base color was the single most expensive draw. Tile small textures for unimportant areas or use sparse textures instead of one giant terrain texture — book:metal-by-tutorials/chapters/ch30-profiling.md
- Storage mode rule: `.private` by default for textures and render targets, `.shared` only when the CPU must read or write, `.memoryless` for transient targets. ## shading-language.md

- MSL kept in a Swift string compiles only at runtime, so a missing semicolon becomes a launch-time failure. Keep shaders in `.metal` files so Xcode compiles them at build time into the default library — book:metal-by-tutorials/chapters/ch02-3d-models.md; book:metal-by-tutorials/chapters/ch03-rendering-pipeline.md [symbols: MTLDevice.makeDefaultLibrary()] [book: ch03 agrees: the Metal 4 triangle sample still loads `newDefaultLibrary`, but names functions through `MTL4LibraryFunctionDescriptor` (`library`, `name`) instead of `makeFunction(name:)`]
- `[[stage_in]]` may mark only one parameter. Its struct may widen a buffer `float3` to `float4`, and Metal fills w = 1. Vertex outputs interpolate unless marked `[[flat]]`. `.point` primitives need a `[[point_size]]` output, or the size is undefined and flickers (max 511 per the Feature Set Tables) — book:metal-by-tutorials/chapters/ch03-rendering-pipeline.md; book:metal-by-tutorials/chapters/ch04-vertex-function.md [symbols: [[stage_in]], [[attribute(n)]], [[flat]], [[point_size]], [[position]], [[vertex_id]]]
- Layout trap: MSL `float3` occupies 16 bytes (padded like `float4`), while a Swift struct of three `Float`s is 12. Read raw Swift arrays as `packed_float3`, or use `SIMD3<Float>` on the Swift side; size buffers and strides with `MemoryLayout<T>.stride`, never `.size` — book:metal-by-tutorials/chapters/ch04-vertex-function.md [symbols: packed_float3, float3, MemoryLayout.stride]
- Address-space rule of thumb from the book: `constant` when many invocations read the same data (uniforms), `device` when invocations read different elements (per-vertex arrays) — book:metal-by-tutorials/chapters/ch04-vertex-function.md [symbols: constant, device]
- Metal's conventions: NDC x and y in [-1, 1] and z in [0, 1] (OpenGL uses z in [-1, 1] and is right-handed); Metal is left-handed with +z into the screen; the GPU performs the divide by w and the viewport mapping. Keep the projection near plane above 0 and rebuild the projection when the drawable resizes — book:metal-by-tutorials/chapters/ch06-coordinate-spaces.md; book:metal-by-tutorials/chapters/ch02-3d-models.md
- simd and MSL matrices are column-major: `float4x4(a, b, c, d)` takes columns, so translation sits in `columns.3`. Compose `projection * view * model * position`, with model = `T * R * S`; rotate about a pivot with `T(p) * R * T(p).inverse`; the view matrix is the inverse of the camera's world transform; directions carry w = 0 and positions w = 1 — book:metal-by-tutorials/chapters/ch05-3d-transformations.md; book:metal-by-tutorials/chapters/ch06-coordinate-spaces.md [symbols: float4x4, simd_float4x4.columns, simd_float4x4.inverse]
- In a fragment function, `in.position.xy` is in drawable pixels with origin top-left, not points: a 400-point view is 800 px on a 2x Mac and 1200 px on a 3x iPhone. The shader cannot query the target size, so pass it in a params struct — book:metal-by-tutorials/chapters/ch07-fragment-function.md [symbols: [[position]]]
- MSL struct declarations are scoped to their `.metal` file, so share `VertexOut` and friends through a shader-only header (`#include <metal_stdlib>`), and keep CPU-visible structs and buffer/texture index enums in the C header both languages import. The book prefers `step`, `mix` and ternaries over `if` in shaders for codegen — book:metal-by-tutorials/chapters/ch07-fragment-function.md [symbols: step, smoothstep, mix, fract]
- `constexpr sampler` defaults per the book's table: `filter::nearest`, `address::clamp_to_edge`, `mip_filter::none`. Without a non-`none` mip filter, generated mips are never used (moiré and sparkle on receding surfaces). `max_anisotropy(n)` takes 1–16; the book uses 8 and warns that each extra sample costs time, so tune per model with an `MTLSamplerState` bound at `[[sampler(n)]]`. `nearest` suits pixel-art looks — book:metal-by-tutorials/chapters/ch08-textures.md [symbols: sampler, filter::linear, address::repeat, mip_filter::linear, max_anisotropy, [[sampler(n)]], MTLSamplerDescriptor]
- Camera math: a first-person view is `(T(position) * R(rotation)).inverse`; swapping to `(R * T).inverse` orbits the world origin instead. Arcball rotates a distance vector by yaw then pitch, adds the target, then uses `lookAt` (`float4x4(eye:target:up:)` is the book's own helper, not an SDK symbol). Orthographic projection suits top-down views and directional shadow maps — book:metal-by-tutorials/chapters/ch09-navigating-3d-scene.md
- MSL cannot size a pointer-passed array, so a light list goes in as `constant Light *lights [[buffer(n)]]` plus an explicit count in the params struct. Shared shader functions take three files: a declaring header kept out of the target, a `.metal` file that defines them, and an import wherever they are used — book:metal-by-tutorials/chapters/ch10-lighting-fundamentals.md
- Do all lighting in one space (the book uses world space): output `worldPosition = (model * pos).xyz / w` and `worldNormal = normalMatrix * normal` from the vertex function, normalize interpolated vectors, and `saturate` every dot product. The book's normal matrix is the upper-left 3×3 of the model matrix, which is wrong under non-uniform scale; the general fix is the inverse-transpose — book:metal-by-tutorials/chapters/ch10-lighting-fundamentals.md [symbols: saturate, reflect, normalize, float3x3]
- Book's Phong reference: diffuse = `saturate(dot(L, N))`; specular = `pow(saturate(dot(reflect(-L, N), V)), shininess)`, computed only where diffuse > 0 (shininess 32 default, try 8–512); point attenuation `1 / (x + y·d + z·d²)`; spot adds a cone test against `cos(coneAngle)` and a falloff `pow(spot, coneAttenuation)`. It is local illumination, so occluded surfaces still light up until shadows exist — book:metal-by-tutorials/chapters/ch10-lighting-fundamentals.md
- Value-or-texture material: send a `Material` struct (base color, roughness, metallic, AO), copy the `constant` parameter into a local so it can be modified, and override a field from its texture only when `!is_null_texture(tex)`. Read scalar maps from `.r`; AO defaults to 1; metallic is effectively 0 or 1 — book:metal-by-tutorials/chapters/ch11-maps-materials.md [symbols: is_null_texture, texture2d] [book: ch11 agrees: `is_null_texture` is in MSL 4.1]
- Normal mapping: the map holds tangent-space normals as linear data (flat = (0.5, 0.5, 1)); remap with `* 2 - 1` and multiply by `float3x3(T, B, N)` in world space. Forgetting either step gives broken lighting. Tools that emit +y-down normal maps need the green channel inverted. Roughness left at 0 collapses specular to a pinpoint — book:metal-by-tutorials/chapters/ch11-maps-materials.md [symbols: float3x3]
- Shadow lookup: divide `shadowPosition.xyz / w`, map xy from [-1, 1] to [0, 1] and flip y (`1 - y`, since texture v runs opposite to NDC y), then sample with a `clamp_to_edge` sampler (a repeating sampler casts phantom shadows off the map edge) and compare against the stored depth plus a bias of 0.001 to kill acne. Paint off-map lookups red while tuning — book:metal-by-tutorials/chapters/ch13-shadows.md [symbols: depth2d::sample, sampler, address::clamp_to_edge, compare_func::less, coord::normalized]
- Counters many threads bump must be `device atomic_int` updated with `atomic_fetch_add_explicit(&x, 1, memory_order_relaxed)`; a plain `device int` incremented by every thread loses updates (the book's mesh counted 2 vertices instead of 15,949, differently on each run). - Post-tessellation vertex functions: `[[patch(quad, 4)]]` on the function, `patch_control_point<ControlPoint>` as `[[stage_in]]`, `float2 [[position_in_patch]]` for (u, v), `[[patch_id]]` for the patch index; the vertex descriptor's step function must be `.perPatchControlPoint`. - A C bridging header needs `#include <stdbool.h>` before declaring `bool` flags shared with MSL. Depth fog: `1 - clamp(exp(-density * z/w), 0, 1)` mixed toward the fog color; the `MTKView` clear color is not geometry, so it stays unfogged until a sky is drawn — book:metal-by-tutorials/chapters/ch20-fragment-post-processing.md
- Split-sum IBL: diffuse = irradiance cube sampled by the normal × base color; specular = sky mip chosen by `level(roughness * 10)` along `reflect(V, N)` × `(F0 * lut.r + lut.g)`, with F0 = `mix(0.04, baseColor, metallic)` (`mix` rather than branching on metallic), times baked AO. - User clip planes: a vertex output `float clip_distance [[clip_distance]] [1];` holding `dot(worldPos, plane)` (plane `(0, 1, 0, -h)` keeps geometry above, `(0, -1, 0, -h)` below); negative distances are clipped before fragment shading. `[[clip_distance]]` is vertex-only, so the fragment function needs a separate input struct without it (MSL signature-matching rules) or it will not compile. - Linearize a [0, 1] depth-buffer value with the camera's near and far: `proj33 = far / (far - near)`, `proj43 = proj33 * -near`, `dist = proj43 / (depth - proj33)`; near and far must match the projection used — book:metal-by-tutorials/chapters/ch22-reflection-refraction.md
- One header, two languages, for argument buffers: branch on `#if __METAL_VERSION__` so MSL sees `array<texture2d<float>, N> textures;` and Swift sees `MTLResourceID textures[N];` (imported via `<Metal/Metal.h>`); Swift then sees the fixed array as a tuple (`textures.0 … .5`). - Escalate draw submission only as far as profiling demands: plain vertex pipeline → instancing → CPU-encoded ICB (thousands of static models) → GPU-encoded ICB (per-frame culling and LOD) → mesh shaders (generated or culled sub-model geometry). ## display-and-upscaling.md

- A compute kernel can write the drawable directly (`texture2d<half, access::write>`, `output.write(color, coord)`) only when `MTKView.framebufferOnly = false`; leaving it at the default `true` lets the drawable stay render-target-only. ## gpu-debugging-and-profiling.md

- Debug by drawing data as color (normals or normalized positions as RGB). In the book, the frame capture (the "M" button in the debug bar, capture 1 frame) is how it found a texture loaded as `RGBA8Unorm` next to one in `RGBA8Unorm_sRGB`: inspect each command's bound buffers and textures and each attachment's pixel format rather than trusting what you think you bound — book:metal-by-tutorials/chapters/ch07-fragment-function.md; book:metal-by-tutorials/chapters/ch08-textures.md
- GPU line width is not configurable, so thin debug lines (the book's `DebugLights`) can vanish at some angles; render intermediate shader values as color instead when possible — book:metal-by-tutorials/chapters/ch10-lighting-fundamentals.md
- The frame capture's dependency view (the book calls it the frame graph) shows which stored textures feed which passes; only `.store` attachments flow on. Small uint IDs render black in the texture viewer because white is the max `uint32`, so remap the viewer's range to see them — book:metal-by-tutorials/chapters/ch12-render-passes.md
- Wrap each model's draws in `pushDebugGroup(_:)` / `popDebugGroup()` so the capture groups commands by name — book:metal-by-tutorials/chapters/ch13-shadows.md [symbols: MTLCommandEncoder.pushDebugGroup(_:), MTLCommandEncoder.popDebugGroup()] [book: ch13 agrees: `MTL4CommandBuffer` also has `pushDebugGroup(_:)` / `popDebugGroup()`]
- In the capture, purple exclamation marks flag redundant per-draw bindings; indirectly bound resources appear under "Indirect" in Bound Resources, and an ICB lists its encoded draws with their resources. The book gates capture-only `useResource` calls behind `#if DEBUG` — book:metal-by-tutorials/chapters/ch25-managing-resources.md; book:metal-by-tutorials/chapters/ch26-indirect-command-encoding.md; book:metal-by-tutorials/chapters/ch27-gpu-command-encoding.md
- Label MPS kernels (`kernel.label`) so they read in captures; while debugging a filter chain, blit an intermediate result into the drawable to see each stage — book:metal-by-tutorials/chapters/ch29-metal-performance-shaders.md [symbols: MPSKernel.label]
- Triage first: if the frame takes long while the GPU's share is small, the CPU is the limit; if the GPU's own time is large, the GPU is, and CPU-side encoding matters less. The target is 16.6 ms for 60 FPS. Read GPU time from the Metal Performance HUD (the book says it is more accurate than the Debug navigator's frame time) and frame time from the GPU report. Book's sample: about 20 ms GPU against 25 ms frame on an iPad mini 6, so GPU-bound — book:metal-by-tutorials/chapters/ch30-profiling.md; book:metal-by-tutorials/chapters/ch31-best-practices.md
- Book's tool order, coarse to fine: Metal Performance HUD (Scheme ▸ Run ▸ Diagnostics ▸ Show Graphics Overview: FPS, GPU time, memory) → GPU report (Debug navigator ▸ FPS) → capture Summary ▸ Insights (Memory: bound-but-unused resources; Bandwidth; API Usage: redundant bindings) → Group by Pipeline State for per-PSO and per-draw cost → Memory viewer sorted by allocated size → timeline captured over 3 frames (group by Command Buffer for the dependency graph, by Performance for per-shader tracks) → shader debugger (per-pixel and per-vertex values, live edit, Reload Shaders) and shader profiler (per-line cost). Insights are leads, not verdicts: it raised a false positive on a vertex buffer, and its "unused tangent buffer" finding actually exposed a shader bug — book:metal-by-tutorials/chapters/ch30-profiling.md
- Capture gotchas: a capture can fail with the HUD on or a nearly full device; Xcode may not prompt to save live shader edits, so copy them before ending the capture; label every buffer, texture and encoder so Insights and the timeline are readable — book:metal-by-tutorials/chapters/ch30-profiling.md
- Timeline reading: a frame where every pass writes the drawable forms a serial chain with gaps; separate render targets let independent vertex, fragment and compute work overlap. In the sample, bloom's MPS encoders ("Coalesced 4 Encoders") were among the longest items, and removing bloom alone took the iPad mini 6 to 60 FPS and 14.5 ms — book:metal-by-tutorials/chapters/ch30-profiling.md
- Symptom-to-cause table worth carrying. Textures that render pink or vanish once argument buffers are in use: resources never made resident. Speckled self-shadowing: acne, add a depth bias. Phantom shadows near the map border: the shadow sampler repeats instead of clamping. A sky that flickers to the clear color: its depth test needs less-or-equal. Unskinned props squashed to a single point: the skinning shader variant was used on them. Gaps between terrain patches: neighbors computed different edge factors. Points changing size: no `[[point_size]]` output. Parts of a model absent: only one submesh drawn, or a zero index offset for all. Noise from a GPU-built ICB: 16-bit versus 32-bit index mismatch. A mesh seen inside-out: handedness or winding disagree with the cull setting. Jittery dynamic data: the CPU rewrote a buffer the GPU was still reading, so add frames in flight — book:metal-by-tutorials/cheatsheet.md

## apple-games/assets.md

- Model I/O fills only the vertex attributes you name: build an `MTLVertexDescriptor`, convert it with `MTKModelIOVertexDescriptorFromMetal`, then set each `MDLVertexAttribute.name` (`MDLVertexAttributePosition` and so on). Unnamed attributes such as normals and UVs are silently not loaded, and the layout stride must cover the whole interleaved vertex, not only the attribute you read — book:metal-by-tutorials/chapters/ch02-3d-models.md [symbols: MTKModelIOVertexDescriptorFromMetal, MDLVertexAttribute, MDLVertexAttributePosition, MDLAsset.init(url:vertexDescriptor:bufferAllocator:)] [book: ch02 agrees: Model I/O loading is not Metal-4-specific]
- An imported mesh is one vertex pool plus one index list per material group (`MTKSubmesh`). Draw every submesh at its own index-buffer offset; drawing only `submeshes.first`, or passing offset 0 for all, drops parts of the model — book:metal-by-tutorials/chapters/ch02-3d-models.md [symbols: MTKMesh.submeshes, MTKSubmesh.indexBuffer, MTKMeshBuffer.offset] [book: ch02 differs: the book passes `indexBuffer:` (an `MTLBuffer`) plus `indexBufferOffset:` to `MTLRenderCommandEncoder`; `MTL4RenderCommandEncoder.drawIndexedPrimitives(primitiveType:indexCount:indexType:indexBuffer:indexBufferLength:)` takes an `MTLGPUAddress`, so the writer adds the submesh offset to `buffer.gpuAddress` and passes the remaining length]
- Blender is Z-up; the book's scenes are Y-up. Re-orient and apply all transforms in the modeling tool before export, or the model imports on its side. Book's format table: USD is Apple's default (`.usda` is ASCII, `.usd` ASCII or binary, `.usdz` an archive); OBJ carries no animation; FBX is proprietary and fading; glTF is a Khronos scene container. `MDLAsset.canExportFileExtension(_:)` then `export(to:)` writes `.usda` for inspection — book:metal-by-tutorials/chapters/ch02-3d-models.md [symbols: MDLAsset.canExportFileExtension(_:), MDLAsset.export(to:)]
- Texture loading: call `asset.loadTextures()` after creating the `MDLAsset`, read a material's texture by semantic through `MDLMaterial.property(with:)` and `textureSamplerValue?.texture`, and load it with `MTKTextureLoader.newTexture(texture:options:)` using `.origin: .bottomLeft` (USD UVs otherwise wrap wrongly) and `.generateMipmaps: true`. Cache by texture name, since submeshes share textures. Asset-catalog Texture Sets (`newTexture(name:scaleFactor:bundle:options:)`) give per-device variants and mipmaps by default; images dropped into the catalog body become images, not textures — book:metal-by-tutorials/chapters/ch08-textures.md [symbols: MDLAsset.loadTextures(), MDLMaterial.property(with:), MDLMaterialProperty.textureSamplerValue, MTKTextureLoader.newTexture(texture:options:), MTKTextureLoader.Option.origin, MTKTextureLoader.Option.generateMipmaps, MTKTextureLoader.newTexture(name:scaleFactor:bundle:options:)]
- Model I/O can generate a tangent basis: `MDLMesh.addTangentBasis(forTextureCoordinateAttributeNamed:tangentAttributeNamed:bitangentAttributeNamed:)` needs positions and UVs, adds two buffers and updates layouts; call it on each `MDLMesh` from `asset.childObjects(of:)` before building `MTKMesh(mesh:device:)`, and extend the vertex descriptor to match. `addNormals(withAttributeNamed:creaseThreshold:)` covers meshes without normals. Material values come from `MDLMaterial.property(with:)` semantics `.baseColor`, `.roughness`, `.metallic`, `.ambientOcclusion`, `.tangentSpaceNormal`. Reality Composer Pro (Xcode > Open Developer Tool) inspects and assigns USD material textures — book:metal-by-tutorials/chapters/ch11-maps-materials.md [symbols: MDLMesh.addTangentBasis(forTextureCoordinateAttributeNamed:tangentAttributeNamed:bitangentAttributeNamed:), MDLMesh.addNormals(withAttributeNamed:creaseThreshold:), MDLVertexAttributeTangent, MDLVertexAttributeBitangent, MDLMaterialSemantic, MTKMesh.init(mesh:device:)]
- Handedness fixes for imported models belong in the asset pipeline: if only some assets are right-handed, negate z once (a kernel suits it) and write the corrected file out, rather than flipping at runtime. Negating z also reverses winding, so the front-facing setting must match the data or culling hides the visible faces — book:metal-by-tutorials/chapters/ch16-gpu-compute.md
- Environment assets: `MDLSkyCubeTexture` generates a procedural sky (`turbidity`, `sunElevation`, `upperAtmosphereScattering`, `groundAlbedo`; the book uses `.float16` channel encoding) and `MDLTexture.irradianceTextureCube(with:name:dimensions:roughness:)` convolves irradiance, but generating irradiance at launch can delay startup by about a minute, so bake it offline and ship a PNG. Model I/O will not load cube textures from the asset catalog; the book ships one image with six 128×128 faces, and an asset-catalog cube with nine fixed mip levels for prefiltered specular — book:metal-by-tutorials/chapters/ch21-image-based-lighting.md [symbols: MDLSkyCubeTexture, MDLTexture.irradianceTextureCube(with:name:dimensions:roughness:)]
- Transform animation from USD: Model I/O exposes only a matrix at a time, so sample `MDLTransform.globalTransform(with:atTime:)` from `asset.startTime` to `asset.endTime` at 1/fps once at load (2.5 s at 60 fps is 150 matrices) and index by `Int(fmod(t, duration) * fps)` at runtime. Multi-mesh models need a per-mesh model matrix inside the mesh loop. USD extensions: `.usd` (assets or links), `.usdz` (single archive), `.usda` (text), `.usdc` (binary). The book recommends an offline asset pipeline over runtime loading for shipping engines (WWDC 2017 "From Art to Engine with Model I/O") — book:metal-by-tutorials/chapters/ch23-animation.md [symbols: MDLTransform.globalTransform(with:atTime:), MDLAsset.startTime, MDLAsset.endTime, MDLObject.transform]
- Keyframe playback: store `Keyframe<Value>` (time, value), find the bracketing pair, interpolate with `simd_mix` for vectors and `simd_slerp` for `simd_quatf` rotations (never Euler, which gimbal-locks and takes wrong paths). Slerp takes the shortest path, so a 0°→360° key pair produces no spin; split it into 90° steps. Keep Euler as an authoring convenience that updates the quaternion in `didSet` — book:metal-by-tutorials/chapters/ch23-animation.md [symbols: simd_quatf, simd_slerp, simd_mix]
- Skeletal assets via Model I/O: `MDLSkeleton` (first from `asset.childObjects(of:)`) gives joint paths, bind and rest transforms; each mesh's `MDLAnimationBindComponent` maps its joint subset to the skeleton (one model can have forty meshes with different maps); clips come from `asset.animations.objects` as `MDLPackedJointAnimation`. A USDZ holds one animation, so ship the rig and each clip as separate files. Vertex descriptors need joints (`ushort4`) and weights (`float4`) attributes named so Model I/O fills them — book:metal-by-tutorials/chapters/ch24-character-animation.md [symbols: MDLSkeleton, MDLAnimationBindComponent, MDLPackedJointAnimation, MDLAsset.animations, MDLVertexAttributeJointIndices, MDLVertexAttributeJointWeights]
