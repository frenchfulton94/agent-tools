# Fix round 1 (2026-10-01): revision round run; decision corrected to KEEP

## What was wrong with the original decision

The original round (above) classified `ad-fire-5`'s two post-edit
failures (`run-1/ad-fire-5.log`, `run-2/ad-fire-5.log`) as the
`--allowedTools` tool-permission leak (`docs/deferred.md` item 6), on the
grounds that both sessions went straight to `Bash`/`Read`/`Edit` without
calling `Skill`. That classification was examined and found invalid:

- **The leaked tool access is present in every `ad-fire-5` session**,
  passing and failing alike — all six sessions across the original sweep
  (`run-1`, `run-2`, `run-3`) and the baseline re-run
  (`baseline-ad-fire-5-1/2/3`) ran under the same `--allowedTools "Skill
  Read"` flag with the same `Bash`/`Edit` leak available. A condition
  that is constant across both outcomes cannot be what explains the
  2-of-6 split between sessions that called `Skill` and sessions that
  did not.
- **`.claude/rules/eval-harness.md` names exactly three categories** for
  classifying a non-passing session: `max_turns`, fixture-dependent, or
  routing miss. "Tool-permission leak" is not one of them. Citing it as a
  fourth, ad hoc category to excuse the finding was itself the error.
- **The failing sessions made the decision with turns still in budget.**
  `run-1/ad-fire-5.log`: text "I'll add a Delete button to the message
  toolbar with a destructive confirmation dialog, following HIG for
  destructive actions" appears before any `Edit` call — the model named
  HIG conformance as the relevant frame and still did not route to the
  skill that owns HIG conformance. `run-2/ad-fire-5.log`: the session ran
  an `Agent`-tool exploration, several `Bash`/`Read` calls, and a
  `SubagentHandback`, then went straight to `Edit` — again a plan chosen
  before turns ran out, not a budget-driven dead end. Per Task 6's own
  precedent (`task-6-evals/classification.md`, the `fire-8` entry), a
  `max_turns` result at the end of a session does not make the routing
  decision inside it a harness defect — the defect is the choice, made at
  full budget. **Corrected classification: `run-1` and `run-2` are
  routing misses**, not harness defects.
- **Pooled across both Duo-wording attempts to date**, the split is
  stark: the *original*, pre-Duo description scored 4/4 on this exact
  prompt (Task 9's one baseline run, Task 9 §7 evidence, plus Task 10's
  three-run baseline, `baseline-ad-fire-5-{1,2,3}`, all PASS). The *two
  different* Duo-heavy edits each tried scored 1/4 combined (Task 9's
  single post-edit run — FAIL, recorded in `docs/deferred.md` item 13 —
  plus Task 10's first post-edit sweep: 1 PASS, 2 FAIL). A 4/4-vs-1/4
  split across two independently-worded edits is not noise; it is
  evidence that Duo-heavy wording specifically perturbs this row.
- **A plausible wording fix exists and was not tried.** `apple-design`
  already documents confirmation dialogs before destructive actions, in
  `references/hig-patterns.md` § Modality (confirmed: `grep -n "Modality"
  references/hig-patterns.md` → line 52, "## Modality: Sheets,
  Full-Screen, and Alerts"). Neither the Step 1 description nor its
  wording ever named confirmation dialogs, and the Duo/pose/fold
  insertion in both attempts pushed "navigation and modality patterns"
  (the clause closest to covering this prompt) further from the front of
  the description. Step 6's revision round ("if a confirmed regression
  ... and a wording change could plausibly address it, revise ... once")
  applied cleanly and had not been used.

The original report's claim "no plausible wording fix exists... the
mechanism is tool-permission leakage, not routing" is retracted. It was
an incorrect diagnosis built on treating a constant condition as the
explanatory variable.
