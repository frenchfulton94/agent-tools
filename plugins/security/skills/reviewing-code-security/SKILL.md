# Reviewing Code Security

Produce security findings that a reader can verify against a published source. Every finding cites
a specific OWASP cheatsheet and section from the corpus vendored in this skill, pinned to an
upstream commit. A finding with no citation is not a finding — it is a guess, and it belongs in the
"unverified observations" section of the report or nowhere.

## Before starting

Establish the scope, because it selects the protocol:

| Scope | Protocol |
|---|---|
| A branch, a pull request, staged changes, "what I just wrote" | Read `references/diff-review.md` |
| A repository, a directory, "audit this codebase", "is this app secure" | Read `references/baseline.md` |
| One named concern ("is this query injectable?") | Neither — retrieve the sheet and answer directly |

A baseline sweep of anything larger than a few dozen files belongs in the `security-auditor`
subagent, which reads the same references in its own context and returns only the findings.

This skill reviews. For writing new code securely, retrieve the relevant sheet and follow it — you
do not need the review protocols to do that.

## Retrieval: grep the index, then read the sheet

The corpus is roughly 620,000 tokens. Never read it whole, never glob it, and never read
`references/index.md` in full either. The index is generated by `scripts/build-index.ts` from
`owasp/`, and the corpus itself is refreshed separately by `scripts/sync-owasp.ts`; neither script
runs during a review. Run `scripts/verify-citations.ts` against a written report to re-check every
citation against the corpus.

1. **Detect the stack.** Lockfiles and manifests first (`package.json`, `requirements.txt`,
   `pom.xml`, `Gemfile`, `go.mod`, `*.csproj`, `Dockerfile`, `.github/workflows/`), then file
   extensions. The stack narrows which sheets apply.
2. **Grep the index** for the topic and the stack:

       rg -i "sql|injection|query" references/index.md
       rg -i "\| node" references/index.md

3. **Read the 1–3 sheets** the matching rows name, from `owasp/<Name>_Cheat_Sheet.md`.
   Three is the ceiling for a diff or single-concern review; a whole baseline audit budgets more
   (see `references/baseline.md`). If more than the budget looks relevant, the scope is too broad —
   split the review.
4. **Cite** the filename and the section heading in every finding.

Files listed under `## Redirects` in the index are empty stubs. Cite the target they name instead.

If a topic has no matching row, say so in the report and mark the observation unverified. Do not
substitute recalled guidance for a citation — ungrounded advice delivered in the same voice as
sourced advice is the failure this skill exists to prevent.

## Severity

Rate by exploitability and blast radius together, not by category name. The full rubric with
worked examples is in `references/findings.md`; the short form:

| Severity | Test |
|---|---|
| Critical | Remotely exploitable by an unauthenticated user, with data loss or code execution |
| High | Exploitable by an authenticated user, or leaks credentials or personal data |
| Medium | Requires unusual conditions, or weakens a control without breaking it |
| Low | Hardening gap with no direct exploit path |

A missing control in code that no request can reach is Low. Say why the path is unreachable, so a
reviewer can challenge that judgement.

## Report

Read `references/findings.md` for the full format before writing the report — it defines the header
(including the corpus sync date from `owasp/SOURCE.json`), the per-finding fields, and
the ordering rules.

Order findings by severity, then by file. Do not pad: a review that finds two real problems reports
two. Inventing findings to look thorough is worse than a short report, because it costs the reader
the ability to trust the long ones.

## Verify

Before reporting done:

- [ ] Every finding names a file and line, and a cheatsheet file and section
- [ ] Every cited filename exists under `owasp/` — a citation you did not open is a fabrication
- [ ] Every quote was confirmed present in its cited *section*, not merely somewhere in the sheet — `rg -F "<quote>" owasp/<Sheet>.md` then check the hit falls inside that section, before the finding is written, not after
- [ ] Severities follow the rubric, and any Low justified as unreachable says why
- [ ] Observations without a citation are in the unverified section, not mixed into findings
- [ ] The header records the corpus SHA and sync date from `SOURCE.json`

## Output contract

The report from `references/findings.md`, and nothing before it except one sentence naming the
scope reviewed and the number of files examined.
