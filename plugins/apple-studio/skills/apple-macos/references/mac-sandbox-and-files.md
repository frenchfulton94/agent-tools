## The sandbox model, and why the Store requires it

App Sandbox is an access-control system that confines a macOS app to a container directory and a small, explicit set of additional capabilities declared as entitlements — the app gets unrestricted read/write only inside its own container, and everything else (other folders, the network, hardware) requires a matching entitlement (App Sandbox, https://developer.apple.com/documentation/security/app-sandbox.md). Apple's docs state this plainly: enabling the App Sandbox capability is required to distribute a macOS app through the Mac App Store (App Sandbox). There is no opt-out for Store distribution — the sandbox is the Store's baseline security contract, not a hardening option you layer on.

The sandbox's default posture on macOS is stricter than iOS in a way that regularly surprises developers moving between platforms: an iOS app can make outgoing network requests with zero extra configuration, but a sandboxed macOS app cannot — you must explicitly add the `com.apple.security.network.client` entitlement (via the "Outgoing Connections (Client)" capability toggle in Xcode) before any request succeeds (macOS by Tutorials, ch. 2). This trips people up even on requests that look entirely local: loading any content into a `WKWebView`, including an in-memory HTML string with no network fetch involved, still requires the same Outgoing Connections capability — the sandbox gates the mechanism `WKWebView` uses internally, not just literal internet traffic (macOS by Tutorials, ch. 10). Treat "does this touch WKWebView at all" as reason enough to add the entitlement, regardless of whether your content is remote.

When Xcode creates a new macOS app, it already carries the App Sandbox entitlement and a starter set of capabilities (Protecting user data with App Sandbox, https://developer.apple.com/documentation/security/protecting-user-data-with-app-sandbox.md). A sandboxed app cannot: use Authorization Services, use accessibility APIs as an assistive app, send Apple Events to arbitrary apps, send `userInfo` in distributed notifications, load kernel extensions, simulate input in Open/Save dialogs, read or write another app's preferences, reconfigure network settings, or terminate other running apps (Protecting user data with App Sandbox). If a feature you're building depends on one of these, the fix is architectural (a helper tool, a different API), not an entitlement — none of them have an entitlement that grants them back.

Every entitlement is a key/value pair baked into the app's code signature at signing time, edited in Xcode as a `.entitlements` property list under Signing & Capabilities (Entitlements, https://developer.apple.com/documentation/bundleresources/entitlements.md). The sandbox itself is switched on by one specific boolean, `com.apple.security.app-sandbox`, set the moment you enable the App Sandbox capability in Xcode (com.apple.security.app-sandbox, https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.app-sandbox.md) — every other entitlement in this file only does anything in the presence of that key; without it, the process isn't sandboxed at all and none of the read-only/read-write file grants below are meaningful. How the completed entitlements plist becomes part of a signed, notarized, or Store-submitted build — provisioning profiles, the App ID's registered capabilities, certificate matching — is out of scope here; see `app-release`'s `signing-and-provisioning.md` for that mechanics. This file covers what each entitlement means and grants once the app is running.

## Choosing a minimal file-access entitlement set

File-access entitlements aren't simple on/off switches the way most sandbox capabilities are — each one is set to None, Read Only, or Read/Write independently (macOS by Tutorials, ch. 9). Treat "minimal" as two separate decisions: which folders does this app shape genuinely need, and for each one, does it need write or is read enough.

**User-selected files** (`com.apple.security.files.user-selected.read-only` / `.read-write`) grant access only to files and folders a person actively picks through an Open/Save panel or a SwiftUI file-import/export dialog — never a standing grant to any location by path (com.apple.security.files.user-selected.read-only, https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.files.user-selected.read-only.md; .read-write, https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.files.user-selected.read-write.md). This is the default and usually correct choice for any app whose file access is inherently document-shaped — a text editor, an image tool, a converter. Reach for read-only unless the app genuinely writes back to the picked file/folder.

**Media-folder entitlements** — Downloads, Pictures, Music, Movies, each with its own read-only/read-write pair (com.apple.security.files.downloads.read-only, https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.files.downloads.read-only.md; .read-write, https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.files.downloads.read-write.md; com.apple.security.assets.pictures.read-only, https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.assets.pictures.read-only.md; .read-write, https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.assets.pictures.read-write.md; com.apple.security.assets.music.read-only, https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.assets.music.read-only.md; .read-write, https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.assets.music.read-write.md; com.apple.security.assets.movies.read-only, https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.assets.movies.read-only.md; .read-write, https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.assets.movies.read-write.md) — exist so an app that genuinely works against a whole standard folder as a category (a music library tool, a photo importer) doesn't have to ask permission file-by-file — Apple's own docs confirm these capabilities grant access to the named folder specifically to avoid requesting consent to access each file individually (Accessing files from the macOS App Sandbox, https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox.md). That's a materially different grant shape than `user-selected` above, which always routes through a picker — this file's judgment is to reserve the media-folder entitlements for apps where "browse this whole category without repeated prompts" is core to the workflow, not requested as a convenience to avoid one picker call in an app that's really document-shaped.

**Network client/server**: `com.apple.security.network.client` allows outgoing connections your app initiates — this is the one almost every network-consuming app needs (com.apple.security.network.client, https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.network.client.md). `com.apple.security.network.server` allows other machines to initiate connections *to* your app — needed only if the app genuinely listens (a local dev server, a peer-discovery/hosting feature), not merely because it also happens to talk to a network (com.apple.security.network.server, https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.network.server.md). Don't add server as a reflexive pair to client; the book calls out explicitly that client alone is sufficient for apps that only initiate requests (macOS by Tutorials, ch. 2).

**Judgment: sizing the set.** Start from zero and add only what the app's actual shape demands:

| App shape | Entitlements | Skip |
|---|---|---|
| Text/document editor, opens and saves files the user picks | User-selected read-write | Media folders, network |
| API-backed client (weather, notes sync, chat) | Network client | Network server, any file entitlement |
| Music-library browser/tagger that treats the whole library as its subject | Music read-write | User-selected (unless it also imports one-off files) |
| Local dev server or peer-hosting feature | Network client *and* server | — both are genuinely needed here, unlike the API-client case |

Every entitlement beyond the minimum is both an attack-surface increase and something an App Store reviewer will ask you to justify — favor the narrowest grant that doesn't produce user-hostile re-prompting, and prefer user-selected access over a standing media-folder grant whenever the app only occasionally touches that folder rather than treating it as primary content.

**Last resorts.** `com.apple.security.files.all` grants blanket file access (com.apple.security.files.all, https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.files.all.md) and, like any capability not covered by a Sandbox checkbox, can be requested as a temporary-exception entitlement directly in the `.entitlements` file — despite the name, such grants don't expire, but Store review may reject them without a documented justification in your review notes (macOS by Tutorials, ch. 9). Turning off App Sandbox entirely (the X button in the Signing & Capabilities App Sandbox section) is the true last resort: some workflows can't be made to fit inside the sandbox at all — the book's example spawns a `Process` to resize and save an image, and a helper tool launched this way does not carry forward the ad hoc, per-URL access grant your app obtained from a Save panel, so the write fails with "Operation not permitted" even though the user just picked that exact location (macOS by Tutorials, ch. 13). Disabling the sandbox fixes it, at the cost of Mac App Store eligibility entirely (macOS by Tutorials, ch. 13) — this is a distribution decision, not a code-quality one, and should be made deliberately, not as a debugging shortcut.

## Security-scoped bookmarks, end to end

The picker moment and the "use this file again later, across launches" moment are two different problems. Getting the URL is easy; keeping access to it is what security-scoped bookmarks solve.

**1. Obtain access.** In SwiftUI, `.fileImporter(isPresented:allowedContentTypes:onCompletion:)` presents the system picker and hands back a security-scoped `URL` in its completion result (fileImporter(isPresented:allowedContentTypes:onCompletion:), https://developer.apple.com/documentation/swiftui/view/fileimporter(ispresented:allowedcontenttypes:oncompletion:).md). In AppKit, `NSOpenPanel` does the same — the system always draws the panel out-of-process on macOS 10.15+, and selecting a file automatically adds it to your app's sandbox (NSOpenPanel, https://developer.apple.com/documentation/appkit/nsopenpanel.md; macOS by Tutorials, ch. 13, which uses `NSOpenPanel` for exactly this — the sandbox-compliant way to grant access to a user-selected file or folder). Picking a folder this way extends access recursively into everything already inside it (Accessing files from the macOS App Sandbox).

**2. Persist access as a bookmark.** A URL alone doesn't survive relaunch. Convert it to bookmark data with the `.withSecurityScope` option, which is what makes the bookmark resolvable and re-grantable in a future launch (bookmarkData(options:includingResourceValuesForKeys:relativeTo:), https://developer.apple.com/documentation/foundation/nsurl/bookmarkdata(options:includingresourcevaluesforkeys:relativeto:).md). Add `.securityScopeAllowOnlyReadAccess` if you'll never need to write back. Store the resulting `Data` — `UserDefaults`, a small file, wherever fits the app.

```swift
.fileImporter(isPresented: $showImporter, allowedContentTypes: [.folder]) { result in
    guard let url = try? result.get() else { return }
    guard url.startAccessingSecurityScopedResource() else { return }
    defer { url.stopAccessingSecurityScopedResource() }

    if let bookmark = try? url.bookmarkData(
        options: .withSecurityScope,
        includingResourceValuesForKeys: nil,
        relativeTo: nil
    ) {
        // persist `bookmark` for reuse on a future launch
    }
}
```

**3. Resolve and re-access later.** On a later launch, resolve the stored bookmark back into a `URL`, then explicitly bracket use of it — this step is not optional or automatic. Apple's own docs draw the distinction sharply: a URL you get live from a panel or a Dock drop already has implicit security-scoped access, as if `startAccessingSecurityScopedResource()` had been called for you, but a URL resolved from *stored* bookmark data gets no such implicit grant — you must call it yourself, and balance it with `stopAccessingSecurityScopedResource()` (Accessing files from the macOS App Sandbox; startAccessingSecurityScopedResource(), https://developer.apple.com/documentation/foundation/nsurl/startaccessingsecurityscopedresource().md; stopAccessingSecurityScopedResource(), https://developer.apple.com/documentation/foundation/nsurl/stopaccessingsecurityscopedresource().md). Apple's own reference sample for `fileImporter` calls start/stop explicitly around the live picker URL too, so the simplest rule to actually follow is: **always** bracket file use in start/stop, regardless of where the URL came from — it costs nothing when access was already implicit, and it's the only safe option once the URL came from a resolved bookmark.

```swift
var isStale = false
guard let url = try? URL(
    resolvingBookmarkData: bookmark,
    options: .withSecurityScope,
    relativeTo: nil,
    bookmarkDataIsStale: &isStale
) else {
    // bookmark failed to resolve: file moved or deleted — degrade gracefully (see below)
    return
}
guard url.startAccessingSecurityScopedResource() else { return }
defer { url.stopAccessingSecurityScopedResource() }
// use url; the defer guarantees the balancing stop call even on early return or throw
```

**The start/stop discipline is load-bearing, not stylistic.** Apple's docs confirm the last balanced `stopAccessingSecurityScopedResource()` call immediately relinquishes access, and that every `startAccessingSecurityScopedResource()` must be matched by exactly one `stopAccessingSecurityScopedResource()` on the same URL (startAccessingSecurityScopedResource(), https://developer.apple.com/documentation/foundation/nsurl/startaccessingsecurityscopedresource().md). What that page doesn't spell out, but is corroborated on Apple Developer Forums: skipping the stop call leaks kernel resources, and enough leaked grants make your app unable to extend its sandbox to *any* further location — via bookmarks or Powerbox — until it's relaunched. Always pair start/stop with `defer` (or a `try`/`finally`-equivalent) rather than a manual call at the end of a function, so an early return or a thrown error still releases access.

## File-access UX: ask once, remember, degrade gracefully

- **Ask once, not per launch.** The picker interaction is the expensive part of this flow from the user's perspective — a security-scoped bookmark exists specifically so you never have to re-prompt for a folder or file the person already granted access to. Persist the bookmark the first time access is granted; treat any subsequent need for the same resource as "resolve the stored bookmark," not "show the panel again."
- **Refresh a stale bookmark silently when you can.** `bookmarkDataIsStale` coming back `true` means the resolved URL still works but the bookmark data itself is out of date (e.g., the volume was reformatted or the path changed shape) — re-create and re-persist the bookmark from the resolved URL rather than surfacing this to the user.
- **Handle a bookmark that fails to resolve at all as an expected case, not an error state to crash on.** A moved, renamed, or deleted file makes resolution throw or return `nil`. Fall back to whatever the app's "no access yet" state already is — an empty state, a re-prompt affordance — rather than assuming the bookmark will always resolve.
- **Distinguish "never granted" from "grant lost."** An app opening for the first time with no bookmark on file should look identical, functionally, to one whose bookmark just failed to resolve: both need the same "let the user pick again" path. Don't build two different empty-state flows for what's the same underlying condition from the user's point of view.

## Hardened Runtime: a different mechanism, often confused with the sandbox

Hardened Runtime and App Sandbox are frequently conflated because both show up as checkboxes in the same Signing & Capabilities tab, but they protect against different things. App Sandbox governs *what resources your app is allowed to touch* — files, network, hardware — via entitlements you request. Hardened Runtime, alongside System Integrity Protection, governs *the runtime integrity of your process itself* — it blocks classes of exploits like code injection, dynamically-linked-library hijacking, and process memory tampering, independent of what files or network access the app has (Hardened Runtime, https://developer.apple.com/documentation/security/hardened-runtime.md). An app can be sandboxed without Hardened Runtime, hardened without being sandboxed (the common case for a notarized, directly-distributed app that isn't going through the Store), or both — they're independent axes of a build, not a single toggle.

Hardened Runtime is not optional for anything Apple notarizes: enabling it is required to submit a macOS app for notarization at all (Hardened Runtime). Its own entitlements — exceptions like allowing JIT-compiled code, disabling library validation, allowing unsigned executable memory — follow the same code-signature mechanics as sandbox entitlements (declared in Xcode, embedded at signing, requested only where the app genuinely needs the exception) but they relax *runtime* protections rather than *resource-access* restrictions. Entitlements in general apply only to the executable that claims them — shared libraries, frameworks, and in-process plug-ins inherit whatever entitlements their host executable has rather than declaring their own (Hardened Runtime). Grant Hardened Runtime exceptions as narrowly as sandbox entitlements: each one reopens a specific class of exploit the runtime would otherwise block.

## Diagnosing a sandbox violation

When a sandboxed operation silently fails (a system library logs to stderr rather than raising a catchable error you can inspect directly), check Console.app filtered to `subsystem:com.apple.sandbox.reporting category:violation`, or inspect the app's own stderr output — the violation message names the offending process, the specific denied action, and a backtrace to the violating code (Discovering and diagnosing App Sandbox violations, https://developer.apple.com/documentation/security/discovering-and-diagnosing-app-sandbox-violations.md). From there you have three real options: add the capability the operation actually needs, split the capability-requiring code into a separate helper tool so the rest of the app doesn't carry that entitlement, or remove the code path if the feature isn't essential (Discovering and diagnosing App Sandbox violations). A helper tool launched via `Process`/fork-exec inherits the launching app's sandbox *entitlements*, but not necessarily the ad hoc per-URL grants the parent obtained at runtime through a panel or bookmark — this is exactly the gap the ImageSipper example hits (macOS by Tutorials, ch. 13); if a subprocess needs direct access to a user-picked path, pass it a resolved, still-open security-scoped URL or route the actual file I/O through the parent process instead of the child.

## Adopting the sandbox in an existing app

Retrofitting App Sandbox onto an app that already writes to arbitrary locations in the user's home folder needs a migration step, not just flipping the capability on: a `container-migration.plist` with a `Move` array (and optionally `MigrateScriptsForApplication` / `Symlink` keys) tells macOS which existing files to relocate into the new sandbox container the first time the updated app launches (Migrating your app's files to its App Sandbox container, https://developer.apple.com/documentation/security/migrating-your-app-s-files-to-its-app-sandbox-container.md). Skipping this means users on an update silently lose access to files the previous, unsandboxed version wrote outside the container.
