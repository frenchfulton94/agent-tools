## The three budgets this file is about

RAM, battery, and disk are the resources the OS rations across every app on the device, not just yours — which is why iOS enforces them by killing you rather than degrading you gracefully. This file is about seeing a budget problem coming and finding its cause, not about UI responsiveness (`responsiveness-hangs-and-hitches.md`), profiling mechanics or `OSSignposter` (`profiling-workflow.md`), or SwiftUI update diagnosis (`swiftui-performance.md`). Measurement discipline still applies here exactly as everywhere else: Release configuration, a real device, and one change at a time — a memory number from a Debug build or the Simulator is not evidence of anything (see below).

## Leaks vs. abandoned memory

This is the distinction that decides which tool you reach for, and getting it wrong is the single most common false-confidence bug in memory work.

- **A leak** is memory that has become genuinely *unreachable* — no live strong-reference path from any root reaches it — but wasn't freed, almost always because a reference cycle disconnected itself from the rest of the graph. Instruments' **Leaks** template exists specifically for this: it periodically scans your app's memory and reports allocated-but-unreachable regions, each with the address, size, and the allocation stack trace.
- **Abandoned memory** is memory your app can still reach and could free, but doesn't. Apple's own example: a dictionary of messages keyed by ID that only grows as someone scrolls a timeline, with nothing ever evicting old entries. Nothing here is a leak — every entry is one dereference away from a root the whole time — so **the Leaks instrument will never flag it**, no matter how long you run it.

This is why "Instruments shows no leaks" is a much weaker statement than it sounds. It means no reference cycle happened to sever itself from the graph during your run. It says nothing about a cache or a subscription that never trims, which in most real apps is the bigger contributor to a growing memory footprint over a session. If memory climbs and Leaks stays clean, stop looking for a cycle and start asking what's still reachable that shouldn't be.

A single example illustrates both halves at once — and a case that is genuinely reachable, not a classic cycle, so Leaks would stay silent on it either way:

```swift
import Observation

@Observable
final class ThumbnailLoader {
    var image: Int = 0
    private var refreshTask: Task<Void, Never>?

    func startRefreshing() {
        refreshTask = Task {
            while !Task.isCancelled {
                await self.reload()
            }
        }
    }

    func reload() async { /* ... */ }
}
```

`refreshTask` holds the running `Task` strongly, and the `Task`'s closure captures `self` strongly to call `reload()` forever. As long as nothing cancels it, the concurrency runtime keeps the task's closure — and therefore `self` — alive and reachable indefinitely, even after the screen that created this loader is gone. Leaks won't report this: `self` is reachable through the running task, not orphaned. The Allocations instrument's timeline is what shows it, as memory tied to a feature you navigated away from that never comes back down (see the Generations workflow below). `[weak self]` in the closure stops the object from being pinned in memory, but note the sharper failure mode underneath it: an unowned/weak fix silences the memory symptom while the `while !Task.isCancelled` loop keeps spinning and calling `reload()` forever — a live battery and CPU cost with no memory signature at all. The actual fix is lifecycle-driven cancellation (call `refreshTask?.cancel()` when the owner goes away, or prefer a structured `.task { }` view modifier whose cancellation is automatic) — a case where a memory-shaped bug is best fixed as a lifecycle bug, not a reference-strength bug.

The textbook, Leaks-catchable shape is different and simpler: two objects each holding a strong reference to the other (a delegate stored strongly instead of `weak`, or a Combine `.sink` closure captured by the object it's stored on) with no path left to either from your app's actual root graph — the whole pair goes unreachable together and Leaks will find it. The runaway-task shape above is the harder case precisely because nothing about it looks like the textbook cycle.

Discarding what you don't currently need is the other side of "abandoned memory," and it's proactive rather than diagnostic: release view-owned content — decoded images, video players, SceneKit/RealityKit scenes — when your app enters the background and recreate it on return to foreground, rather than letting it sit resident while nobody can even see it.

## Retain-cycle diagnosis: the actual workflow

1. **Debug Memory Graph** (the icon in Xcode's debug bar at the bottom of the workspace window, or the equivalent Debug Navigator entry) renders every live object, heap allocation, and memory-mapped file as a node, with arrows for what references what. It shows you the *shape* of ownership; it does not tell you which arrows are wrong.
2. Turn on **Malloc Stack Logging** first (the "Malloc Stack" checkbox in the Diagnostics tab of your scheme's Run settings) — without it, a node in the graph tells you an object exists and what points to it, but not which line of your code allocated it. With it on, the inspector for a selected node shows the allocating stack trace.
3. Export the graph (File > Export Memory Graph) to hand to a teammate or inspect later with command-line tools like `vmmap` and `leaks` outside Xcode.
4. Run the **Leaks** Instruments template alongside real usage of the suspect feature, not just at idle — cycles often only form once a specific interaction chain runs (open → configure a closure-holding callback → dismiss without an explicit teardown).
5. What the tooling gives you: the exact set of live objects, the exact reference graph between them, and (with Malloc Stack on) exactly where each was allocated. **What it does not give you: which of those references *should* exist.** A view-model-owns-service reference and an accidental cycle look identical in the graph — the judgment call ("does this reference need to be `weak`?") is entirely yours. That judgment almost always comes down to ownership direction: the object that conceptually *owns* the lifecycle (a parent, a container, a coordinator) holds strong; anything reached the other way — a child calling back to its parent, a delegate, a closure capturing the object that scheduled it — should default to `weak` or `unowned` unless you have a specific reason it must outlive the call that captured it.
6. **Do not wait for the graph to flag a cycle for you.** Apple's own page describes the graph's structure, the Malloc Stack workflow, and export — and documents *no* automatic cycle-detection indicator (checked 2026-09-02). Common lore says the Debug Navigator marks suspected cycles; that is not something the documentation promises, so do not build a workflow on it. The documented escape hatch is the exported graph plus the command-line tools the same page names: `leaks` and `vmmap`, both present at `/usr/bin` (verified 2026-09-02). `leaks` accepts a **memory-graph file**, not just a live pid — `leaks [options] pid | partial-process-name | memory-graph-file` — so an exported graph is directly analyzable, and `--traceTree=<address>` prints a reverse tree of references from a block up to the process roots, which is the mechanical way to see a cycle rather than eyeballing arrows.

## Memory limits and termination

The system samples memory as *pages in use × page size* — typically 16 KB per page on iOS — so writing a single new byte can cost a full 16 KB if it forces a new page to be mapped. Only **dirty** memory (pages your app has actually written to) counts against you; memory it has merely allocated but not touched ("clean") doesn't need physical RAM backing it yet.

There is no single published number for "the" memory limit — Apple states plainly that it varies per device — but the mechanism is uniform:

- Crossing an internal warning threshold delivers a low-memory warning through any of: `applicationDidReceiveMemoryWarning(_:)` on the app delegate, `didReceiveMemoryWarning()` on active view controllers, `didReceiveMemoryWarningNotification`, or a dispatch source with `DISPATCH_SOURCE_TYPE_MEMORYPRESSURE`. This does **not** mean you're about to be killed — only that you're approaching the line.
- Crossing the actual per-process limit gets you terminated. If this happens in the foreground, the user watches your app vanish, and the next launch is cold — no state restoration head start.
- A **jetsam event report** — the record the system writes when it kills a process to reclaim memory — is not a crash report: it's JSON, covers every process on the device (not just yours), and carries no thread backtraces. It looks like a crash to the user even though nothing in your code faulted.

Reading a jetsam report: multiply the process's `rpages` field by the header's `pageSize` to get bytes used at kill time. Check `largestProcess` in the header — if it names you repeatedly even on runs where you weren't the one killed, you're the reason other apps are dying. The `reason` field on the killed process explains why:

| `reason` | What actually happened |
|---|---|
| `per-process-limit` | Crossed the system-wide per-process cap. Extensions have a much lower cap than foreground apps — avoid high-baseline-memory APIs (`MKMapView`, SpriteKit) in an extension; use a snapshot (`MKMapSnapshotter`) instead. |
| `vm-pageshortage` | System-wide pressure; a background process paid for the foreground app's demand. |
| `vnode-limit` | System-wide open-file exhaustion; you can be killed in the background to free file-backing structures even if you never opened an unusual number of files yourself. |
| `highwater` | A *system daemon* exceeded its expected footprint — not your bug. |
| `fc-thrashing` | Something thrashed the shared file cache via non-sequential mapped-file I/O; again, you can be killed in the background even if you weren't the thrasher. |
| `jettisoned` | Catch-all for other system-chosen reasons. |

**Seeing it coming, instead of reading about it after the fact:** the Xcode Debug navigator's memory gauge while running (yellow = warning territory, red = termination risk) during manual testing; the Organizer's **Memory** pane for peak-use and use-at-suspension across releases, filterable by 50th/90th percentile and comparable release-over-release; and `MetricKit`'s equivalent metrics for the same two numbers from the field. **The Simulator gauge always reads green** — macOS doesn't issue memory warnings or terminations — so it's useful for continuing to run and debug an app that iOS keeps killing, but a green gauge there proves nothing about safety on-device. Termination from the lifecycle/watchdog side (background task expiration, launch-time watchdogs) is `responsiveness-hangs-and-hitches.md`'s territory; this section is only the memory-limit half of "why did my app die."

## Battery use and the Power Profiler

CPU is rarely the real story. The Organizer's **Battery Usage** pane and the Debug navigator's Energy Impact gauge both break power into categories — Audio, Networking, Processing (CPU+GPU), Display, Bluetooth, Location, Camera, Torch, NFC, Other — and it is common for Display or Networking to dominate a CPU-light app. Concretely: prefer `URLSession` (built-in connection pooling and scheduling) over rolling your own sockets; batch and compress requests instead of issuing them piecemeal; set `waitsForConnectivity` instead of retry-spinning on connection failure, and drop `allowsExpensiveNetworkAccess`/`allowsConstrainedNetworkAccess` for anything non-essential. On the CPU side specifically, size concurrent units of work to roughly 10–100 ms each — fine enough to spread across cores, coarse enough that scheduling overhead doesn't eat the win — and use the lowest `DispatchQoS` the task tolerates, since the scheduler runs low-QoS work in more energy-efficient ways. On location, prefer `CLMonitor`/region-based updates over continuous tracking once the device goes stationary, and treat `CLBackgroundActivitySession`/always-authorization as a last resort, not a default.

**Power Profiler** (the Instruments tool, not a separate app) needs iOS 26 or iPadOS 26 or later on a real device — there's no Simulator story. Capture a trace: Product > Profile, choose the **Blank** template, add the **Power Profiler** instrument, target your specific process (not "All Processes" — that only records system-wide power, nothing app-attributed), record, interact with the feature under test, stop. The track shows overall system power draw as a fraction of battery-per-hour, plus charging state, thermal state, and display brightness; expand your app's row for the CPU/GPU/display/networking lanes underneath. Two gotchas that will otherwise read as bugs in the tool: **while charging (cable or MagSafe), Instruments reports overall system power as `0`** — pair over wireless debugging instead if you need real numbers; and power-impact values are device-model-specific, so a trace from one device is not comparable to a trace from another model, only to another trace on the *same* model.

For scenarios you can't reproduce tethered to a Mac (low-battery behavior, CarPlay), Power Profiler also runs standalone on-device: Settings > Developer > Performance Trace, turn it on, set the mode to Power Profiler, enable tracing for your app in the app list, then add a Performance Trace tile to Control Center (Control Center > Add a Control) to start/stop a capture (up to 10 hours) without Xcode attached at all. Share the resulting file from Settings > Developer > Performance Trace; double-clicking the received `.aar` in Finder expands it to a `.atrc` you open directly in Instruments. This whole path is GUI/on-device-only — there is no CLI equivalent, and none of this is scriptable from `xctrace`.

Field-side, gather the same categories through `MetricKit` rather than waiting for someone to file a battery complaint: `CPUTimeMetric`/`CPUInstructionsCountMetric` for processing, `GPUTimeMetric` for GPU, `PixelLuminanceMetric` for display, `LocationActivityTimeMetric` for location, and the `TotalWiFi`/`TotalCellular` upload/download metrics for networking — each maps directly onto one of the Organizer's Battery Usage categories, so a spike in one metric tells you which category to go chase in Instruments. On Bluetooth specifically, the cheapest win is simply not holding a connection open longer than you're actively communicating with the accessory — prefer `AccessorySetupKit` for discovery/configuration, which manages that connection lifetime for you instead of leaving it to your own bookkeeping.

Apple also names a specific, easy-to-miss lever for push-driven UI: a Live Activity update sent with `apns-priority` set to `5` is delivered on the system's own energy-efficient schedule and doesn't count against your app's Live Activity update budget — use it for any update that doesn't need to land immediately.

An **energy exception report** appears in the Organizer's Energy pane (also gatherable via `MetricKit`) when your app crosses an internal, Apple-undisclosed energy threshold over a 24-hour window; each report names the responsible function, a sample stack trace, and a 14-day trend, and Xcode can paste that context straight into a coding-assistant session via "Generate Recommendations" in the Inspector.

## Disk writes: why they cost more than the bytes suggest

Writes and reads to the same SSD block serialize — a write in flight queues up any read that touches that block — so a write-heavy pattern degrades read latency too, not just write latency. Three concrete costs that are easy to underestimate:

- **Block granularity.** The disk controller writes in blocks, commonly 4 KB. A one-byte change to a file still writes a full 4 KB block.
- **Filesystem metadata.** Creating or deleting a file writes about 8 KB of directory metadata; renaming or moving one costs up to 16 KB. Writing "atomically" (the atomic-write paths on `NSString`/`NSArray`/`NSDictionary`/`NSData`) adds a temp-file create, a write, an unlink, and a rename on top of the real content write — don't reach for atomic writes by default.
- **Explicit sync calls.** `fsync`/`F_FULLFSYNC` force a flush of the unified buffer cache and are a genuine "best-effort" persistence guarantee, not an absolute one (power loss can still lose data) — most apps that think they need a durability barrier actually only need `F_BARRIERFSYNC`, which is far cheaper.

An app that crosses an internal disk-write threshold over 24 hours gets a **disk write exception report**, visible in the Organizer's Disk Writes pane or via `MetricKit`, with the responsible function, a stack trace, and a 14-day trend — same shape as the energy exception report above, same "Generate Recommendations" assist. The Organizer's Disk Writes metrics chart separately reports daily logical MB written per version (50th/90th percentile, filterable by device), which is the number to sanity-check against what your app's actual data footprint should require — writing 500 MB/day to persist 100 KB of real content is a sign you're rewriting the same data repeatedly, not that your app legitimately needs that throughput.

To find *which* code is responsible: the **File Activity** Instruments template pairs the Filesystem Activity instrument (logical read/write/mmap syscalls, each with size, duration, and backtrace) with Disk Usage and Disk I/O Latency (the resulting physical reads/writes) — logical and physical sizes don't correlate directly because of the block-rounding above, which is exactly why both views exist.

For anything backed by SQLite (directly, or via Core Data/SwiftData): keep connections open rather than repeatedly opening/closing them (each open/close pays for consistency checks and journal writes); wrap related edits in a single transaction rather than one write per field change; add indices for columns you sort or filter by — `EXPLAIN QUERY PLAN` reporting `USE TEMP B-TREE FOR ORDER BY` on a hot query means you're missing one; turn on write-ahead logging (`journal_mode` = WAL) to coalesce writes to the same page and let reads proceed concurrently with a writer; and avoid the `VACUUM` command, which rewrites the entire database — use incremental auto-vacuum instead. Serialized formats (property lists, JSON, XML) are fine for read-mostly bundle metadata but wrong for documents that change frequently, since any edit rewrites the whole file — use SQLite/Core Data/SwiftData once content is edited often.

## Storage metrics and purgeable storage

The Organizer's **Storage** pane tracks two separate charts across releases: **Documents & Data** (your cache-folder usage vs. everything else) and **App Size** (installed bundle size), each against an anonymized comparison line for similar apps. A sudden jump in either without a matching intentional feature is the signal to look at what shipped in that version.

Only put content your app can regenerate or live without into `cachesDirectory` or `temporaryDirectory` — the system purges both automatically under storage pressure, but treat that as a backstop, not your cache-eviction strategy: frequently-used apps are less likely to get purged automatically, so proactively bound and trim what you put there. For local copies of iCloud-backed files you're not actively using, `evictUbiquitousItem(at:)` drops the local copy while the iCloud original stays intact (re-fetch later with `startDownloadingUbiquitousItem(at:)`); calling `removeItem(at:)` on an iCloud file instead deletes the iCloud copy too, non-recoverably. On APFS, `copyItem(at:to:)` creates a copy-on-write clone that shares storage with the original until one side is modified — prefer it over any copy path that actually duplicates bytes on disk.

## App size: what dominates it, and how to measure it for a specific app

Assets dominate almost every app's size, not code — so optimize in this order: image/video/audio format choice, then unused-file removal, then binary-vs-catalog placement, and only then anything structural. Concretely: prefer HEIF over PNG/JPEG and HEVC over uncompressed video; an 8-bit PNG can be roughly a quarter the size of a 32-bit one; compress audio as AAC or MP3 and question whether you actually need a 44.1 kHz sample rate at full bit rate, since a lower rate is often imperceptible; ship images, textures, and bundled data through **asset catalogs** rather than as loose files or (worse) literal data in source — asset catalogs are also the prerequisite for app thinning and on-demand resources, and moving data out of source into asset files shrinks the compiled binary directly, not just the bundle. Group rarely-used assets as **on-demand resources** so they're not part of the initial download at all.

A build artifact you already have — the `.app` bundle, the `.xcarchive`, or the `.ipa` you'd upload — is *not* a valid size measurement for any of them: each carries extra content (dSYMs, per-device-variant data) that a real download never includes. The archive/export mechanics themselves (how to produce a distributable build) are `app-release`'s territory; what belongs here is reading the output. Exporting with "All compatible device variants" selected produces an **app size report** (`App Thinning Size Report.txt`) listing each variant's compressed (download) and uncompressed (installed) size — that report, or the Organizer's App Size chart across releases, or App Store Connect's per-variant size display once a build is live, are the only numbers worth trusting. To see *what's* taking the space inside a specific IPA without waiting for a report, unpack it — it's a ZIP archive with the app bundle under `Payload/` — and inspect the contents directly rather than guessing from source-tree size.

One easy-to-miss trap when chasing update size specifically: the App Store computes a diff between your new build and prior versions of *the entire bundle contents*, including files you didn't mean to touch. Don't rely on file creation/modification timestamps as a proxy for "did this change" — the diffing engine looks at content, not metadata, but a build step that rewrites a file's bytes without changing its logical content (re-running an asset compiler that isn't byte-stable, for instance) will bloat every update even though nothing meaningful changed. Diff two build outputs directly when an update's size looks larger than the actual content delta should justify.

## Catching regressions before they ship

All three budgets have an `XCTest` performance-test metric that turns "we think this got worse" into a CI-visible number: pass `XCTMemoryMetric()` to `measure(metrics:)` around a block that exercises the feature to record peak memory and allocation growth during it, or `XCTStorageMetric()` for blocks written to disk to record blocks written. Either way, run it once to click "Set Baseline" in the test-results UI, and the test then fails when a later change significantly exceeds that baseline — which catches an abandoned-memory or disk-write regression at review time instead of at "why did our Organizer chart jump this release." Test *authoring* mechanics (test plans, running these in CI) belong to `swift-testing`; the point here is only that these two metrics exist and which of your budgets each one guards. **`XCTest` here is not legacy drift** — Swift Testing has no performance/measurement API, so performance regression tests stay in an `XCTestCase` subclass even in an otherwise fully migrated target. That finding is recorded independently in `swift-testing`'s `swift-testing-framework.md`; this file relies on it rather than re-deriving it.

## Classic pitfalls

- **"No leaks" ≠ "no memory problem."** Leaks only catches unreachable cycles; a growing, still-reachable cache or subscription list is invisible to it by design.
- **The Simulator's green memory gauge proves nothing.** macOS doesn't enforce memory pressure or termination the way iOS does; a Simulator run can look perfectly healthy for a build that gets jetsam-killed constantly on-device.
- **`[weak self]` fixes the memory symptom, not necessarily the underlying bug.** An orphaned task that keeps running after its owner should be gone still burns CPU and battery even once it stops pinning memory — cancel it, don't just weaken the reference to it.
- **Assuming CPU is the energy story.** Display, networking, and location routinely outweigh CPU in the Organizer's category breakdown; profile the categories, don't assume.
- **A charging cable silently zeroes out Power Profiler's system-power reading** — a "no power impact" trace captured while plugged in is not a measurement, it's an artifact.
- **Logical writes and physical disk writes are different numbers.** Block rounding (4 KB) and metadata overhead (8–16 KB per file create/rename) mean a tiny logical change can be a much larger physical write; don't reason about disk cost from file-size deltas alone.
- **Reaching for `F_FULLFSYNC` or atomic writes as a default** adds real write overhead most apps don't need; `F_BARRIERFSYNC` and non-atomic writes cover the common case.
- **Combining `NSCache` with `NSPurgeableData`** is explicitly discouraged by Apple — and don't walk your whole object graph looking for memory to release on a low-memory warning either: both patterns pull compressed memory pages back out of the compressor, which increases system memory demand at exactly the moment you're trying to reduce it.
- **A `vnode-limit` or `fc-thrashing` jetsam kill on your app doesn't mean your app caused the pressure** — both can terminate a well-behaved background app to relieve system-wide contention someone else created.
- **Debug/archive/IPA-uploaded binaries all overstate or misstate real download size** — none of them is the number to optimize against; only an app size report, the Organizer, or App Store Connect is.
