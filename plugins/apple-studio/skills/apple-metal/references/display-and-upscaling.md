## Choosing the presentation surface

All three options present `CAMetalLayer` drawables. They differ in who owns the
loop, which thread it runs on, and how much timing you see.

| Option | Loop and thread | Timing you get | Use it for |
|---|---|---|---|
| `MTKView` + `MTKViewDelegate` | MetalKit's timer, on the **main actor** | none beyond "draw now" | tools, editors, prototypes, the first triangle |
| `CAMetalLayer` + your own loop | yours, any thread | whatever you build | rare; when even a display link is in the way |
| `CAMetalDisplayLink` on a `CAMetalLayer` | a run loop you choose, so a dedicated render thread | target timestamps plus a drawable handed to you | shipping games |

What decides it:

- **`MTKView` is main-actor-bound.** The SDK marks the class and both delegate
  methods `NS_SWIFT_UI_ACTOR`; the docs show `@MainActor func draw(in:)`. Every
  frame's encoding then competes with UI and input handling on the main thread.
- **`MTKView` defaults to 60 fps.** `preferredFramesPerSecond` defaults to 60,
  and the view picks a factor of the screen's maximum rate. On a 120 Hz panel
  you get 60 until you raise it. (On iPhone you also need the Info.plist key in
  `apple-games/game-loop-and-threading.md`.)
- **`MTKView` draw modes.** The default is timer-driven (`isPaused == false`,
  `enableSetNeedsDisplay == false`), which is the only mode for a game. Setting
  `enableSetNeedsDisplay` with `isPaused` makes it event-driven, for editors.
  Subclass it or give it a delegate, not both.
- **`CAMetalDisplayLink` (macOS 14, iOS 17) is the game choice.** You create it
  from the layer with `init(metalLayer:)` and register it on a run loop with
  `add(to:forMode:)`. The system then calls
  `metalDisplayLink(_:needsUpdate:)`, and the `CAMetalDisplayLink.Update` it
  passes carries the `drawable`, a `targetTimestamp` deadline for calling
  `present()`, and a `targetPresentationTimestamp` estimate of when the frame
  shows. Animate from the presentation timestamp delta, as the docs advise.
- **`preferredFrameLatency` accepts only `1.0` and `2.0`.** It is how many frames
  of time you ask for. At `2.0` the GPU may keep working after the
  `targetTimestamp` deadline, which only bounds the CPU's `present()` call. The
  system can add latency of its own, for example for a windowed game on macOS.
- **A display link forbids timed presents.** Calling `present(at:)` or
  `present(afterMinimumDuration:)` on its drawable asserts. Use `present()`.
- **The link's `delegate` is `weak`.** Hold the renderer strongly elsewhere, or
  callbacks stop silently.
- **`CADisplayLink` exists on macOS 14 and later.** The custom-view sample says
  it is iOS-only and builds on `CVDisplayLink` instead. That is stale: treat
  `CVDisplayLink` as legacy.

```swift
final class Renderer: NSObject, CAMetalDisplayLinkDelegate {
    let queue: any MTL4CommandQueue
    let commandBuffer: any MTL4CommandBuffer

    init?(device: any MTLDevice) {
        guard let queue = device.makeMTL4CommandQueue(),
              let commandBuffer = device.makeCommandBuffer() else { return nil }
        self.queue = queue
        self.commandBuffer = commandBuffer
    }

    func metalDisplayLink(_ link: CAMetalDisplayLink,
                          needsUpdate update: CAMetalDisplayLink.Update) {
        let drawable = update.drawable
        // Core frame from command-model.md's "Frame structure": reset the
        // allocator, begin, encode the pass into drawable.texture, end.
        queue.waitForDrawable(drawable)      // before any commit that touches it
        queue.commit([commandBuffer])
        queue.signalDrawable(drawable)       // once, after the last such commit
        drawable.present()                   // never present(at:) with a display link
    }
}

final class RenderLoopThread: Thread {
    let layer: CAMetalLayer
    let renderer: Renderer                   // strong: the link's delegate is weak

    init(layer: CAMetalLayer, renderer: Renderer) {
        self.layer = layer
        self.renderer = renderer
        super.init()
    }

    override func main() {
        let link = CAMetalDisplayLink(metalLayer: layer)
        link.delegate = renderer
        link.preferredFrameLatency = 2
        link.preferredFrameRateRange = CAFrameRateRange(minimum: 60, maximum: 120, preferred: 120)
        link.add(to: .current, forMode: .default)
        while !isCancelled {
            _ = RunLoop.current.run(mode: .default, before: .distantFuture)
        }
        link.invalidate()
    }
}
```

Pick a `preferredFrameRateRange` you can hold. The system rounds to a factor of
the display's maximum rate and can lower it for Low Power Mode, thermal state,
or accessibility settings; the default is the display's maximum.

A view without MetalKit hosts the layer itself. A UIKit view returns
`CAMetalLayer` from `layerClass`; an AppKit view sets `wantsLayer` and returns a
`CAMetalLayer` from `makeBackingLayer()`. Recreate the display link when the
view moves to another screen (`didMoveToWindow` / `viewDidMoveToWindow`), and
stop it when the window closes.

## Drawables: acquire late, hold briefly

A `CAMetalLayer` owns a small pool of drawables. Only a drawable presents: a
texture you allocated must be drawn or copied into one first.

- **Pool size.** `maximumDrawableCount` defaults to 3 and accepts only 2 or 3;
  any other value is ignored and throws.
- **Acquisition blocks.** `nextDrawable()` waits while the pool is empty,
  usually until the next refresh. After one second it returns `nil`. It also
  returns `nil` for an invalid layer configuration or when out of memory.
  `allowsNextDrawableTimeout = false` makes it wait forever; never set that in
  a game.
- **The MTKView accessors acquire too.** `currentRenderPassDescriptor` and
  `currentMTL4RenderPassDescriptor` fetch a drawable as a side effect. Read them
  after the offscreen passes (shadows, G-buffer, reflections), right before the
  pass that writes the drawable. Both can be `nil`, and a skipped frame is
  normal: return early. `currentMTL4RenderPassDescriptor` is not in the
  Simulator SDK.
- **Release references.** The layer reuses a drawable only when it is off screen
  and nothing holds it strongly. A leaked reference drains the pool, and later
  acquisitions return `nil`. Retaining one only to read `presentedTime` after
  presentation is fine.
- **Measure what reached the glass.** `addPresentedHandler(_:)` runs after
  presentation. In it, `presentedTime` is the host time the frame appeared, or
  `0.0` if the frame was dropped. Differences between successive values are the
  true frame interval.
- **`framebufferOnly`.** Defaults to `true`: drawables get only `.renderTarget`
  usage, which Core Animation can optimize. A compute kernel, an MPS filter, or a
  blit that reads or writes the drawable needs `false`, at a performance cost.
  MetalKit asserts "frameBufferOnly texture not supported for compute"
  otherwise. Prefer rendering into your own texture and finishing with one
  render pass into the drawable.
- **Reading pixels back** (screenshots, pickers). Set `framebufferOnly = false`
  and copy the region into a shared buffer in the same frame, before presenting.
  Presentation discards the contents.
- **`presentsWithTransaction`.** Defaults to `false`: Metal frames reach the
  screen asynchronously to Core Animation. Set `true` only when UIKit or AppKit
  content must move in the same frame as the Metal layer. The docs' recipe then
  commits, waits until scheduled, and calls `present()` directly; a
  command-buffer `present` variant does not wait for the transaction.
- **`displaySyncEnabled`** (vsync, default `true`) is macOS-only. The symbol page
  lists iOS too, but the SDK header marks it unavailable on iOS, tvOS, and
  visionOS; the SDK wins. Setting `false` trades tearing for latency.

## The Metal 4 present sequence

`MTL4CommandBuffer` has no `present`. Presentation is a queue-level handshake
around your commit:

1. `queue.waitForDrawable(drawable)` before committing any command buffer that
   targets the drawable. It returns at once; the wait is on the GPU timeline.
   Call it once per queue if several queues touch the drawable.
2. `queue.commit(...)` the work.
3. `queue.signalDrawable(drawable)` after the last commit that touches it. It
   fails if called twice, or after any `present`. Work committed after it is not
   guaranteed to finish before presentation.
4. `drawable.present()`.

Residency is the other Metal 4 difference. Drawables are not tracked
automatically: add the layer's `residencySet` to the queue. The layer keeps that
set current, and you must not modify it. It does not exist while the layer's
`device` is `nil`, and changing the device invalidates it, so fetch it again
afterwards. `MTKView.residencySet` holds the view's own depth and multisample
textures, but it is **macOS 26.4 / iOS 26.4**, not 26.0: gate it.

```swift
@MainActor
func addViewResidency(of metalView: MTKView, to queue: any MTL4CommandQueue) {
    if let layer = metalView.layer as? CAMetalLayer {
        queue.addResidencySet(layer.residencySet)    // drawables, 26.0
    }
    if #available(macOS 26.4, iOS 26.4, *) {
        queue.addResidencySet(metalView.residencySet) // depth and MSAA targets
    }
}
```

On macOS the layer's `device` defaults to `nil` and must be set before the first
drawable; on iOS it defaults to the system device.

## Sizing the drawable

- `drawableSize` defaults to the layer bounds times `contentsScale`, in pixels.
  `MTKView` resizes it for you while `autoResizeDrawable` is `true`, and calls
  `mtkView(_:drawableSizeWillChange:)` on resize, rotation, and moves between
  displays. Rebuild size-dependent targets and the projection there.
- Render 2D UI at the backing size, and the 3D scene into a separate target
  sized for the device, then upscale it (MetalFX below, or your own pass). A
  fixed drawable such as 3840×2160 is also valid.
- Letterbox an aspect mismatch with `contentsGravity = .resizeAspect` and a black
  layer background.
- **macOS direct-to-display.** When the game is full screen, the `CAMetalLayer` is
  opaque (its default), the content is RGB, and the Mac is Apple silicon, the
  display hardware composites the drawable straight to the panel, scaling it at
  almost no cost. The drawable need not match the panel resolution. Confirm it
  in the Metal HUD or Instruments rather than assuming it.
- Apple silicon Macs have one GPU, so `preferredDevice` and
  `CGDirectDisplayCopyCurrentMetalDevice(_:)` matter only on Intel Macs, which
  this skill does not cover.

## HDR and EDR

EDR is display-referred: 1.0 is SDR reference white, not the panel's peak.
Values from 0 to 1 look exactly like SDR. Headroom is the multiple of SDR white
the display can show now. It changes live, usually grows as the user lowers
brightness, and can be 1.0 even on an HDR panel at maximum brightness.

Pick the route by what your pixels are:

| Content | Layer setup | Who tone-maps |
|---|---|---|
| Rendered game frames (the usual case) | `wantsExtendedDynamicRangeContent = true`, `.rgba16Float`, an extended-linear color space, no `edrMetadata` | you, to the current headroom, every frame |
| Already-encoded HDR you only display (PQ) | `wantsExtendedDynamicRangeContent = true`, `.bgr10a2Unorm`, `CGColorSpace.itur_2100_PQ` | the system applies the transfer function |
| Linear HDR video that must match AVFoundation | `.rgba16Float`, `CGColorSpace.extendedLinearITUR_2020`, `edrMetadata` set | the system, from the metadata |

Plain video belongs in `AVPlayerLayer` or `AVSampleBufferDisplayLayer`, which
handle HDR themselves.

```swift
func configureForGameHDR(_ layer: CAMetalLayer) {
    layer.wantsExtendedDynamicRangeContent = true
    layer.pixelFormat = .rgba16Float
    layer.colorspace = CGColorSpace(name: CGColorSpace.extendedLinearDisplayP3)
    layer.edrMetadata = nil          // nil: no system tone mapping; you own it
}

@MainActor
func currentHeadroom(of metalView: MTKView) -> CGFloat {
    #if os(macOS)
    return metalView.window?.screen?.maximumExtendedDynamicRangeColorComponentValue ?? 1
    #else
    return metalView.window?.windowScene?.screen.currentEDRHeadroom ?? 1
    #endif
}
```

The gotchas:

- **Read headroom per frame and tone-map into `[0, headroom]`.** The system
  clamps anything above it. On macOS the current value is
  `NSScreen.maximumExtendedDynamicRangeColorComponentValue`. It reads 1.0 until
  something on screen requests EDR, so read it after enabling EDR. Changes post
  `NSApplication.didChangeScreenParametersNotification`.
- **Capability is a different property.**
  `maximumPotentialExtendedDynamicRangeColorComponentValue` is fixed when the
  `NSScreen` is created; above 1.0 means the display can do EDR. On iOS the pair
  is `UIScreen.currentEDRHeadroom` and `potentialEDRHeadroom`.
- **Reference displays.** A non-zero
  `maximumReferenceExtendedDynamicRangeColorComponentValue` means a calibrated
  reference mode. Keep values within it and the hardware applies no further tone
  mapping; its ceiling can sit below the current EDR maximum.
- **`colorspace` defaults to `nil`, which means no color matching.** Set it
  explicitly for every layer, SDR included.
- **`edrMetadata` must be set before `nextDrawable()`.** It also needs a pixel
  format above 1.0 and a linear color space, and the docs warn that system tone
  mapping costs significant memory and GPU time. Build it with
  `CAEDRMetadata.hdr10(minLuminance:maxLuminance:opticalOutputScale:)`, not an
  initializer: `init()` is unavailable. With an `opticalOutputScale` of 100, a
  shader value of 1.0 means 100 nits. A normalized pixel format implies 10,000.
- **Which EDR switch: the SDK has moved.** In the Xcode 27 SDK,
  `CALayer.wantsExtendedDynamicRangeContent` is deprecated (macOS 14–26,
  iOS 17–26) in favor of `CALayer.preferredDynamicRange` (`.automatic`,
  `.standard`, `.constrainedHigh`, `.high`; OS 26). `CAMetalLayer` redeclares
  its own `wantsExtendedDynamicRangeContent`, which is **not** deprecated and
  compiles without a warning at the 26.0 floor. Keep using it on a Metal layer.
  The header describes `preferredDynamicRange` in terms of headroom-tagged
  `contents` and `CGColor`s, and says nothing about drawables, so test it before
  relying on it for one.
- **`contentsHeadroom`** (OS 26) lets a `CAMetalLayer` declare how much headroom
  its drawables use. A small value reduces the power cost of EDR. 0 means
  untagged; values between 0 and 1 are undefined.
- **`toneMapMode`** (macOS 15, iOS 18) is `.automatic` by default, or `.never`,
  or `.ifSupported` (tone-map PQ, HLG, and extended-range content whenever the OS
  can). It applies to `CAMetalLayer` drawables.
- **EDR and `CAEDRMetadata` are unavailable on tvOS** in the SDK.
- **Pixel formats.** The `pixelFormat` symbol page lists nine:
  `.bgra8Unorm` (default), `.bgra8Unorm_srgb`, `.rgba16Float`, `.rgb10a2Unorm`,
  `.bgr10a2Unorm`, and the extended-range `.bgra10_xr`, `.bgra10_xr_srgb`,
  `.bgr10_xr`, `.bgr10_xr_srgb`. The `CAMetalLayer.h` comment still names only
  the first two; it is stale. The extended-range formats have every texture
  capability from Apple3 (Feature Set Tables, "Texture capabilities for
  extended-range and wide-color formats by GPU family").
- The Metal debugger's attachment viewer hatches pixels above the current
  headroom, which is the quickest check that the tone mapper's ceiling is right
  (`gpu-debugging-and-profiling.md`).

## MetalFX: choose the effect by the inputs you can produce

The MetalFX index lists four effects, each with a Metal 3 type and a Metal 4
(`MTL4FX`) type. They share one descriptor class per effect.

| Effect | Inputs it needs | Family floor (Feature Set Tables) | Metal 4 factory |
|---|---|---|---|
| Spatial scaler | color only | Apple3 | `MTLFXSpatialScalerDescriptor.makeSpatialScaler(device:compiler:)` → `MTL4FXSpatialScaler` |
| Temporal scaler | color, depth, motion; optional exposure and reactive mask | Apple7 | `MTLFXTemporalScalerDescriptor.makeTemporalScaler(device:compiler:)` → `MTL4FXTemporalScaler` |
| Frame interpolator | color, previous color, depth, motion, camera parameters; optional UI | Apple5 | `MTLFXFrameInterpolatorDescriptor.makeFrameInterpolator(device:compiler:)` → `MTL4FXFrameInterpolator` |
| Temporal denoised scaler | color, depth, motion, diffuse and specular albedo, normal, roughness, camera matrices; optional extras | Apple9 | `MTLFXTemporalDenoisedScalerDescriptor.makeTemporalDenoisedScaler(device:compiler:)` → `MTL4FXTemporalDenoisedScaler` |

The family floors come from the Feature Set Tables' "Metal feature availability
by GPU family". Gate at run time with the effect's own class methods, not the
family: `supportsDevice(_:)` for the Metal 3 type, and `supportsMetal4FX(_:)`
before using an `MTL4FX` type. The `MTL4FX` types encode with
`encode(commandBuffer:)` taking an `MTL4CommandBuffer`.

**Availability: trust the SDK, symbol by symbol.** The framework page lists
iOS 16, macOS 13, and visionOS 1. The SDK says:

- Spatial and temporal scalers: macOS 13 / iOS 16.
- Frame interpolator and every `MTL4FX` type: macOS 26 / iOS 26.
- Denoised scaler descriptor: macOS 26 / iOS 18. Its base protocol is
  macOS 26 / iOS 26, so treat it as 26 on both.
- The temporal scaler, interpolator, and denoiser are unavailable on visionOS.
  Only the spatial scaler is available there.
- The symbol pages add tvOS 27.1.
- Several member pages carry nonsense floors such as iOS 8 for `exposureTexture`;
  ignore those.

Rules for every effect:

- **Create once, reuse every frame.** Creation is slow. Build the effect at
  launch or on a display-resolution change. `requiresSynchronousInitialization`
  (temporal and denoised) defaults to `false`: creation returns quickly and runs
  a slower interim upscaler while the fast one compiles in the background. Image
  quality is the same either way. Set it `true` when you create the effect
  behind a loading screen and want full speed on frame one.
- **The descriptor fixes formats and sizes; texture identity is free.** MetalFX
  does not track which texture objects you assign, so a ring of targets is fine.
  Each one must match the descriptor's pixel format and dimensions.
- **Create the effect first, then allocate its textures.** Each effect reports the
  minimum usage per input (`colorTextureUsage`, `depthTextureUsage`,
  `motionTextureUsage`, `outputTextureUsage`, ...). Your texture descriptors must
  include those bits, and extra bits are fine.
- **Outputs must be `.private`.** Every effect's `outputTexture` page says so.
  Upscale into your own private texture, then composite UI into the drawable in
  a final pass; do not aim the effect at a `framebufferOnly` drawable.
- **Encode between passes.** End the encoder that wrote the inputs, then call
  `encode(commandBuffer:)`. The `fence` property is documented only for Metal 3
  untracked resources. The pages say nothing about Metal 4 barriers around the
  effect's work, so check the ordering in the Metal debugger's dependency viewer
  (`gpu-debugging-and-profiling.md`).
- **HUD check.** The Metal Performance HUD lists active MetalFX scaling modes and
  counts interpolated frames in its frame number.

### Spatial scaler

The spatial scaler is the cheap path when you have no motion vectors.
`colorProcessingMode` must describe the input: `.perceptual` is the default and
means sRGB-encoded; `.linear` is linear in `[0, 1]`; `.hdr` is linear above 1,
which MetalFX handles with a reversible tone map. *Metal by Tutorials* measured a
1.25× upscale as a small gain at acceptable quality and 2× as fast but muddy.
At small factors the encode overhead can erase the gain, so profile it.

### Temporal scaler

This is the mode for a game that can write motion vectors.

```swift
func makeTemporalUpscaler(device: any MTLDevice, compiler: any MTL4Compiler,
                          renderWidth: Int, renderHeight: Int,
                          outputWidth: Int, outputHeight: Int) -> (any MTL4FXTemporalScaler)? {
    guard MTLFXTemporalScalerDescriptor.supportsMetal4FX(device) else { return nil }
    let desc = MTLFXTemporalScalerDescriptor()
    desc.inputWidth = renderWidth
    desc.inputHeight = renderHeight
    desc.outputWidth = outputWidth
    desc.outputHeight = outputHeight
    desc.colorTextureFormat = .rgba16Float
    desc.depthTextureFormat = .depth32Float
    desc.motionTextureFormat = .rg16Float
    desc.outputTextureFormat = .rgba16Float
    desc.isAutoExposureEnabled = true
    return desc.makeTemporalScaler(device: device, compiler: compiler)
}

func makeEffectTexture(device: any MTLDevice, format: MTLPixelFormat,
                       width: Int, height: Int, usage: MTLTextureUsage) -> (any MTLTexture)? {
    let desc = MTLTextureDescriptor.texture2DDescriptor(pixelFormat: format, width: width,
                                                        height: height, mipmapped: false)
    desc.usage = usage                  // at least what the scaler reports
    desc.storageMode = .private         // required for the output
    return device.makeTexture(descriptor: desc)
}

func encodeUpscale(_ scaler: any MTL4FXTemporalScaler, into commandBuffer: any MTL4CommandBuffer,
                   color: any MTLTexture, depth: any MTLTexture, motion: any MTLTexture,
                   output: any MTLTexture, jitter: SIMD2<Float>, cameraCut: Bool) {
    scaler.colorTexture = color
    scaler.depthTexture = depth
    scaler.motionTexture = motion
    scaler.outputTexture = output
    scaler.inputContentWidth = scaler.inputWidth
    scaler.inputContentHeight = scaler.inputHeight
    scaler.jitterOffsetX = jitter.x               // in input pixels
    scaler.jitterOffsetY = jitter.y
    scaler.motionVectorScaleX = Float(scaler.inputWidth)   // UV-space vectors -> pixels
    scaler.motionVectorScaleY = Float(scaler.inputHeight)
    scaler.isDepthReversed = true                 // set it explicitly either way
    scaler.reset = cameraCut                      // true for one frame after a cut
    scaler.encode(commandBuffer: commandBuffer)
}
```

Allocate each input with `makeEffectTexture(... usage: scaler.colorTextureUsage)`
and the matching property for the others, after the scaler exists.

The inputs, and where they go wrong:

- **Motion vector convention.** MetalFX multiplies each motion value by
  `motionVectorScaleX/Y` to get pixels. At scale 1.0 a vector points from the
  pixel in this frame to where that pixel was at the previous encode. So an
  object moving 10 pixels down and right has vector `(-10, -10)`, in Metal's
  top-left-origin pixel space. Vectors are at input resolution, and by default
  they must not include the jitter.
- **Jitter.** Jitter the projection by a sub-pixel offset each frame, and report
  it in `jitterOffsetX/Y` in input pixels. The docs do not state the sign
  convention. Verify on a static scene: a wrong sign shows as shimmer or blur
  that a correct one removes.
- **Depth.** `isDepthReversed` means 0 is far. The temporal scaler's docs give no
  default, unlike the interpolator and denoiser (both `true`), so always set it.
- **History.** `reset` discards history. Set it on the frame after a camera cut
  or teleport, and clear it afterwards, because it is a plain stored property.
- **Exposure.** Either `isAutoExposureEnabled`, or `exposureTexture`: a 1×1
  `.r16Float` texture whose R value multiplies the input color, best written by
  the GPU. Auto exposure ignores the texture. `preExposure` is for input that
  was already scaled by a constant, which is rare.
- **Reactive mask.** Particles and other alpha-blended content with poor motion
  data smear. Enable `isReactiveMaskTextureEnabled` (macOS 14.4, iOS 17.4) and
  supply `reactiveMaskTexture` in `[0, 1]`: 0 is normal behavior, 1 ignores
  history for that pixel.
- **Dynamic resolution.** Set `isInputContentPropertiesEnabled` and
  `inputContentMinScale/MaxScale` on the descriptor. Clamp those to
  `supportedInputContentMinScale(device:)` / `supportedInputContentMaxScale(device:)`.
  Then vary `inputContentWidth/Height` per frame inside a fixed-size color
  texture. The aspect ratio must not change.
- **macOS 27 / iOS 27 additions; gate them.**
  - `isJitteredMotionVectorsEnabled`: your vectors include the jitter, and
    MetalFX subtracts it.
  - `isOutputResolutionMotionVectorsEnabled`: motion at output size.
  - `colorContentOffsetX/Y` and the other content offsets.
  - `reactiveMaskTextureUsage`, which replaces the now-deprecated
    `reactiveTextureUsage`.

```metal
#include <metal_stdlib>
using namespace metal;

// Clip-space positions of one surface point this frame and last frame, both
// computed without the jitter offset. The result is in UV units (top-left
// origin), so the host sets motionVectorScaleX/Y to the input width/height.
float2 motion_uv(float4 currentClip, float4 previousClip) {
    float2 currentNDC  = currentClip.xy  / currentClip.w;
    float2 previousNDC = previousClip.xy / previousClip.w;
    // NDC y points up; texture and pixel y point down.
    float2 currentUV  = currentNDC  * float2(0.5, -0.5) + 0.5;
    float2 previousUV = previousNDC * float2(0.5, -0.5) + 0.5;
    return previousUV - currentUV;               // current -> previous
}
```

The sign and scale above follow from the documented `(-10, -10)` example. If you
store NDC-space vectors instead, the Y scale must be negative and half the
height.

The exposure and pre-exposure inputs imply HDR, pre-tone-map scene color.
Upscale the 3D scene before tone mapping, and draw UI at output resolution
afterwards.

### Frame interpolator

The interpolator generates an extra frame from two rendered frames. It raises
the displayed frame rate, not responsiveness, and it can add latency: the frame
in between can only be built once the later frame exists. That is an inference
from how the effect works; the docs do not describe a presentation schedule. You
present its `outputTexture` yourself, so you own the pacing. Verify the result
in the HUD, which counts interpolated frames.

What it needs per frame:

- `colorTexture` and `prevColorTexture`. The previous one must hold exactly what
  `colorTexture` held at the last encode, unless `shouldResetHistory` is set.
  `requiresPrevColorTexture` (macOS 27 / iOS 27, default `true`) lets MetalFX
  keep it for you when set `false`.
- `depthTexture` and `motionTexture` at the descriptor's `inputWidth/Height`. The
  output is `outputWidth/Height`.
- `motionVectorScaleX/Y`. At 1.0 each vector points to the pixel's position in
  `prevColorTexture`, with the same sign convention as the scaler.
- Camera state: `deltaTime` (seconds between the two frames), `nearPlane`,
  `farPlane`, `fieldOfView` (vertical, **degrees**), and `aspectRatio`. These
  must be the values your projection used.
- `jitterOffsetX/Y`, and `isDepthReversed`, which defaults to `true` here.
- UI: pass HUD and menus as `uiTexture` (format fixed by `uiTextureFormat`) so
  MetalFX overlays it instead of warping it. If your color already has the UI
  composited in, set `isUITextureComposited` and MetalFX separates it.
- `shouldResetHistory` on scene cuts.
- `descriptor.scaler`: the effect that upscales the frames, any
  `MTLFXFrameInterpolatableScaler`. The temporal and denoised scalers conform;
  the spatial scaler does not. The docs give no further contract for it.

The macOS 27 / iOS 27 SDK adds content sub-rectangles, `worldToViewMatrix` /
`viewToClipMatrix`, and barrel-distortion correction
(`isDistortionTextureEnabled`, `distortionTexture`).

### Temporal denoised scaler

The denoised scaler is for ray-traced or path-traced frames that are cheap and
noisy: it denoises and upscales in one effect. Beyond color, depth, and motion
it needs a G-buffer: `diffuseAlbedoTexture`, `specularAlbedoTexture`,
`normalTexture`, and `roughnessTexture`, each with a descriptor format. It also
needs `worldToViewMatrix` and `viewToClipMatrix` every frame. Optional inputs
are switched on in the descriptor:

- `isSpecularHitDistanceTextureEnabled` → `specularHitDistanceTexture`.
- `isDenoiseStrengthMaskTextureEnabled` → `denoiseStrengthMaskTexture`. It is
  single-channel; 1.0 marks a pixel the denoiser leaves alone.
- `isTransparencyOverlayTextureEnabled` → `transparencyOverlayTexture`: RGBA in
  linear space, RGB from 0 to unbounded, alpha as opacity. Put particles here
  rather than in the noisy color.
- `isReactiveMaskTextureEnabled`, with the same meaning as for the temporal
  scaler.

Exposure, jitter, `shouldResetHistory`, and `isDepthReversed` (default `true`)
behave as above. It needs Apple9 (A17 Pro, A18, M3, M4 and later) per the Feature
Set Tables, so ship the temporal scaler as the fallback path.

## Maintaining older code: Metal 3

The Metal 3 path applies to GPU families below Apple7 (A13 and earlier; A14 and
M1 are Apple7) and to OS releases before 26.0. Gate on both:

```swift
func presentsWithMetal4(_ device: any MTLDevice) -> Bool {
    guard #available(macOS 26.0, iOS 26.0, *) else { return false }
    return device.supportsFamily(.metal4)
}
```

Snippets in this section compile at the file's macOS 26.0 floor; they are not compile-checked against earlier OS releases.

| Metal 3 | Metal 4 |
|---|---|
| `commandBuffer.present(drawable)` then `commit()` | `waitForDrawable` → `commit` → `signalDrawable` → `drawable.present()` on the `MTL4CommandQueue` |
| `present(_:atTime:)` / `present(_:afterMinimumDuration:)` on the command buffer | `present(at:)` / `present(afterMinimumDuration:)` on the drawable, after `signalDrawable` (never with a display link) |
| drawables tracked implicitly | add `CAMetalLayer.residencySet` (and, from 26.4, `MTKView.residencySet`) to the queue |
| `MTKView.currentRenderPassDescriptor` | `MTKView.currentMTL4RenderPassDescriptor` |
| `makeSpatialScaler(device:)`, `makeTemporalScaler(device:)` → `encode(commandBuffer:)` on an `MTLCommandBuffer` | `...(device:compiler:)` with an `MTL4Compiler` → `encode(commandBuffer:)` on an `MTL4CommandBuffer` |
| `supportsDevice(_:)` | `supportsMetal4FX(_:)` |
| `fence` on an effect, for untracked resources | no documented equivalent; check the ordering in the debugger |

```swift
func presentMetal3(queue: any MTLCommandQueue, drawable: any CAMetalDrawable,
                   spatial: any MTLFXSpatialScaler) {
    guard let commandBuffer = queue.makeCommandBuffer() else { return }
    // ...encode the scene into spatial.colorTexture...
    spatial.encode(commandBuffer: commandBuffer)
    // ...composite spatial.outputTexture and the UI into drawable.texture...
    commandBuffer.present(drawable)
    commandBuffer.commit()
}
```

The frame interpolator and denoised scaler also have Metal 3 types
(`MTLFXFrameInterpolator`, `MTLFXTemporalDenoisedScaler`), but both need
OS 26 in practice. The interpolator is macOS 26 / iOS 26 outright. The
denoiser's iOS 18 marking rests on a base protocol marked iOS 26. So a pre-26
fallback has only the spatial and temporal scalers.

## Classic pitfalls

- **Shipping on `MTKView` defaults.** It renders on the main actor and runs at
  60 fps on a 120 Hz panel.
- **Calling `present(at:)` with a `CAMetalDisplayLink`.** It asserts.
- **Letting the display link's delegate deallocate.** The reference is weak.
- **Calling `signalDrawable` twice, or after `present()`.** It fails, and work
  committed after the signal may land after presentation.
- **Forgetting the layer's residency set** in Metal 4, or reaching for
  `MTKView.residencySet` at a 26.0 floor (it is 26.4).
- **Acquiring the drawable early.** That includes reading
  `currentMTL4RenderPassDescriptor` before the offscreen passes, which stalls
  on a pool of three.
- **`allowsNextDrawableTimeout = false`.** A lost drawable becomes a hang.
- **Tone-mapping to 1.0 on an EDR display**, or to a headroom read once at
  launch.
- **Leaving `colorspace` nil.**
- **Building `CAEDRMetadata` with an initializer**, or setting it after
  `nextDrawable()`.
- **Pointing a MetalFX effect at a shared or `framebufferOnly` texture.** Outputs
  must be private.
- **Motion vectors with the wrong sign or units, or with jitter baked in.** All
  three ghost or smear. Leaving `reset` set after a cut does the same.
- **Gating MetalFX by GPU family.** Ask the effect: `supportsMetal4FX(_:)`.
- **Using `isJitteredMotionVectorsEnabled`, the content offsets, or
  `requiresPrevColorTexture` at a 26.0 floor without `#available`.** They are 27.0.
