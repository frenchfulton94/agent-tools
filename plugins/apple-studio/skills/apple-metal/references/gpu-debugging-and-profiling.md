## Pick the tool by question

| Question | Tool | Agent can run it? |
|---|---|---|
| Is the frame rate bad, and is it the CPU or the GPU? | Metal Performance HUD (`MTL_HUD_ENABLED=1`) | Yes, its log goes to the console |
| What did this draw actually write, and with which pipeline? | GPU trace, then `gpudebug` | Yes |
| Which pass, shader, or draw costs the most? | `gpudebug` `profile run`, or the Metal debugger's Performance view | Yes (`gpudebug`, M3/A17 Pro and later) |
| Where inside the shader does the time go? | Shader cost graph, per-line profiling | GUI only |
| Why does this pixel have this value? | Shader debugger | GUI only |
| Wrong API usage on the CPU side | API Validation (`MTL_DEBUG_LAYER=1`) | Yes |
| Out-of-bounds, non-resident, nil, NaN on the GPU side | Shader Validation (`MTL_SHADER_VALIDATION=1 MTL_SHADER_VALIDATION_REPORT_TO_STDERR=1`) | Yes |
| Print a value from inside a shader | Shader logging (`os_log` in MSL) | Yes |
| GPU time per frame or per pass, in your own HUD or telemetry | `MTL4CommitFeedback`, `MTL4CounterHeap` | Yes |
| Stutters across many frames, CPU and GPU together | Instruments: Game Performance, Metal System Trace | Record and export yes; analysis GUI only |

"GUI only" means no command-line or API route exists: do not invent a flag for it.
Hand those steps to the user with the exact menu path.

## Make every trace readable before you need it

A trace of an unlabelled engine is a wall of `MTLBuffer 37`. Labels and debug groups
cost nothing at runtime and are the only names `gpudebug`, the Metal debugger, the
HUD's top-labelled lists, and Instruments' resource events can show.

- Set `label` on every queue, buffer, texture, heap, pipeline descriptor, and encoder.
  The HUD's "top labelled command buffers and encoders" lists skip anything unlabelled.
- Group work with `pushDebugGroup(_:)` and `popDebugGroup()` on the `MTL4CommandBuffer`
  and on each encoder, and mark points with `insertDebugSignpost(_:)` on the encoder.
- **A reused `MTL4CommandBuffer` keeps only its last label.** Metal 4 reuses one
  command buffer object across frames. In a trace of three commits, `gpudebug` showed
  all three command buffers under the label set last, while the `api_calls` list
  kept each frame's own `setLabel:` (runtime-checked). Put the frame number in a
  debug group instead. Debug groups keep their per-frame names.

```swift
func encodeLabelledFrame(queue: any MTL4CommandQueue,
                         commandBuffer: any MTL4CommandBuffer,
                         allocator: any MTL4CommandAllocator,
                         pass: MTL4RenderPassDescriptor,
                         frameIndex: Int) {
    commandBuffer.beginCommandBuffer(allocator: allocator)
    commandBuffer.pushDebugGroup("Frame \(frameIndex)")
    // No early return between begin and end: pop the group and end the buffer on every path.
    if let encoder = commandBuffer.makeRenderCommandEncoder(descriptor: pass) {
        encoder.label = "Forward pass"
        encoder.pushDebugGroup("Opaque")
        // Opaque draws go here.
        encoder.popDebugGroup()
        encoder.insertDebugSignpost("Transparent begins")
        encoder.endEncoding()
    }
    commandBuffer.popDebugGroup()
    commandBuffer.endCommandBuffer()
    queue.commit([commandBuffer])
}
```

In the trace, a debug group becomes a `grpN` node at whatever level it was pushed. The
probe's draw sat at `commands/cb0/grp0/re0/grp0/draw0`: the frame group, then the
encoder, then the "Opaque" group.

### Shader source in the trace

The shader debugger, per-line costs, and the shader cost graph need the source compiled
into the library. Set **Produce Debugging Information** (`MTL_ENABLE_DEBUG_INFO`) for
Debug builds:

| Value | Compiler flags | Gives you |
|---|---|---|
| `NO` (the default) | none | No shader views in the debugger |
| `YES` | `-gline-tables-only` | Line tables only |
| `INCLUDE_SOURCE` | `-gline-tables-only -frecord-sources` | Everything; required for the shader debugger |

Set Release back to `NO`. An App Store build must not carry shader source. To debug a
release library anyway, write the source to a companion `.metallibsym` file and keep it
out of the bundle. Both forms below ran here (runtime-checked):

```bash
# One step: writes default.metallib and default.metallibsym
xcrun -sdk macosx metal -frecord-sources=flat Shadow.metal Lights.metal

# Several steps: compile to .air, link with sources, then strip them into a .metallibsym
xcrun -sdk macosx metal -c -frecord-sources Shadow.metal
xcrun -sdk macosx metal -frecord-sources -o Scene.metallib Shadow.air
xcrun -sdk macosx metal-dsymutil -flat -remove-source Scene.metallib
```

`-frecord-sources=flat` replaces the deprecated `-MO`. The `-c` step writes `.air`
files; one older page calls them `.ir`. Load the `.metallibsym` in Xcode from the
debugger's Import Sources prompt, or ahead of time with Debug > Import Metallib Debug Info.

## Capturing a GPU trace

A `.gputrace` is a bundle that holds the Metal calls and every resource needed to replay
them. Three ways to get one:

| Route | Needs | Use when |
|---|---|---|
| Xcode's Metal Capture button | Xcode running the app | Interactive debugging |
| `MTLCaptureManager` in code | `MTL_CAPTURE_ENABLED=1` or `MetalCaptureEnabled` | A rare frame, a test, an agent, a non-Xcode build |
| `gpucapture` in a terminal | `MTL_CAPTURE_ENABLED=1` and a debuggable binary | No code change; any process you launch |

**Replay is not portable.** A trace replays reliably only on the same device type, GPU,
and OS it came from. Capture on the machine that will replay it, or export it from the
Metal debugger with **Embed performance data** so that its profile opens on any Mac
without a replay.

### From Xcode (GUI)

GPU Frame Capture is a scheme option (Edit Scheme > Run > Options), and Xcode turns it
on whenever the target links Metal. It costs a little CPU time: set it to Disabled when
you measure peak performance. The Capture popover offers a frame, a layer, a queue, the
device, or any labelled custom scope, with a count. Its Advanced section has Profile
after Replay, a keyboard shortcut (macOS only), MetalFX temporal-scaler history (slower
capture, better replayed textures), and the shared-memory optimization (Automatic,
Always, Never; choose Never if the replay looks wrong). To capture a build Xcode did
not make, use Debug > Debug Executable, pick the app, set GPU Frame Capture, then
Product > Run. Save with File > Export.

### From code, to a `.gputrace` file

Capture works only when the capture layer is loaded at launch. Either set
`MetalCaptureEnabled` to `YES` in Info.plist (build setting
`INFOPLIST_KEY_MetalCaptureEnabled`), or on macOS 14 and later launch with
`MTL_CAPTURE_ENABLED=1`. Drive either from a build setting or a launch flag so that
release builds stay clean, because loading it costs a little CPU time.

Without it, `supportsDestination(.gpuTraceDocument)` returns `false`, and
`startCapture(with:)` throws `MTLCaptureError` code 1, "Capture layer is not inserted."
(runtime-checked).

```swift
enum TraceError: Error { case captureLayerMissing }

/// Records every command buffer any queue of `device` commits between
/// `startTrace` and `stopTrace` into a .gputrace bundle at `url`.
func startTrace(device: any MTLDevice, url: URL) throws {
    let manager = MTLCaptureManager.shared()
    // False unless the process launched with MTL_CAPTURE_ENABLED=1
    // or carries MetalCaptureEnabled = YES in its Info.plist.
    guard manager.supportsDestination(.gpuTraceDocument) else {
        throw TraceError.captureLayerMissing
    }
    let descriptor = MTLCaptureDescriptor()
    descriptor.captureObject = device
    descriptor.destination = .gpuTraceDocument
    descriptor.outputURL = url          // must end in .gputrace
    try manager.startCapture(with: descriptor)
}

func stopTrace() {
    MTLCaptureManager.shared().stopCapture()
}
```

This exact code captured a Metal 4 probe that committed one reused `MTL4CommandBuffer`
twice through an `MTL4CommandQueue`. The trace held two command buffers, `cb0` and
`cb1`, and replayed the triangle correctly (runtime-checked). The rules:

- Only command buffers committed while the capture runs are recorded. Start it before
  the frame's first commit and stop it after the last one you want. One capture can span
  several frames.
- `captureObject` must be an `MTLDevice`, an `MTLCommandQueue`, or an `MTLCaptureScope`
  (the header's list). An `MTL4CommandQueue` is not an `MTLCommandQueue`, so to capture
  a Metal 4 engine, pass the device, or a scope.
- `stopCapture()` also cuts short a scope's `end()`. `isCapturing` reports whether a
  capture is running.

**Scopes.** A scope delimits a capture with `begin()` and `end()` instead of start and
stop calls. Create it once, outside the frame loop, and keep a strong reference for as
long as it should exist. Never allocate one yourself: get it from the capture manager.
Assign it to `defaultCaptureScope` to make Xcode's Capture button grab exactly your
frame. With no default scope, Xcode delimits a frame by drawable presents, which an
offscreen or compute-only engine never makes.

```swift
@MainActor
final class FrameCapture {
    let scope: any MTLCaptureScope

    init(device: any MTLDevice) {
        scope = MTLCaptureManager.shared().makeCaptureScope(device: device)
        scope.label = "Engine frame"
        MTLCaptureManager.shared().defaultCaptureScope = scope
    }

    /// Call `scope.begin()` before the frame's first commit and `scope.end()`
    /// after its last one. A capture started here stops at the next `end()`.
    func captureNextFrame(to url: URL) throws {
        let descriptor = MTLCaptureDescriptor()
        descriptor.captureObject = scope
        descriptor.destination = .gpuTraceDocument
        descriptor.outputURL = url
        try MTLCaptureManager.shared().startCapture(with: descriptor)
    }
}
```

A device scope used as `captureObject` recorded only the first `begin()`…`end()`
span of three (runtime-checked).

**The Metal 4 queue overload.** `MTLCaptureManager` also has
`makeCaptureScope(commandQueue: any MTL4CommandQueue)`, and the scope it returns
reports the queue in `mtl4CommandQueue`. The programmatic-capture article shows Metal 3
types only. **On macOS 27.0.1, passing such a scope as `captureObject` crashed the
process** inside `startCapture(with:)` with `-[MTLCaptureScope traceStream]:
unrecognized selector` (runtime-checked, `NSInvalidArgumentException`). A
`makeCaptureScope(device:)` scope captured the same Metal 4 queue correctly. For
programmatic capture, use the device route. Whether the queue scope works as
`defaultCaptureScope` behind Xcode's Capture button is not runtime-checked.

Launch with the variable set; a relative trace path resolves against the process's
working directory:

```bash
MTL_CAPTURE_ENABLED=1 ./MyEngine
```

### From the terminal, with no code change: `gpucapture`

`/usr/bin/gpucapture` captures any process that was launched with
`MTL_CAPTURE_ENABLED=1` and is debuggable (`com.apple.security.get-task-allow` on
macOS). `gpucapture list` marks other processes `[non-debuggable]`. A `swiftc` build
qualified as it stood. A hardened, notarized release build will not.

```bash
gpucapture list                                     # capturable processes and PIDs
gpucapture boundaries --pid 12345                   # Device, Queue, Layer, Scope boundaries by ID
gpucapture start --pid 12345 --count 1 --output "$PWD/Frame.gputrace"
gpucapture stop --pid 12345
```

- `--boundary <ID>` or `--label <label>` picks the trigger. A labelled queue, layer, or
  scope survives from run to run when the IDs change.
- `--count` counts command buffers for a Device or Queue boundary, frames for a Layer
  boundary, and `end()` calls for a Scope boundary.
- With no boundary, `start` picks the app's `CAMetalLayer` if there is exactly one, and
  otherwise the device.
- For a short command-line run, launch the target with `MTLCAPTURE_WAIT_FOR_SIGNAL=1`.
  The process then stops at device creation until a `start` arrives. Capture with
  `--until-exit`.
- **Give `--output` an absolute path.** A relative path failed with "failed to create
  valid output directory" after the capture had finished. An absolute path wrote the
  trace, which `gpudebug` then opened (runtime-checked, including `--until-exit` on an
  `MTL4CommandQueue` workload).
- The man page describes Device and Queue boundaries in terms of `MTLCommandBuffer`.
  The device boundary captured Metal 4 command buffers; a Queue boundary on an
  `MTL4CommandQueue` is not runtime-checked.

## Reading a trace from the terminal: `gpudebug`

`/usr/bin/gpudebug` (version 1.0) opens a `.gputrace`, replays it on the local GPU, and
gives a text interface over the whole trace. Every node lists its children and the
actions it supports, so an agent can explore a trace it has never seen. Apple's advice
for agents is to read `man gpudebug` and then open the trace. The man page is the full
reference.

**`gpudebug --help` does not list `-c`.** The man page and both articles use it, and it
works.

### Sessions: the commands to run

A session is a background process that holds the loaded trace and the replayer.
Loading takes seconds to minutes on a big trace, so open the trace once and send every
later command to the session. This script ran as written against the probe's trace
(runtime-checked):

```bash
id=$(gpudebug -q -t Frame.gputrace -c "list" | sed -n 's/^Session \([0-9]*\) created\./\1/p')
gpudebug -s "$id" -c "status"                                  # replayer: loading... / ready
gpudebug -s "$id" -c "go /commands"                            # command buffers cb0, cb1, ...
gpudebug -s "$id" -c "find opaque"                             # labels and groups, as absolute paths
gpudebug -s "$id" -c "go /commands/cb0/grp0/re0/grp0/draw0" -c "info" -c "info pipeline"
gpudebug -s "$id" -c "go /commands/cb0/grp0/re0/grp0/draw0" -c "fetch color0 --out $PWD/draw0.png"
gpudebug -s "$id" -c "go /api_calls" -c "list --all"
gpudebug --terminate "$id"
```

- The draw path assumes one command-buffer debug group and one encoder debug group, as
  `encodeLabelledFrame` pushes. With other grouping, run `go /commands/cb0` and follow
  the listing, or `find <label>`.
- `-q` hides the banner, but `Session N created.` still prints. The `sed` above
  extracts the ID from that line.
- `--oneshot -t <trace> -c ...` opens, runs, and closes a session in one call. It pays
  the whole load cost every time, so use it for a single question only.
- `exit` detaches from an interactive session and leaves it alive. `gpudebug -l` lists
  sessions, and `gpudebug --terminate all` ends them all. A session dies with the shell
  that owns it, or after 2 hours idle (`--timeout <seconds>`, `0` disables it).
- `--json` (for example `gpudebug -s "$id" --json -c "go /commands"`) returns
  `{"children":[...],"totalCount":N}` for listings. Use it when a script parses the
  output.
- `fetch` writes PNG files for textures, `.bin` files for buffers, and shader sources
  under their own file names. Without `--out` or `-o <dir>`, output goes to
  `$TMPDIR/gpudebug_out/<trace name>/`. `fetch` waits for the replayer to be ready.
  `list`, `go`, and most `info` calls answer at once.

### The tree

The root has four children: `commands`, `performance`, `api_calls`, and `resources`.

- `commands`: `cbN` command buffers, then `reN`, `ceN`, and `beN` encoders, then `drawN`,
  `dispN`, and `blitN`. Debug groups appear as `grpN` at any level. An encoder holds
  `color0…`, `depth`, and `stencil` with their final contents. Each draw holds
  `pipeline`, `vertex` and `fragment` (bound `buf[i]`, `tex[i]`, and `sources`), its own
  attachments, and `indexBuffer`.
- `api_calls`: every call in order, with its arguments. Metal 4 calls appear under
  their real selectors, such as `[MTL4CommandQueue commit:count:]`.
- `resources`: buffers, textures, libraries, pipelines, residency sets, shared events,
  and so on, as `@buf0`, `@tex3`, `@rps0`. `go @tex0`, `info @rps0`, and `fetch @tex0`
  work from anywhere.
- Links: from a draw, `go :a` jumps to its API call. From an API call, `go :d` jumps back
  to the draw. `:ps`, `:pt`, `:pe`, `:pc`, and `:l` link to profiling data and library
  entry points.

### Profiling from the terminal

`profile run` replays the trace with profiling on and fills `/performance`. The man
page says it needs an M3 or A17 Pro or later. `--gpu-state default|low|medium|high`
pins the GPU performance state; `--exec overlapping|serial` chooses concurrent or
serialized passes; `--embed` saves the result into the trace. `profile load` reads
a profile that is already embedded.

**Embed the profile, then load it in a new session.** A plain `profile run` printed
"Profile data collected", but every list under `/performance` stayed empty, and
`profile load` in the same session did not fill them. Embedding, closing the
session, and loading the profile in a new session worked (runtime-checked):

```bash
gpudebug -s "$id" -c "profile run --embed"                       # "Profile data collected. (6.6s)"
gpudebug --terminate "$id"
id=$(gpudebug -q -t Frame.gputrace -c "list" | sed -n 's/^Session \([0-9]*\) created\./\1/p')
gpudebug -s "$id" -c "profile load"                              # "Profile data loaded. (2.9s)"
gpudebug -s "$id" -c "go /performance" -c "go commands"         # draws ranked by cost
gpudebug -s "$id" -c "go /performance" -c "go shaders"          # frag0, vert0, ... with cost share
gpudebug -s "$id" -c "go /performance" -c "go commands" -c "go draw0" -c "go heatmap" -c "go fragment" -c "fetch cost --out $PWD/cost.png"
```

The heatmap `fetch` wrote the PNG and a `draw0_fragment_cost_top100.json` next to it.
The fragment heatmap node also offers `alu`, `nonalu`, `divergence`, `instr_count`,
`overdraw`, `draw_mapping`, and `raytracing` (runtime-checked). This is the
GUI's heat-map and cost data, readable by an agent.

### Traps (all runtime-checked)

- **A failed command still exits 0.** `error: 'cb0' not found in re0` came back with exit
  status 0. Read the output, not the exit code.
- **The session remembers where you are.** A relative `go cb0` after an earlier
  `go /commands/cb1/re0` failed. Start every scripted path with `/`.
- **`'commands' has no info` means that no profile is loaded.** Every `go` into
  `/performance` printed it after a plain `profile run`, and the lists were `(empty)`.
  With a profile loaded, `go /performance/commands` worked in one step.
- **Compile pipelines before you start the capture.** In one trace, the capture
  recorded an `MTL4Compiler` compute-pipeline compile. On that trace, `profile run`
  never returned, because the replay service crashed in
  `MakeMTL4PipelineStageDynamicLinkingDescriptor`. `list`, `find`, `info`, and
  `fetch` still worked. The same frames, with the pipeline compiled before
  `startCapture`, profiled in 6.7 s.
- **Performance names are their own.** `/performance/commands/draw0` linked (`:d`) to
  `/commands/cb1/.../draw0`, not to `cb0`. Follow the `:d` link before you blame a draw.
- **`--list-devices` numbered the local Mac `0`.** The article's example shows the local
  machine as `local` and a phone as `0`. Check the table before you pass `-d`. Listing
  remote devices needs Xcode running.

## Validation

Both layers are environment variables, read once when the first `MTLDevice` is created.
Set them at launch, not later. They work on any build, including one whose source you do
not have. `man MetalValidation` lists them all.

### API Validation: CPU-side misuse

`MTL_DEBUG_LAYER=1` turns it on. It costs a little CPU time.

- `MTL_DEBUG_LAYER_ERROR_MODE`: `assert` (the default), `ignore`, or `nslog`.
  `MTL_DEBUG_LAYER_WARNING_MODE`: `assert`, `ignore` (the default), `nslog`, or `oslog`.
- `MTL_DEBUG_LAYER_VALIDATE_LOAD_ACTIONS=1` turns every `dontCare` load into a fuchsia
  clear. `MTL_DEBUG_LAYER_VALIDATE_STORE_ACTIONS=1` writes a red and white checkerboard
  wherever a `dontCare` store happens. Together they show at a glance which passes rely on
  undefined tile contents.
- `MTL_DEBUG_LAYER_VALIDATE_UNRETAINED_RESOURCES` is a bitfield (`0x1` by default; `0x4`
  reports at deallocation rather than at commit). **It checks `MTLCommandBuffer` only,
  never `MTL4CommandBuffer`.** A Metal 4 engine that frees a resource the GPU still reads
  gets no API Validation error for it.
- **API Validation did not report a Metal 4 render target that was missing from every
  residency set.** Shader Validation did (next section; runtime-checked).

### Shader Validation: GPU-side faults

`MTL_SHADER_VALIDATION=1` instruments every shader. It catches out-of-bounds and nil
resource access, non-resident resources, NaN or infinity written to an interpolant other
than `[[position]]`, bad casts from the generic address space, the wrong acceleration
structure kind, tensor misuse, and stack overflow in indirect or recursive calls. It
slows the GPU and runtime compiles noticeably.

**It is the Metal 4 residency checker.** With the probe's render target left out of every
residency set, `MTL_SHADER_VALIDATION=1 MTL_SHADER_VALIDATION_REPORT_TO_STDERR=1` printed
"Resource residency error - MTLTexture is not resident at the time of commit", named the
texture's label and the encoder's label ("Forward pass"), and gave the allocation stack.
The process then exited 0 (runtime-checked). Add `MTL_SHADER_VALIDATION_ABORT_ON_FAULT=1`
when a test should fail on the first fault.

- **Set `MTL_SHADER_VALIDATION_REPORT_TO_STDERR=1` to read the reports.** Without it they
  go only to the unified log. There, `log stream --process <name>` shows each report under
  `com.apple.Metal` / `GPUDebug` with its text replaced by `<private>`, so the log tells you
  that a fault happened but not which (runtime-checked). The article writes `-process`;
  `man log` spells it `--process`.
- `MTL_SHADER_VALIDATION_FAIL_MODE`: `zerofill` (the default: bad reads return 0, bad
  writes are dropped) or `allow` (cheaper, but the command buffer may fail).
- **The man page and the article disagree on defaults.** The article lists
  `..._GLOBAL_MEMORY`, `..._THREADGROUP_MEMORY`, and `..._TEXTURE_USAGE` as checks you
  turn on with `=1`. `MetalValidation(1)` on the machine says each defaults to `1`, and
  documents `MTL_SHADER_VALIDATION_RESOURCE_USAGE` (also default `1`), which the article
  omits. The shipped man page wins: treat them as on, and set one to `0` to cut its cost.
- **Selective validation keeps a big game playable.** Set
  `MTL_SHADER_VALIDATION_DEFAULT_STATE=none` and list pipelines in
  `MTL_SHADER_VALIDATION_ENABLE_PIPELINES`, or keep `all` and exclude some with
  `..._DISABLE_PIPELINES`. Entries are pipeline labels or UIDs, separated by commas, and
  a space counts as part of the name. `MTL_SHADER_VALIDATION_DUMP_PIPELINES=1` logs the
  UIDs. They are stable across runs; filter Console on "Shader Validation UID". In code,
  `MTL4PipelineOptions.shaderValidation` (`.enabled` or `.disabled`) does the same per
  pipeline. The Feature Set Tables' GPU features table gates per-pipeline shader
  validation at Apple6.
- Constraints: Shader Validation does not work with binary archives. Indirect command
  buffers need pipeline and buffer inheritance. It does not track residency of the
  pages behind sparse resources.
- Set the deployment target to the OS you run on, even briefly, to get the newest
  diagnostics. Revert it afterwards.

In Xcode, the same switches live in Edit Scheme > Run > Diagnostics. That tab applies
to the Run action only. There, "Raise Runtime Issues on Error" stops at the faulting
shader line and adds a Shader Validation breakpoint.

```swift
func pipelineOptionsForValidation(enabled: Bool) -> MTL4PipelineOptions {
    let options = MTL4PipelineOptions()
    options.shaderValidation = enabled ? .enabled : .disabled
    return options
}
```

## Shader logging

`os_log` works inside MSL from Metal 3.2 on (macOS 15, iOS 18), and needs Apple6 or later
(Feature Set Tables, GPU features table). Logging has a cost even when nothing prints, so
it is opt-in at compile time. Build with `-fmetal-enable-logging` in Other Metal Compiler
Flags, or set `MTLCompileOptions.enableLogging = true` for a library compiled from source.
For the Metal 4 compiler, pass those options through `MTL4LibraryDescriptor.options`.

```metal
#include <metal_logging>

constant os_log engineLog("com.example.engine", "gpu");

kernel void cull_lights(uint tid [[thread_position_in_grid]],
                        constant uint &lightCount [[buffer(0)]])
{
    // Every thread runs this line. Gate it, or one dispatch fills the buffer.
    if (tid == 0) {
        engineLog.log_info("lights: %u", lightCount);
    }
}
```

Format strings must be literals. `%s`, `%n`, and `%@` are not allowed. A vector prints
as `%v<count><length><conversion>`, and 4-byte element types need the `hl` length
modifier: `%v4hlf` for a `float4`. `half` arguments promote to `double`.
`os_log_default` logs with no subsystem or category.

**Metal 4 attaches the log state per command buffer, at `begin`.**
`MTL4CommandBufferOptions.logState`, passed to `beginCommandBuffer(allocator:options:)`,
holds it until `endCommandBuffer()`. A handler receives each message with its subsystem
and category. Without a handler, messages go to the unified log. This ran as written,
and a kernel's `log_info` reached the handler (runtime-checked):

```swift
func makeShaderLoggingOptions(device: any MTLDevice) throws -> MTL4CommandBufferOptions {
    let descriptor = MTLLogStateDescriptor()
    descriptor.level = .debug
    descriptor.bufferSize = 64 * 1024          // bytes; minimum 1 KB
    let logState = try device.makeLogState(descriptor: descriptor)
    logState.addLogHandler { subsystem, category, level, message in
        print("[GPU \(subsystem ?? "-")/\(category ?? "-") \(level.rawValue)] \(message)")
    }
    let options = MTL4CommandBufferOptions()
    options.logState = logState
    return options
}
// Each frame: commandBuffer.beginCommandBuffer(allocator: allocator, options: loggingOptions)
```

- The buffer drains only after the command buffer completes, so order across draws is not
  guaranteed. When it fills, later messages are dropped until the CPU empties it. Command buffers
  that share one log state share one buffer, which can drain later.
- Each log state is separate memory. Make one and reuse it.
- With no API log state, the environment applies instead: `MTL_LOG_LEVEL` (default
  `MTLLogLevelDebug`), `MTL_LOG_BUFFER_SIZE` (default 1024 bytes, 1 KB to 1 GB), and
  `MTL_LOG_TO_STDERR=1` to see messages in Xcode's console. An attached log state
  overrides them.

## Measuring GPU time

### In code: commit feedback and counter heaps

**Per commit**, Metal 4 replaces the command buffer completion handler with a feedback
handler on `MTL4CommitOptions`. The feedback gives `gpuStartTime` and `gpuEndTime` (host
time, in seconds) and `error` for the commit as a whole. Handlers run on an internal queue,
or on `MTL4CommandQueueDescriptor.feedbackQueue` if you set one, which must be serial.

```swift
func commitTimed(_ commandBuffer: any MTL4CommandBuffer, on queue: any MTL4CommandQueue) {
    let options = MTL4CommitOptions()
    options.addFeedbackHandler { feedback in
        if let error = feedback.error {
            print("GPU error: \(error)")
        }
        let milliseconds = (feedback.gpuEndTime - feedback.gpuStartTime) * 1000
        print("GPU time: \(milliseconds) ms")
    }
    queue.commit([commandBuffer], options: options)
}
```

**Per pass**, write timestamps into an `MTL4CounterHeap` of type `.timestamp`. The
heap's only real type is `.timestamp`. Metal 4 has no stage-utilization or statistics
sets; those exist only on the Metal 3 path. The Feature Set Tables gate counter heaps at
Apple7, with at most 32 per process (feature limits table).

- Compute encoders: `writeTimestamp(granularity:counterHeap:index:)`. Render encoders:
  `writeTimestamp(granularity:after:counterHeap:index:)` with an `MTLRenderStages`.
  Whole command buffer: `writeTimestamp(counterHeap:index:)`.
- `.relaxed` may fold all timestamps of a pass together. `.precise` may split encoders
  and so cost time. Use `.precise` only while measuring.
- Resolve on the CPU with `resolveCounterRange(_:)` once the work has completed (wait on
  your shared event first). Resolve on the GPU with
  `resolveCounterHeap(_:range:buffer:fenceToWait:fenceToUpdate:)`, which runs in the blit
  stage.
- **Heap timestamps are GPU ticks, not nanoseconds.** Divide by
  `queryTimestampFrequency()`. The M4 Pro reported 24,000,000 ticks per second, with
  8-byte entries (`size(ofCounterHeapEntry: .timestamp)`). The Metal 3 `MTLTimestamp`
  is documented in nanoseconds, so code ported from it is off by a factor of about 42
  here. A dispatch timed both ways gave 29.58 ms from the heap and from commit feedback
  (runtime-checked).

```swift
struct PassTimer {
    let heap: any MTL4CounterHeap
    let ticksPerSecond: Double

    init(device: any MTLDevice) throws {
        let descriptor = MTL4CounterHeapDescriptor()
        descriptor.type = .timestamp
        descriptor.count = 2
        heap = try device.makeCounterHeap(descriptor: descriptor)
        ticksPerSecond = Double(device.queryTimestampFrequency())
    }

    func begin(_ encoder: any MTL4ComputeCommandEncoder) {
        encoder.writeTimestamp(granularity: .precise, counterHeap: heap, index: 0)
    }

    func end(_ encoder: any MTL4ComputeCommandEncoder) {
        encoder.writeTimestamp(granularity: .precise, counterHeap: heap, index: 1)
    }

    /// Call only after the GPU work has completed.
    func milliseconds() throws -> Double? {
        guard let data = try heap.resolveCounterRange(0..<2) else { return nil }
        let ticks = data.withUnsafeBytes { Array($0.bindMemory(to: MTL4TimestampHeapEntry.self)) }
        return Double(ticks[1].timestamp &- ticks[0].timestamp) / ticksPerSecond * 1000
    }
}
```

### The Metal Performance HUD

The HUD is an overlay with FPS, GPU time, frame interval, memory, present mode (direct
or composited), and whether Game Mode is on. It is the first check: if frame time is long
and GPU time is a small share of it, the CPU is the limit, and GPU work matters less. The
book reads GPU time from the HUD rather than from the debug navigator.

```bash
MTL_HUD_ENABLED=1 MTL_HUD_LOG_ENABLED=1 ./MyEngine        # once a second: metal-HUD: <frame>,<gfx mem>,<proc mem>,<interval>,<gpu time>,...
MTL_HUD_ENABLED=1 MTL_HUD_INSIGHTS_ENABLED=1 ./MyEngine   # flag patterns seen in at least half the frames over 5 s
```

- Other switches: the scheme's Show Graphics Overview (logging also needs Log Graphics
  Overview), `MetalHudEnabled` in Info.plist, the user default `MetalHUDForceEnabled=1`,
  and on iOS Settings > Developer > Graphics HUD (needs a development profile). Per
  layer, `CAMetalLayer.developerHUDProperties` takes `mode` (`default`, `main`,
  `disabled`), `logging`, `positionX`, and `positionY`. Set `main` on the layer that
  should drive GPU time when there are several.
- `MTL_HUD_LOG_SHADER_ENABLED=1` logs every runtime shader compile under subsystem
  `com.apple.metal.hud`, category `Logging`, with its compile time and whether it was
  cached. That is the quickest way to catch a compile hitch.
- `MTL_HUD_ENCODER_TIMING_ENABLED=1` adds per-encoder GPU time, a timeline of the last
  few frames, and the top labelled command buffers and encoders. It does not work if the
  app uses counter sample buffers itself.
- **The two HUD pages disagree on one name.** The metric-range switch is
  `MTL_HUD_SHOW_VALUE_RANGE` on the monitoring page and `MTL_HUD_SHOW_METRICS_RANGE` on
  the customizing page. Neither is checked. Use the configuration panel's toggle, or Copy
  HUD Configuration, which writes the variables your build accepts.
- HUD insights map to Metal 4 fixes: many render encoders with similar attachments
  (merge them with color attachment mapping), blit encoders splitting passes (copies now
  live on the compute encoder), serial runtime compiles (the Metal 4 compiler's parallel
  compilation), and CPU-bound encoding.
- Performance reports (from the macOS menu bar, 5 s to 30 min, saved to the temporary
  folder or `MTL_HUD_REPORT_URL`) add a frame-interval distribution with 1% low and 99%
  high, and a list of every shader compiled in the window.

### Instruments: Metal System Trace and Game Performance

Use Instruments for anything spread over time: stutters, CPU-GPU overlap, compile hitches,
thermal throttling. **Game Performance** adds thread state, system calls, Time Profiler,
thermal state, and display to the Metal instruments. **Game Memory** pairs Allocations,
which does not show `.private` Metal resources, with Metal Resource Events and VM
Tracker. GPU limiter and utilization counters are off by default. Turn them on in
Recording Options > Counter Set > Performance Limiters.

```bash
xcrun xctrace list templates                       # includes Metal System Trace, Game Performance, Game Memory
xcrun xctrace record --template 'Metal System Trace' --output run.trace --launch -- ./MyEngine
xcrun xctrace export --input run.trace --toc
xcrun xctrace export --input run.trace --xpath '/trace-toc/run[@number="1"]/data/table[@schema="metal-application-command-buffer-submissions"]'
```

All four ran. The recording exited 0 when the target quit by itself. The probe's
`MTL4CommandQueue` commits appeared as three rows of
`metal-application-command-buffer-submissions` (runtime-checked). Two more results
came from a probe that commits about 20,000 command buffers a second
(runtime-checked):

- **Keep Metal System Trace recordings short.** `xctrace export` crashed with SIGBUS
  (exit 138) while it loaded recordings of 50,000 and 100,000 frames (280 MB and
  520 MB). Recordings of 20,000 frames (142 MB) and of a 1 s `--time-limit` (112 MB)
  exported. A Game Performance recording of the same 100,000 frames (380 MB) also
  exported.
- **Exit 54 does not mean that the target succeeded.** `record` returned 54 when
  `--time-limit` ended the recording, and also when the target exited non-zero
  (`/usr/bin/false`). In the `--toc` output, read `return-exit-status` and
  `termination-reason` on the `<process>` element whose `type` is `launched`. `record` passes the
  target's stdout through only with `--target-stdout <file>`, and never its stderr.

For the template picker and call trees, see
`apple-performance/references/profiling-workflow.md`.

Reading the Game Performance timeline: a display interval far longer than its
neighbours is a stutter. If the GPU track is busy across it, the GPU is the cause. If the
GPU track has gaps while the render thread shows little blocked time, the CPU is. A
render thread preempted under load needs a higher priority. Apple recommends 45 for
rendering threads. Render-thread setup is part of the game loop and outside this skill.

## Reading the Metal debugger's views (GUI only)

Hand these to the user. `gpudebug` covers the cost ranking and heatmaps; nothing else
below has a command-line form.

- **Summary > Insights** first: Memory (sorted by bytes saved, such as a storage mode
  where memoryless would do), Bandwidth, Performance, and API Usage. Insights are leads,
  not verdicts: the book hit a false positive on a vertex buffer.
- **Group by Pipeline State** in the debug navigator, after profiling, ranks PSOs by
  their share of shader samples. That is the fastest way to the costliest PSO in a
  shader-bound frame.
- **Performance timeline** (Apple GPUs only): vertex, fragment, and compute tracks that
  overlap, per-shader waterfalls, and counter tracks. A *limiter* counts busy time
  including stalls. *Utilization* excludes them. Occupancy is the share of the GPU's
  resident-thread capacity in use. Each shader shows its maximum theoretical occupancy.
  Low occupancy with low limiters means little work. Very high occupancy can thrash
  caches. Profile in **Serial** mode for clean per-pass numbers that do not match
  runtime, and **Concurrent** (the default) for real overlap. Pin a GPU performance state
  for comparisons.
- **Heat maps and the shader cost graph** need an A17 Pro or M3 or later; per the Feature
  Set Tables' GPU table those are Apple9 parts. Heat maps cover render encoders, render
  pipelines, and compute dispatches, but not compute encoders or compute pipeline
  states. Divergence is 1 − active/total instructions. The cost graph is per pipeline
  state and splits each line by instruction type and data type (Float16, Float32,
  Integer, Bits).
- **Shader debugger**: select the draw or dispatch, then Debug. It needs embedded source.
  Option-click Debug to limit which functions it instruments, which cuts its start-up
  time. A pixel outside the draw's green overlay was not written by that draw. Reload
  Shaders edits live only in the debugger, so copy them back into your source.
- **Attachments viewer** hatches pixels that are infinite, NaN, or beyond the display's
  EDR headroom. A divide-by-zero shows up at once.
- **Bound Resources > Accessed** filters to what the shader actually touched. In a
  bindless frame, that is the useful view.
- **Dependencies viewer**: solid edges carry data, dashed edges only synchronize (a
  clear-on-load pass still waits). Unused resources show up as wasted work.

**Doc error:** Apple's GPU bottleneck article says to opt in to `-ffast-math`, but `MTL_FAST_MATH` already defaults to on. The real choice
is the math mode (`MTL_MATH_MODE`); see `shading-language.md`.

## Symptom first

Triage before tooling. Draw intermediate values as color (normals or positions as RGB).
Then check each command's bound textures and their pixel formats in the trace instead
of trusting what you think you bound. In the book, a texture loaded as `RGBA8Unorm`
beside one in `RGBA8Unorm_sRGB` was found that way.

| Symptom | Usual cause | First tool |
|---|---|---|
| Pink, black, or missing textures once argument buffers are in | Resource not in a residency set | Shader Validation |
| Fuchsia or checkerboard areas with load/store validation on | A pass relies on `dontCare` contents | API Validation load/store flags |
| Noise from a GPU-built indirect command buffer | 16-bit versus 32-bit index mismatch | Bound Resources |
| Mesh inside out | Winding or handedness disagrees with the cull mode | `gpudebug` `info` (cull mode, winding) |
| Jittery dynamic data | CPU rewrote a buffer the GPU still reads | `command-model.md` frames in flight |
| Small uint IDs render black in the viewer | White is the maximum `uint32` | Remap the texture viewer's range |

## Doc errors and traps

- The programmatic-capture article shows Metal 3 types only; for a Metal 4 queue,
  capture the device (see the queue-overload crash above).
- The SDK marks `startCapture(device:)`, `startCapture(commandQueue:)`, and
  `startCapture(scope:)` deprecated in favour of `startCapture(with:)`; the overview

## Maintaining older code: Metal 3

The Metal 3 path applies when the GPU is below Apple7 (earlier than A14 and M1), or the
OS is earlier than macOS 26.0 or iOS 26.0. Gate once, at startup:

```swift
func supportsMetal4(_ device: any MTLDevice) -> Bool {
    if #available(macOS 26.0, iOS 26.0, *) {
        return device.supportsFamily(.metal4)
    }
    return false
}
```

Snippets in this section compile at the file's macOS 26.0 floor; they are not compile-checked against earlier OS releases.

| Concern | Metal 3 | Metal 4 |
|---|---|---|
| Capture a queue | `captureObject = commandQueue` (`MTLCommandQueue`) | `captureObject = device`; the `MTL4CommandQueue` scope overload exists but crashed as `captureObject` here |
| Per-commit GPU time and errors | `addCompletedHandler(_:)`, then `gpuStartTime`, `gpuEndTime`, `status`, `error` | `MTL4CommitOptions.addFeedbackHandler(_:)` |
| Pass timing | `MTLCounterSampleBuffer` from `makeCounterSampleBuffer(descriptor:)`, attached through pass descriptors' `sampleBufferAttachments`, or `sampleCounters(sampleBuffer:sampleIndex:barrier:)` | `MTL4CounterHeap` and `writeTimestamp` |
| Counter sets | `timestamp`, `stageUtilization`, `statistic` (`MTLCommonCounterSet`), discovered through `counterSets` | Timestamps only |
| Timestamp unit | `MTLTimestamp`, documented in nanoseconds; correlate with `sampleTimestamps()` | Ticks; divide by `queryTimestampFrequency()` |
| Shader log state | `MTLCommandBufferDescriptor.logState` or `MTLCommandQueueDescriptor.logState` | `MTL4CommandBufferOptions.logState` at `beginCommandBuffer` |
| Unretained-resource validation | Covered | Not covered |
| Usage-flag mismatch (Shader Validation) | Checked against `useResource` usage | Not applicable; residency sets |

Metal 3 counter notes that do not carry over: Apple GPUs sample only at stage boundaries
(`supportsCounterSampling(.atStageBoundary)`), while immediate-mode GPUs sample between
draws, dispatches, and blits. A device can list a counter set and still lack some of its
counters, so check `counters` before you use one. The Feature Set Tables cap a counter
sample buffer at 32 KB. `makeCounterSampleBuffer(descriptor:)` can throw when the driver
runs out of them. The HUD's encoder timing is built on counter sample buffers, so it
switches off when the app uses them.

```swift
func commitTimedMetal3(_ commandBuffer: any MTLCommandBuffer) {
    commandBuffer.addCompletedHandler { buffer in
        // Both values stay 0.0 until the GPU finishes the command buffer.
        let milliseconds = (buffer.gpuEndTime - buffer.gpuStartTime) * 1000
        print("GPU time: \(milliseconds) ms, status \(buffer.status.rawValue)")
    }
    commandBuffer.commit()
}
```
