## Compiling pipelines: the compiler, not the device

In Metal 4 a render pipeline is built by an `MTL4Compiler`, which you create
from the device with `makeCompiler(descriptor:)`. The device's own
`makeRenderPipelineState(descriptor:)` takes the Metal 3
`MTLRenderPipelineDescriptor` and belongs to the Metal 3 path. Model priors,
the *Metal by Tutorials* book, and even the `MTL4RenderCommandEncoder` page
(which still says pipeline states come from `MTLDevice` methods) all point the
wrong way.

What changed on the descriptor, and why each change bites a port:

| Metal 3 habit | Metal 4 (`MTL4RenderPipelineDescriptor`) |
|---|---|
| `vertexFunction` / `fragmentFunction` take an `MTLFunction` | `vertexFunctionDescriptor` / `fragmentFunctionDescriptor` take an `MTL4FunctionDescriptor`; use `MTL4LibraryFunctionDescriptor` (`library` + `name`) |
| `depthAttachmentPixelFormat`, `stencilAttachmentPixelFormat` | **Do not exist.** The header has no depth or stencil format. Measured: a pipeline with none wrote depth correctly into a pass with a `.depth32Float` attachment |
| `isBlendingEnabled: Bool` | `blendingState: MTL4BlendState` (`.disabled`, `.enabled`, `.unspecialized`) |
| `isAlphaToCoverageEnabled` | `alphaToCoverageState: MTL4AlphaToCoverageState` |
| `supportIndirectCommandBuffers: Bool` | `MTL4IndirectCommandBufferSupportState` |
| `vertexBuffers[i].mutability` | No mutability hints at all |
| `binaryArchives` | Not on the descriptor; archives go in `MTL4CompilerTaskOptions.lookupArchives` |
| `shaderValidation` | `options: MTL4PipelineOptions` carries `shaderValidation` and `shaderReflection` |

`vertexDescriptor`, `rasterSampleCount`, `colorAttachments[i].pixelFormat`,
and `inputPrimitiveTopology` keep their names.

**Depth-only pipelines: leave rasterization on.** The
`fragmentFunctionDescriptor` and `isRasterizationEnabled` pages both say to set
`isRasterizationEnabled = false` when there is no fragment function. Do not do
that for a shadow map or a depth prepass. Measured: with rasterization off and
a vertex function that returns a position, pipeline creation fails ("the
vertex shader's return type is not void"); with rasterization on and no
fragment function, the pass wrote depth. Turn rasterization off only for a
vertex function that returns `void` (it writes buffers instead of drawing).

```swift
import Metal

enum PipelineError: Error {
    case noDefaultLibrary
    case notARenderDescriptor
}

/// One compiler per workload, made once at startup and labelled for captures.
func makeSceneCompiler(device: any MTLDevice) throws -> any MTL4Compiler {
    let descriptor = MTL4CompilerDescriptor()
    descriptor.label = "Scene pipelines"
    return try device.makeCompiler(descriptor: descriptor)
}

func functionDescriptor(_ name: String, in library: any MTLLibrary) -> MTL4LibraryFunctionDescriptor {
    let function = MTL4LibraryFunctionDescriptor()
    function.library = library
    function.name = name
    return function
}

/// Opaque scene pipeline. The depth attachment needs no format here.
func makeOpaquePipeline(compiler: any MTL4Compiler,
                        library: any MTLLibrary,
                        colorFormat: MTLPixelFormat) throws -> any MTLRenderPipelineState {
    let descriptor = MTL4RenderPipelineDescriptor()
    descriptor.label = "Opaque"
    descriptor.vertexFunctionDescriptor = functionDescriptor("sceneVertex", in: library)
    descriptor.fragmentFunctionDescriptor = functionDescriptor("sceneFragment", in: library)
    descriptor.colorAttachments[0].pixelFormat = colorFormat
    return try compiler.makeRenderPipelineState(descriptor: descriptor)
}

/// Shadow-map pipeline: vertex stage only, rasterization left at its default (on).
func makeShadowPipeline(compiler: any MTL4Compiler,
                        library: any MTLLibrary) throws -> any MTLRenderPipelineState {
    let descriptor = MTL4RenderPipelineDescriptor()
    descriptor.label = "Shadow depth"
    descriptor.vertexFunctionDescriptor = functionDescriptor("shadowVertex", in: library)
    return try compiler.makeRenderPipelineState(descriptor: descriptor)
}
```

### When compiles run, and on which threads

The point of a dedicated compiler is that you decide when a compile happens.
Build every pipeline a level can need at load time, never on first use inside
the frame. Apple's own guidance is that synchronous compiles suit prototypes
and that large games should compile asynchronously.

- **Swift has no `MTL4CompilerTask`.** The header marks it unavailable in
  Swift ("Use Swift Task instead"). The docs describe compiler tasks with a
  status and `waitUntilCompleted()`; in Swift, call the `async throws`
  overloads of `makeRenderPipelineState` and the other factory methods.
- **QoS follows the caller.** A compile issued directly runs at the calling
  thread's QoS; one run on a dispatch queue runs at that queue's QoS. The
  system promotes a lower-QoS compile that a higher-QoS task is waiting on.
- **iOS throttles background compile threads** to save energy and memory.
  The compiler multithreads by default on both platforms, so profile the load
  on a device, not on the Mac.
- **Adopt it per pipeline.** Moving the most hitch-prone pipelines to a
  dedicated compiler first is a supported migration.

`MTL4Compiler`, `MTLLibrary`, and `MTLRenderPipelineState` are `Sendable`;
`MTL4RenderPipelineDescriptor` is not. Under Swift 6, build each descriptor
inside the task that compiles it, from `Sendable` inputs:

```swift
import Metal

struct PipelineRecipe: Sendable {
    let label: String
    let vertexName: String
    let fragmentName: String
    let colorFormat: MTLPixelFormat
}

/// Compiles a level's pipelines concurrently, before the level starts.
func compileLevel(_ recipes: [PipelineRecipe],
                  compiler: any MTL4Compiler,
                  library: any MTLLibrary) async throws -> [String: any MTLRenderPipelineState] {
    try await withThrowingTaskGroup(of: (String, any MTLRenderPipelineState).self) { group in
        for recipe in recipes {
            group.addTask {
                let descriptor = MTL4RenderPipelineDescriptor()
                descriptor.label = recipe.label
                let vertex = MTL4LibraryFunctionDescriptor()
                vertex.library = library
                vertex.name = recipe.vertexName
                let fragment = MTL4LibraryFunctionDescriptor()
                fragment.library = library
                fragment.name = recipe.fragmentName
                descriptor.vertexFunctionDescriptor = vertex
                descriptor.fragmentFunctionDescriptor = fragment
                descriptor.colorAttachments[0].pixelFormat = recipe.colorFormat
                return (recipe.label, try await compiler.makeRenderPipelineState(descriptor: descriptor))
            }
        }
        var states: [String: any MTLRenderPipelineState] = [:]
        for try await (label, state) in group { states[label] = state }
        return states
    }
}
```

Find what still compiles at runtime with the Metal HUD: launch with
`MTL_HUD_ENABLED=1 MTL_HUD_LOG_SHADER_ENABLED=1`. The HUD logs one line per
shader compile with the function name, the time, and a `cached:` flag. The

## Variants: function constants, flexible pipelines, attachment mapping

Pick the cheapest mechanism that expresses the variation:

| The variation is... | Use | Why |
|---|---|---|
| Per thread (depends on the data) | A runtime branch | The only option |
| Per draw, in shader logic (has a normal map, has skinning) | Function constants | One library ships; the back end specializes at pipeline creation. Apple: a per-draw `if` costs registers and occupancy |
| Per draw, in the `#if` style | Avoid it | Every macro permutation is a separate offline library, and runtime `#if` defeats build-time precompilation |
| Only the color format or blend state | A flexible (unspecialized) pipeline | The shader body compiles once; each variant fills in only the missing state |
| Only which attachment each output lands in | Color attachment mapping | One pipeline serves passes with different attachment layouts |

**Function constants.** Declare them in MSL; an argument tagged with a
constant exists only when that constant is true. The FST allow 65,536 function
constants. Function specialization is Apple2 and later.

```metal
constant bool has_normal_map [[function_constant(0)]];
constant bool has_skinning [[function_constant(1)]];
constant bool needs_uv = has_normal_map;

struct SceneOut {
    float4 position [[position, invariant]];
    float2 uv;
};

vertex SceneOut sceneVertex(uint vid [[vertex_id]],
                            const device float4* positions [[buffer(0)]],
                            const device float4x4* bones [[buffer(1), function_constant(has_skinning)]]) {
    SceneOut out;
    float4 p = positions[vid];
    if (has_skinning) {
        p = bones[0] * p;
    }
    out.position = p;
    out.uv = needs_uv ? p.xy : float2(0.0);
    return out;
}

fragment half4 sceneFragment(SceneOut in [[stage_in]],
                             texture2d<half> normalMap [[texture(0), function_constant(has_normal_map)]]) {
    half4 color = half4(1.0h);
    if (has_normal_map) {
        constexpr sampler linearSampler(filter::linear);
        color = normalMap.sample(linearSampler, in.uv);
    }
    return color;
}
```

In Metal 4 the values go in an `MTL4SpecializedFunctionDescriptor` that wraps
the library function descriptor:

```swift
import Metal

func specialized(_ name: String,
                 in library: any MTLLibrary,
                 hasNormalMap: Bool,
                 hasSkinning: Bool) -> MTL4SpecializedFunctionDescriptor {
    var normalMap = hasNormalMap
    var skinning = hasSkinning
    let values = MTLFunctionConstantValues()
    values.setConstantValue(&normalMap, type: .bool, index: 0)
    values.setConstantValue(&skinning, type: .bool, index: 1)

    let base = MTL4LibraryFunctionDescriptor()
    base.library = library
    base.name = name

    let function = MTL4SpecializedFunctionDescriptor()
    function.functionDescriptor = base
    function.constantValues = values
    function.specializedName = "\(name)_n\(hasNormalMap ? 1 : 0)_s\(hasSkinning ? 1 : 0)"
    return function
}
```

Two traps. Metal ignores a value that matches no constant in the function,
with no error or warning (documented for `makeFunction(name:constantValues:)`),
so a mistyped index or name is not reported where you made it. And every constant
combination is a separate pipeline compile: a combination missing from your
binary archive falls back to a runtime compile, which is the hitch you were
trying to remove.

**Flexible pipelines** (Metal 4, Apple7 and later). Compile once with the
varying state set to its unspecialized value, then derive concrete pipelines.
Unspecialized values exist for the pixel format (`MTLPixelFormat.unspecialized`),
`MTL4BlendState.unspecialized`, `MTLBlendFactor.unspecialized`,
`MTLBlendOperation.unspecialized`, and `MTLColorWriteMask.unspecialized`. The
rules: specialization changes only properties that were unspecialized, resets
unspecialized properties you leave unset to their defaults, and cannot
re-specialize a pipeline that is already specialized. (Measured: a
re-specialization call returned without an error, so a success proves nothing;
keep the flexible pipeline and specialize from it.) Get the descriptor to
fill from the pipeline itself; it comes back as the concrete descriptor type.
Measured: this path works for the color format. (The
`MTLPixelFormat.unspecialized` doc page is wrong: its text describes a YUV 4:2:2
format.)

```swift
import Metal

/// Compiled once at launch with no color format.
func makeFlexiblePostPipeline(compiler: any MTL4Compiler,
                              library: any MTLLibrary) throws -> any MTLRenderPipelineState {
    let descriptor = MTL4RenderPipelineDescriptor()
    descriptor.label = "Post (flexible)"
    descriptor.vertexFunctionDescriptor = functionDescriptor("fullscreenVertex", in: library)
    descriptor.fragmentFunctionDescriptor = functionDescriptor("postFragment", in: library)
    descriptor.colorAttachments[0].pixelFormat = .unspecialized
    return try compiler.makeRenderPipelineState(descriptor: descriptor)
}

/// Cheap per-format variant: the shader body is not recompiled.
func postPipeline(for format: MTLPixelFormat,
                  from flexible: any MTLRenderPipelineState,
                  compiler: any MTL4Compiler) throws -> any MTLRenderPipelineState {
    guard let descriptor = flexible.makeRenderPipelineDescriptorForSpecialization()
            as? MTL4RenderPipelineDescriptor else {
        throw PipelineError.notARenderDescriptor
    }
    descriptor.colorAttachments[0].pixelFormat = format
    return try compiler.makeRenderPipelineStateBySpecialization(descriptor: descriptor, pipeline: flexible)
}
```

**Color attachment mapping** (Metal 4, Apple7 and later). A pipeline whose
`colorAttachmentMappingState` is `.inherited` takes its logical-to-physical
output mapping from the encoder at draw time. That needs the pass descriptor's
`supportColorAttachmentMapping = true`, then
`setColorAttachmentMap(_:)` on the encoder. The map's subscript is indexed by
the logical output and stores the physical attachment. The payoff is on the GPU
as well as the CPU: draws that used to need separate render encoders because
their outputs differed can share one pass. The Metal HUD's insight "many render
encoders with similar color attachments" points at exactly this, and the HUD
performance report's frame-encoding table finds the candidates.

```swift
import Metal

func makeMappedPass(gbuffer: [any MTLTexture]) -> MTL4RenderPassDescriptor {
    let pass = MTL4RenderPassDescriptor()
    pass.supportColorAttachmentMapping = true
    for (index, texture) in gbuffer.enumerated() {
        pass.colorAttachments[index].texture = texture
        pass.colorAttachments[index].loadAction = .clear
        pass.colorAttachments[index].storeAction = .store
    }
    return pass
}

/// Routes a pipeline's logical color(0) into physical attachment `physical`.
func routeOutput(_ encoder: any MTL4RenderCommandEncoder, toAttachment physical: Int) {
    let map = MTLLogicalToPhysicalColorAttachmentMap()
    map[0] = physical
    encoder.setColorAttachmentMap(map)
}
```

## Shipping without compile hitches: harvest, archive, load

At build time Xcode compiles `.metal` files to Metal IR in `default.metallib`.
IR still compiles to GPU code on the device when you create the pipeline. A
library built from a source string at runtime compiles twice (source to IR,
IR to GPU), and its errors surface only at runtime, so ship `.metal` files.
A binary archive holds per-GPU machine code and skips the device compile.
Apple's archive article says archives also carry an IR slice, so an OS update
that invalidates the GPU binary costs a recompile rather than a failure. One
`metal-tt` archive measured below failed outright on a newer OS, so write the
load path for both outcomes.

### Harvesting at runtime with a pipeline data set serializer

Attach an `MTL4PipelineDataSetSerializer` to the compiler descriptor. It
records every pipeline that compiler builds, and nothing from any other
compiler. Its contents are opaque. Measured behavior that the docs get wrong
or leave out:

| Configuration | `serializeAsPipelinesScript()` | `serializeAsArchiveAndFlush(url:)` |
|---|---|---|
| Unset (`rawValue` 0; the docs call `.captureDescriptors` the default) | Works | Throws, writes nothing |
| `.captureDescriptors` | Works | Throws, writes nothing |
| `.captureBinaries` | Works | **Works** |
| `[.captureDescriptors, .captureBinaries]` | Works | Throws, writes nothing |

So set the configuration to exactly `.captureBinaries` when you want an
archive. "Flush" is literal: a second archive write from the same serializer
throws "Nothing to serialize". The archive is not tied to the URL's extension.
On macOS, write runtime archives outside the app bundle, because writing
inside it breaks code signing.

```swift
import Foundation
import Metal

/// Development builds: a compiler that records what it builds.
func makeHarvestingCompiler(device: any MTLDevice)
        throws -> (compiler: any MTL4Compiler, serializer: any MTL4PipelineDataSetSerializer) {
    let serializerDescriptor = MTL4PipelineDataSetSerializerDescriptor()
    serializerDescriptor.configuration = .captureBinaries
    let serializer = device.makePipelineDataSetSerializer(descriptor: serializerDescriptor)

    let compilerDescriptor = MTL4CompilerDescriptor()
    compilerDescriptor.label = "Harvest"
    compilerDescriptor.pipelineDataSetSerializer = serializer
    return (try device.makeCompiler(descriptor: compilerDescriptor), serializer)
}

/// After a play-through that touched every pipeline. Empties the serializer.
func writeHarvest(_ serializer: any MTL4PipelineDataSetSerializer, to url: URL) throws {
    try serializer.serializeAsArchiveAndFlush(url: url)
}
```

### Loading: fall back or fail

Open an archive with `device.makeArchive(url:)`. There are two ways to use it,
and they differ on a miss (measured):

- **Through the compiler**, with `MTL4CompilerTaskOptions.lookupArchives`. A
  hit skips the compile; a miss compiles normally. Ship this.
- **Straight from the archive**, with `archive.makeRenderPipelineState(descriptor:)`.
  A miss throws ("Failed to find fragment function..."). Use this in QA as the
  Metal 4 counterpart of Metal 3's `failOnBinaryArchiveMiss`: every throw is a
  hitch a player would have hit.

**Opening the archive can fail too, so never make it fatal.** Measured: an
archive that `metal-tt` built for a macOS 26.0 target would not open on macOS
27.0.1 ("deployment target for architecture applegpu_g16s ... is not compatible
with current OS"), while one built for a 27.0 target opened and hit. A player's
OS update can therefore turn a shipped archive into a load error. Treat it as a
miss and compile.

```swift
import Foundation
import Metal

func loadScenePipeline(device: any MTLDevice,
                       compiler: any MTL4Compiler,
                       archiveURL: URL,
                       descriptor: MTL4RenderPipelineDescriptor,
                       failOnMiss: Bool) throws -> any MTLRenderPipelineState {
    guard let archive = try? device.makeArchive(url: archiveURL) else {
        // Missing, or built for another OS: compile from IR instead.
        return try compiler.makeRenderPipelineState(descriptor: descriptor)
    }
    if failOnMiss {
        return try archive.makeRenderPipelineState(descriptor: descriptor)
    }
    let options = MTL4CompilerTaskOptions()
    options.lookupArchives = [archive]   // searched in order; must match this device
    return try compiler.makeRenderPipelineState(descriptor: descriptor, compilerTaskOptions: options)
}
```

Shader Validation instruments shaders live, so it cannot be used together with
binary archives. Validate on a build that compiles at runtime. To keep it off
one hot pipeline, set `MTL4PipelineOptions.shaderValidation` to `.disabled`.

### Building archives offline with metal-tt

`metal-tt` builds a binary archive from a metallib plus a JSON pipeline
script whose file name ends in `.mtlp-json`. What was checked on this machine:

- **A hand-written script works.** One in the format of Apple's
  custom-configuration-script article compiled, and the result loaded as an
  `MTL4Archive` and hit for an `MTL4RenderPipelineDescriptor`. Binary archives
  load in both Metal 3 and Metal 4. The format's top-level keys are
  `libraries.paths[]`, `pipelines.render_pipelines[]` (and
  `compute_pipelines[]`), and `specialized_functions[]`. Functions are
  referenced as `alias:<library label>#<name>`.
- **The harvested script did not work.** `metal-tt` rejected the JSON that
  `serializeAsPipelinesScript()` produced, with a parse error in its
  `libraries` array, which is a different shape from the documented format.
  The harvested script also records the metallib's absolute path on the
  harvesting machine. Until you have run that leg end to end on your
  toolchain, harvest archives at runtime instead, or hand-maintain the script.
- **`-target` must not be older than the metallib.** A metallib built with the
  default deployment target, run through `-target air64-apple-macos26.0`,
  failed with "image AIR version (2.9) is bigger than the one of the target
  (2.8)". Build the metallib for the same OS floor you pass to `metal-tt`.
- **By default it builds every architecture the target OS runs on.** For a
  macOS 27.0 target, one trivial pipeline came out at 240 KB with 18 Apple GPU
  slices. For a macOS 26.0 target it also tried AMD slices and failed
  ("amdgpu-nt command failed") until `-gpu-family metal4` limited it to the
  14 Apple slices. Split per device with `metal-lipo -thin <arch> -output
  <file>`; `metal-lipo -archs` lists the slices. `metal-lipo` only merges
  slices of the same pipelines; merging different pipelines is `metal-pack`.
- **The archive is tied to its target OS** (see "Opening the archive can fail
  too" above). Load it defensively.

```bash
xcrun -sdk macosx metal -std=metal4.0 -mmacosx-version-min=26.0 Shaders.metal -o Shaders.metallib
xcrun -sdk macosx metal-tt -target air64-apple-macos26.0 -gpu-family metal4 Shaders.metallib pipelines.mtlp-json -o Shaders.binary.metallib
xcrun -sdk macosx metal-lipo -archs Shaders.binary.metallib
```

All three lines ran on this machine against a hand-written script.

### Smaller and faster-compiling libraries

- **Optimize for size where it measures better.** The default favors speed
  (inlining, unrolling), which can bloat code and compile time. `-Os` (Xcode
  build setting `MTL_OPTIMIZATION_LEVEL` = Size, or
  `MTLCompileOptions.optimizationLevel = .size` for runtime source) often
  compiles faster. Which one runs faster depends on the shader; measure.
- **Dynamic libraries** hold shared utility code that would otherwise be
  compiled into, and duplicated in, every pipeline. Render and compute dynamic
  libraries are Apple6 and later, and are gated by separate device flags:
  `supportsRenderDynamicLibraries` and `supportsDynamicLibraries`. Apple's
  Swift sample on the dynamic-library page does not compile (it uses `fn` and
  a nonexistent `MTLComputePipeline` type), so do not copy it.

## Render passes: attachments, load and store actions

`MTL4RenderPassDescriptor` reuses the Metal 3 attachment classes
(`MTLRenderPassColorAttachmentDescriptor`, `MTLRenderPassDepthAttachmentDescriptor`,
`MTLRenderPassStencilAttachmentDescriptor`), so load and store actions,
`clearColor`, `clearDepth`, and `resolveTexture` are unchanged. The encoder
comes from the command buffer with
`makeRenderCommandEncoder(descriptor:options:)`.

**The defaults are a trap.** A color attachment defaults to load `.dontCare`
and store `.store`; depth and stencil default to load `.clear` and store
`.dontCare`. A color attachment you forgot to configure therefore starts with
undefined contents. On an Intel or AMD Mac, which renders straight to memory, a
wrong load or store action often shows nothing. On an Apple GPU, `.dontCare`
really skips the tile load or store, and the result is garbage. Code ported
from macOS-only engines often carries these latent bugs.

| Need | Load | Store |
|---|---|---|
| Every pixel is overwritten this pass | `.dontCare` (free) | |
| Some pixels drawn, old contents not needed | `.clear` (one write per pixel) | |
| Old contents needed | `.load`, which Apple calls significantly slower than the other two | |
| Used only inside this pass (most depth, stencil, G-buffer) | | `.dontCare` |
| A later pass or the CPU reads it; always for a drawable | | `.store` |
| MSAA: keep only the resolved image | | `.multisampleResolve` |
| MSAA: keep samples and the resolve | | `.storeAndMultisampleResolve` (one render encoder) |
| Decide later | | `.unknown`, then `setColorStoreAction(_:index:)`, `setDepthStoreAction(_:)`, or `setStencilStoreAction(_:)` before `endEncoding()` |

Rules that come with it:

- **Memoryless attachments** (`MTLStorageMode.memoryless`, tile memory only,
  textures only) cannot use `.load`, `.store`, or `.storeAndMultisampleResolve`.
  Measured: they also must not go in a residency set. Adding one fails API
  validation with "residency sets do not support memoryless resources", and a
  pass with memoryless MSAA color and depth rendered and resolved correctly
  without one. Everything else the pass touches does need residency
  (`command-model.md`).
- **The store setters reject `.unknown`.** It is a placeholder on the
  descriptor, and a real action has to replace it before the pass ends.
- **`storeActionOptions` is dead on Apple silicon.** The
  custom-sample-positions article says to set `.customSamplePositions` on a
  depth attachment. The SDK deprecates the property with "Store action options
  have no effect on Apple Silicon", and `MTL4RenderCommandEncoder` has no
  store-action-option setters. The SDK wins; skip it.
- **Narrow `MTLTextureDescriptor.usage`** to what each target needs
  (`[.renderTarget, .shaderRead]` for one a later pass samples). Metal lays the
  texture out for exactly those uses.
- **A pass boundary is a store plus a reload** on a TBDR GPU, and each pass
  also has a fixed setup cost. Merge logical passes that share targets into
  one Metal pass; how is in `apple-gpu-tbdr.md`.
- **Metal 4 does not order passes for you.** A pass that samples what an
  earlier pass rendered needs a barrier or fence (`command-model.md`). Metal 3
  inferred that order; ported code silently loses it.
- **Do not sample the depth attachment you are writing** in the same pass, and
  do not bind one texture to two arguments if either can write it. Results
  differ across GPUs, and API Validation catches both.

### Occlusion queries

Point `visibilityResultBuffer` at a buffer of 8-byte slots, and before each
draw call `setVisibilityResultMode(_:offset:)` with `.boolean` or `.counting`
and a byte offset that is a multiple of 8. `visibilityResultType` chooses
whether results accumulate across encoders (fragment visibility count
accumulation is Apple7 and later) or reset. Results arrive a frame late, so
keep a ring of frames in flight plus one shared buffers. The proxy-draw culling
recipe (cheap enclosing proxies, depth test on and writes off, scaled up for
moving objects) is in Apple's visibility-result sample, which uses the Metal 3
spellings.

### Encoding one pass from several threads

Metal 4 has no `MTLParallelRenderCommandEncoder`. Instead, a render pass can
span command buffers. Each thread encodes its share in its own
`MTL4CommandBuffer` with its own allocator, and the pass is stitched back
together. The rules:

1. Commit every command buffer of the pass together, in one array, with
   `commit(_:options:)`.
2. The first holds the pass started with `.suspending`, the last with
   `.resuming`, and every one between with `[.resuming, .suspending]`.
3. No compute, blit, acceleration-structure, or machine-learning work may be
   interleaved in that sequence.
4. A command buffer that already holds a resuming pass must not also start a
   suspending one.

```swift
import Metal

/// Two threads' worth of draws, one render pass. Each half has its own allocator.
func encodeSplitPass(device: any MTLDevice,
                     queue: any MTL4CommandQueue,
                     pass: MTL4RenderPassDescriptor,
                     allocators: (any MTL4CommandAllocator, any MTL4CommandAllocator),
                     encodeFirstHalf: (any MTL4RenderCommandEncoder) -> Void,
                     encodeSecondHalf: (any MTL4RenderCommandEncoder) -> Void) {
    guard let first = device.makeCommandBuffer(),
          let second = device.makeCommandBuffer() else { return }

    first.beginCommandBuffer(allocator: allocators.0)
    if let encoder = first.makeRenderCommandEncoder(descriptor: pass, options: .suspending) {
        encodeFirstHalf(encoder)
        encoder.endEncoding()
    }
    first.endCommandBuffer()

    second.beginCommandBuffer(allocator: allocators.1)
    if let encoder = second.makeRenderCommandEncoder(descriptor: pass, options: .resuming) {
        encodeSecondHalf(encoder)
        encoder.endEncoding()
    }
    second.endCommandBuffer()

    queue.commit([first, second], options: nil)
}
```

In a real engine the two halves run on two threads; the only ordering that
matters is the array order at commit.

## Depth and stencil

- **Depth state is a separate object.** Build each `MTLDepthStencilState` once
  from an `MTLDepthStencilDescriptor` (`depthCompareFunction`,
  `isDepthWriteEnabled`, `frontFaceStencil`, `backFaceStencil`) and set it per
  draw with `setDepthStencilState(_:)`. Pipelines and depth states combine
  freely, and the pipeline carries no depth format to match.
- **Formats.** `.depth32Float` is the default choice. For stencil, use
  `.depth32Float_stencil8` on both `depthAttachment` and `stencilAttachment`;
  some devices allocate 64 bits per pixel for it. `.depth24Unorm_stencil8` is
  never available on Apple silicon: the SDK deprecates
  `isDepth24Stencil8PixelFormatSupported` with exactly that reason, and on iOS
  it does not exist. The iOS Simulator accepts only combined depth-stencil
  formats and needs depth, stencil, and MSAA textures to be private.
- **Filtering depth** (FST): `Depth32Float` and `Depth32Float_Stencil8` become
  filterable only at Apple9; `Depth16Unorm` is filterable everywhere. Check
  this before a shadow-map technique relies on linear filtering of depth on
  A14 to A16 or M1 and M2.
- **Shadow maps** use the vertex-only pipeline above, a fixed-size depth target
  (`.clear` and `.store`, not resized with the window), and
  `setDepthBias(_:slopeScale:clamp:)` before the draws. The map pass and the
  pass that samples it must be separate passes with a barrier between them.
- **Depth bounds testing** (`setDepthTestBounds(_:)`) is Apple10 only.

Multipass techniques (a depth prepass followed by an equal-test pass, shadow
volumes) need bit-identical positions in every vertex function involved. The
Apple GPU compiler fuses and reorders floating-point work aggressively, so
without this you get z-fighting that other GPUs do not show. Mark the output
`[[position, invariant]]`, as in the MSL above, and compile with
`-fpreserve-invariance` offline (add it to Xcode's Other Metal Compiler Flags)
or set `MTLCompileOptions.preserveInvariance = true` for runtime source. In
Metal 4 those options travel in `MTL4LibraryDescriptor.options` to the
compiler's `makeLibrary(descriptor:)`. Without the option, `[[invariant]]` is
ignored.

Keep early depth rejection when the fragment function writes depth by
declaring which way it moves depth. `[[early_fragment_tests]]` forces the tests
before the fragment function runs, and it is a compile error to combine it
with a depth or stencil output.

```metal
struct DecalOut {
    half4 color [[color(0)]];
    float depth [[depth(less)]];
};

// Only ever pulls depth toward the camera, so early rejection survives.
fragment DecalOut decalFragment(float4 position [[position]]) {
    DecalOut out;
    out.color = half4(1.0h);
    out.depth = position.z * 0.999;
    return out;
}

[[early_fragment_tests]]
fragment half4 alphaTestedFoliage(float4 position [[position]]) {
    return half4(0.2h, 0.6h, 0.2h, 1.0h);
}
```

Writing a value against the declared direction gives undefined results.

## MSAA

- **Sample counts** (FST): 4 on every Apple family; **8 only on Apple10** (A19,
  M5). The `supportsTextureSampleCount(_:)` page still says 8 works on "some
  macOS devices"; on Apple silicon the tables win. Probe 2 and 8 with
  `supportsTextureSampleCount(_:)` and default to 4. The Simulator has no
  2-sample MSAA.
- **Match counts.** The pipeline's `rasterSampleCount` must equal the
  attachment's `sampleCount`, so MSAA and non-MSAA variants are different
  pipelines. If a pass has no attachments, set
  `defaultRasterSampleCount` on the pass descriptor.
- **Tile size shrinks with samples** (FST): 32×32 without MSAA or at 2×,
  32×16 at 4×, 16×16 at 8×.
- **On Apple GPUs, MSAA color and depth should be memoryless** with
  `.multisampleResolve`: the samples never reach system memory. Measured in a
  Metal 4 pass, as below.
- **Resolve your own way** when the operation does not commute with
  averaging, such as tone-mapping HDR samples before averaging them (which
  avoids bright edge aliasing). On Apple GPUs a tile shader resolves in tile
  memory before the store (Apple4 and later; `apple-gpu-tbdr.md`). Elsewhere,
  a compute pass reads a private `texture2d_ms`.
- **Watch for per-sample shading.** A fragment function that takes
  `[[sample_id]]`, uses a `sample_` interpolation qualifier, or reads a
  `[[color(n)]]` input on a multisampled target may run once per sample.
  Programmable blending on MSAA can quietly multiply shading cost.
- **Custom sample positions** are `samplePositions` on the pass descriptor
  (an empty array turns them off), on a 16×16 sub-pixel grid. Use them for
  temporal jitter.

```swift
import Metal

/// 4x MSAA scene pass whose samples never leave tile memory.
func makeMSAAScenePass(device: any MTLDevice,
                       resolveTarget: any MTLTexture) -> MTL4RenderPassDescriptor? {
    func transient(_ format: MTLPixelFormat) -> MTLTextureDescriptor {
        let descriptor = MTLTextureDescriptor.texture2DDescriptor(pixelFormat: format,
                                                                  width: resolveTarget.width,
                                                                  height: resolveTarget.height,
                                                                  mipmapped: false)
        descriptor.textureType = .type2DMultisample
        descriptor.sampleCount = 4
        descriptor.usage = .renderTarget
        descriptor.storageMode = .memoryless   // never in a residency set
        return descriptor
    }
    guard let color = device.makeTexture(descriptor: transient(resolveTarget.pixelFormat)),
          let depth = device.makeTexture(descriptor: transient(.depth32Float)) else { return nil }

    let pass = MTL4RenderPassDescriptor()
    pass.colorAttachments[0].texture = color
    pass.colorAttachments[0].loadAction = .clear
    pass.colorAttachments[0].storeAction = .multisampleResolve
    pass.colorAttachments[0].resolveTexture = resolveTarget   // this one must be resident
    pass.depthAttachment.texture = depth
    pass.depthAttachment.loadAction = .clear
    pass.depthAttachment.clearDepth = 1.0
    pass.depthAttachment.storeAction = .dontCare
    return pass
}
```

The pipeline drawing into this pass needs `rasterSampleCount = 4`.

## Forward or deferred

Switch to deferred when the light count dominates the frame, not the geometry.

On Apple GPUs, deferred does not have to mean a fat G-buffer in system memory:

- **Single-pass deferred.** The G-buffer attachments are memoryless, lighting
  reads them through programmable blending in the same encoder, and only the
  lit result is stored. Every pipeline in that merged pass must declare the
  identical full attachment set. Details and the raster-order-group setup are
  in `apple-gpu-tbdr.md`.
- **The G-buffer budget is per pixel, not just per attachment count.** The
  summed per-pixel, per-sample size of all color attachments in a pass must fit
  the implicit imageblock limit: 128 B on Apple7 and later. A layout a discrete
  GPU accepts can fail here, because non-Apple GPUs limit only the count (8).
  Pack it: the book's layout is albedo in `.bgra8Unorm` with a shadow factor in
  alpha, normal and position in `.rgba16Float`, and depth in `.depth32Float`
  stored `.dontCare`.
- **The Simulator and Intel Macs cannot read render targets in the fragment
  shader.** If you test in the Simulator, keep a two-pass path (G-buffer stored
  to private textures, then sampled). Apple's Swift deferred sample picks the
  path with `supportsFamily(.apple1)`.
- **Alternatives.** Forward+ bins lights per tile with tile shaders (Apple4
  and later). A visibility buffer stores `[[primitive_id]]` and
  `[[barycentric_coord]]` and reconstructs attributes later (Apple7 and later).

Transparency stays forward in either design. Draw opaques first with the plain
pipeline, then only the transparent submeshes, sorted back to front, with a
separate blending pipeline (`blendingState = .enabled`), because blending
pipelines cost more. Hidden-surface removal makes opaque draw order free of
overdraw on Apple GPUs, which is why only transparents need sorting.
Order-independent transparency through imageblocks is in `apple-gpu-tbdr.md`.

## Layered, multi-view, and variable-rate rendering

| Technique | What it saves | Gate (FST) | Gotcha |
|---|---|---|---|
| Layer selection: `[[render_target_array_index]]` plus `renderTargetArrayLength` | One draw writes cube faces or array slices (shadow cubes, one-pass reflections) | Apple5; to MSAA targets Apple7 | The pipeline must fix `inputPrimitiveTopology`. The index must be constant per primitive. Several attachments are not allowed with a 3D target |
| Viewport selection: `[[viewport_array_index]]` plus `setViewports(_:)` | Several viewports per draw | Apple5, 16 viewports | Pass the same count to `setViewports(_:)` and `setScissorRects(_:)` |
| Vertex amplification: `maxVertexAmplificationCount` plus `setVertexAmplificationCount(_:)` | Fetches each vertex once for N views (stereo, cascades) | Apple6, max 2; Apple7 and later, 8 | Probe `supportsVertexAmplificationCount(_:)` with 2 or more; passing 1 is a validation error. Amplification multiplies with instancing |
| Variable rasterization rate: `rasterizationRateMap` on the pass | Shading cost in low-detail regions | Apple6 | Never render straight into the final target: render at `physicalSize(layer:)`, then upscale. Draw UI after the upscale |

Variable rate pays only when per-pixel cost is high enough to beat the upscale.

## Maintaining older code: Metal 3

Snippets in this section compile at the file's macOS 26.0 floor; they are not compile-checked against earlier OS releases.

**When the Metal 3 path applies:** GPU families below Apple7 (A13 and earlier
iPhones and iPads; every Apple silicon Mac is Apple7 or later) and OS releases
before 26.0. Gate at runtime on both the OS and the family. The family check
is `supportsFamily(.metal4)`; the Feature Set Tables put the Metal 4 model at
Apple7 and later.

```swift
import Metal

func usesMetal4Pipelines(_ device: any MTLDevice) -> Bool {
    if #available(macOS 26.0, iOS 26.0, *) {
        return device.supportsFamily(.metal4)
    }
    return false
}

/// The Metal 3 equivalent of the Metal 4 archive load, including fail-on-miss.
func makeMetal3ScenePipeline(device: any MTLDevice,
                             library: any MTLLibrary,
                             archive: any MTLBinaryArchive,
                             failOnMiss: Bool) throws -> any MTLRenderPipelineState {
    let descriptor = MTLRenderPipelineDescriptor()
    descriptor.vertexFunction = library.makeFunction(name: "sceneVertex")
    descriptor.fragmentFunction = library.makeFunction(name: "sceneFragment")
    descriptor.colorAttachments[0].pixelFormat = .bgra8Unorm
    descriptor.depthAttachmentPixelFormat = .depth32Float   // Metal 3 only
    descriptor.binaryArchives = [archive]
    let options: MTLPipelineOption = failOnMiss ? [.failOnBinaryArchiveMiss] : []
    let (state, _) = try device.makeRenderPipelineState(descriptor: descriptor, options: options)
    return state
}
```

How each concept maps:

| Metal 3 | Metal 4 |
|---|---|
| `device.makeRenderPipelineState(descriptor:)` with `MTLRenderPipelineDescriptor` | `MTL4Compiler.makeRenderPipelineState(descriptor:)` with `MTL4RenderPipelineDescriptor` |
| `vertexFunction` / `fragmentFunction` (`MTLFunction`) | `vertexFunctionDescriptor` / `fragmentFunctionDescriptor` (`MTL4LibraryFunctionDescriptor`) |
| `library.makeFunction(name:constantValues:)` | `MTL4SpecializedFunctionDescriptor` (`functionDescriptor`, `constantValues`, `specializedName`) |
| `depthAttachmentPixelFormat`, `stencilAttachmentPixelFormat` | None |
| `device.makeLibrary(source:options:)` | `compiler.makeLibrary(descriptor:)` with `MTL4LibraryDescriptor` (`source`, `options`) |
| `MTLDevice.shouldMaximizeConcurrentCompilation` (macOS only) | A compiler per workload; QoS from the calling queue |
| `MTLBinaryArchive`: `addRenderPipelineFunctions(descriptor:)`, then `serialize(to:)` | `MTL4PipelineDataSetSerializer` with `.captureBinaries`, then `serializeAsArchiveAndFlush(url:)` |
| `MTLRenderPipelineDescriptor.binaryArchives` | `MTL4CompilerTaskOptions.lookupArchives` |
| `MTLPipelineOption.failOnBinaryArchiveMiss` | Load from `MTL4Archive` directly; a miss throws |
| `MTLParallelRenderCommandEncoder` | Suspending and resuming render encoders across command buffers |
| `storeActionOptions`, `MTLStoreActionOptions` | Removed; no effect on Apple silicon |
| Pass-to-pass order inferred for tracked resources | Explicit barriers (`command-model.md`) |
| Tessellation (Apple3 and later) | Not in the Metal 4 model; use mesh shaders (`compute-and-gpu-driven.md`) |

The Metal 3 runtime harvest needs some care. Create the `MTLBinaryArchive`
from a descriptor whose `url` is nil (which creates an empty archive), before
the pipelines it records, so compiles are faster and use less memory. Call
`addRenderPipelineFunctions(descriptor:)` for every pipeline, then
`serialize(to:)`. On-device serialization of specialized functions needs
macOS 15 or iOS 18. Apple states that both Metal 3 and Metal 4 load binary
archives; the Metal 4 side of that was measured here with a `metal-tt` archive.
