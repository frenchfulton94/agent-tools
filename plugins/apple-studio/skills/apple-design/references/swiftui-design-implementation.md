# SwiftUI Design Implementation

## Modifier order and semantics

A modifier wraps a view in a new view; it does not mutate the original in place. Applying position/sizing modifiers (`padding`, `frame`) before fill/decoration modifiers (`background`, `border`, `overlay`) gives you "decorate a sized box"; reversing the order gives you "decorate the intrinsic content, then add space around the already-decorated result" — same two modifiers, structurally different outcome, because each modifier's input is the wrapped output of the one before it, not the "original" view (SwiftUI by Tutorials, ch. 3). Read a suspicious `padding`/`background`/`border` chain inside-out, not as a flat property list.

Order isn't only visual — it can be a compile error. Some modifiers are typed to only accept a specific view's return type: a `Text`-only modifier chains fine after other modifiers that still return `Text`, but once any earlier modifier in the chain widens the type to `some View`, `Text`-specific modifiers are no longer available further down. The same applies to shape-only modifiers (e.g. one requiring a `Shape`, not `some View`) — they must come before whatever in the chain first erases the concrete type.

## Custom control styling: ButtonStyle vs. inline modifiers

Once button-specific styling (background shape, shadow, sizing) is reused or clutters a view, extract a type conforming to `ButtonStyle` rather than repeating the modifier chain at every call site (SwiftUI by Tutorials, ch. 3). `ButtonStyle.makeBody(configuration:)` still exposes `configuration.label` and `configuration.isPressed` in current SwiftUI (confirmed against live `ButtonStyleConfiguration` DocC).

Classic mistake: a custom `ButtonStyle` silently drops two things the system default gave you for free — the label's default tint, and press-down visual feedback. Both need to be rebuilt explicitly: add back an explicit foreground color if you relied on the system tint, and drive some visible change (commonly an opacity or background swap) off `configuration.isPressed` yourself. A `ButtonStyle` implementation with no reference to `isPressed` looks identical whether or not the user is actually pressing it, which reads as an unresponsive control, not a styling choice.

`configuration.isPressed` is specifically the hook for touch-down feedback, not touch-up: it's already `true` while the finger is still down, and driving the visible change from it — rather than from a tap action that only fires on release — is what makes the response land at the moment someone is actually watching the control. Feedback that only appears on release reads as dead, because the press itself already came and went unacknowledged. When the visible change is a `scaleEffect`, keep it subtle — 0.95 to 0.98 — since anything larger reads as rubbery rather than pressed; `scaleEffect` applied to the button's label scales any icon inside that label along with the text, and that's what makes the shrink read as one physical object being pressed rather than two pieces animating independently (confirmed against live `ButtonStyleConfiguration` DocC).

`*Style` protocols (`ButtonStyle`, `TextFieldStyle`, etc.) behave differently from a plain modifier in one important way: setting `.buttonStyle(_:)`/`.textFieldStyle(_:)` higher in the tree cascades through the environment to every matching control beneath it, not just the view you called it on. That's the deciding factor against a `ViewModifier`: use a `*Style` protocol when one declaration should theme every control of that kind in a subtree; use a `ViewModifier` when styling needs to be explicit and opted into per call site, independent of control type.

## Custom ViewModifier: when to extract one

For the general question of extracting a separate `View` type vs. a computed property, and for `ViewModifier` vs. a container view that owns layout, defer to `architecture-patterns.md`'s composition section — don't re-derive that here. This file adds one further axis specific to styling: `*Style` protocols cascade via environment and are locked to one control type (above); a `ViewModifier` plus a `View` extension convenience method is explicit-per-call-site and applies across otherwise-unrelated view types — a border/shadow "card" treatment shared by both a button and a text field, say (SwiftUI by Tutorials, ch. 6). Prototype the exact modifier chain inline first, at one call site, before promoting it into a named `ViewModifier` — don't design the modifier's shape in the abstract before it's been seen working.

## Dark mode and preview fidelity

Don't fully trust the canvas preview's dark-mode toggle for anything backed by system chrome — an `.alert`, for instance, can render in the wrong color scheme in the preview environment while behaving correctly at runtime (SwiftUI by Tutorials, ch. 3). If a dark-mode issue reproduces only in the preview and not on a simulator or device, treat it as a preview artifact rather than debugging it as a real bug — confirm system-chrome-dependent UI on a simulator or device (using the debug environment overrides for appearance) before trusting what the canvas shows.

## Text sizing in constrained frames

A `Text` given more room than it needs inside a fixed `.frame` renders at its natural size and leaves the frame's slack empty; given less room than it needs, it wraps and then truncates (an ellipsis) once it runs out of lines (SwiftUI by Tutorials, ch. 3). `.minimumScaleFactor(_:)` is the deliberate trade of truncation for a smaller font instead of lost content — pass the smallest acceptable fraction of the original size (e.g. `0.5`) and treat it as a narrow, content-length-driven escape hatch (user-generated text, localized strings whose length you can't predict at design time), not a general substitute for correct layout or for Dynamic Type support — see `hig-foundations.md` § Typography and Dynamic Type for the structural fixes (stacking, column reduction) that should come first.

## GeometryReader and proportional sizing

`GeometryReader` inverts SwiftUI's usual sizing behavior: instead of sizing to its content, it expands to consume all of the space proposed to it, then hands that size down through a proxy (confirmed against live `GeometryReader` DocC: "returns a flexible preferred size to its parent layout"). That makes it a poor default for "I just need this view's size" — dropping one into an otherwise tightly-sized layout can make that spot in the tree unexpectedly greedy and distort sibling views that assumed natural sizing. Reach for it specifically when a computation genuinely needs the proposed size (an offset, a proportional dimension, custom drawing math), not as a general-purpose size-inspection tool.

Hardcoded proportional constants derived from a single reference design — a fraction measured off one specific device's safe-area dimensions in a design file — are brittle: they track only the device they were measured against, ignore Dynamic Type, and need re-deriving by hand for every new device size (SwiftUI by Tutorials, ch. 3). Prefer the layout system's own relative sizing (stacks, `Spacer`, `.aspectRatio`) over baked-in ratio constants; if a `GeometryReader`-derived fraction is unavoidable, keep it narrowly scoped and check it against both the smallest and largest supported device sizes, not only the currently active simulator.

## Stack layout: adaptivity, ordering, and laziness

The parent-proposes/child-chooses sizing model, `ZStack` vs. `.overlay`/`.background`, `.fixedSize()`, and `.layoutPriority` are covered in `architecture-patterns.md`'s composition section — this file doesn't repeat them. One layer underneath `.layoutPriority` worth knowing: a container sorts children by how adaptive each currently is, least-flexible first, and the modifiers already applied change that adaptivity — an `Image` without `.resizable()` is essentially inflexible (it ignores the proposed size and renders at native resolution), while the same `Image` with `.resizable()` becomes fully flexible (it accepts whatever size it's offered) (SwiftUI by Tutorials, ch. 7). When a stack allocates space in a surprising way, check what modifiers changed a child's adaptivity before reaching for `.layoutPriority` as the fix.

`HStack`'s `.firstTextBaseline`/`.lastTextBaseline` alignment options solve a common problem `.center`/`.top`/`.bottom` don't: a row mixing different font sizes, or `Text` next to a `Button`, tends to look misaligned under `.center` because centering is based on each view's frame, not its visual text baseline. Default to a baseline alignment whenever an `HStack` mixes differently sized text or text-plus-control content, instead of hand-tuning offsets.

`.layoutPriority(_:)` doesn't just reorder which child a stack sizes first — it changes the actual space math. The stack computes the bare-minimum size every *lower*-priority sibling needs, subtracts that from the space it has, and proposes what's left to the highest-priority child; lower-priority siblings then get squeezed toward that bare minimum, not toward zero (SwiftUI by Tutorials, ch. 7). That's why a single `.layoutPriority(1)` sibling in a crowded `HStack` can end up claiming most of the row while its neighbors still render (shrunk, wrapped, or truncated) rather than disappearing — useful to know before assuming a priority bump broke the layout. Leaving `spacing:` at its default (`nil`) doesn't mean zero gap — it's a real, platform-dependent spacing value; pass `spacing: 0` explicitly when a flush layout is actually the goal.

`Spacer()` carries no content of its own — it's a flexible view that expands to consume whatever space its stack siblings don't claim along the stack's major axis, and it's the idiomatic way to pin content to one edge rather than fighting the default center alignment with offsets: a `Spacer` placed after content pins that content to the leading/top edge, one placed before pins it to the trailing/bottom edge, and one on each side centers it while still allowing the container around it to grow. Nest a small `VStack`/`HStack` containing just a `Spacer` plus one child when you need to edge-pin something inside a container (a `ZStack`, say) that has no alignment parameter of its own to lean on.

Eager stacks (`HStack`/`VStack`) materialize every child up front; lazy stacks (`LazyHStack`/`LazyVStack`) materialize children only as they approach the visible viewport. Default to eager stacks for small, bounded content; switch to lazy stacks once a collection is large or scrollable — but only inside a `ScrollView`, since a lazy stack with no scrolling viewport to skip work against gets none of the benefit (SwiftUI by Tutorials, ch. 7). Both take a `pinnedViews:` parameter for pinning section headers/footers during scrolling (confirmed against live `LazyVStack` DocC). Because a lazy stack can deallocate off-screen rows, don't assume a row's local `@State` survives being scrolled far off-screen and back the way it reliably would in an eager stack — this is standard, documented lazy-container behavior, not an edge case. `state-and-di.md` covers the general rules for what state survives identity churn; this is a lazy-container-specific instance of that same hazard, not a separate mechanism.

`ForEach(_:id:)`'s `id` parameter is a data-identity decision, not a formality — get it wrong and rows lose or misattribute their `@State`, the same identity hazard `state-and-di.md` covers for whole views, just at per-row granularity inside a collection (SwiftUI by Tutorials, ch. 7). Prefer a stable, meaningful identifier already on the data (a database ID, a `UUID` assigned at creation) over `\.self` or a positional index: `\.self` requires the whole element to be `Hashable` and ties identity to the *value*, so an element that's replaced by an equal-but-distinct instance, or mutated on a field the hash depends on, can read to SwiftUI as a different row rather than an update to the same one; an index-based id is worse still, silently reattaching a row's local `@State` to whatever now occupies that position after an insert, delete, or reorder.

The historical "10 children per `@ViewBuilder` block" ceiling this book (2022) would have described is gone on a current toolchain. Live `ViewBuilder` DocC no longer documents the fixed-arity `buildBlock(_:_:)` … `buildBlock(_:_:_:_:_:_:_:_:_:_:)` overload ladder (arity 2 through 10) that produced it — the topic listing shows only `buildBlock()` and a single `buildBlock(_:)`, and that remaining symbol's declaration is a parameter-pack-generic overload, `static func buildBlock<each Content>(_ content: repeat each Content) -> TupleView<(repeat each Content)> where repeat each Content: View`, which accepts an arbitrary number of children in one block rather than one fixed count per overload. If you're maintaining code that splits a large stack's children into nested `Group`s specifically to route around a 10-child cap, that split is a legacy workaround for a limit that no longer exists on a modern (Swift 5.9+/Xcode 15+) toolchain — safe to flatten back out when you're already touching that code, though there's no correctness reason to do it proactively. A build error today from "too many children" is worth investigating as something else (a genuine type-inference failure, or the compiler timing out on an unusually large single closure) rather than assumed to be this historical cap.

## Grids: fixed, flexible, and adaptive columns

`LazyVGrid`/`LazyHGrid` inherit the same laziness rule as lazy stacks above — same tradeoff, same "only inside a scroll container" caveat. The real design decision lives in the column/row description (`GridItem`), which comes in three kinds solving different problems (SwiftUI by Tutorials, ch. 16):

- **`.fixed(width)`** — an exact, unchanging column size. Use it when the target width is known up front and predictability matters more than adaptability; column count is simply the number of `GridItem`s supplied.
- **`.flexible(minimum:maximum:)`** — a fixed column *count* (still the array length) with each column's width flexing inside a range. Use it when the count matters ("always exactly two columns") but the exact width shouldn't be hardcoded.
- **`.adaptive(minimum:maximum:)`** — a single `GridItem` repeats to fill available width with as many columns as fit inside the bounds. Default to this for anything that must respond to rotation, multitasking width changes, or running across iPhone and iPad without device-specific branches — it's the one column type where count itself adapts, not just width.

A column's size is a proposal, not a constraint: a `.fixed` or `.flexible` maximum doesn't clip or resize an oversized child to fit — a child wider than its column still renders at whatever size it decides on and can visually overlap its neighbor, consistent with SwiftUI's general parent-proposes/child-decides sizing model (no view clips by default without an explicit `.clipped()`). The fix isn't a bigger column, it's not hardcoding the child's own `.frame` — use `.aspectRatio(_:contentMode:)` so the child sizes itself proportionally within whatever the grid actually proposes.

Grouping content within a grid — an "awarded vs. not-awarded" split, say — is `Section` with a `header`/`footer` view, the same construct used inside `List`; nothing grid-specific is required (SwiftUI by Tutorials, ch. 16). Extract the repeated per-item content (the `ForEach` plus its cell view) into its own small view once it's duplicated across more than one section, rather than pasting the same `ForEach` block per section.

## Reusable views: generic containers over ViewBuilder

For when to extract a separate `View` type at all, see `architecture-patterns.md`. The pattern specific to building a genuinely reusable *container* — fixed layout/behavior, varying displayed content — is a generic type with a `@ViewBuilder` closure parameter, e.g. a timeline view generic over `Content: View` that takes `@ViewBuilder content: (Item) -> Content` (SwiftUI by Tutorials, ch. 21). This buys type-safe content injection without the runtime cost and API-shape loss of erasing to `AnyView`.

Reach for the generic-plus-`@ViewBuilder` shape only when the same container is genuinely instantiated with more than one concrete content type across the app; if a "reusable" wrapper only ever gets used with one concrete view, the generic signature is ceremony — drop the generic parameter and take a concrete view (or a plain, non-`@ViewBuilder` closure) directly. This is the same "don't build the seam before something needs it" judgment `architecture-patterns.md` applies elsewhere — it isn't unique to views.

## macOS window and menu structure

For *why* macOS requires a menu bar, why windows carry main/key/inactive state, and when to branch platform code at all, see `platform-idioms.md` — this section covers only how to structure the SwiftUI code once that decision is made.

A `WindowGroup`'s root view doesn't inherit an implicit size the way an iPhone screen does — set `.frame(minWidth:minHeight:)` on it (and `minWidth`/`minHeight` on individual resizable panes inside any split layout), or a user can drag the window or a pane divider down to an unusable size. For the `Settings { }` scene and its automatic App-menu-item/Cmd-, wiring, see `hig-patterns.md` § Settings.

Scope persisted UI state to the correct lifetime deliberately: `@AppStorage` is shared across every window of the app; `@SceneStorage` is scoped to a single window (both confirmed current, undeprecated property wrappers against live DocC). Picking the wrong one is an easy, real bug specifically on macOS, since it's the one platform where several windows of the same app are routinely open at once — using `@AppStorage` for something that should be window-local (a selected tab, a selected row) makes every open window jump in sync the moment one of them changes it, which reads as a bug rather than a deliberate app-wide setting (SwiftUI by Tutorials, ch. 23).

Structure menu-bar and toolbar customization as their own types once they exceed a couple of items, in a dedicated file, the same way any other non-trivial view gets extracted: a type conforming to `Commands` for menu content (`CommandGroup(before:/after:/replacing:)` to insert into an existing menu, `CommandMenu` for a wholly new top-level one), and a type conforming to `ToolbarContent` for toolbar content (`ToolbarItem` for a single control, `ToolbarItemGroup` for several that belong together), wired in via `.commands { }` / `.toolbar { }` (SwiftUI by Tutorials, ch. 22). All confirmed current against live DocC (`Commands` protocol, `CommandGroup`, `CommandMenu` fetched directly; `ToolbarContent`/`ToolbarItem`/`ToolbarItemGroup` are stable, unchanged SwiftUI toolbar APIs).

## macOS multi-pane and multi-window layout

`NavigationSplitView`'s automatic collapse/expand behavior (see `adaptive-layout.md` § System containers first) is the right default. Reach for `HSplitView`/`VSplitView` — a macOS-only pair for user-draggable split panes (confirmed against live DocC: macOS 10.15+, not available on iOS/iPadOS/tvOS/watchOS) — specifically when a permanent, non-collapsing side-by-side layout is needed, or pane selection is being driven manually rather than through `NavigationLink`'s push behavior. Pair a manual split layout with `@SceneStorage`-scoped selection (above) rather than `NavigationLink`, since there's no navigation stack to carry the selected item for you.

Every resizable pane in a manually composed split layout needs its own `minWidth`/`minHeight`, not just the outermost container — a sidebar, a list pane, and a detail pane each need independent minimums, or a divider can be dragged until one pane's content becomes unusable even though the window itself still respects its own minimum size (SwiftUI by Tutorials, ch. 23).

Content and frames authored against iOS's tall aspect ratio don't translate automatically into macOS's auxiliary presentations — a background image or `.aspectRatio` sized for an iPhone screen can make a `.sheet` or `.popover` render far taller or wider than the content needs. Set an explicit `.frame(width:height:)` on ported sheet/popover content rather than assuming it sizes itself sensibly in the new context. Prefer `.popover` over `.sheet` for lightweight, click-outside-to-dismiss auxiliary content on macOS — macOS popovers dismiss on an outside click by default (inherited platform-standard popover behavior), while a sheet requires explicit dismissal.

When wrapping custom, non-text content inside a `Button` or `NavigationLink` on macOS, apply `.buttonStyle(.plain)` or the platform's default button chrome renders as a visible background/border behind that content — a frequent "why does this card look boxed" surprise that pairs with the custom-`ButtonStyle` judgment above (SwiftUI by Tutorials, ch. 23). This is well-documented, current macOS `Button`/`NavigationLink` behavior.
