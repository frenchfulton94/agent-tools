advanced — the decision tree

# If… Schema Chain
1 Production is broken now — incident, outage, users blocked hotfix triage → tasks → postmortem
2 Shipping a build to TestFlight or the App Store — installed only in Apple-native app repos; if the schema is absent, this entry does not apply app-release release-scope → preflight → tasks → post-release
3 New repository or project bootstrap — init, scaffold, set up the project setup decisions → conventions → tasks
4 Behaves wrong versus intent — bug, error, crash, regression, "too slow". Performance is a bugfix bugfix reproduction → rootcause → fix → tasks
5 Dependency, framework, platform version change — bump, EOL, CVE, migrate to vN upgrade inventory → surfaces → migration → tasks → verification
6 Structure changes, behaviour must not — clean up, extract, rename, de-dupe. Coverage backfill is a refactor refactor characterization → strategy → tasks
7 An open question answered by building — try, compare, POC, feasibility spike question → apply → findings
8 New capability or intentional behaviour change — including removals and deprecations feature brainstorm → constraints → proposal → specs → design → migration → review → tasks → plan → verification
9 Trivial, low-risk, no contract impact — typo, copy, config value, docs rapid proposal → tasks

Prompt signals

→ bugfix

"X is broken / throws / returns the wrong thing" · "add tests for X"? no — that is refactor

→ hotfix

"prod is down" · "urgent" · "do we roll back?"

→ app-release

"cut a release / submit to the App Store / push to TestFlight" · installed only in Apple-native app repos; if the schema is absent, this entry does not apply

→ upgrade

"upgrade to <framework> vN" · "Node LTS" · "patch the CVE"

→ refactor

"no behaviour change" stated or implied · "add tests for X" · "raise coverage"

→ spike

"prototype" · "spike" · "see if" · "which of A or B"

→ setup

"new repo" · "greenfield project" · "bootstrap"

→ feature

"add / build / support / let users…" · "remove feature X" (REMOVED deltas plus a migration and sunset plan)

→ rapid

Typo, copy, config value, docs · standing-doc upkeep (memory audit, TOOLS refresh, glossary), invoking the owning skill

Guardrails — reclassify when these fire

rapid → feature

The moment a public API, URL, analytics event, data schema, or config contract is touched — or the change turns out non-trivial. Stop and recreate.

refactor → feature

Any test assertion has to change. Behaviour is changing; this was never a refactor.

bugfix-flow → mattpocock-bridge

The fix alters behaviour the product cares about, rather than restoring behaviour it already promised. A fault whose fix is a redesign is a change.

spike

Code is throwaway and never merges. Learnings graduate through a new feature.

hotfix

Must spawn a follow-up bugfix or feature for the durable fix. postmortem.md links it. Mandatory.

De-escalate too

A feature brainstorm revealing bounded work → recreate as rapid. Revealing a question in disguise → spike. One command against hours of ceremony.

Bigger than one change

A change is a single unit of work. For an epic, map it with /wayfinder (user-invoked) as decision tickets, then create one change per resolved chunk. Accepted opportunities from /improve-codebase-architecture each become their own refactor. Ambiguous between two schemas? Ask one multiple-choice question, then route.
