Model & effort card

Every row carries a source column, because the two kinds of answer here are not interchangeable: a pin executes on its own, and a recommendation is advice you have to act on at an artifact boundary. Tier changes the budget, not the pick.

Pin

A model: / effort: line in an agent file this plugin installs. It runs whether or not anyone reads this card, and it outranks your session's setting.

Recommendation

From an attached usage guide. Nothing enforces it — if you want it, you set it at an artifact boundary.

Tier note

What your subscription changes. Never which model you can pick — only what the weekly bucket lets you spend, and how Fable is billed.

The rule, in four lines

  1. Planning gets depth. Durable multi-step judgement — specs, root cause, refactor strategy, migration plan — at low token volume. A wrong plan is the most expensive error in the chain.
  2. Implementation gets speed. Apply is a long loop of edits, commands and test runs; it is latency- and output-dominated. Except where the implementation is genuinely hard.
  3. Interactive means high, not xhigh. With you in the loop between short turns, the top setting mostly buys latency. Reserve xhigh for the deep artifacts that run without you.
  4. Escalate on evidence. Shallow spec from a strong model → go up. Rework from a cheap implementation pass → go up. Otherwise leave it alone.

Tier adaptation

All three consumer tiers can select every model. What differs is the weekly bucket and how Fable is billed — so tier changes what you can afford, not what you can pick.

Pro Not in-plan — usage credits only Opus 5 xhigh replaces Fable at both feature gates, which is what this plugin ships. opusplan for planning-heavy schemas. Protect bugfix root cause and the hotfix postmortem at xhigh; drop marginal refactor/upgrade planning to Sonnet when the bucket is tight. No Opus on spike
Max 5x In-plan, ≤50% of weekly limits Opus 5 default; Opus-plan plus Sonnet-implement holds across a disciplined workweek. A Fable session weighs about twice an Opus one, so the 50% cap arrives in roughly half the sessions the figure suggests — gates only, if at all

Hitting the Fable cap ends Fable for the week, not the week itself — the recovery is switching to Opus, not waiting for a reset.

Burn control

opusplan

Opus in plan mode, Sonnet in execution, switched at the boundary. It is rules 1 and 2 above expressed as one alias, and the first thing to reach for on Pro.

Effort defaults

Default effort is high on every current model; xhigh must be opted into. The deliberate moves are down to medium for mechanical loops and up to xhigh at a gate.

Nothing rescues you

Hitting a usage limit never triggers a model switch — rate-limit, billing, auth, request-size and transport errors are all excluded from the fallback machinery. Manage it yourself.

Context hygiene

One task per session, clear between tasks. Long uncleared sessions are the main cause of surprise burn — which is also why every schema here says one slice per session.

Monitoring

/usage for session and weekly buckets, /status for the current model and account, /cost for API spend. /status covers model and effort continuously.

Fable's strings

Mandatory 30-day retention on its traffic class, unavailable under zero-data-retention, and classifiers that fall back more often. Opus 5 wins most published head-to-heads at half the rate — benchmark before pinning Fable anywhere.

Two things that silently defeat every pin

The subagent-model override

CLAUDE_CODE_SUBAGENT_MODEL sits highest in the resolution order — above the per-invocation model and above frontmatter model:. Set it and all eight pins collapse to one tier, with no warning. The per-axis review split stops being a split. Leave it unset; inherit is the same as unset.

The organisation's model allowlist

A model: value is checked against availableModels, and an excluded value is skipped — the agent runs on the inherited model instead. If opus is unavailable to you, your design gate is running on your session's model while the schema still says otherwise.

Resolution order, highest first: CLAUDE_CODE_SUBAGENT_MODEL → the per-invocation model → frontmatter model: → the main conversation's model. Subagents inherit the main conversation's extended-thinking configuration; there is no per-subagent thinking setting.

Confirm, do not assume

/status reports the live model and effort alongside the agent name, workspace, git state, and context usage. Switch at artifact boundaries and glance at it after each switch.

Why gate agents draft and return

AskUserQuestion is removed from every subagent regardless of what tools: says. A gate whose sign-off needs a human answer therefore cannot get one — which is why all four design gates draft the artifact and return open questions to the caller, and why the caller must resolve them before finishing. Anything a subagent needs must be in its prompt: a subagent inherits no conversation, no files read, no skills invoked.
