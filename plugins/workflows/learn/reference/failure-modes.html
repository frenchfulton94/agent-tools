Failure modes

Everything in this system that fails quietly. Grouped by where it bites, symptom first. If something "isn't working", start here rather than editing.

Run diagnostics in a plain terminal, unpiped

Half the entries below produce a console.warn on stderr that would have told you exactly what happened. A pipe, a redirect, or a tool that only surfaces stdout loses it. This is the single most common reason a silent failure stayed silent.

The three commands that settle almost everything

openspec --version                                       # is the CLI there, and how old
openspec schema which --all                              # which schema wins, and from where
openspec instructions <artifact> --change <name> --json  # what the assistant actually receives

The third is decisive for anything about context, rules, or templates. Absent from that payload means the problem is upstream of the assistant.

Configuration that does nothing

Symptom Cause Fix
The whole context never appears It is over 50KB. The entire field is dropped, silently Summarize, or point at a file instead of pasting it. Treat the cap as a ceiling to stay far below, not a budget
A rule never fires Its key matches no artifact id in the schema this change uses. Unknown artifact ID in rules: X on stderr, every command openspec schemas --json lists ids per schema. Common right after adopting a schema that renamed artifacts
Nothing in the config applies at all The file is not where OpenSpec looks. Only openspec/config.yaml and openspec/config.yml are probed, in that order A root-level file, or one a directory up, is invisible. If both exist, .yaml wins and your .yml edits do nothing
One field applies, another does not That field failed its type check. Parsing is per-field and resilient — the bad field is dropped, everything else loads Read stderr. The rest of the config working is not evidence this field did
Invalid YAML anywhere The whole config is ignored, with a warning Run it through a YAML validator
openspec config set succeeded, nothing changed That writes the machine JSON config, never the project YAML Edit openspec/config.yaml by hand
Waiting for a restart None is needed Config is read fresh on every command
A top-level key is ignored Only these exist: schema, context, rules, operations, references, store, githubCopilot Anything else is ignored outright

Markup that parses to nothing

Symptom Cause Fix
A scenario is silently ignored Scenarios need exactly four hashes — #### Scenario:. Three hashes, or a bullet, does not parse Count the hashes. There is no lenient parse for this
Scenarios vanish after an archive A MODIFIED requirement replaces the whole block. Archive matches on the requirement header Copy the entire requirement block, header included, carrying every surviving scenario — not only the edited ones
A task never shows in progress tracking Its checkbox is not exactly - [ ] . Apply parses that form; any other shape is invisible, not an error Fix the marker. * [ ] and -[ ] both fail
A placeholder reached an executor "Write tests for the above" in a plan.md. The implementer may see only their own task Placeholders are plan failures. Write the real test code, the real handling, the repeated code

Status and structure that lie

Symptom Cause Fix
An artifact reads done with nothing behind it Status is pure filesystem existence: BLOCKED (missing deps) → READY (deps done) → DONE (file exists). Writing tasks.md by hand marks tasks done with no specs Walk each artifact's requires edges transitively rather than trusting status
An escape-hatch key seems to do nothing skip_grill and skip_surface are not read by the CLI — only paths under specs/ get a real skipped status Write the one-line stub file. The key records the judgement; the file moves the graph
A change archives without merging anything A custom schema satisfies only one of the two specs rules: the id must be specs and generates must stay under specs/ Archive and sync find deltas through the id; skip_specs matches on the path prefix. Satisfy both
Validation rejects a change with no deltas A change with zero spec deltas fails unless it declares skip_specs Declare it — but declaring it and writing spec files is a validation conflict, so a stale marker cannot linger
Archive aborts on a capability A REMOVED entry takes a capability's last requirement Add retire_capabilities: true. The deletion is recoverable only from git, which is why it is opt-in
A post-apply artifact never gets written The archive warning counts tracked checkboxes, not artifact files. Ticking the last box satisfies it Write findings.md / postmortem.md before ticking the last box
A forked schema does nothing Nothing in the precedence chain names it --schema flag → the change's .openspec.yaml → openspec/config.yaml → spec-driven

Commands and sessions

Symptom Cause Fix
A slash command "does not exist" Wrong half of the product — /opsx:propose goes in the assistant's chat, not a shell The most common failure there is. Check where you typed it
/opsx:continue is missing It is not in the core profile. There is no expanded preset — extra workflows come from a custom selection openspec config profile, then openspec update in the project. Upgrade the CLI first
openspec update reports everything current Instruction files are generated by the installed CLI. An outdated one never writes the newer workflows Upgrade the package before running update
/opsx:apply or /opsx:continue asks which change you mean Both infer the change from the conversation when you omit the name, and you cleared the window or started a new session — so there is nothing to infer from Not a fault. Name the change: /opsx:apply <change>. Do it every time and it never comes up
Apply drifts, re-litigates settled decisions, or runs out of room The planning window was carried into implementation. Everything apply needs is already written down in the artifacts; the session copy is dead weight /clear, re-pick with /model or /effort, then /opsx:apply <change>. Clearing loses nothing — artifact state is file existence
A model switch does not seem to change anything It was made inside a full window, which still travels with every following turn /clear first, then switch. Confirm with /status rather than assuming
Archive exits 1 in CI or from an agent It asks up to three confirmations, and stdin is closed Pass the change name and --yes
Customisation disappeared after an update Generated skill and command files are OpenSpec's to own; openspec update overwrites them Customization belongs in config.yaml, schemas, and templates — never in the generated files

Models and subagents

Symptom Cause Fix
Every gate seems to run on the same model CLAUDE_CODE_SUBAGENT_MODEL is set. It outranks frontmatter model:, so all eight pins collapse — no warning Unset it. inherit is equivalent to unset
A gate pinned to opus did not run on it The value is not in the organisation's availableModels allowlist. An excluded value is skipped, and the agent inherits instead Confirm what is available to you before trusting a pin. There is no fallback ladder — it inherits
A dispatched agent produced something generic A subagent inherits nothing — no conversation, no files read, no skills invoked Name every input in its prompt. The schemas spell out per agent what must be carried (change directory, base SHA, head SHA, tracker reference)
A gate agent never asked its question AskUserQuestion is removed from every subagent regardless of tools: It returns open questions instead. You resolve them before finishing the artifact
Quality degrades late in a long session A session degrades once it passes roughly 150k tokens One slice per session. Each slice is self-contained, so the finished slice's context is disposable

Setup itself

Symptom Cause Fix
A file you edited comes back as a collision every run Working as designed. Your edit changed the content hash, so the file is now yours Keep the edit and decline, or revert the bytes to hand ownership back. A content hash, not a timestamp
The plan's plugin and status-line sections look wrong .claude/settings.json could not be read. That warning leads the list and invalidates both sections Fix the file, do not approve around it
Setup stopped before touching the config The artifact-id lookup from the CLI failed. Classifying rules against an empty union would discard every rule you wrote Correct outcome. Fix the CLI, then re-run
Verification failed on a plugin A managed marketplace blocked it. The check uses the planned list, not what install reported Also the correct outcome — a result to report, not an obstacle to route around
A teammate cloned the repo and has no plugins A committed .claude/settings.json records intent; it does not install anything for anyone They install the plugin and run /workflows:setup once. Reconcile mode installs only what is missing
