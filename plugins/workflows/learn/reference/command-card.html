Command card

Split by where you type it, because that is the single most common failure: /opsx:propose goes in the assistant's chat, openspec … goes in a terminal.

In the assistant's chat

Command Does Profile
/workflows:setup [level] [--check|--dry-run] Sets up or reconciles this repository's OpenSpec workflow. One question, a plan, and nothing written before you approve it —
/opsx:explore Think through an idea. No structure required, no change created yet core
/opsx:propose <name or a sentence> Create a change and generate all its planning artifacts in one step. The default quick path core
/opsx:apply <change> Work through tasks, ticking them off. Name the change — with the window cleared, there is nothing left for it to infer from core
/opsx:update <change> - <what changed> Revise existing planning artifacts and keep them coherent, in any direction. Never edits code, never creates missing artifacts core
/opsx:sync <change> Merge this change's delta specs into the main specs while the change stays active. Optional core
/opsx:archive <change> Archive when done. Prompts you to sync if you have not core
/opsx:new <name or a sentence> The way to start a change. Takes a kebab-case name or a description it derives one from; name a schema in the sentence to route it. Scaffolds and shows the first artifact's template — writes no artifacts custom
/opsx:continue <change> Show what is ready, then create one artifact. The artifact-at-a-time loop every level's flow assumes, and the way to resume a change in a brand-new session — it reads the filesystem, not your history custom
/opsx:ff <change> Fast-forward: create all planning artifacts at once custom
/opsx:verify Validate the implementation against the artifacts custom
/opsx:bulk-archive Archive several completed changes custom
/opsx:onboard OpenSpec's own guided walkthrough of one end-to-end change custom
core is the default profile's six. The rest need a custom workflow selection — openspec config profile, then openspec update. Spelling is per tool: Codex uses $openspec-propose, Kimi /skill:openspec-propose, Amazon Q @opsx-propose.

The loop, in order

/opsx:new     <what you want, in a sentence>, using <schema>

/opsx:continue <change>        # once per artifact, naming the change every time
   ↳ /clear, then /model or /effort, whenever the next artifact wants a different depth

── all planning artifacts created ──────────────────────────────────
/clear                          # 1. the artifacts are files now; apply needs the room
/model                          # 2. model with up/down, its effort with left/right
                                #    (or /effort alone, when only the depth is wrong)
/opsx:apply    <change>         # 3. with the name — you just cleared what it would infer from
────────────────────────────────────────────────────────────────────

/opsx:sync    <change>         # optional
/opsx:archive <change>
Clear before you switch, and clear before you apply

A model or effort switch made inside a full window still drags that window into every turn that follows, so /clear comes first, not after. And nothing a chain needs lives in a session — artifact state is pure file existence — so clearing costs the change nothing and buys the implementation loop its whole window back.

The one thing it does take is the assistant's ability to guess which change you mean. Name the change in every opsx command and that cost disappears too.

In a terminal

Orientation — run these when lost

openspec --version                    # is the CLI there, and how old (needs Node >= 20.19)
openspec schemas                      # which schemas exist, and where each resolves from
openspec schema which --all           # project vs user vs package, per schema
openspec config list                  # the machine profile, delivery, selected workflows
openspec status --change <name> --json  # which artifacts exist, are ready, or are blocked

Doing the work

The first line is the optional terminal form of /opsx:new — same scaffold, but you write the slug and you get no first-artifact template. Prefer it in scripts. 

openspec new change <slug> --schema <schema>   # lowercase kebab-case; leading number allowed
openspec validate --all --strict
openspec schema validate <name>                # structure, templates exist, no cycles
openspec archive <name> --yes                  # --yes required with stdin closed

The decisive diagnostic

openspec instructions <artifact> --change <name> --json

The only way to see what the assistant actually receives: resolved template, injected context, matching rules, dependency paths. If a value is absent here, the problem is upstream of the assistant. Run it unpiped — dropped-field warnings go to stderr.

Setting the profile

npm install -g @fission-ai/openspec@latest   # upgrade FIRST, or update writes stale files
openspec config profile                      # wizard; select new + continue at minimum
openspec update                              # regenerate this project's tool files
Machine versus project

openspec config get/set/edit operates on the machine JSON config only. It never touches openspec/config.yaml. Conflating the two is the most common wasted edit there is.

This plugin's flags

Flag Writes Use it when
--check Nothing at all You want a drift report, including on a repository you do not maintain
--dry-run .claude/workflows-plan.json, and nothing else You want the plan as data, to read or to diff against last time's

Files, and who owns them

Path Scope Owner
openspec/config.yaml This project: default schema, injected context, per-artifact rules You — replaced by setup, after a backup, with a diff you approve
openspec/schemas/<name>/ This project: workflow definitions Setup, additively — yours the moment you edit one
openspec/changes/<change>/.openspec.yaml One change: schema, skip_specs, retire_capabilities You
openspec/specs/, openspec/changes/ Your work product You, entirely. Setup never writes here
.claude/agents/*.md This project: subagents Setup, additively — same ownership rule as schemas
.claude/settings.json This project: plugins You. Setup fills only keys you have not decided
.claude/workflows.json What setup installed: level, version, date, a hash per owned file Setup. Merged, never replaced
~/.config/openspec/config.json This machine: profile, delivery, telemetry You, via openspec config. Setup never writes it
