Lesson 10·Running them·workflows

advanced, the everyday four

feature, bugfix, refactor, rapid — ten artifacts down to two. Each chain has one gate that is the whole reason it exists, and learning the four gates is faster than learning the nineteen artifacts.

By the end

You can drive all four chains, and for each one you can name the gate, say what it blocks, and say what happens when it fails.

Prerequisites: Lesson 08 for the loop, lesson 06 for the router. A repository set up at advanced.

The four gates, first

Schema The gate It blocks
feature review must PASS tasks. No implementation plan is generated until a stronger model has reviewed the specs, design and migration
bugfix rootcause before fix Any proposed fix. "No fix may be proposed before this completes" — the debugging skill's own rule
refactor characterization before anything moves Every code move. Behaviour is pinned by tests first, and coverage gaps get closed before the restructure starts
rapid The contract check, in the proposal Itself. Touch a public API, URL, analytics event, schema, or config contract and the whole change is recreated as feature

Strictly linear, unlike the standard chains. It absorbs what used to be separate greenfield and brownfield schemas: constraints and migration scale from three lines for net-new flag-gated work to full rigour on an existing system.

The review gate in detail

  1. If the proposal's Surfaces line names any surface, dispatch taste-preflight first — a mechanical anti-slop UI check on a cheap model. Pass it the change directory path.
  2. Then dispatch review-gate, pinned to the top tier at xhigh. Its prompt carries the change directory path and the taste-preflight findings verbatim when they exist.
  3. Write its returned content here verbatim as review.md.
  4. On BLOCK: surface the [Critical] findings, fix the upstream artifacts, and re-dispatch. The gate must PASS before tasks are generated.
Do not re-adjudicate the gate

From the schema, verbatim: "Do not soften or re-adjudicate its findings in this session; the gate runs on a stronger model than this one." That single clause is the reason the gate is worth anything. A gate you can argue with from a weaker model is not a gate.

Two file-format traps

  • Checkboxes in tasks.md must be exactly - [ ] . Apply parses that form; any other shape is invisible to progress tracking. Not an error — invisible.
  • Placeholders in plan.md are plan failures. Write the real failing-test code in a fenced block above its checkbox, the real error handling, the repeated code. "Write tests for the above" is a defect, because the implementer may see only their own task.

tasks is the coarse, tracked list; plan is the micro-step two-to-five-minute decomposition. Two files, two jobs — do not merge them.

Ten artifacts is ten /opsx:continue calls, not one session

Open with /opsx:new <a sentence>, using feature, then /opsx:continue <name> once per artifact, naming the change each time. This is the longest chain in the plugin, and unlike mattpocock-bridge — which wants its planning run in one unbroken window — feature's own session discipline is to compact at artifact boundaries. So the boundaries are where you clear and re-pick, and the chain does not notice, because its whole state is on disk.

plan is the last planning artifact, and the boundary the lesson 08 reset exists for: /clear → /model (arrow for effort) or /effort → /opsx:apply <name>. Everything the planning window held is now written down in ten files that apply reads for itself.

bugfix — the cause gates the fix

  • →
  • rootcause
  • →
  • fix
  • →
  • tasks

Three things this chain does that a casual bug fix does not:

  • It traces to the faulty assumption, not the faulty line. Five whys, and no fix proposed until that completes.
  • It scans for the same bug class elsewhere and records hits or "none found". Those hits become tasks — addressed or explicitly ticketed.
  • It classifies the spec three ways, and names the common answer:
    Finding Spec delta owed
    The spec covered the case and the code disagreed None — the regression test holds the line
    The spec was silent about the case that broke — expect this to be the common outcome An ADDED requirement whose scenario is the reproduction made permanent. That silence is the bug behind the bug
    The spec said something the fault proves wrong MODIFIED, copying the entire requirement block, header included — archive replaces the block by matching that header
A symptom fix is legitimate — written down

"A symptom fix under deadline or behind a migration is a legitimate decision when written down: state what a proper cause fix requires, so the next person inherits the choice rather than the surprise." The artifact's job is to make the decision inheritable, not to forbid it.

Performance work comes here too. Establish the measured baseline and a numeric target in reproduction; that measured target is the regression guard.

refactor — pin behaviour, then move code

  • characterization
  • →
  • strategy
  • →
  • tasks

Characterization tests come first and coverage gaps get closed before anything moves. Then every task is one mechanical step — extract, rename, move, inline — with a single acceptance criterion: "suite green, no assertion changed".

Coverage-only work is a valid degenerate case: state "no restructure" and let tasks be the test list.

A changed assertion ends the refactor

It means behaviour changed, which means this was never a refactor. Stop and reclassify as feature. This is the same guardrail as lesson 06, and it fires most often here.

rapid — two artifacts, and a tripwire

  • proposal
  • →
  • tasks

One or two paragraphs on what and why. No specs, no design. The discipline rides in the config rules rather than in extra artifacts — which is what makes it cheap.

The tripwire is in the proposal instruction itself: if the change touches a public API, URL, analytics event, schema, or config contract — or turns out non-trivial — stop and recreate under feature. Apply still runs TDD and an evidence-before-completion pass; cheap is not the same as unverified.

Appendix · the fallback chains

Every skill invocation in these schemas carries a named fallback chain, and the last link is always "follow the template manually". bugfix's investigation, for example, reads: superpowers:systematic-debugging → mattpocock-skills:diagnosing-bugs → agent-skills:debugging-and-error-recovery → the template. Skill names are written pack:skill, and the schemas say to confirm the exact prefix in the agent's skill list, since installation prefixes vary. A schema that names a skill you do not have degrades; it does not fail.
