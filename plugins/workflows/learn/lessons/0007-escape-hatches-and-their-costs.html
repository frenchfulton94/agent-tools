Lesson 07·Choosing·workflows

Escape hatches and their costs

Every schema has doors marked "this artifact does not apply here". Two of them the CLI actually understands. The others are conventions that only work because someone writes a stub, and knowing which is which saves you a confusing afternoon.

By the end

You can skip an artifact a change genuinely does not need, and you know which hatches change what the CLI reports versus which only leave an audit trail.

Prerequisites: Lesson 06. Short lesson — ten minutes.

Where hatches live

All of them go in the change's own .openspec.yaml, beside its schema: line. That file is created by openspec new change and edited by hand for exactly these declarations. 

# openspec/changes/refresh-nav-markup/.openspec.yaml
schema: mattpocock-bridge
skip_specs: true
skip_surface: true

The two the CLI reads

Hatch Use when What the CLI does
skip_specs: true Pure refactor, tooling, or docs work — no spec-level behaviour change is owed openspec status renders the stage as [~] specs (skipped: change declares skip_specs) and excludes it from the progress count. Without it, validate rejects a change with zero deltas
retire_capabilities: true A REMOVED entry takes a capability's last requirement Archive deletes openspec/specs/<capability>/spec.md instead of aborting, names each retirement in its warnings, and prints the restoring git checkout
skills/configuring-openspec/references/config-reference.md. These are the only two boolean declarations OpenSpec itself understands.
Declaring skip_specs and then writing spec files is a validation conflict

That is deliberate: it means a stale marker cannot linger unnoticed. If you set the hatch and later discover a delta is owed, remove the marker in the same edit that adds the spec.

retire_capabilities is recoverable only from git

That is why it is opt-in rather than inferred. Set it in the same edit as the REMOVED entry, and say so out loud to whoever is reviewing — a deleted spec file is the one thing in this whole system that leaves no trace in openspec/specs/.

The ones that are conventions, not features

mattpocock-bridge defines two more hatches. Both are read by the schema instruction, not by the CLI — because only paths under specs/ get a real skipped status.

Hatch Use when What actually unblocks the graph
skip_grill: true The change is genuinely one decision wide A stub grill.md — one line, giving the reason and the date. The key itself does nothing to the CLI
skip_surface: true Backend, data, tooling, or infrastructure — nothing a person looks at A stub surface.md, same shape. The key records the judgement; the file moves the graph
payload/levels/minimal/openspec/schemas/mattpocock-bridge/schema.yaml, the grill and surface instructions: "The CLI does not read this key (only paths under specs/ get a real skipped status), so the stub file is what unblocks the rest of the graph and what leaves the audit trail."

So the mental model is: the key is for the humans and the agent; the stub file is for the dependency graph. Writing the key without the stub leaves the chain blocked and you wondering why. Writing the stub without the key loses the reason.

Skipping design — no key at all

Both mattpocock-bridge and craft-driven treat design as conditional, and neither uses a declaration for it. You skip it deliberately and say so. The conditions are stated in the schemas:

  • Skip it when the change is one module, adds no dependency, and raises no security, performance, or migration question.
  • Write it when the change is cross-cutting, adds a dependency, introduces a new pattern, or carries data-model, security, performance, or migration complexity — or when there is genuine ambiguity about the approach.

That condition list is worth memorising, because it is also the trigger for the most expensive model setting in the whole system — lesson 12 comes back to it.

The reopen hatches

Two schemas tell you to abandon the chain rather than skip an artifact. These are not failures; they are the routing guardrails firing late.

  • bugfix-flow → mattpocock-bridge: when diagnose finds a fault whose fix is a redesign. The signal is the fix altering behaviour the product cares about rather than restoring behaviour it already promised.
  • mattpocock-bridge → bugfix-flow: when grill realises this is a defect fix. It says so and offers the reopen command rather than interviewing you about a bug.

Reopening is a fresh change under the other schema — one sentence, with the schema named:

/opsx:new <what the fix really is>, using bugfix-flow

Or in a terminal, when you already know the slug you want:

openspec new change <name> --schema bugfix-flow
A post-apply artifact is gated by a checkbox, not a file

spike's findings and hotfix's postmortem are written after the work. They are held open by checkboxes in the tracked task file, because the CLI's archive warning counts tracked checkboxes, not artifact files. Ticking the box before writing the artifact is how a postmortem quietly never happens.
