Apple-native repos

Detection does not treat a Swift package and an app the same way, and it should not: a library has nothing to release. Two tiers, one conditional schema, one human step no agent can complete for you.

By the end

You can say which detection tier a repo trips and what each one adds, walk the app-release chain artifact by artifact, and connect Xcode's MCP bridge — or explain, correctly, why xcode-loop fell back to headless commands instead.

Prerequisites: Lesson 02 — installing the plugin and picking a level; everything below is layered on top of that choice. And Lesson 11 — this chain's escape hatch names hotfix by name.

Two tiers of detection

Setup scans a repository for two different kinds of Apple signal, and they gate two different things.

Tier 1 — any Apple signal at all

A root Package.swift is enough on its own. So is anything from tier 2 below — tier 2 is a subset of tier 1, not a separate check. Tripping tier 1 merges settings.base.apple.json into the plugin manifest, which does exactly one thing: enable the apple-studio plugin. That happens at every level — minimal, standard, and advanced all get it, because a Swift package still benefits from apple-studio's build, test, and screenshot skills even when nothing about it ships as an app.

Tier 2 — a full app project

This is a narrower, stricter check: an .xcodeproj or .xcworkspace bundle at the repo root or exactly one directory down — so a monorepo's ios/App.xcodeproj counts, but nothing deeper does — or a Tuist Project.swift/Tuist directory, or an XcodeGen project.yml, each checked at the root. Tripping tier 2 additionally requires being on the advanced level before it adds anything: only then does it install the app-release OpenSpec schema and the apple-design-gate subagent from payload/levels/advanced/apple/. The same repository on minimal or standard gets tier 1's plugin layer and stops there — the schema and the gate agent do not exist on those levels at all.

A bare package never reaches tier 2

A repository with only Package.swift and no .xcodeproj, .xcworkspace, Tuist, or project.yml anywhere trips tier 1 and stops. It gets the plugin layer, full stop — there is no app to release, so there is no app-release schema to install, on any level. The scan's own comment says why the one-directory-deep walk exists at all: monorepos put the app in ios/ or apps/, and a full recursive walk would make scanning a node_modules-sized tree unaffordable.

The app-release chain

Four artifacts, then an operation: release-scope → preflight → tasks → post-release, with apply running after tasks — an operation, not an artifact, so it never appears as a chain id of its own.

release-scope — what ships, decided and owned

Marketing version against build number, decided explicitly and with a reason — CFBundleShortVersionString is user-facing, CFBundleVersion only ever increases. What merged since the last release, pulled from the archive and git history as a decision record rather than a changelog dump. Phased-release intent, and a go/no-go owner named by name.

preflight — the evidence-per-item rule

Signing and provisioning, the privacy manifest and nutrition-label answers checked against what the code actually does, screenshots and metadata, export compliance, review notes with a working demo account. The rule that makes this artifact worth writing: every item names the evidence checked — a command run, a screenshot, an App Store Connect page state. A bare checkbox is not preflight.

tasks — a signal per step, and the code-defect guardrail

Archive, upload, TestFlight, submit — in order, and each one carries its own — Verify: line naming the observable proof it worked: the archive succeeds with the release configuration, the build appears in App Store Connect processing, it installs and launches on a physical device, the review state transitions to In Review. "It uploaded" without the signal is how a release stalls silently.

One line in this artifact is a guardrail on the whole chain: a code defect discovered here stops the release and spawns a bugfix change — the release chain never absorbs code fixes. Fix nothing inline; link the bugfix and resume only when it ships.

The tracked checkbox that closes the loop

tasks.md's own checklist carries a last item most schemas would leave to the dependency graph alone: "Complete post-release.md with the monitoring plan — Verify: thresholds and watcher named in post-release.md." That checkbox exists because the graph itself would not catch its absence — post-release only requires: [tasks], so a change can read tasks as done with no monitoring plan ever written. The checkbox is what keeps that promise honest without changing the dependency graph.

post-release — completed before archiving

Crash-rate and key-metric thresholds that pause the rollout, who watches them and for how long, and every follow-up change this release surfaced, linked. Completed after the release ships and before the change archives — a release without a monitoring plan is a release you learn about from reviews.

The hatch

An urgent fix already live in the store routes its code work through hotfix — the expedited-review submission still goes through this chain, referencing it. The two schemas never merge into one; hotfix owns the code, app-release owns the submission.

Connecting Xcode

Xcode 27 ships xcrun mcpbridge, a STDIO bridge between an MCP client and Xcode's own MCP tool service. Wiring it up is a human step — setup's plan lists it, but nothing in it can flip a toggle inside Xcode for you.

  1. In Xcode: Settings → Intelligence → "Allow external agents to use Xcode tools". Without this, the bridge has nothing to connect to even if the binary works.
  2. Register it for the agent: 
    claude mcp add --transport stdio xcode -- xcrun mcpbridge
  3. Xcode must have the target project open for project-aware operations — edits, builds tied to the open workspace — to work through the bridge at all.
Don't block on it

Headless xcodebuild is the default and the only option in CI or whenever Xcode is not running with the project open — no interactive session exists, the xcode MCP server is not connected, or the Intelligence setting above is not enabled. xcode-loop does not wait for a human to fix Xcode settings first: unavailable or unconfigured, it falls straight through to headless commands.

Setup only surfaces the human step at all when an app was detected and .mcp.json does not already list a configured xcode server — read, never spawned, because a subprocess is too much machinery for a question one file answers.
