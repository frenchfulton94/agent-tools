Lesson 01·Orientation·workflows

Three layers, one command

Almost every confusing thing about this plugin becomes obvious once you know which of three places a file lives in. Learn the three places first; everything else in the course hangs off them.

By the end

You can point at any file /workflows:setup touches and say which layer owns it — the plugin, your repository, or your own work product — and you can recite the six things setup refuses to do.

Prerequisites: none. You do not need OpenSpec installed to finish this lesson, and you should not install anything yet.

The problem this plugin exists to solve

Spec-driven development with OpenSpec needs a pile of configuration: which workflow a change follows, what context every prompt carries, which subagents exist, which skill packs are enabled. Set that up by hand in five repositories and you get five slightly different setups, all drifting. Copy it between repositories and the copies drift faster.

/workflows:setup is one command that writes all of it, and — this is the part that matters — is safe to run again. Re-running is how a repository takes updates.

The design insight

The plugin splits its content on one question, and it is not "code or prose". It is when does this guidance have to fire? A schema router has to fire at a known moment — before a change is created — so it lives in your repository where memory reliably loads it. Reference prose you consult on demand lives in the plugin, as a skill, so there is one copy that updates when the plugin does.

Layer 1 — the plugin

Installed once, lives outside your repository, updates when you update the plugin. You never edit anything here.

What Where Why it is here
The setup procedure skills/setup/SKILL.md One copy of the procedure, updated with the plugin
OpenSpec reference prose skills/configuring-openspec/ Consulted on demand, so it never needs to be in memory
Detect, plan, verify, record scripts/*.mjs Facts a procedure must never derive by hand
Everything it installs payload/ The schemas, agents and config examples, per level

Layer 2 — your repository

Copied in by setup, then committed. Version-controlled, visible to CI, visible to teammates. This is the layer you may edit — and editing it has a specific consequence you will learn in lesson 04.

What Where Written by
Workflow definitions openspec/schemas/<name>/ Setup, additively
Subagents .claude/agents/*.md Setup, additively
Project config openspec/config.yaml Setup — the one file it replaces, after backing it up
Plugin and status-line choices .claude/settings.json Setup, filling only keys you have not decided
What setup installed .claude/workflows.json Setup — the level, version, date, and a hash per file it owns
Stack and memory docs TOOLS.md, CLAUDE.md Skills setup invokes, not setup itself

Layer 3 — your work product

openspec/specs/ holds what your software is contracted to do. openspec/changes/ holds the changes in flight. Setup manages the schema and configuration layer around these two directories and never writes into them.

That guarantee is not a promise in prose. Setup hashes both directory trees before it touches anything, hashes them again afterwards, and reports a failed check if either moved.

The six refusals

A tool that rewrites files in a repository it is a guest in earns trust by what it declines to do. Setup declines six things, always, at every level.

  1. It will not overwrite a value already in .claude/settings.json. A plugin you disabled on purpose stays disabled. Setup fills only keys you have not decided.
  2. It will not touch openspec/specs/ or openspec/changes/. Those are layer 3.
  3. It will not replace a schema or subagent without naming it first. A same-name collision is shown before you approve, never applied silently — and that includes a file setup itself wrote that you have since edited.
  4. It will not run openspec init over an existing openspec/. Only a repository with no openspec/ at all gets initialized, because init has a legacy-cleanup path.
  5. It will not write openspec config profile. That value is machine-global — shared by every project you run OpenSpec in on this machine. Setup reports its current value and leaves the decision to you.
  6. It will not transmit anything. Every openspec invocation the plugin makes sets OPENSPEC_TELEMETRY=0 and DO_NOT_TRACK=1, because every openspec subcommand runs a hook that POSTs to a third-party endpoint.
plugins/workflows/README.md — "What it will not do". Refusal 6 is pinned by tests on both halves: the scripts on every spawn, and the setup procedure on every command it tells the agent to run.
