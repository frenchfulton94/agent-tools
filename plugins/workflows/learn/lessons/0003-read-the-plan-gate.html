Lesson 03·Install and set up·workflows

Read the plan gate

Setup shows you a plan and stops. Nothing is written before you approve it — not a schema, not a config, not a scratch file. That gate is the whole safety model, and reading it is the single most useful skill in this course.

By the end

You can read a /workflows:setup plan line by line and say, for each entry, what will happen to that file and whether you should approve it. You know why collide is asked one file at a time.

Prerequisites: Lesson 02, plugin installed, a level in mind.

Why the gate exists

"This command replaces a file the user wrote, in a repository you are a guest in, so that gate is the whole safety model."

plugins/workflows/skills/setup/SKILL.md

Setup runs in four movements: detect (read the repository's real state), ask (one question — the level, carrying a recommendation setup read off your commit history), plan (build the complete list of intended writes), approve, then apply. The plan is a data structure, not a summary: the agent renders it for you, saves the approved copy outside the repository, and applies that exact copy.

Why the approved copy is frozen

Re-running the planner partway through apply would replan against a half-applied repository, and hand you something you never approved. So the approved plan is written to a temporary path outside the repo and followed literally.

skills/setup/SKILL.md §3, final paragraph
The gate survives auto mode

The level question and the plan approval are both an AskUserQuestion, which no permission mode auto-approves — not auto, not even bypassPermissions. Running the session in auto mode removes the routine prompts around the file writes setup performs after you approve; it does not touch the gate itself.

What is in a plan

Field Values What it decides
mode fresh · reconcile Whether .claude/workflows.json exists — i.e. whether this repository has been set up before
web boolean Detected, never asked. Adds the web plugin overlay
openspecInit boolean True only when openspec/ is genuinely absent — never inferred another way
schemas, agents copy · update · collide The three groups. This is the safety story — see below
config create · replace, plus backupTo The one destructive step, and where your old file is saved
plugins install · disable · skip Every skip carries a reason. Read the reasons; that is where "you already decided this" shows up
humanSteps list What will still be left for you afterwards
probeChange zz-workflows-setup-probe The throwaway change verification creates and removes to prove config reached the model
warnings list Read these first, not last
Field names and value sets from plugins/workflows/scripts/plan.d.mts (the Plan interface).

The three groups, and why they matter

Schemas and agents are each sorted into three groups. The difference between them is the entire ownership model.

Group Means Setup will
copy Not there yet Write it
update A previous run wrote it and nobody has edited it since — the hash in .claude/workflows.json still matches Refresh it. This is how a re-run takes updates.
collide Your own file — or one of setup's that you have since changed Report it. Never replace it unless you approve that specific name
"Approve all" is not an answer

Collisions are asked about individually, by name. That is written into the procedure, not left to the agent's judgement — because a blanket yes is how someone's customised subagent gets silently replaced. If you are ever offered a single yes/no over a list of collisions, that run is not following the skill.

skills/setup/SKILL.md §3 — "'approve all' is not an answer to this question"
The warning that invalidates half the plan

If .claude/settings.json cannot be read, the plugin and status-line sections of the plan are meaningless — setup cannot know what you have already decided. That warning leads the list, and the correct response is to fix the file, not to approve around it.

A plan, and what to make of it

Here is a realistic plan for a web repository being reconciled at standard. Read it before the questions below. 

{
  "mode": "reconcile",
  "level": "standard",
  "web": true,
  "openspecInit": false,
  "schemas": {
    "copy": ["surface-driven"],
    "update": ["craft-driven"],
    "collide": []
  },
  "agents": {
    "copy": ["verification-reviewer.md"],
    "update": [],
    "collide": ["craft-design-gate.md"]
  },
  "config": {
    "action": "replace",
    "backupTo": "openspec/config.yaml.bak-20260828T144102-1"
  },
  "plugins": {
    "install": ["impeccable@impeccable", "taste-skill@taste-skill"],
    "disable": [],
    "skip": [
      { "id": "playwright@claude-plugins-official",
        "reason": "already decided in .claude/settings.json" }
    ],
    "marketplaces": [
      { "name": "impeccable", "source": { "repo": "pbakaus/impeccable" } }
    ]
  },
  "humanSteps": [
    "Run /impeccable init - writes PRODUCT.md and DESIGN.md.",
    "Run /reload-plugins to activate the newly installed plugins."
  ],
  "probeChange": "zz-workflows-setup-probe",
  "warnings": []
}

Three things in that plan deserve a decision from you:

  • craft-design-gate.md is a collision. Either you customised it, or setup wrote it and you edited it. You will be asked about this one file by name. Decline unless you know what you changed and want it gone.
  • playwright was skipped because you already decided it. If that surprises you, the surprise is in settings.json, not in setup.
  • Nothing is written before you approve. Read the whole plan; the collisions and skips above are the only places a decision is being asked of you.

The one destructive step

openspec/config.yaml is replaced, not merged. Your existing file is input, not the base — the level's example is the base, and your file supplies what is project-specific. Four things happen in order:

  1. Backup. To the plan's backupTo path, which is collision-resistant by construction — a timestamp plus a per-process counter, so two backups in the same millisecond cannot overwrite each other.
  2. Get the authoritative artifact-id union. From the OpenSpec CLI, never from schema YAML and never by guessing. If that call fails, setup stops — because classifying your rules against an empty union would mark every rule you wrote as unmatched and discard it.
  3. Classify your rules. Rules keyed to an artifact id any installed schema defines are carried. Rules keyed to anything else are unmatched — and unmatched rules are never dropped and never left under rules:, where OpenSpec would warn about them on every command. They go into a trailing comment block, verbatim.
  4. Show you the diff — carried over, dropped with the reason, unmatched — and get agreement before writing.
skills/setup/SKILL.md §5 and scripts/config-facts.mjs — backupPath, artifactIds, classifyRules, commentBlock, contextSize
The 50KB cliff

context: is injected into every artifact prompt and is hard-capped at 50KB. One byte past the cap and OpenSpec drops the entire field, silently. Treat the cap as a ceiling to stay far below, not a budget to spend. You will prove whether yours arrived in lesson 13.

Do this now

  1. Run the read-only version first. It writes nothing at all: 
    /workflows:setup standard --check
  2. Then get the plan as data. This writes exactly one file, .claude/workflows-plan.json, and nothing else: 
    /workflows:setup standard --dry-run
    Open it. Compare it against the field table above until every key means something.
  3. Now run it for real and approve deliberately — declining every collision on the first pass is a perfectly good answer. 
    /workflows:setup standard

Recall check

A schema is in the update group. What is true about it?

The artifact-id lookup from the OpenSpec CLI fails. What should happen?

In the plan above, why was playwright skipped?

Where does an unmatched rules: entry from your old config end up?

Appendix · for the plugin's author

The plan's own failure mode is worth knowing: plan.mjs writes nothing to stdout unless buildPlan succeeds, so a pipeline consumer can never receive JSON it might mistake for a real plan. An unknown level exits non-zero with empty stdout and just its message; any other error gets a full stack, because that is a defect in the module rather than a typo. payloadRoot is a test-only seam and throws on a bad path rather than degrading to an empty but plausible plan — which is exactly what it used to do.
