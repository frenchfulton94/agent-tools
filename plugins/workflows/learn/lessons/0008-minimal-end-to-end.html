Lesson 08·Running them·workflows

minimal, end to end

One change, from an idea to an archived spec, using the two schemas the minimal level installs. This is the lesson where the whole thing stops being theory.

By the end

You have driven a real change through mattpocock-bridge — grill to archive — and you know which command to type at each artifact, what to do to your session in the gap between the last planning artifact and the first line of code, and which schema to reopen under when it turns out to be a defect.

Prerequisites: Lesson 05 (setup finished, including /setup-matt-pocock-skills) and lesson 06. Pick a small, real piece of work — not a toy.

The two chains

mattpocock-bridge — the default

  • grill
  • →
  • proposal
  • →
  • surface
  • →
  • specs
  • →
  • design
  • →
  • tasks
  • →
  • apply

The arrows are not the real graph — the real graph is requires, and it forks. specs needs both proposal and surface; design needs proposal and specs; tasks needs specs and design. So the CLI can offer you more than one next artifact, and declaration order breaks the tie.

bugfix-flow — the companion

  • diagnose
  • →
  • specs
  • →
  • tasks
  • →
  • apply

No interview, no proposal — a defect needs no case made for fixing it. What it adds instead is a gate: nothing can be written until the root cause is.

Drive it

  1. Create the change — in the assistant's chat, in a sentence. 
    /opsx:new let advisors export their degree plans as a PDF
    The argument is the change name in kebab-case, or a description of what you want to build — a sentence is a first-class input here, not a fallback. It derives the slug, scaffolds the change, shows the artifact status, prints the first artifact's template, and then stops without writing anything. Name the other schema in the same sentence when the work is a defect: 
    /opsx:new fix the export timezone offset, using bugfix-flow

    The terminal equivalent, when you want it. openspec new change let-advisors-export-plans, with --schema bugfix-flow to name the other one. Same scaffold — but you supply the slug yourself, and you get no first-artifact template. Reach for it in a script, or when you already know the exact name you want.

  2. See what is ready. /opsx:continue opens by showing you this, so most of the time no separate check is needed. When you want it as data — or when the assistant and the filesystem seem to disagree — go to a terminal: 
    openspec status --change let-advisors-export-plans --json
    It tells you which artifacts exist, which are ready, and which are blocked on what.
  3. Build one artifact at a time, and name the change every time. 
    /opsx:continue let-advisors-export-plans
    It shows what is ready, then creates one artifact. Run it again for the next.

    The name is optional in the command and worth typing anyway: with it omitted, continue infers the change from the conversation and has to ask you when it cannot. That inference is the first thing to break — the moment you clear the window or come back tomorrow, there is no conversation left to infer from. This is also the command that resumes a change in a brand-new session: it reads the filesystem, not your history.

    On the core profile you do not have continue — see the note below.

  4. Expect the grill to interview you. Rounds of numbered questions, each carrying a recommended answer. Facts are the agent's job; decisions are yours. What gets settled lands in CONTEXT.md and ADRs, not just in the change folder.

    If it opens by telling you this is a defect and offering --schema bugfix-flow, take the offer.

  5. Skip what does not apply, deliberately. No visible surface? Set skip_surface: true and write the one-line stub — lesson 07. One module, no new dependency, no security or migration question? Skip design and say so.
  6. Write the delta specs carefully. Two formatting rules break archiving silently if you get them wrong:
    • Scenarios need exactly four hashes — #### Scenario:. Three hashes, or a bullet, fails quietly.
    • A MODIFIED requirement replaces the whole block, so it must carry every surviving scenario, not only the edited ones.
  7. Confirm the seams before implementing. design's Seams table is the one thing tdd needs agreed up front, and this level's config carries a rule making that confirmation explicit: "Confirm the Seams table with the user before marking this artifact done."
  8. Reset, once the planning artifacts are all created. Three commands, in this order, before you implement anything:
    1. /clear — the planning window is spent, and apply needs the room for code, test output, and shell noise. OpenSpec's own guidance says the same thing: it works best with high-reasoning models and a clean context window, and you should clear context before implementation.
    2. /model — pick the model for implementation, and set its effort with the left and right arrows on the same picker. If the model is already right and only the depth is wrong, /effort on its own does the second half. For this chain that is the step down from planning depth to an implementation tier — lesson 12 is the whole argument.
    3. /opsx:apply let-advisors-export-plans — with the name, because you just deleted the conversation it would otherwise have inferred it from.

    Do not clear between the planning artifacts on this chain. mattpocock-bridge asks for grill through tasks in one unbroken window, so the interview, the proposal, and the slices build on the same thinking — this reset belongs at the apply boundary and nowhere earlier. Switching depth between artifacts is still free: /effort changes nothing about the window. And if that planning run gets long, compact at the nearest artifact boundary rather than clearing.

    payload/levels/minimal/openspec/CLAUDE.md.fragment.md, "Context hygiene", and mattpocock-bridge/schema.yaml around line 519.
  9. Implement one slice per session. Each slice: failing test at the agreed seam → smallest code to pass → affected tests as you go, full suite at the end → the two-axis review → tick the boxes and commit. Then stop, and start the next slice in a fresh session — /clear, then /opsx:apply let-advisors-export-plans again. Each slice is self-contained by construction, so the finished slice's context is disposable.
  10. Finish. sync is optional and merges this change's deltas into your main specs while the change stays active; archive prompts you to sync if you have not. 
    /opsx:sync let-advisors-export-plans      # optional
/opsx:archive let-advisors-export-plans
Clearing is free. Not clearing is not.

Nothing about a change lives in your session. Artifact state is pure filesystem existence — a file is there or it is not — so /clear destroys nothing a chain depends on, and /opsx:continue <name> picks the work up from disk exactly where it was. Carrying a spent planning window into apply, on the other hand, costs you the room the implementation loop needs and buys you nothing back.

The one thing /clear does take is the assistant's ability to guess which change you mean. That is the entire reason every command above carries the change name.

The /opsx:new argument contract and the clean-context guidance are both in skills/configuring-openspec/references/using-openspec.md — "The loop" and the command reference.
On the core profile

No continue and no new. Use /opsx:propose, which takes the same sentence and creates the change and every planning artifact in one step, then /opsx:apply <name>. You lose the per-artifact gates, which is the main reason lesson 05 pushes you toward the custom selection. The reset before apply is unchanged: everything the propose step filled your window with is exactly what apply does not need.

Archiving in CI or from an agent

openspec archive asks up to three confirmations. With stdin closed — CI, a script, a non-interactive agent — pass the change name and --yes or it exits 1.

What the two-axis review is, and why it is two

At the review step of every slice, two subagents run in parallel, and they are deliberately kept in separate lanes.

Agent Axis Judges Model tier
code-review-spec Spec The diff against the proposal and delta specs. Did it do what was asked? Mechanical comparison — it does not judge style Cheap
code-review-standards Standards The code as code, against the repo's documented standards and smell baseline. It does not judge whether the code does what was asked Strong
payload/levels/minimal/agents/. Each prompt carries the slice's start commit, the change directory, and the tracker reference — subagents inherit nothing from your conversation, so anything unstated is unavailable.

If either agent is missing, the schema falls back to invoking code-review directly and letting it run its own parallel subagents. Every skill invocation in every schema carries a fallback like this, and degrades to the template when the skill is absent.

Recall check

A #### Scenario: heading written with three hashes. What happens?

You are modifying a requirement that has four scenarios and changing one. What goes in the MODIFIED block?

A slice finishes and its tests pass. What does the schema tell you to do next?

During bugfix-flow's apply, the reproduction still triggers after your fix. Which artifact is wrong?

Every planning artifact is written. Why is /clear safe before /opsx:apply?

You cleared the window, then typed /opsx:apply with no change name.

Appendix · the user-invoked skills you are offered, not given

mattpocock-bridge carries the discipline of five user-invoked skills in prose because an agent cannot fire them by design: /grill-with-docs, /to-spec, /to-tickets, /implement, /triage, and /wayfinder. Where the schema says "if the user would rather run /to-tickets themselves — it is user-invoked, so only they can fire it — ask them to, then write the mirror from what it published", that is an offer to you, not something the agent will do unprompted.
