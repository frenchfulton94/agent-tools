advanced, the situational four

setup, spike, upgrade, hotfix — the four kinds of work that get mangled when a repository only knows how to do features and bugs. Each one inverts something the other chains take for granted.

By the end

You can drive all four, and you can say what each one inverts — which is the thing that makes it a separate schema rather than a variation.

Prerequisites: Lesson 10. These four are shorter chains than feature, so this is a lighter lesson than the last one.

What each one inverts

Schema The inversion
setup No specs artifact at all — no behaviour exists yet to spec. It writes the standing documents every other schema reads
spike The code never merges. The deliverable is a written answer, and a hard timebox is part of the artifact
upgrade The constraints come from someone else's release notes, and success means behaviour is unchanged
hotfix Depth comes after shipping. A minutes-long triage gates the mitigation; the full investigation is backfilled

setup — bootstrap a repository

  • decisions
  • →
  • conventions
  • →
  • tasks

decisions is a one-question-at-a-time stack interview, and nearly every choice becomes an ADR — at bootstrap almost everything passes the ADR three-gate test, because everything is hard to reverse later.

conventions is written to be copied, not summarized. Its content gets materialized during apply into CONTEXT.md, AGENTS.md, the OpenSpec config context, and a DESIGN.md stub for UI projects.

The exit criterion for tasks is a walking skeleton: the thinnest end-to-end slice building, testing, and deploying green in CI.

Why TOOLS.md comes last

There is one deliberate post-skeleton task: generate TOOLS.md via mapping-project-tooling. That skill's own rule forbids writing it before evidence exists on disk, so it runs after the skeleton lands, never at scaffold time. A stack map written from intentions rather than from a lockfile is worse than none.

spike — a question, timeboxed

  • question
  • →
  • apply
  • →
  • findings

This is the one chain where apply does not track tasks.md — it tracks question.md, whose experiment checkboxes are the task list.

question frames one primary question, the decision it informs, what evidence would count as an answer, and a hard timebox. When the timebox expires, findings get written with whatever evidence exists — an unbounded spike is just unplanned development.

Apply works in an isolated worktree that will never merge, with quality bars relaxed by design. Then findings: the answer first, evidence rather than impressions, a recommendation, and a mandatory disposition — code discarded, and either a follow-up feature change for the learnings or an explicit decision not to proceed.

A spike without written findings produced nothing

The code is thrown away by design, so if the findings are not written the whole change was wasted. And remember from lesson 07: the archive warning counts tracked checkboxes, not artifact files, so ticking the last experiment box before writing findings.md is how this quietly goes wrong.

upgrade — someone else's breaking changes

  • inventory
  • →
  • surfaces
  • →
  • migration
  • →
  • tasks
  • →
  • verification

inventory records current and target versions and inventories breaking changes from official release notes and changelogs, citing URLs. The premise is stated plainly: memory of an API is not evidence of its current shape. Each entry gets an applies-to-us verdict, and stepping-stone versions are listed if the jump spans several majors.

surfaces is the artifact that actually bounds the work. For each applicable breaking change, find real call sites by search — grep or AST — with paths and counts. Start from TOOLS.md's dependency map when it exists, then grep-verify: the map narrows, the search proves. Then classify each surface:

Class Means
mechanical Codemod-able
behavioral Needs a test to prove equivalence
unknown Spike first
Skipping this scan is how upgrades discover breakage in production.

Apply fixes mechanical surfaces first, then behavioral ones with their equivalence tests. On an unexplained behavioural diff: stop, and either fix forward or roll back — never ship a changed behaviour as an "upgrade". Commit the lockfile with the code, then refresh TOOLS.md, because an upgrade that leaves it stale plants the next agent's wrong-package-manager bug.

hotfix — ship first, document after

  • triage
  • →
  • tasks
  • →
  • apply
  • →
  • postmortem

triage takes minutes, not hours: what is broken, since when, severity, who is affected. The first diagnostic is what changed recently — deploys, flags, config. Then decide rollback versus forward-fix explicitly, and name the approver.

Every step in tasks names the observable signal proving it worked — error rate, a monitor, a user report — because under incident pressure "it should be fixed now" is how incidents recur an hour later.

Rollback beats forward-fix when both are viable. It is faster and better understood.

The postmortem is the one place the reset runs upward

Everywhere else, the step between planning and /opsx:apply is a step down in depth. Here it is the other way round: the postmortem comes after apply, and it is one of the few artifacts in the whole plugin that wants the top tier at xhigh (lesson 12). Do the same three commands, aimed the other way — /clear, /model or /effort up to that depth, then /opsx:continue <name>. Clearing matters more here than anywhere: the window you are carrying is an incident, and the artifact that follows it is meant to be blameless.

A hotfix without a follow-up leaves the root cause in production

postmortem is blameless — timeline, root cause, why existing tests and review missed it — and it applies the full investigation rigour triage skipped, retrospectively. Then it creates the follow-up change that does the durable fix, usually a bugfix, and links it. That creation is mandatory, not encouraged.

Recall check

Why does setup have no specs artifact?

A spike's timebox expires with the question unanswered. What now?

In upgrade, what proves where a breaking change actually lands?

Both a rollback and a forward-fix would work in an incident. Which does the schema prefer?

Appendix · setup the schema versus /workflows:setup the command

Two different things with the same word, and the collision is worth naming out loud for a teammate. /workflows:setup is this plugin's command — it configures a repository's OpenSpec layer. The setup schema is one of the eight advanced workflows — it bootstraps a repository's code, CI and standing docs. You would typically run the command first and then, in a genuinely new repository, create a change under the schema.
