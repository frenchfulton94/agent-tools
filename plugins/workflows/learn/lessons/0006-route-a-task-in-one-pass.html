Lesson 06·Choosing·workflows

Route a task in one pass

Nothing picks the workflow for you. OpenSpec has no auto-selection — the schema is chosen at the moment a change is created, and choosing badly costs you the whole chain. This is the lesson that pays for the course.

By the end

Given a one-line work request, you name the right schema in one pass and cite the rule that decided it. You can also state the four guardrails that force a reclassification mid-flight.

Prerequisites: Lesson 02. You do not need setup to have run — this lesson is pure judgement, and it is worth doing before your first real change.

First, how a schema actually gets chosen

Four sources, in strict precedence order. The first one present wins.

# Source Scope
1 --schema <name> on the command This one change, decided now
2 The change's .openspec.yaml This one change, decided earlier
3 openspec/config.yaml's schema: Every change in this project by default
4 spec-driven OpenSpec's built-in fallback
From skills/configuring-openspec/SKILL.md. A schema you installed does nothing at all until something in this list names it.

So routing, concretely, is one sentence in the assistant's chat with the schema named in it: 

/opsx:new <what you want, in a sentence>, using <schema>

/opsx:new takes either a kebab-case change name or a description, derives the slug when you give it the latter, and passes --schema through only when you actually named one — otherwise it lets row 3 of the table decide. Naming the schema in the sentence is therefore how you exercise row 1.

The terminal form is the same routing decision, with the slug written by you rather than derived: 

openspec new change <slug> --schema <schema>

Change names are lowercase kebab-case; a leading number is allowed (100-add-export).

At minimal and standard, it is a two-way call

Neither level ships a router, because with two schemas you do not need one. Both decisions come down to a single distinguishing factor — which is exactly how a good router works.

Level Default The other one What distinguishes them
minimal mattpocock-bridge bugfix-flow Is the problem known and the cause unknown? Then it is a defect, and a defect needs no case made for fixing it — no interview, no proposal, and the fix gated behind a written root cause.
standard craft-driven surface-driven Is the change primarily a user-facing surface — a landing page, dashboard, flow, redesign, component system? Then design leads and Superpowers executes. Otherwise behaviour leads.
A fault whose fix is a redesign is not a bugfix

bugfix-flow's own diagnose artifact says to stop and reopen under mattpocock-bridge when this happens. The signal: the fix alters behaviour the product cares about, rather than restoring behaviour it already promised.

At advanced, the router does the work

ROUTING.md is installed where your agent reads instructions, and the agent reads it before creating any change. Eight branches, and first match wins — which is why the order is not alphabetical or aesthetic. It is triage order.

# If… →
1 Production is broken now — incident, outage, users blocked hotfix
2 New repository or project bootstrap — "init", "scaffold", "set up the project" setup
3 Something behaves wrong versus intent — bug, error, crash, regression, "too slow" bugfix
4 Dependency, framework or platform version change — bump, EOL, CVE, "migrate to vN" upgrade
5 Structure changes but behaviour must not — clean up, extract, rename, de-dupe, tech debt refactor
6 An open question answered by building — try, compare, POC, feasibility, "which library" spike
7 New capability or intentional behaviour change — including removals and deprecations feature
8 Trivial, low-risk, no contract impact — typo, copy, config value, docs rapid
payload/levels/advanced/openspec/ROUTING.md. Two sub-rules matter more than they look: performance work is a bugfix (measure a baseline and set a numeric target before changing code), and coverage backfill is a refactor (characterization is the deliverable).

The four guardrails

Routing is not a one-time decision you defend. These four force a reclassification the moment they trigger, and all four are in the router itself.

  • rapid → feature: the moment a public API, URL, analytics event, data schema, or config contract is touched. Stop and recreate.
  • refactor → feature: if any test assertion has to change, behaviour is changing. Stop and reclassify.
  • spike: code is throwaway and never merges. Learnings graduate through a new feature change.
  • hotfix: must spawn a follow-up bugfix or feature change for the durable fix. postmortem.md links it.
De-escalate as readily as you escalate

The router says so explicitly. When a feature brainstorm reveals bounded work, recreate under rapid. When it reveals a question in disguise, recreate under spike. One command against hours of ceremony.

Drill · route these

Twelve real-shaped requests, shuffled each time you load this page. Pick the schema, then read the rule you should have used. Assume advanced.

  1. "Checkout is returning 502s. Nobody can pay. What do we do?"
  2. "Move the service to the current Node LTS before the old one goes EOL."
  3. "The CSV export drops the last row for accounts in Alaska."
  4. "The date-parsing helper is copy-pasted in four files. Extract it."
  5. "Let advisors export a student's degree plan as a PDF."
  6. "Drizzle or Prisma for the new service? Build a slice of each and see."
  7. "There's a typo in the footer copyright line."
  8. "Start the admissions-dashboard repo from nothing."
  9. "The search page takes nine seconds. Get it under two."
  10. "Coverage on the billing module is 40%. Add tests."
  11. "Take out the legacy SAML login path."
  12. "There's a CVE in the image library. Patch it."

Recall check

A rapid change turns out to rename an analytics event. What now?

Mid-refactor, you find you must change a test assertion. What does that mean?

A schema is installed and validates, but no change ever uses it. Why?

Appendix · when the work is bigger than one change

A change is a single unit of work. For an epic, the router points at /wayfinder (user-invoked, mattpocock pack) to map it as decision tickets, then one OpenSpec change per resolved chunk. Similarly, /improve-codebase-architecture is a codebase scan whose accepted opportunities each become their own refactor change. Standing-doc upkeep — a CLAUDE.md audit, a TOOLS.md refresh, glossary maintenance — routes to rapid and invokes the owning skill.
