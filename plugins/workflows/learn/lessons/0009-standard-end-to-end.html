Lesson 09·Running them·workflows

standard, end to end

Two schemas that differ only in what leads. One puts behaviour first and treats the surface as a consequence; the other puts the surface first and treats behaviour as its implementation. Getting the choice right is most of the work.

By the end

You have driven a change through craft-driven, you can say when design-brief and design exist at all, and you can choose surface-driven for the right reason.

Prerequisites: Lesson 08 — the artifact-at-a-time loop and the spec formatting rules carry over unchanged.

The two chains

craft-driven — behaviour leads

  • brainstorm
  • →
  • proposal
  • →
  • specs
  • +
  • design-brief
  • +
  • design
  • →
  • tasks
  • →
  • apply
  • →
  • verification

specs, design-brief, and design all depend only on proposal, so all three become ready together and tasks waits for all three. Two of them are conditional.

surface-driven — the surface leads

  • design-brief
  • →
  • proposal
  • →
  • specs
  • →
  • tasks
  • →
  • apply
  • →
  • quality

Strictly linear, and the brief comes first — before anything is written down as a requirement. The proposal is deliberately short, because the brief already carries the decisions.

Choosing between them

One question: is this change primarily a user-facing surface? A landing page, a dashboard, a flow, a redesign, a component system. If yes, the design brief should lead and you want surface-driven. If the surface is a consequence of new behaviour rather than the point of the work, you want craft-driven. 

/opsx:new redesign the admissions dashboard, using surface-driven

Or in a terminal, when you would rather write the slug yourself: openspec new change redesign-admissions-dashboard --schema surface-driven.

Not a project-wide decision

craft-driven is the config default; surface-driven is selected per change by naming it — in the sentence you give /opsx:new, or as --schema on the command. A repository will use both, and that is the intended shape.

The loop is the same one you already know

/opsx:continue redesign-admissions-dashboard for each artifact, naming the change every time. Then, once the last planning artifact lands and before a line of code is written: /clear, /model — arrow left or right for effort, or /effort on its own — and /opsx:apply redesign-admissions-dashboard. Lesson 08 has the reasoning; it does not change between levels.

The two conditional artifacts

design-brief — gated on the proposal's own words

Create it only if the proposal's Surfaces section names at least one user-facing surface. If it says "None — no UI impact", skip the artifact, tell the user you skipped it and why, and move on.

That makes the proposal's Surfaces line load-bearing rather than decorative: it is the switch that turns the whole UI path on or off. Write it honestly.

What the brief must settle, so a builder cannot re-litigate it mid-task:

  • Visitor mode for each surface — Persuade, Operate, Read, or Experience — chosen from the surface, not the product. A tool's landing page is still Persuade; a fashion house's docs are still Read.
  • Visual authority — does the surface inherit the incumbent visual world (refinement preserves), or was a replacement world chosen and approved (redesign replaces)? Never split the difference.
  • The selected direction, scope and anti-goals, material states and realistic content ranges, and the constraints that bind.

State intent, not CSS. Three to five bullets for a settled refinement; the full structure only for ambiguous or multi-screen work.

design — gated on complexity

Create design.md only if any of these apply:

  • the change is cross-cutting — multiple services or modules — or introduces a new architectural pattern;
  • it adds an external dependency, or significant data-model changes;
  • it carries security, performance, or migration complexity;
  • there is ambiguity that benefits from technical decisions before coding.

Otherwise skip it and tell the user why.

The trigger is the tier signal

Notice that this artifact only exists when the change is already the hard case. That is why the schema dispatches a subagent for it, and why that subagent is pinned to the top tier — lesson 12 builds on exactly this.

The subagent dispatch pattern

Both of craft-driven's expensive steps hand off to a pinned subagent, and the pattern is identical each time. Learn it once.

Step Agent Its prompt must carry
design craft-design-gate The change directory path
verification, step 3 verification-reviewer The change directory path, the base SHA, and the head SHA
payload/levels/standard/agents/. Both are pinned to a strong model at xhigh effort, and the schema says why: "so this session can stay on the cheap tier".

Three rules that come with the pattern:

  1. A subagent inherits nothing. Not your conversation, not files you have read, not skills you invoked. If the prompt does not name it, the agent does not have it. That is why the required inputs are spelled out per agent.
  2. It returns a draft plus caller actions. It cannot ask you questions — it has no way to. So it collects open questions and hands them back, and you resolve every one before finishing the artifact. A question that would change the specs, the approach, or the task breakdown must be settled now, not baked in as an assumption.
  3. Missing is not fatal. If the agent is absent or fails to launch, say so and do the work inline — the schema gives the sections. Every dispatch in every schema has a stated fallback.

The archive gate

Both schemas put an evidence artifact last on purpose: verification for craft-driven, quality for surface-driven. openspec archive warns about an incomplete change until it exists, which turns "it works" into a written, evidence-backed claim.

What counts as evidence

Every claim must be backed by a command you ran while writing this file and its observed output. "Should pass" is not evidence. A run from earlier in the session is not evidence. A subagent's success report is not evidence — it is a lead. If you have not run the command for this file, run it now.

And: a verdict of ready-to-archive with any Critical finding unresolved, or any test failing, contradicts itself. The verdict follows the evidence.

One clause worth reading twice, in verification step 3: receive the reviewer's feedback with technical evaluation, not performative agreement — verify each finding against the codebase and push back in writing where the reviewer is wrong.

A trap worth knowing before it bites

Artifact status is pure filesystem existence: 

BLOCKED ──────────► READY ──────────► DONE
missing deps      all deps done     file exists

So an artifact can read done while its dependencies were never written — writing tasks.md by hand marks tasks done with no specs at all. openspec status will tell you the chain is fine. It is not.

This is also, incidentally, why a skipped artifact's one-line stub works: the file exists, so the graph moves.

skills/configuring-openspec/references/custom-schemas.md, "Dependency graph semantics"

Recall check

What decides whether craft-driven's design-brief gets written?

A dispatched design-gate subagent hits an open question. What does it do?

A subagent reports the suite passed. Can you cite that in verification.md?

openspec status shows tasks as done. What does that prove?

Appendix · one detail the guides disagree on

The attached mattpocock guide assigns surface-driven's quality artifact to a mid-tier model at medium effort and says "this schema never needs Fable". The plugin source ships no subagent at all for that artifact — both of standard's agents belong to craft-driven. So the quality pass runs in your main session at whatever model you are on, and the guide's recommendation is advice to you rather than a pin in a file. Worth knowing before you assume something is enforcing it.
