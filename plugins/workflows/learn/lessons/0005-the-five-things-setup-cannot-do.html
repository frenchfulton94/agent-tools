Lesson 05·Install and set up·workflows

The five things setup cannot do

Setup finishes by telling you what is left. Four of those are interactive by nature — three write something, and one is a preference only you can set. The fifth is a decision it declines to make for you because it would affect every project on your machine.

By the end

Your repository is fully configured, including the parts no agent can do — and you have made the machine-global profile decision knowingly, understanding which /opsx commands it gives you.

Prerequisites: Lesson 03 — setup has actually run and reported its human steps.

Four interactive steps

These appear in the plan's humanSteps, conditionally — you only see the ones your repository and level actually need.

The last two are ordered, and the order is the point

An output style ships with its plugin — controlled-english lives in plugins/meta-skills/output-styles/ — so it does not appear in the /config list until meta-skills is active. Reload first, then select. Told the other way round, you go looking for a style that is not there yet and conclude it was never installed.

It is also the only human step that changes nothing on disk and everything about the register of the replies you get. Unlike the two interviews above, re-running /workflows:setup afterwards has nothing to fold in.

Re-run after the first two

Both write files setup would have folded into openspec/config.yaml's context: if they had existed. So the sequence is: setup → do the interviews → /workflows:setup again. The second run's update group picks up what the interviews produced.

The fifth: the machine-global profile

This one is not in humanSteps. It arrives as a warning in the plan, because setup refuses to run the command that would settle it.

"openspec config profile is machine-wide: it changes the profile for every project on this machine, not just this one, so setup never runs it for you."

plugins/workflows/scripts/plan.mjs, the profile warning

What the profile actually controls

It controls which /opsx:* slash commands exist in your projects. There are two presets.

Profile Commands you get
core — the default propose, explore, apply, update, sync, archive
custom — a selection you make The six above, plus whichever of new, continue, ff, verify, bulk-archive, onboard you select
CORE_WORKFLOWS in plugins/workflows/scripts/detect.mjs, mirroring the OpenSpec CLI's own fixed list, cross-checked against OpenSpec's commands doc.
Drift · there is no "expanded" preset

OpenSpec's docs call new, continue, ff, verify, bulk-archive and onboard the "expanded workflow commands", and one README inside this plugin's payload (payload/levels/minimal/openspec/schemas/mattpocock-bridge/README.md) tells you to run openspec config profile and "choose: expanded". There is no expanded option to choose. The CLI ships exactly one preset, core; selecting extra workflows is what makes the profile custom. plan.mjs is the precise account — trust it over that README line.

Why you probably want the custom selection

Every level's documented flow builds artifacts one at a time, so each interactive artifact gets its own step and its own approval. That is /opsx:continue, and continue is not in core. Without it you are on /opsx:propose, which generates all the planning artifacts in one step — fine for a two-artifact rapid change, wrong for a ten-artifact feature chain where the whole point is the gates between artifacts.

Making the decision

  1. See where you stand. Setup already reported this, but you can ask directly: 
    openspec config list
  2. Upgrade the CLI first. Instruction files are generated by the installed CLI, so an outdated one reports everything up to date while never writing the newer workflows. 
    npm install -g @fission-ai/openspec@latest
  3. Choose the workflows. An interactive wizard — it starts with a current-state summary. Select new and continue at minimum. 
    openspec config profile
  4. Apply it to the project. The config change alone does nothing; this is what regenerates the project's tool files. 
    openspec update
This is a team decision, not a repository one

One profile serves every OpenSpec project on the machine. If your repositories should all use the one-artifact-at-a-time flow, then everyone's machine needs the custom selection, and that belongs in onboarding documentation rather than in a per-repository step. Setup surfaces the gap and hands you the decision precisely because it cannot scope the fix to one repository.

Confirm the whole thing landed

openspec --version          # exists, and is Node >= 20.19
openspec schemas            # your level's schemas, and where each resolves from
openspec schema which --all # project vs user vs package, per schema
openspec validate --all --strict

openspec schemas should list exactly the set your level installs. If a schema is missing, it did not survive validation — OpenSpec drops fields that fail and warns only to stderr, which is why file presence proves nothing here.
