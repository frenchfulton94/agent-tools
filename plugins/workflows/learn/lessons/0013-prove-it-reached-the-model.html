Lesson 13·Models and proof·workflows

Prove it reached the model

A configuration that does nothing looks exactly like one that works. OpenSpec drops bad fields and carries on, warning only to stderr — so the last thing to learn is the one command that shows what the assistant actually receives.

By the end

You can prove that your context: and every rule you wrote are actually reaching the model, and you can name the five ways they silently fail to.

Prerequisites: Lesson 03 and lesson 08. This is the last lesson, and the one to come back to whenever something "isn't working".

Why silence is not success

"Parsing is deliberately resilient: an invalid or unparseable field is dropped with a console.warn and the rest of the config still loads."

plugins/workflows/skills/configuring-openspec/SKILL.md

That is a good design — one bad field should not break a project. It is also why every OpenSpec configuration problem presents identically: nothing happens. No error, no failure, no missing file. The rule you wrote just never fires.

Run diagnostics in a plain terminal, not piped

Dropped-field warnings go to stderr and are trivially lost to a pipe, a redirect, or a tool that only surfaces stdout. This is the single most common reason a warning that would have explained everything was never seen.

The five silent failures

What went wrong What you see Fix
context: is over 50KB Nothing. The entire field is dropped Summarize, or point at a file instead of pasting it. Treat the cap as a ceiling to stay far below
A rules: key matches no artifact id Unknown artifact ID in rules: X — on stderr, on every command openspec schemas --json lists the ids per schema. Common right after adopting a schema that renamed artifacts
The config file is not where OpenSpec looks Nothing at all Only openspec/config.yaml and openspec/config.yml are probed, in that order. A root-level file, or one a directory up, is invisible
One field failed its type check A console.warn on stderr; everything else loads normally Read stderr. The rest of the config working is not evidence this field did
You used openspec config set The command succeeds. The project is unchanged That writes the machine JSON config, never the project YAML. Edit openspec/config.yaml by hand
skills/configuring-openspec/references/troubleshooting.md, "Config not applied". No restart is ever needed — config is read fresh on every command.

The command that settles it

Three diagnostics, and the third is decisive:

openspec --version                                       # is the CLI there, and how old
openspec schema which --all                              # which schema wins, and from where
openspec instructions <artifact> --change <name> --json  # what the assistant actually receives

That last one is the only way to see the resolved template, the injected context, the matching rules, and the dependency paths — the real payload. If a value is absent from that output, the problem is upstream of the assistant. Read it before changing anything else.

How setup proves it, and why the probe exists

Setup's own verification step does not check that files exist. File presence proves nothing here, precisely because OpenSpec drops fields that fail validation and warns only to stderr. So it does three behavioural checks instead.

Check How
Your specs and changes are untouched Compares tree hashes taken before anything was written against hashes taken after
The config actually reaches the model Creates a throwaway change — zz-workflows-setup-probe — runs openspec instructions … --json against it, and confirms the payload really contains context and every expected rule
The planned plugins are installed Confirms every id in the plan's install list appears in claude plugin list --json
plugins/workflows/scripts/verify.d.mts.

Two details in there are worth stealing for your own tooling.

The probe is deleted, never archived

Removing it with openspec archive would merge its delta specs into openspec/specs/ — writing into your work product, which is the one thing setup must never do. So the probe's directory is deleted directly, at both its active path and any archived path found by suffix match. A survivor at either, or any thrown error along the way, is reported as a failed check rather than allowed to propagate.

The plugin check uses the planned list, not the reported one

Feeding it what the install step reported installing would make the check assert that what install said it installed is installed — which cannot fail for the case it exists to catch. A plugin a managed marketplace blocked never enters that second list. So the check uses the plan's list, and a blocked plugin failing this check is the correct outcome — a result to report, not an obstacle to route around.

Do this now

  1. Pick a real change and dump its payload. Any artifact id from its schema: 
    openspec instructions specs --change let-advisors-export-plans --json
  2. Find your context in it. Not a summary of it — the text. If it is missing, check its byte count against the 50KB cap first.
  3. Find a rule you know is keyed to that artifact. If it is absent, the key does not match an artifact id in the schema this change uses. Confirm with: 
    openspec schemas --json
  4. Break it on purpose, then watch it fail silently. Add a rule under a key like notarealartifact:, run any openspec command in a plain terminal, and read stderr. Seeing Unknown artifact ID in rules once, deliberately, is worth more than reading about it. Then remove it.
  5. Run the whole gate. 
    openspec validate --all --strict

One more thing status will not tell you

From lesson 09: artifact status is pure filesystem existence. DONE means a file is there — not that it validates, not that its dependencies were ever written. An agent should build the required set by walking each artifact's requires edges transitively, not by trusting status. So should you.

Appendix · what this plugin does not prove about itself

The README is unusually candid, and reading it is part of using the plugin honestly. The setup skill's own orchestration is unverified end to end: claude -p --plugin-dir cannot drive it, because the meta-skills dependency does not resolve under --plugin-dir loading and the approval gate cannot complete inside one -p turn. The prose has been reviewed, not executed. Invariant I3 is proven narrower than it sounds. The config.yaml backup path and the artifact-id union are covered by unit tests rather than the end-to-end suite. And the Windows %APPDATA% path has never been run on Windows. None of that makes the plugin untrustworthy — it makes its claims legible, which is the more useful property.
