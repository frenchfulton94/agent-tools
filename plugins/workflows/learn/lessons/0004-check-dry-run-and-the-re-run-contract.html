Lesson 04·Install and set up·workflows

--check, --dry-run, and the re-run contract

Re-running setup is not a repair operation. It is the update mechanism, and it works because one file remembers, byte for byte, what setup wrote.

By the end

You can answer "which of our repositories have fallen behind?" with command output rather than a guess, and you can explain exactly what editing a file setup wrote does to your future re-runs.

Prerequisites: Lesson 03, and one repository already set up.

Two flags that stop early

Flag Writes Reach for it when
--check Nothing at all You want a drift report. Safe on a repository you do not own and have no intention of changing
--dry-run .claude/workflows-plan.json — and nothing else You want the plan as data, to read carefully or to diff against last time's
neither Everything in the approved plan You have read the plan and decided

Both flags stop before the approval gate. Neither asks you anything beyond the level, and --check is the one to reach for by reflex when the question is diagnostic.

The file that remembers

.claude/workflows.json holds four things: the level, the plugin version, the date, and — the load-bearing part — a content hash of every schema and subagent that run owns.

That hash answers one question on every later run, per file:

On disk versus the recorded hash Group What happens
No record for this name copy or collide copy if the file is absent; collide if a file with that name exists but setup never wrote it
Matches — still byte-identical update Refreshed automatically. This is how you take an update
Differs — you edited it collide Reported by name, never reverted. Your edit made the file yours.
plugins/workflows/scripts/record.d.mts and the grouping logic in plan.mjs. Absent hashes mean nothing can be proven to be setup's, so every existing name is reported as a collision — the conservative answer, never a silent overwrite.
This is the point, not a limitation

A tool that reverted your edits on every update would be a tool you stopped running. A tool that never updated anything would drift. The hash gives you both: setup's untouched files refresh, your edited ones are reported and left alone, and you find out which is which before anything is written.

The set of owned files is derived, not typed

A run owns copy plus update, for schemas and agents alike, and the recorder derives that set from the approved plan itself rather than from a list the agent assembles. A mistyped list cannot make a file setup's that the plan never claimed.

There is exactly one thing the plan cannot know — which collisions you approved, since approval happens after the plan is built. Those names are passed separately, and each is honoured only if it actually appears in the plan's collision list. Anything else is reported as ignored.

Never pass a declined name

Recording a name you declined would make your file setup's, and the next run would replace it with no gate and no mention. This is the one place in the whole procedure where a careless argument causes silent data loss on a future run.

Why the record is written before verification

Step 8 records the run; step 9 verifies it. That order is deliberate, and the reasoning is worth borrowing for your own tools.

Verification exits non-zero on a failed check — and a plugin that a managed marketplace legitimately blocked is a failed check. Reverse the order, and a managed-marketplace repository would apply the entire payload and then never record it. Every file that run wrote would come back on the next run as yours, as a collision, for ever.

The record states what setup wrote. That is true whether or not the config reached the model.

Do this now — prove the hash to yourself

  1. Confirm the baseline. In a repository you have already set up: 
    /workflows:setup --check
    Every schema and agent should be in update, and nothing in collide.
  2. Edit one file setup wrote. Add a comment line to a schema — a real edit, but a harmless one: 
    echo '# note: our team keeps the design gate mandatory' \
  >> openspec/schemas/craft-driven/schema.yaml
  3. Check again. That schema has moved from update to collide. Nothing was written; the report just changed. 
    /workflows:setup --check
  4. Revert, and check a third time. It is back in update. The hash is a content hash, not a timestamp — putting the bytes back puts the ownership back. 
    git checkout -- openspec/schemas/craft-driven/schema.yaml
/workflows:setup --check

Four commands, and you now know from observation rather than from this page what an edit costs and what it buys.

The department-scale question

"Which of our repositories have fallen behind?" is the question --check was built for. It writes nothing, so it is safe to run across every repository you have, including ones you do not maintain.

The other half of the answer is the recorded plugin version: a repository set up at 0.1.0 whose record still says 0.1.0 has not taken any update since, whatever its files look like.

A committed settings file installs nothing

.claude/settings.json commits, and it records which plugins should be enabled — but cloning a configured repository does not install them for the person cloning. Every teammate installs the workflows plugin and runs /workflows:setup once. Reconcile mode installs only what is missing, so on a correctly configured repository that run is nearly a no-op.

Appendix · for the plugin's author

The README is explicit that invariant I3 — a plugin id you have already decided is skipped, never installed over — is not proven end to end. The fixture disables a plugin the level's manifest never mentions, so what that test establishes is narrower: nothing in the pipeline rewrites .claude/settings.json wholesale. The rule itself is covered by unit tests in tests/workflows-plan.test.ts and tests/workflows-settings.test.ts. Worth knowing before you cite I3 to a colleague.
