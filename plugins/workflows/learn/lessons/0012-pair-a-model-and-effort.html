Lesson 12·Models and proof·workflows

Pair a model and effort with each phase

Leaving one model and one effort level on for a whole change is the most common way to overpay and under-think at the same time. Eight of these decisions are already made for you in files on disk. The rest follow one rule.

By the end

You can say which model and effort each phase of a change wants and why, for all twelve workflows; you know which eight are pinned in files rather than left to you; you know the three commands that make a switch and the order to run them in; you know what your subscription tier does and does not change; and you know the settings that silently defeat every one of those pins.

Prerequisites: Lesson 08, plus 09 or 10. You need to have felt a chain before tuning it.

The rule: depth follows the artifact

All three attached usage guides arrive at the same principle from different directions, so it is worth stating once and reusing:

  1. Planning artifacts that encode durable, multi-step judgement get the strong model. A wrong spec, a wrong root cause, a wrong refactor strategy, a wrong migration plan is the most expensive error in the whole chain — and planning is where token volume is lowest. Depth is cheap here and mistakes are not.
  2. Implementation loops favour the fast model. Apply is a long agentic loop of file edits, shell commands, and test runs. That is latency- and output-dominated, so the cheap tier wins — except where the implementation is genuinely hard.
  3. Interactive artifacts want high, not xhigh. When the reasoning happens between short turns — a grill round, a shape interview, a seam sign-off — xhigh mostly adds latency you sit through. Reserve xhigh for the deep artifacts that run without you in the loop.
  4. Escalate on evidence, not on nerves. If a strong-model planning artifact still produced a shallow spec, go up. If a cheap implementation pass keeps causing rework, go up. Spraying the top setting across a whole chain multiplies cost without commensurate quality.

Read straight out of the model: and effort: lines in plugins/workflows/payload/levels/*/agents/*.md.

Three patterns are visible in that table, and all three are deliberate:

  • Every design gate is opus at xhigh. Remember from lesson 07 that the design artifact only exists when the change is cross-cutting, adds a dependency, or carries security or migration complexity. The trigger is the tier signal: when the artifact exists at all, it is by definition the hard case.
  • Review splits by axis, and the axes get different tiers. Comparing a diff against a spec is mechanical — sonnet at medium. Judging code as code against a standards baseline is judgement — opus at high. One review, two models, because it is really two jobs.
  • The expensive work is pushed out of your session, on purpose. The schemas say so: dispatch the gate "so this session can stay on the cheap tier". You get top-tier reasoning at the two or three moments that need it without paying for it across the whole change.

Two settings that silently defeat all eight

1 · CLAUDE_CODE_SUBAGENT_MODEL

It sits at the top of the resolution order — above the per-invocation model and above frontmatter model:. Set it, and every pin in the table above collapses to one tier, with no warning and no visible difference in how the schemas read. The per-axis review split stops being a split. Leave it unset (or inherit, which is the same thing).

Drift · the one piece of tier advice not to follow here

The subscription guide recommends CLAUDE_CODE_SUBAGENT_MODEL=claude-sonnet-5 on all three tiers, so that subagent fan-out never bills at Opus rates. That is sound advice for a generic Claude Code setup where nothing is pinned — and it is actively wrong in a repository this plugin has configured, because it would collapse both design gates and the review gate to Sonnet while every schema still reads as though a stronger model had judged them.

You do not need the variable to get the saving it is after. This plugin already does the same job per agent, which is the precise version of the same idea: code-review-spec and taste-preflight are pinned sonnet because their work is mechanical, while the three gates are pinned opus because theirs is not. Cheap fan-out where it belongs, depth where it belongs, and no single switch that flattens both.

2 · your organisation's model allowlist

A model: value is checked against the organisation's availableModels allowlist, and an excluded value is skipped — the agent runs on the inherited model instead. So if opus is not available to you, your design gate is quietly running on whatever your session is on. The schema still says the gate ran on a stronger model. It did not.

Both from plugins/meta-skills/skills/authoring-subagents/references/frontmatter.md, the model section.

Confirm it, do not assume it

/status reports the current model and effort, alongside the account, workspace, and context usage. It is the cheapest possible check that you are where you think you are.

How you actually switch

Switch at artifact boundaries, and run /status after each switch. Three commands do the whole job:

Command Does
/clear Empties the context window. Do this first — a switch made inside a full window still drags the old window's contents into every turn that follows
/model Opens the picker. Choose the model with up and down, and set that model's effort with left and right — both knobs, one dialog
/effort Effort alone, when the model is already the one you want and only the depth is wrong. The common case mid-chain

The boundary that matters most

Every chain in this plugin has one switch that is worth more than all the others: the gap between the last planning artifact and the first line of code. It is the largest single change in depth in the whole chain — rules 1 and 2 above are exactly this gap — and it is also the moment your window is fullest of material apply does not need.

  1. /clear. The planning artifacts are files now. Apply reads them off disk; it does not need your memory of writing them, and it does need the room. OpenSpec's own guidance says the same: high-reasoning models, and a clean context window before implementation.
  2. /model, arrows for effort — or /effort alone. Down from planning depth to an implementation tier, per the table further down this lesson. Check /status before you type anything else.
  3. /opsx:apply <change-name>. With the name. You just removed the conversation the command would otherwise have inferred it from — which is why the name stops being optional the moment you take clearing seriously.

Between planning artifacts, the middle step travels alone. Re-pick model and effort at every artifact boundary — that costs the window nothing. Whether to also /clear there is the chain's call, not a general rule:

Chain Between planning artifacts
mattpocock-bridge Do not clear. It wants grill through tasks in one unbroken window so they build on the same thinking. If that run gets long, compact at the nearest artifact boundary
feature Clear or compact at the boundaries. Its own session discipline says so, and at ten artifacts a single window would not survive the chain anyway
payload/levels/minimal/openspec/CLAUDE.md.fragment.md and payload/levels/advanced/openspec/schemas/feature/schema.yaml, around line 291.

The reset before apply is the one that is universal — every schema here puts implementation in a fresh session — and nothing is lost by it either way: artifact state is pure file existence, so a cleared window costs a chain exactly nothing.

Two facts that change how you read your own effort settings

Default effort is high on every current model, and xhigh has to be opted into — it is not any model's default any more. So an artifact you never touched is already at high, which is where rule 3 wants most interactive work anyway. The switches that matter are the deliberate steps down to medium for mechanical loops and up to xhigh at a gate.

Nothing downgrades you automatically. Hitting a usage limit never triggers a model switch — authentication, billing, rate-limit, request-size and transport errors are all excluded from the fallback machinery. Do not plan a workflow around being rescued; manage it with opusplan, /effort, and /usage.

ANTHROPIC_API_KEY silently changes who pays

With that variable in the environment, Claude Code bills the API instead of your subscription — no prompt, no warning. If /cost is showing spend you did not expect, or /usage shows a weekly bucket that never moves, check the environment before anything else.

Drift · the two design gates on a Max plan

The guide puts both design artifacts on the very top tier. The shipped agents pin opus. On a Pro plan those are the same thing; on a plan with a higher tier available they are not — the pin will not escalate on its own. Raising it means editing the agent file, and from lesson 04 you know exactly what that does: the file becomes yours, and every future re-run reports it as a collision instead of updating it. That is a fair trade, made knowingly.

Your tier changes what you can afford, not what you can pick

All three consumer tiers can select every model — Opus 5, Sonnet 5, Haiku 4.5, and Fable 5. The old "Pro is Sonnet-only in the terminal" claim is out of date. What differs is the weekly usage bucket and how Fable is billed.

Tier Fable 5 What to do differently
Pro Not in-plan — usage credits only Substitute Opus 5 at xhigh for Fable at both feature gates — which is exactly what this plugin ships. Use opusplan for planning-heavy schemas. Keep bugfix root cause and the hotfix postmortem at xhigh whatever else you cut; drop marginal refactor/upgrade planning to Sonnet when the bucket is tight
Max 5x In-plan, up to 50% of weekly limits Opus 5 is the default and Opus-plan plus Sonnet-implement is sustainable across a disciplined workweek. A Fable session weighs roughly twice an Opus one, so the 50% cap arrives in about half the sessions the number suggests — keep Fable to the two feature gates if you use it at all
Max 20x In-plan, same 50% cap Nothing needs downgrading. Opus planning daily is fine. Fable at the gates stays well inside the cap for gate-only use — but do not make it the default driver
opusplan is the one alias worth learning

Opus in plan mode, Sonnet in execution, switched for you at the boundary. It maps almost exactly onto rules 1 and 2 at the top of this lesson, which is why it is the single most useful burn control on any tier — and why it is the first thing to reach for on Pro.

Drift · the Fable question, now settled

An earlier version of this lesson flagged that one guide puts both design gates on the very top tier while the shipped agents pin opus, and left the choice open. The subscription guide closes it: Opus 5 wins most published head-to-heads at half the rate, and Fable carries operational strings — mandatory 30-day retention on its traffic class, unavailable under zero-data-retention, and content classifiers that trigger a fallback more often. Treat Fable as a measured exception you benchmark on your own change, not a default upgrade. Until you have that benchmark, leave the pins as shipped.

Appendix · why gate agents draft and return instead of asking

A subagent cannot use AskUserQuestion — it is removed from every subagent regardless of what tools: says. So a design gate whose sign-off genuinely needs a human answer cannot get one. That is exactly why all four design gates in this plugin draft the artifact and return open questions to the caller: the main session, which can ask. The attached guide arrives at the same conclusion and calls it the draft-and-return pattern. If you ever write a gate agent of your own, this is the constraint that shapes it.
