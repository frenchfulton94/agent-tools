# Configuring OpenSpec

OpenSpec is a spec layer between a person and their AI coding assistant: proposals, delta specs, design, and tasks live as Markdown in a change folder, and archiving merges the deltas into `openspec/specs/`. It has two halves that run in different places — the `openspec` CLI in a terminal, and `/opsx:*` slash commands in the assistant's chat.

This skill covers the configuration surfaces: project config, custom schemas and templates, change metadata, and the setup/verification commands around them. Facts here were verified against OpenSpec v1.9.0 source, not only its docs; where the two disagree the source wins and the difference is called out.

## Establish the ground truth first

Do these before editing anything, because most bad edits come from guessing at state:

```bash
openspec --version                 # CLI must exist; needs Node >= 20.19.0
openspec schemas                   # which schemas exist and where each resolves from
openspec schema which --all        # project vs user vs package for each
```

Config is read fresh on every command, so there is nothing to restart or reload after an edit.

## The file map

| File | Scope | Format |
|---|---|---|
| `openspec/config.yaml` | This project: default schema, injected context, per-artifact rules | YAML |
| `openspec/schemas/<name>/schema.yaml` + `templates/` | This project: custom workflow definition | YAML + Markdown |
| `openspec/changes/<change>/.openspec.yaml` | One change: schema, `skip_specs`, `retire_capabilities` | YAML |
| `~/.config/openspec/config.json` (XDG) | This machine: profile, delivery, `defaultStore`, telemetry | JSON |

`openspec config get/set/edit` operates on the **machine-level JSON config only**. It never touches `openspec/config.yaml`, which is edited by hand or created by `openspec init`. Conflating the two is the most common wasted edit.

## Setup

```bash
npm install -g @fission-ai/openspec@latest
cd your-project && openspec init            # or: openspec init --tools claude,cursor
```

`openspec init` scaffolds `openspec/` and writes skill/command files into each selected AI tool's directory. To change which slash commands are installed, set the profile first and then apply it — the config change alone does nothing to the project:

```bash
openspec config profile     # core (default) or a custom workflow selection
openspec update             # regenerates the project's tool files
```

Upgrade the package *before* running `openspec update`: instruction files are generated by the installed CLI, so an outdated CLI reports everything up to date while never writing the newer workflows.

Generated skill and command files are OpenSpec's to own; `openspec update` overwrites them. Customization belongs in `config.yaml`, schemas, and templates — never in the generated files.

## Project config: what actually reaches the model

`openspec/config.yaml` has exactly these top-level keys: `schema`, `context`, `rules`, `operations`, `references`, `store`, `githubCopilot`. Anything else is ignored.

- **`context`** is injected into *every* artifact's instructions, wrapped in `<context>` tags. Keep it tight — it is a per-request cost, and it is hard-capped at 50KB (over the cap the whole field is dropped).
- **`rules`** is a map of artifact id → list of strings, injected *only* for the matching artifact. Artifact-specific formatting belongs here, not in `context`.
- Both are constraints *for the assistant*, never content to copy into the generated artifact.

Parsing is deliberately resilient: an invalid or unparseable field is dropped with a `console.warn` and the rest of the config still loads. **Silence is not success** — a config that "does nothing" is usually a dropped field, a `.yml` extension (only `config.yaml` and `config.yml` are probed, in that order), or a `rules:` key matching no artifact id.

Read `references/config-reference.md` when writing or debugging a `config.yaml`, or when the user asks about operation guidance, referenced stores, or multi-language output.

## Custom schemas

A schema defines which artifacts a change has and how they depend on each other. Fork before writing from scratch — a fork brings working templates with it:

```bash
openspec schema fork spec-driven my-workflow    # → openspec/schemas/my-workflow/
```

`openspec schema init` exists but only accepts the four built-in artifact ids (`proposal`, `specs`, `design`, `tasks`); despite the docs' framing, it cannot scaffold a novel artifact like `research`. Add new artifacts by hand-editing `schema.yaml` after forking, and create the matching template file yourself.

Every artifact needs **four** fields — `id`, `generates`, `description`, `template` — plus optional `instruction` and `requires`. The customization doc's table reads as though `template` were optional; the Zod schema rejects an artifact without it.

Two structural rules that break archiving silently if ignored:

- Keep an artifact whose **id is `specs`** and whose **`generates` stays under `specs/`**. Archive and sync find delta specs through the id, while `skip_specs` matches on the path prefix — a schema that satisfies only one of the two archives without merging anything.
- `requires` are enablers, not gates; declaration order breaks ties between artifacts that become ready together, so list artifacts in the order you want them written.

Read `references/custom-schemas.md` before creating or editing any `schema.yaml` or template.

## Verify every change

Never hand back an edited config or schema unverified:

```bash
openspec schema validate my-workflow                  # structure, templates exist, no cycles
openspec validate --all --strict                      # changes and specs
openspec instructions <artifact> --change <name> --json
```

The last command is the only way to see what the assistant actually receives — resolved template, injected `context`, matching `rules`, dependency paths. When a user says their config "isn't working", read that output before changing anything else.

There is no bundled validator script here on purpose: the CLI is the authoritative validator, and a reimplementation would drift from the real schema. If the CLI is unavailable, apply the manual checklists in the reference files.

## Gotchas

- `/opsx:propose` goes in the assistant's chat; `openspec ...` goes in a terminal. Typing a slash command into a shell is the single most common failure.
- Slash command spelling is per tool: `/opsx:propose`, `/opsx-propose`, `@opsx-propose` (Amazon Q), `$openspec-propose` (Codex), `/skill:openspec-propose` (Kimi). Read the "Getting started" line `openspec init` printed rather than guessing.
- Schema selection precedence: `--schema` flag → the change's `.openspec.yaml` → `openspec/config.yaml` → `spec-driven`. A forked schema does nothing until something names it.
- Schema *resolution* precedence is separate: project `openspec/schemas/` → user `~/.local/share/openspec/schemas/` → package built-ins. Prefer project-local so schemas are version-controlled with the code.
- Scenarios need exactly four hashes (`#### Scenario:`). Three hashes or a bullet fails silently.
- A `MODIFIED` requirement replaces the whole block, so it must carry every surviving scenario, not only the edited ones.
- A change with zero spec deltas fails validation unless its `.openspec.yaml` sets `skip_specs: true`; deleting a capability's spec on archive requires `retire_capabilities: true`.
- `openspec archive` asks up to three confirmations. In CI, an agent, or any run with stdin closed, pass the change name and `--yes` or it exits 1.
- Change names must be lowercase kebab-case; a leading number is allowed (`100-add-feature`).

## Output contract

When changing someone's OpenSpec setup, deliver: the edited file(s) in full, one line naming which precedence rule makes the change take effect, and the exact verify command to run. When diagnosing, report the cause before the fix — most "config ignored" reports are a dropped field or a precedence surprise, and the fix is wrong if the cause is guessed.
